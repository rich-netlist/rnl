# Optimized solver measurement tools

These tools collect bounded Windows GNU CLI evidence of how fast an optimized
`rnl solve` does a fixed work on files of the language 0.4. Ordinary pull-request
CI runs the file/mock checks and an owned-process smoke test; it does **not**
start a performance collection. Existing Rust, WebAssembly, golden and
conformance checks remain enabled on pull requests.

## Inputs (manifest schema 2)

`manifest.json` lists every input with its SHA-256 and byte count:

* **12 representatives**: the reviewed cases of
  [`tests/integration/solver-0.4`](../integration/solver-0.4/README.md), copied
  with the bytes Git holds for them (LF), whatever line endings the checkout
  wrote. Their solver records are not in them, so each is solved from scratch.
* **4 scale families**, each at n = 2, 4, 8, ..., 1024, generated by
  `prepare_inputs.py` in the language 0.4 (UTF-8, LF, a final newline):

| Family | Meaning of n | Host devices |
| --- | --- | ---: |
| chain | Resistors in a chain under one `$SIGNAL_FLOW` | n |
| diffmirror | Grouped cells of a `$DIFFERENTIAL_PAIR_N` and its `$CURRENT_MIRROR_P` load | 5n |
| star | Resistors sharing a hub, with an ALIGN and an ORDER of them all | n |
| distances | Pairs of resistors, each a DISTANCE left-to-right between 8 and 12 | 2n |

`distances` was `disjunctions` in schema 1: in 0.3 its DISTANCE ran either way on
x, a choice of two; in 0.4 a DISTANCE has a direction, so the family is one fact
per pair.

A file of 0.4 loads the standard packages the command holds, so no package files
are prepared. No input is committed here: `prepare_inputs.py` writes them into a
new directory outside the repository and checks every byte against the manifest.
`manifest.previous` names the commit and SHA-256 of the manifest of schema 1 (the
eleven inputs of 0.2 and 0.3 and their pinned packages), which stays in history.

## What a run does

Every solve is

```sh
rnl solve FILE -o DIR --solver-options time_limit=none \
  --solver-config 'limit="work",work=100000000,safety_seconds=600'
```

as `manifest.solve` says: a fixed work on the scale of the pivot charge of #716,
the one the solver tests use, and no time limit of the resolution, so that a run
writes the same drawing on every machine and its time measures how fast the
command does that work. The safety limit is set past every cap below, so it never
cuts a run short. `rnl solve` prints the **replay options** of each level; they are
kept and compared, one per level written. The profile of a level names the
options asked for (`run=work:100000000`), its record those of the replay (the work
taken), so a profile's problem hashes are matched with the records' by their
problem part, before the `.`.

The profile's exclusive stages are `resolve`, `structure`, `search`, `tree`,
`place`, `lines`, `coords`, `route` and `score`.

## Manual entry point

Use **Actions → Rust → Run workflow**. Both special-mode switches default to
false. Enable one of them and give full, immutable 40-character public
`rich-netlist/rnl` commit SHAs:

| Input | Other inputs | Action |
| --- | --- | --- |
| `solver_performance=true` | `baseline_sha`, optional `candidate_sha` | Build, then collect the representative/adaptive matrix |
| `solver_build_only=true` | `work_candidate_sha` | Build one downloadable optimized CLI; no solver invocation |

The measured revisions must solve 0.4 within a work on the scale of #716; the
default baseline is the commit that added the reviewed cases. From a branch:

```sh
gh workflow run rust.yml --repo rich-netlist/rnl --ref BRANCH \
  -f solver_performance=true \
  -f baseline_sha=PUBLIC_BASELINE_40_CHARACTER_SHA \
  -f candidate_sha=PUBLIC_CANDIDATE_40_CHARACTER_SHA
```

Omit `candidate_sha` for a baseline only. For a build without measurement:

```sh
gh workflow run rust.yml --repo rich-netlist/rnl --ref main \
  -f solver_build_only=true -f work_candidate_sha=PUBLIC_CANDIDATE_40_CHARACTER_SHA
```

The work diagnostic of schema 1 (`solver_profile_work`, one profiled run of a
0.3 input with `--profile-work`) is gone: the command no longer has that option.
No dispatch accepts a patch, source archive or alternate repository.

The reusable jobs build sequentially using the default release profile, pinned
Rust 1.97.1, target `x86_64-pc-windows-gnu`, jobs=4 and `windows-2022`. All
builds finish before measurement. Two resource samples at least five seconds
apart require 8 GiB free and no compiler, solver or browser driver. Every solver
command runs sequentially in an owned Windows Job, with cleanup receipts, an
empty working directory and no `RNL_SOLVER_CONFIG` override.

## Collection scope and interpretation

* Each representative gets one **off** command and then one profiled **on**
  command, each capped at 60 seconds (`manifest.caps`). A release build takes
  about 4 to 13 seconds for one of them, a level of each within the work. There
  are no retries. Whether an off command took 10 seconds or less is recorded too.
* Each scale family doubles from n=2. Off has ten seconds. A complete off gets
  one on capped at 30 seconds, so that a point near ten seconds still has its
  profile, then continues; the first off timeout gets one diagnostic
  on capped at 120 seconds, then stops the family. Other off errors mark on
  NOT_RUN and stop the family. n=1024 is a queue guard, not a measured boundary.
* The cap covers CreateProcess through owned-tree exit, including CLI writeback.
  Compile, resource waits, CLI profile time and solver subtotals remain separate.
  Late returns are censored failures. Partial profiles preserve the last observed
  boundary; inclusive nested spans must not be added to exclusive stages.

A green collection means valid collection evidence, **not** performance
acceptance. On completion cannot rescue off timeout. Missing replay options,
malformed profiles, errors, incomplete equality and observed memory pressure
stay explicit. Each point is one observation, not a repeat distribution.
`comparison.json` and `comparison.md` set the two versions side by side: points
both complete, measured timeout-to-complete transitions, regressions, errors and
adaptive NOT_RUN points, and the off seconds of every point. A comparison is
clean when the replay options of the two versions, with the work each level
took, are the same. Complete outputs are compared as actual bytes and hashes.
This describes one Windows GNU runner, not a universal desktop or Web guarantee.

## Downloading results

Open the completed Rust run in **Actions**, then its **Artifacts** section.
Artifacts include the run ID and attempt and are retained for **14 days**:

* `solver-performance-binaries-RUN_ID-ATTEMPT`: optimized EXEs and build receipts,
  uploaded before the first measured command.
* `solver-performance-RUN_ID-ATTEMPT`: final matrix evidence, including EXEs,
  the manifest, source/compiler/binary identities, stdout/stderr, exact solved
  files, raw complete or partial profiles, timing/memory/resource observations,
  cleanup receipts, per-point measurements, summaries and `comparison.json/md`.
* `solver-build-RUN_ID-ATTEMPT`: a build-only candidate.

The final upload runs even on failure. Preserve these downloads before retention
expires. For example:

```sh
gh run download RUN_ID --repo rich-netlist/rnl \
  --name solver-performance-RUN_ID-ATTEMPT --dir OUTPUT_DIRECTORY
```

## Lightweight offline checks

```sh
git fetch --no-tags origin 7ef1fb5455f28e1cb3dff00447d70b0bbce5aa48
python scripts/solver-performance/test_inputs.py
python scripts/solver-performance/test_benchmark.py
python scripts/solver-performance/prepare_inputs.py --output NEW_DIRECTORY_OUTSIDE_REPOSITORY
python scripts/solver-performance/benchmark.py --fixtures NEW_DIRECTORY_OUTSIDE_REPOSITORY
```

The fetch gives the previous manifest, which one check compares; without it that
check is skipped. These checks compile nothing and call no solver. The real
owned-process smoke uses only Python fixture processes and is explicitly Windows
CI-only. `ci_build.py` rejects local execution. `canonical-main.json` holds the
replay options, profile options and hashes of one solve of a reviewed case at the
manifest's work, which the checks read the options against. The files here change
measurement tooling only; solver code, objectives, defaults and specification
text are unchanged.

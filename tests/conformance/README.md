# conformance

Conformance corpus for RNL 0.3, the language standard in [`spec/`](../../spec/README.md), and for RNL 0.2, which the tools still read. The cases were written against the draft the standard was consolidated from; section numbers in file comments and diagnostics are the standard's.

| Path | Content |
| --- | --- |
| `cases/NAME.sp` | A netlist with RNL records. Files it includes or packages it names sit next to it (`04-hierarchy-lib.inc`, `11-acme-style.rnl`). |
| `cases/NAME.expected.json` | What the case must give: the effective model of every drawing level, and the level and place of every diagnostic. |
| `cases/NAME.snapshot.json` | The editor interface's snapshot of the case, with the host circuit and the model of every drawing level. |
| `equivalence/NAME.sp`, `NAME.scs` | The same circuit in SPICE and in Spectre with the same RNL. Both must give the same effective model. |
| `cases-0.3/NAME.sp`, `NAME.scs` | Cases of the language 0.3, read as the toolkit reads every file, with expected and snapshot files of their own. They use the standard series 0.3 of [`libraries/standard`](../../libraries/standard/README.md), which a file of 0.3 uses implicitly. |

The first 15 cases were written with the Python prototype of the language and cover its features one area at a time: symbols and standard rules, hierarchy and packages, definitions, sets and selections, styles and text, buses and bundles, constraints and priorities, the header record and aliases, diagnostics, version handling, `ROUTE`, and a document written with Chinese aliases. Case 16 was added with the Rust toolkit: names equally close to an unknown one, and several overridden symbol statements, whose order once followed a hash map and changed from run to run. Its expected file records neither the messages nor the overridden statements; the tests of the WebAssembly binding build it again and again and compare whole Documents. Case 17 was added with the Rust renderer's line styles: every style on every shape kind, with and without a width, in a symbol and on a wire. Its expected file records the styles; the tests of [`rnl-view`](../../crates/rnl-view/README.md) check the strokes the renderer draws them with, such as a double line as two strokes on rectangles, circles and ellipses as on paths. Case 18 was added with the texts the shipped fonts do not map ([decision 0009](../../docs/decisions/0009-fonts-shipped-with-the-core.md)): hangul, emoji sequences, Arabic, Devanagari, Thai, combining marks and a zero width space, among characters the fonts map, in every kind of markup and alignment. Its expected file records the texts; the tests of `rnl-view` check that those characters are laid out in runs of their own, as wide as estimated, and that the SVG draws them centred and not stretched. Case 19 was added with the revised rule on cycles of sets (5.2.2): a cycle of additions, one through a removal, and one that closes in a subcircuit through package sets that hold selections. In each, the statement that closes the cycle in order of position fails, and the rest is drawn; before, the removal made the whole interpretation fail, and the sets holding selections overflowed the stack. Case 20 was added with the rule that places a text axis by axis (13.3): on each axis the PLACE or the offset written later, else the position the symbol gives a label it defines. Before, a scene offset on a label the symbol defines did nothing, a PLACE of one axis was dropped there, and an offset on one axis only was dropped wherever the other axis was free, so the texts with only a `dx` in cases 02, 08, 09 and 11 moved too. Case 21 was added with the order of the facts of one pipe (8.5): when later segments of a statement place or turn the same object again, the later segment is written later and, at equal priority, is kept. Before, the facts of the segments shared their statement's position and the first one was kept. The comment lines starting with `*!` describe each case.

The corpus of 0.2, `cases` and `equivalence`, is the regression suite of 0.2: every case in it declares its version, and a file it includes without a header record follows it, so that it is read in 0.2 with the standard series 0.2 (16.1, 16.3), although a main file without a header record is read in 0.3, the tool's default. The cases of 0.3 are kept apart from it, in `cases-0.3`, whose files never change its expected files, and are read without any switch. Case 1 gives T, O, U and Z the terminal names that 0.3 adds to the defaults of the SPICE family (6.12), wired by name, and a DEVICE of the file over them. Cases 2 to 4 drop the standard rule package of the other dialect (16.3): a Spectre file does not use `rnl-std-spice` and a SPICE file it includes does not use `rnl-std-spectre`, a `simulator lang=` in the middle of a file not changing its dialect (2); a rule package that the file writes is kept (3); a file that pins the series 0.2, which has no such packages, drops nothing (4). Cases 5 and 6 write every element that the SPICE and the Spectre adapter read natively, one line each, and each gets its default symbol of the series 0.3, by element letter and model type in SPICE and by master and model type in Spectre. Case 7 is a Spectre netlist as Virtuoso writes it, whose instances of subcircuits are named `I0` and `I1`: they are not drawn as current sources. Until the series 0.3 was bundled, cases 2 and 3 named a stand-in of it by `path=`, and case 1 used the series 0.2, as every file did; now that each file uses the series of its own language version, they use the bundled series 0.3: case 1 draws T, O, U and Z with symbols of their own, and the fill adds grounds and port tags in cases 2 and 3. Cases 8 to 12 were added when the toolkit came to read 0.3 by default. Case 8 is a main file without a header record: it is read in 0.3, the tool's default (16.1), with the series 0.3, whose `$RESISTOR` it writes, and T1 has the terminal names of 0.3. Case 9 is a file of 0.2 that includes a file without a header record, which follows it (16.1): the included file is read in 0.2 and finds `$RES` and `$GND` of the series 0.2. Case 10 has a record of the solver that refers to the objects without a name by number, with the check of the numbers in its `numbering` (5.9), and rewrites the authored wire with WIRE given the wire (13.1). Case 11 has the hints of a conflict of geometric facts (8.5): two coordinates and two orientations, each discarded against the one kept, and an ALIGN discarded against the coordinates that leave it no solution, each statement told what was discarded because of it. Case 12 is the example of 9.5: a DISTANCE expanded from a definition whose two roles one instance fills, which has no solution on its own, fails with an error, and only it is dropped.

Cases 13 to 24 were written by a contributor from outside the project against the toolkit of cf14cf9, each checked against the text of 0.3; the structure of the series 0.3 that came after (#71) and its Chinese aliases (#76) changed none of their results. Case 13 numbers the objects without a name in the order of 5.9: the authored records, the body of a usage right after it, the records with `scope=`, and then the objects of the record of the solver. Case 14 checks the numbers of an object with several `%` names by the name bound first (5.9, 2.6). Case 15 has a check of the numbers out of date, numbers used where none can be, and a binding to a number (4.1, 5.9). Case 16 rewrites wires with WIRE, with a rewrite that fails, SELECT-TERMINAL with `wired=`, and a wire in the net slot (13.1, 10.2). Case 17 resolves conflicts by priority and by the later segment of a pipeline, fails the constraints that contradict themselves, and decides at the tolerance 1e-6 (2.7, 5.5, 8.5, 11.7, 14.1-14.5). Case 18 decides the dialect of a file and of each library section, with `simulator lang=` and a rule package written in a level (16.3). Case 19 has header records in the wrong places, a second VERSION, library sections each of its own version, and an alias that 0.3 makes a standard word (2.8, 16.1, 16.5). Case 20 has the default terminal names of the Spectre primitives, a switch of several throws and the model families, and a DEVICE over them (6.12). Case 21 binds names across a subcircuit and the records with `scope=` it (2.6, 6.6, 6.7). Case 22 counts a set as one member of a constraint by its centre, and a DISTRIBUTE of fewer than three members holds (14.1, 14.4). Case 23 has rules that take the difference of two sets, and add no usage where one is written (10.5). Case 24 writes empty sets as members of ORDER, ALIGN and DISTRIBUTE: they are no members, so each constraint reads as written without them, and an ORDER left with one member twice fails (14.1, 8.5).

## The expected files

An expected file is written by `rnl`'s conformance dump (`rnl_cli::dump::conformance`). It records:

- for each drawing level, the symbols in use with their pins, graphics and boxes; the drawn instances, bundles and usages with their symbol, position, orientation, style and layer; the wires with their routed vertices; the scene graphics; the texts with their anchors and parsed content; the lines a viewer may draw for `ROUTE`; the constraint statuses; and the objects left without a position;
- for each diagnostic shown to the user, its level, file, line and column.

Messages are not recorded: the language fixes which items fail and where, not how a tool words it (7.6). Hints are recorded too, although the standard does not require them, because this corpus also guards the reference implementation against unintended changes.

A snapshot file is what `rnl snapshot` prints for the case, the snapshot of the editor interface that a converter or an editor reads ([`rnl-view`](../../crates/rnl-view/README.md)): for each drawing level the host circuit, and the model by the ids a transaction writes back. The runtime's version, the revision and the diagnostics are left out: the first two change with the toolkit and its bundled packages rather than with the case, and the expected file holds the diagnostics. The snapshot is not a part of the language; its files guard the toolkit's interface, and the tests of the WebAssembly binding check that the WebAssembly core gives the same snapshots, the revision included.

## Running

```bash
cargo test -p rnl-cli --test conformance
```

After a change that is meant to alter a result, write the expected files again and review the difference:

```bash
RNL_BLESS=1 cargo test -p rnl-cli --test conformance
```

`RNL_BLESS_0_3=1` writes those of `cases-0.3` instead, and leaves the others as they are; `RNL_BLESS=1` does not write those of `cases-0.3`. The expected files of each corpus are written only when that corpus is asked for, so that blessing a change of 0.3, whose text is still a draft, never rewrites the regression suite of 0.2.

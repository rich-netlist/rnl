# rnl-edit

Writing RNL into host netlists: the edit transactions of the editor interface (`notes/rnl-editor-interface/spec-draft.md` in rnl-dev, section 4). This is the first part, what a tool needs that prints a netlist and its drawing together, such as Analog Canvas's SPICE+RNL and Spectre+RNL export:

```rust
pub fn write(request: &WriteRequest) -> Result<String, String>
```

`WriteRequest` holds the netlist, its dialect (`"spice"` or `"spectre"`), the `author` of the records, the ops, as the draft writes them in JSON, and optionally `file`, the name the netlist is saved under, such as `top.net`. `write` reads the netlist with the host adapter of the dialect, under that name (`entry_of`): its suffix tells the Spectre adapter the mode a file starts in, the Spectre mode for a `.scs` file and the SPICE mode for any other, up to its `simulator lang=spectre` (2.2). Without `file`, a Spectre netlist is read as a `.scs` file and a SPICE netlist as a `.sp` file, as before. It and returns it with the ops written in; the netlist's own text stays as it is, line endings included.

The optional `language_version` is `"0.3"` or `"0.4"`; leaving it out keeps the released default, 0.3. Choose `"0.4"` to write independent pin names, unbound pins, or a one-terminal bus pin. A `define-symbol` pin accepts `names`, the local names to bind in order, and `bus`, which preserves the difference between `terminal=1` and `terminal=[1]`. An empty `terminals` list writes a pin without a terminal binding. `label` remains display text and does not name the pin. These features are refused with the default version. Wire vertices with no source `reference` are refused; an opaque pin id cannot be used as RNL source.

- **The header record** goes where a new header goes (`writeback::add_header`, the rules of the solver's `with_header`; 2.2, 2.8, 16.3): after line 1, which is never read, and after the lines that continue it; in a Spectre netlist that is not a `.scs` file and whose first statement is `simulator lang=spectre`, right after that statement, with `//`, and otherwise above it with `*`, which is a comment in the SPICE mode. The records follow its comment marker. It holds VERSION (the requested language version, or the default 0.3, 16.1), then a USE-PACKAGE for each `use-package` op, each name and version once. The `level` of a `use-package` is not used.
- **One record of the author's for each level** the ops name, `subckt:NAME` (case-insensitive in SPICE), or `file` or `file:PATH` for the file level, at the end of the level's own text (17): before the `.ends` of a subcircuit, before the `.end` of the file, or at the end of the file. When the end lies in a region written to be encrypted (`.prot … .unprot`, Spectre's `protect … unprotect`), where a record is gone once the region is encrypted (2.2), the record goes before the region, and before the subcircuit that holds that place. The statements are in the order of the ops.
- **The comment carrier** is the header's, `*` or `//`, but `*` in a `simulator lang=spice` section of a Spectre netlist, where `//` is no comment (2.2).
- **The standard form** (4.3): the object first, positional parameters before named ones, numbers rounded to a millionth in their shortest form, the default orientation R0 and `mode="auto"` left out. A line is at most 132 characters, the comment marker included; a longer statement breaks at spaces outside strings and brackets, the further lines indented by four more spaces. A header record that does not fit on one line has one statement a line.
- **Texts**: `markup` as written, or `lines` of runs, as the Document's `Text.lines` holds them, written as markup (13.6) that reads back as the same runs. A backslash is written `\textbackslash{}`, and `_ { } $ % & # ^` with a backslash before them.

The ops written so far are `set` (symbol, style, position, orientation; `terminals`, the host terminals the symbol's pins bind, `[[1, "d"], [2, "g"]]`, written `@SET-SYMBOL(terminals=[[1, "d"], [2, "g"]]) $NMOS`, for a call whose ports are not named as the symbol's terminals: a number from 1 or a name with the symbol's terminal name, needing a `symbol` and `language_version: "0.4"`, and `add-usage` takes it as well; on `#`, the level itself, the symbol of a subcircuit, 9.2.6), `add-usage` (each object or point with the name of the role it fills, `$DIFFERENTIAL_PAIR @ATTACH #M2(in_n) #M1(in_p)`, so that the roles are those of the request whatever order it gives them in, and a role the definition lacks fails when the netlist is read, 9.4; a role that is not an ASCII name is written in quotes, the name itself, 16.5; a set role takes the list of its members, each an id or a point, written in braces, `{#M3 #M9}(ref)`, and `{}` for none; its `params`, in the order given, `$CANVAS_NAME @ATTACH(name="M1") #XM1(part)`, each a string, a number, a boolean or a list of them, a number exactly, so that the snapshot gives them back as given in `ObjectView.params`, and a parameter the definition lacks fails as a written one does; a string with a line break is refused, as a record cannot hold it), `add-point`, `add-wire` (several nets as one set, `{&in &out} @WIRE {…}`, a bus, 13.1), `add-text` (`fix_rotate` is an optional boolean requiring `language_version: "0.4"`; an explicit `false` is preserved to override a symbol label; for a text with a `key`, `halign`, `valign` and `rotate` are written as given, since a value left out is the one its symbol gives that key and not the default, 13.3; for a text without, a value equal to the default is left out), `add-rule` (`language_version: "0.4"`: `{"op": "add-rule", "level": …, "select": {"kind": "instance" | "usage" | "terminal" | "net", "params": {"name": "R*"}}, "action": {"op": "add-text", "markup": "", "key": "name"}}`, a rule that draws a text on what it selects, 10.4, in the level it is written in only, and in the levels below too when a condition says `"recursive": true`, as the 0.4 selections do not go down by default; written `# @SELECT-INSTANCE(name="R*") => @TEXT("", key="name")`; the conditions in the order given, each a string without a line break, a number or a boolean, its name an identifier and not checked against the selection's own conditions, as the `params` of `add-usage` are not (a wrong one is reported when the netlist is read); one action, an `add-text` without `attach`, `at`, `name` or `level`; the same rule twice in a level is written once, where it first comes), `add-to` and `remove-from` (several items as one set, `{&in &VSS} @REMOVE-FROM $PORT_FILL_SET`, whose members are added or removed, 5.2.2), `use-package`, and:

- `add-shape`, a graphic in the scene (13.4): `line`, `rectangle`, `circle`, `ellipse`, `arc` or `bezier`, its points, its `params` (width, height, radius, fill, arrow) and `style`, written in that order; a rectangle, circle or ellipse given by its centre and its size is written on its centre. A `layer` comes after it as `@LAYER`. The writer keeps the order of the ops, which is the order the graphics of a layer are drawn in (11.6).
- `define-symbol`, a symbol (9.2): its `box`, `pins` (terminals by number or name, position, direction, `label` as markup or lines of runs) and `prims`, graphics as `add-shape` takes them, in the symbol's coordinates. It is written one statement of its body a line.

The `style` of `set` and `add-usage` is style properties (9.3), such as `{"linecolor": "#2275e2", "textcolor": "#2275e2"}`, written the standard way: a style `$style1 = @DEFINE-STYLE(linecolor="#2275e2", textcolor="#2275e2") {}` that the object's statement gives it, `#M1 @SET-STYLE $style1 => @PLACE(0, 0)` (11.3). Each level defines once, first in its record, each style it uses, the styles of the same properties and values being one; the names are numbered over the whole request, so a level that uses the style of another defines its own and hides nothing above it (6.8), and an included file reads the same opened on its own. A property the language does not know is written as given and fails when the netlist is read, as one written by hand does (9.3). The editor interface's snapshot gives the style back in `ObjectView.style`.

A line that cannot break outside brackets breaks after a comma inside them, such as between the parameters of a long TEXT. An op that cannot be written refuses the whole request with the reason and the op's index: an unknown op or field, a level the netlist does not have, a graphic whose points do not fit its shape, a field of the draft not written yet (`layer` of `set`, `add-usage` and `add-wire`; `unset` and `remove`). So is an op whose level lies in a region written to be encrypted, such as a subcircuit whose `.subckt` lies in one, which has no place for a record that is not gone once the region is encrypted (2.2). A netlist that has RNL records already is refused too. Merging with them, `replace_own`, `base` and refusing ops that do not take effect are set aside (2026-10-17): Analog Canvas, which writes with this crate, reads RNL into its own format and writes it anew, and is no RNL editor ([roadmap](../../docs/roadmap.md)).

`rnl write REQUEST.json -o OUT` ([`rnl-cli`](../rnl-cli/README.md)) and the `write` request of the [WebAssembly binding](../../bindings/runtime-wasm/README.md) call it.

## Replacing the records of a level

`write` refuses a netlist that has RNL records already, as a tool that writes anew has no use for merging. The one thing this crate does with such a netlist is narrow: a tool that holds the whole new drawing of one level, such as Analog Canvas after an engineer tidied one subcircuit, puts it back into the netlist's own files, which may be several with includes, and changes nothing else.

```rust
pub fn replace::replace_records(
    reading: &replace::Reading,
    files: &dyn Provider,
    title: &str,
    records: &str,
) -> Result<replace::Replacement, replace::Failure>
```

`reading` names the main file of the netlist (`entry`), its dialect and formats, and the runtime's options; `files` reads it and what it includes. `title` is the level as the commands take it: a subcircuit name, which compares by the case rule of its dialect, or the name of a file for a file level. `records` is RNL source without comment markers, one or more `@RNL(…) {…}`, the level's whole new drawing. The answer is the one file that holds the level, `path` and `text`, with how many records went (`removed`) and came (`added`); the caller writes it, and no other file changes.

Every record of the level in its file goes, the authored ones and the solver's (`type="generated"`, and one written for the level with `scope=` above it in the same file), but a header record. The records given are written at the end of the level's own text (17), where `writeback::record_line` puts a record, behind the comment marker the file uses for RNL, in the file's line endings. The header record, the records of every other level, host statements, comments and every other byte stay, and nothing is merged into the records that were there. The records given with nothing in them only take the old ones out. A file of the language version 0.3 or the draft 0.4 is written alike: the version is read from the files.

It refuses, giving no text, a `Failure::Refused` with the kind and the reason of the refusal (`rnl_runtime::writeback::Refused`, RNL8403 to RNL8411): no level has the title, or several do; the level has no place for a record, as its text lies in a region written to be encrypted (`.prot … .unprot`), a host region excluded from writing, or a library section the netlist lacks (2.2); the records would come before the header record of their file (2.8); the file declares a language version that is not interpreted (16.1); or the records do not read. For the last, the netlist is read again with the new text of the file, and the records are refused when an error lies in the new lines or when they read back otherwise than they were given; the reason names the lines of the records given. A netlist that cannot be read at all is `Failure::Unreadable`. The runtime half, which works on a host document and a function that reads it again, is `rnl_runtime::writeback::replace_records`.

`rnl replace-records` ([`rnl-cli`](../rnl-cli/README.md#replace-records)) and the `replace_records` request of the [WebAssembly binding](../../bindings/runtime-wasm/README.md#replacing-the-records-of-a-level) call it.

With `language_version="0.4"`, structured text and pin labels accept `kind:"sqrt"` with `radicand` runs, and the optional run style `upright`. The writer checks that a formula reads back with the same content and style. Expanded literal attributes with spaces or unsupported styled fragments may have no equivalent in the formula subset; provide their original `markup` instead of reconstructed `lines`. Such requests are refused rather than changing their text. Existing runs and the default output version keep their behavior.


### Numbered edit errors

`write_diagnosed` and `write_with_options_diagnosed` return `Written { text, diagnostics }`
or `Refusal { code, message, diagnostics }`. Operation errors use the existing RNL8600–RNL8624
kinds; host errors retain their own kind and source location. The `write` and
`write_with_options` string interfaces remain available. Draft 0.4 refuses a host parse error
before writing; released output versions retain their behavior. Diagnostics are available
through the diagnosed interfaces even when a released-version write succeeds.

For explicit 0.4 requests, the CLI prints the diagnostic number. The WASM response keeps its
`error` string and adds `code`, `name` and `diagnostics`. Both direct and Worker JavaScript
calls reject with an Error carrying `code`, `diagnosticName` and `diagnostics`. Existing
requests keep their old error response shape. No Viewer application changes are required
to keep displaying the message; frontends can use the added fields for diagnostic links.


For `language_version: "0.4"`, `add-point` with `junction: true` takes its dot definition from the target level's effective `SOLVER-CONFIG(junction=...)`. `write_with_options_diagnosed` resolves it after package ops and `include_std` have been persisted, then writes dot usages in a final record of the same author. Without a setting, or with an empty string, it writes only the point. An invalid definition setting adds the located warning `RNL8118` to `Written.diagnostics` and writes no dot. The definition must accept a point in its first role; no standard definition name is assumed.

Low-level clients can use `form::statements_with_junction(op, style, definition)` with the resolved reference. The older `form::statements` entry retains its released behavior, as do writes that request or default to 0.3.

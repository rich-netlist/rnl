# rnl-view

Optional inspection geometry is always included as `Level.usages[].frame` and `Level.currents`
in SVG pixels with y down. `overlays::svg(level, &OverlayOptions)` exports it in separate
`usage-underlays`, `usage-overlays` and `current-overlays` groups; `overlays::apply` applies
export options to a Document. Defaults keep the original SVG bytes. Geometry has no style
fields, does not change hits/primitives and has no effect on solver problems. See the
[npm options](../../packages/runtime/README.md#inspection-overlays) and
[design record](../../docs/decisions/0014-inspection-overlay-geometry.md).

The core interface of [decision 0008](../../docs/decisions/0008-shared-core-per-platform-frontends.md): a workspace in, a Document out. The desktop viewer and `rnl view` call it natively; the [web viewer](../../apps/web/README.md) calls it through WebAssembly.

```rust
pub fn build(entry: &str, files: &dyn Provider, options: &BuildOptions) -> Result<Document, String>
```

- `entry` is the path of the file to open as the frontend names it, `/`-separated (a `\` is read as `/`). It need not exist on disk: an untitled text is an entry in an in-memory provider. `build` fails when the entry cannot be read. Name the files of a workspace by rooted paths, such as `/w/top.sp`, as the desktop names them by absolute ones (see below).
- `files` is the frontend's file access: `FsProvider` from [`rnl-cli`](../rnl-cli/README.md) on the desktop and in the CLI, a `MemoryProvider` of the texts a frontend holds elsewhere. The standard packages in [`libraries/standard`](../../libraries/standard/README.md) are bundled here and layered under it, in the directory `<bundled>`, one package directory for each version, as in `libraries/standard`: `<bundled>/0.2/rnl-std.rnl`. Extension and PDK packages are supplied explicitly through the pool or search paths. `build.rs` lists every `.rnl` file of every version directory, so a new version is bundled by adding its files.
- `BuildOptions` holds the dialect, instead of guessing it from the entry, the runtime's options, such as leaving out the standard package at the root (16.3), and the outputs: whether to write each level's SVG (`svg`, on by default), whether to give its primitives (`primitives`, off by default), whether to give its solve status (`status`, off by default), and whether to give its constraints (`constraints`, off by default).

The Document holds, for each drawing level, its drawing, what on it can be clicked, its status without a solver, its subcircuit instances and the objects it does not draw because they have no position, each with its symbol drawn alone (`unplaced`, [below](#the-objects-not-drawn)); for the document, the source files with the places of their records and of the statements that do not take effect (7.5), the instances and nets of every level with the places that name them, the drawn usages with their independent identities, and the diagnostics. The references in the records come from the runtime (`Interpretation::refs`), so aliases, scopes and subscripts are resolved as the language says. The field names are what the viewers read; `rnl view FILE` prints the Document as JSON.

A level's `hits` are what on its drawing can be clicked, in pixels with y down, each standing for objects (indexes into `objects`): a `box` for each symbol, `points` its top-left and bottom-right corners, which stands for its instance, or, for a usage such as a ground, its own `usage` object first and then the net it is on (if any); a `pin` for each pin with a net, one point, standing for its nets; a `wire`, its vertices, for its nets; and a `label` for each text attached to an object, `points` the corners of its box, standing for what the object stands for (the instance, the net, the nets of a wire, and for a terminal the nets of its pin, as the pin does) and for nothing when it is attached to something that is not an instance, a bundle, a usage, a wire, a net or a terminal drawn at a pin with a net; a text at a point is no label. Usage objects have the runtime's `ItemView::object_id` as their `name` (such as `%gnd1` or a source-location identity for an unnamed usage), and have no `lines` or `opens`. A usage's label keeps its net first, preserving label clicks, and also lists the usage; its pins and wires still stand only for nets. A hit's `id` is the `data-id` of the SVG groups that draw it: `item-K` for a symbol, `wire-K` for a wire, and for a label its text's id, such as `#R1::name`. Repeated text ids, including unnamed supply labels such as `%s::name`, get distinct display ids (`text-K`, with collision avoidance) while preserving their runtime object identities and attachment targets. A box has a `name` when it is a usage that the netlist names, such as a port `%pi`, and has none for a usage it does not, as for an instance, which has its objects' name. The primitives of a label have its id as their `owner`. `TextView::target` and `ItemView::object_id` of the runtime's model are what the labels' hits and the boxes' names come from.

`path` is the entry as given. A file of the document is named relative to the entry's directory when it is in it or below, and otherwise as the provider names it, so the entry's directory joined with a file's path (`rnl_runtime::source::join`) is the file in the workspace. That needs a rooted or absolute entry: with a relative entry in a directory, such as `w/top.sp`, a file outside it keeps a relative name, such as `x.inc`, which can be that of a file inside it (`w/x.inc`), and the Document then holds only one of the two. The host adapters name the files this way. A `..` above the root stays in a path: `../x.inc` beside an entry at the root, `/top.sp`, is `/../x.inc` and not `/x.inc`. A file system reads it as `/x.inc`; a workspace in memory has it only when the frontend gives it.

`missing` lists the files the core asked for by path and did not get, such as an include or a package file named by `path=` that is not in the workspace, each once, as the provider was asked for it, in the order first asked. A frontend that can read them adds them to the workspace and builds again until nothing new is missing. A package found by name comes only from the provider's package directories (`Provider::package_files`, such as `MemoryProvider::package_dirs`), so it is never missing: a frontend gives its package directories before it builds.

With `status`, each level has `solve`, what a frontend decides from whether to solve it (decision 0008): `"fixed"`, nothing for a solver to decide; `"unsolved"`, something to decide and no record of the solver; `"solved"`, a record of the solver that is up to date; `"stale"`, one whose input or numbering is out of date ([`rnl_runtime::previous::solve_status`](../rnl-runtime/README.md#the-previous-result-and-the-solve-status) says exactly). Without it the Document is as before, and with it nothing else changes. It takes the problems of the levels read without their records of the solver: a document that has such records is read once more, without them, and one that has none is read once, with the problems built. On the conformance corpus in WebAssembly that doubles the time of a document with a record of the solver, and adds a tenth to one without.

`read_previous(entry, dialect, files, options)` makes the two readings of a solver, with the bundled packages: the problems, read without the records of the solver, and the previous result of each level, from the reading with them, as hints for a warm start (`rnl_runtime::previous::read_previous`).

The crate also has what the `rnl` command needs that reads no files: dialect detection, reading a host document, interpreting a netlist or a package file checked on its own, and the status lines of `rnl check`.

The crate does no file I/O, so it builds for `wasm32-unknown-unknown`.

## The objects not drawn

`Document.symbols` contains the subcircuit symbol inspector data: runtime identity deduplication, rendered preview, pin/label templates, and the exact defining member's original text and location. `Level.symbol` references the subcircuit's own block symbol; `Child.symbol` references the effective symbol of that particular instance in its parent. Default symbols with identical terminal lists share one preview. Preview rendering copies only reachable nested symbols, while the exposed terminals and labels are the root symbol's interface. Package attribution comes from the defining unit, so local aliases do not change its origin or version. `SourceFile.semantics` lists physical lines containing parser-recognized free text for the viewer's semantic-line filter.

`Level::unplaced` lists the objects of the level that have no position, as the count in its `status` says ("3 without a position"), in the order of the netlist: an instance, a bundle of instances or a usage such as a ground symbol, left to a solver. Each has its `kind`; its `name`, an instance's name or, for a bundle or a usage, the label the diagnostics give it; the `symbol`'s name; `objects`, the instances it stands for as indexes into `Document::objects` (one, a bundle's members, or none for a usage, which no statement of the netlist writes); and its drawing alone, `svg` and `primitives` as the frontend's outputs ask: the symbol at the origin with its orientation, and the name of the net at each pin, in blue beside the pin on the side the pin points to. The runtime gives the objects as items at the origin (`LevelView::unplaced_items`, with the symbols they are drawn with in `unplaced_symbols`, which the level's `symbols` do not hold), and the renderer draws each on a level of its own, so that a frontend lays out no text of it. A list of them in a viewer needs nothing else.

After them, `Level::unplaced` lists the devices that are not drawn at all, whatever their position, since no symbol can be chosen for them: a transistor (`M`, `Q`, `J`, `Z` of SPICE) whose model card the netlist does not have is drawn by the type of its model alone, so without the card the standard package gives it no symbol, and the renderer's own would only pretend. Each has a `reason`, `model card not found`, no `symbol` (empty), no `svg` and no `primitives`; it is not counted in the `status`, which a solver cannot change, and the reading gives a warning for each missing model, naming the devices. A rule or a statement of the file that gives such a device a symbol draws it. The runtime gives them in `LevelView::undrawn`.

A netlist that has no positions yet lists every object, and each drawing is some 1.3 KB of SVG, so a Document of tens of thousands of devices would carry tens of megabytes for a list that shows a screenful. `build_drawn` builds the same Document without those drawings, `svg` and `primitives` of `Level::unplaced`, and gives them apart as `Drawings`; `Drawings::unplaced(level, items, names)` draws the objects at `items` of `Level::unplaced`, in that order, as `UnplacedDrawing`s, which hold what the Document would have carried (`BuildOptions::svg` and `primitives` as asked). `names` are the objects' names as the Document lists them, and are checked, so that a frontend that built the document again is refused, not answered with the drawings of other objects. `Drawings` holds the model's items, which are not `Send`: a frontend keeps it in the thread that built it ([`apps/desktop`](../../apps/desktop/README.md) in a thread of its own, the WebAssembly core in its Worker).

## Snapshots

```rust
pub fn snapshot(entry: &str, files: &dyn Provider, options: &BuildOptions, parts: Parts) -> Result<Snapshot, String>
```

gives the editor interface's view of a document (`notes/rnl-editor-interface/spec-draft.md` in rnl-dev, section 3), from the same interpretation as its Document, for a converter or an editor that reads the document by objects rather than draws it. This first part has what Analog Canvas's import needs:

- the language version, the one the main file declares, or 0.3, the tool's default, when it declares none (16.1); the packages in effect by name and version, the files, the diagnostics, and the Document as `drawing` unless `parts.drawing` is false;
- for each drawing level, by its id (`subckt:NAME`, or `file:PATH` for the file level), when `parts` ask:
  - `host`, the host circuit: the ports, the instances with their masters and terminals (number, name and net), and the nets, each net written as on the first line that names it;
  - `model`, what the RNL makes of it: the instances, bundles and usages, drawn or not, with their symbols, positions, orientations and pins where they are drawn; the named points and whether a junction is drawn at them; the wires with their vertices as written and as routed; the texts with their markup, lines, anchors and alignment; the graphics of the scene (13.4) as an `add-shape` op writes them, in the order written; and a subcircuit's own symbol, `#` (9.2.6), as `symbol`.
- Objects go by ids that a transaction can write back: `#M1`, `&vout`, `&"vdd!"`, `%gnd1` for a name the level binds, and `@file:line:col` for an object without one, where the statement that made it is, with `#n` after it when the statement made several. A name bound in a definition's body, which each expansion binds anew, does not count. An instance's terminals are written by number, `#M1:1`; a usage's pins by role. A usage's `attach` gives each role what fills it: an id or a point, and for a set role (9.4), such as `ref` and `out` of `$CURRENT_MIRROR` or `tail` of `$DIFFERENTIAL_PAIR`, the list of its members, each an id or a point, nested sets followed down, `[]` when the role is left empty.
- A symbol is named by an id unique among the level's symbols: its name, or its name and where it is defined after `@` when two share it, as a subcircuit's symbol (9.2.6) and one of the file's may. A symbol the document defines comes with its `definition`: its box, its pins with their names (as markup and as runs), and its graphics; a package's symbol is known by its name. A subcircuit's own symbol is among the symbols of its level, though nothing there is drawn with it.
- The `style` of a wire, a text or a graphic holds what the document's own records give, not the standard package's defaults, so that a converter reads back what it wrote. A text with nothing to show, such as a label emptied by `rnl-std-no-labels`, is left out; `written` tells a text the document writes from a label its symbol alone gives, such as the formula of a block.
- `revision` is the fingerprint of what the snapshot is made from (3.7): the texts of the host files and of the packages read, their line endings made `\n`, and the build's options, hashed with SHA-256. The same texts and options give the same revision; any change to a text, a space included, gives another, so that a transaction can say which revision it was made for.
- Each value is a slot with a `source`, which stays null until the snapshot's `sources` come.
- An object view, and a net of the host circuit, that is a member of some usage has `usages` (`UsageOf`): the list of [the usages of an object](#the-usages-of-an-object), each usage by its id, its file by index in `files`, a group's with `kind` `"group"`. A level that has groups (11.5) has `groups` in its model (`GroupView`), each with its id, its members by id, its statement's file and line, `source`, `state` and the groups it is within.

`rnl snapshot FILE` prints it, with the host circuit and the model by default.

## Catalog

```rust
pub fn catalog(files: &dyn Provider, options: &CatalogOptions) -> Catalog
```

lists the symbols, ordinary definitions and sets of the packages the core has: the bundled ones, the standard series 0.2 and 0.3, and those of the package directories of `files` (`Provider::package_files`), for a frontend that maps its own parts onto them, as Analog Canvas does. Each package file is read through the runtime as `rnl check PACKAGE.rnl` reads it, checked on its own (2.7) with `options.runtime` (`rnl_runtime::interp::catalog::package_contents`), so a symbol's pins and box are the ones the drawings have: its box is the model's, the one it writes or the extent of its graphics (9.2.3).

- Of each name and version the first file the package directories have is listed, the frontend's before the bundled ones, as the runtime finds a package by name (16.2); of each name the newest version, by the runtime's order of versions, or every version with `all_versions`; and only the names `packages` gives, when it gives them.
- `packages`: name, version, `language` (the language version the file declares, or 0.3 when it declares none), `file` (its file name), `references` (the packages its header record names with USE-PACKAGE), `series` (`rnl-std` or `rnl-std-*`) and `implicit` (`rnl-std`), by name and then by version.
- `symbols`: `symbol`, `package`, `version`, `file`, `definition`, `pins` (one for each terminal, in terminal order: `terminal` as the symbol writes it, a number or a name, `at`, and `direction`: `"right"`, `"up"`, `"left"`, `"down"` or null), `box` and `labels` (the texts it writes with a key, with `key`, `text` as written, `at`, `halign` and `valign`, `"start"` and `"baseline"` when it writes none, as the model draws them).
- `definitions`: `definition`, `package`, `version`, `file`, `roles` as `roles=` writes them, `parameters` as `[name, default]`, the default null when there is none, and `symbol`.
- `sets`: `set`, `package`, `version` and `file`.
- A symbol's `definition` and a definition's `symbol` come from the rules of the packages listed written `# @SELECT-USAGE $DEF => @SET-SYMBOL $SYM`, which draw every usage of the definition with the symbol, each name found as the runtime finds it where the rule is written (16.2): `$GROUND_SYMBOL` draws `$GROUND`. A rule of another form, such as the fill's `$NAMED_GROUND_NET_SET @SELECT-ANCESTOR-USAGE $GROUND => @SET-SYMBOL $NAMED_GROUND_SYMBOL`, links nothing.
- The symbols, definitions and sets go package by package as `packages` lists them, each in the order of its file.

`rnl catalog` prints it; the WebAssembly core gives it for a catalog request.

## Drawings

A level's drawing comes in the outputs the frontend asks for. A level has an `svg` field only when the SVG was asked for, and a `primitives` field only when the primitives were; its `scale` is always there.

- The primitives (decision 0008) are what the renderer draws, in drawing order: paths, rectangles, circles, ellipses, texts and flylines, each with its layer and place in the drawing order (11.6), its bounding box, and its `owner`, the `data-id` of the SVG group that draws it. A symbol's drawing has its item, such as `item-3`, and a wire's its wire, such as `wire-0`, as the hits' `id` names them, one for each run of a wire drawn in runs while some of its points have no position; any other text has the name the diagnostics give it, such as `#R1::name`, which several texts can share and no hit has; a shape written in the scene and a flyline have none. The styles and the renderer's defaults are resolved, so a frontend draws the primitives without reading the model: fills; strokes, each shape's in turn over its fill, with their colour, width, dashes and dash offset, in scene units or in pixels (the hairline is 1.2 pixels wide at every zoom), cap and join, which is all a canvas needs to draw the line styles as the SVG does (a double line is two strokes, the second narrower in the colour between the lines, and a flyline a grey dashed stroke of 1 pixel; a shape of no size is drawn as SVG draws it, which the types describe, since Canvas 2D draws some of them otherwise); texts laid out by the core with the metrics of the fonts shipped with it ([decision 0009](../../docs/decisions/0009-fonts-shipped-with-the-core.md)): runs, each a piece of text in one face and size from the start of its baseline, with its width, and bars, the bars of fractions and the lines over overlined runs, as strokes; what the fonts do not map in runs of its own, `fallback`, whole grapheme clusters drawn in a font of the system's, whose width is an estimate; with the lines of markup (13.6) they come from, the size, colour, font hint, alignment after turning and direction. A colour is written as in the language and in CSS, `#RGB`, `#RGBA`, `#RRGGBB` or `#RRGGBBAA`, with the opacity last. The primitives are this crate's own serializable types, converted from the renderer's, which stay free to change. In the JSON, a primitive, a path segment and a run each name their `kind`, and a point is an `[x, y]` array.
- The renderer decides how a line style looks (the hairline's width, the dashes, double lines, flylines) and the SVG writer writes the strokes as they are, with the dashes to at most 6 decimals, so that a long dashed line keeps in step with them. The renderer also lays out the texts, and the SVG writer writes each run where it is, in the shipped family with no kerning or ligatures, held to its width with `textLength`; a run the fonts do not map, in the font the browser picks after that family, not held to its estimated width but centred on it. A frontend that draws the runs and bars in Noto Sans SC Regular and Bold the same way, and the runs the fonts do not map in a font of its system's, draws the texts as the SVG does, with no alignment, baseline or measuring of its own; the types say how, and a test holds the SVG writer to what they say. The font a style names is a hint (9.3) that the drawing does not follow.
- The primitives are in scene units, x to the right and y up, as in the model, but for the strokes in pixels, which the SVG draws in its own. The SVG and the hits are in pixels, x to the right and y down: a point (x, y) of a primitive is at (x·scale, −y·scale) in them, with the level's `scale`. The SVG is written from the same primitives, and its view box frames them with a margin.

## Type definitions

[`types/document.d.ts`](types/document.d.ts) declares the Document and everything in it in TypeScript, for frontends and their checks; the page in [`apps/viewer-ui`](../../apps/viewer-ui/README.md) refers to it. [`types/snapshot.d.ts`](types/snapshot.d.ts) declares the snapshot, and [`types/catalog.d.ts`](types/catalog.d.ts) the catalog. They are generated from the Rust types by [ts-rs](https://crates.io/crates/ts-rs), which the types derive in the tests only, and laid out by the test to be read. The test fails when the file is not what the types give; after a change to them that is meant, write it with:

```bash
RNL_BLESS=1 cargo test -p rnl-view types
```

The serde field names are the contract, and the declarations keep them as they are.

See the [roadmap](../../docs/roadmap.md) for planned work.

`Level.usages` lists every usage in that drawing scope, including semantic usages without a symbol. Each entry shares a selectable `Document.objects` identity with its symbol when it has one; it carries the creating statement and its source, the definition name, its own symbol classification, whether it creates drawing objects in its body/descendants, and role references. Roles contain deduplicated selectable members, special wire display groups, and visible extents in SVG pixel coordinates. Set roles, nested semantic usages, quoted references and fragmented wires retain their geometry; shared nested usages are memoized. Unavailable role members keep their references with no extent. The frontend alone assigns display colors and draws usage overlays; exporting usages does not construct a solver problem.

Each entry has `state`, as [the usages of an object](#the-usages-of-an-object) give it: `in-effect`, `overridden` (with `reason`) or `disabled`. An application that failed made no usage and has no entry.

The groups (11.5) follow the usages in `Level.usages`, each a `Usage` of `kind` `"group"` (a usage's is `"usage"`) with an empty `definition` and one role, `members`, which holds its members as a set role does, so a group has a frame like a usage's. Its `Document.objects` entry is of kind `"group"`, its id `%core` when a record of the level names the set, otherwise where GROUP is written, `@file:line:col`. The runtime gives the groups in `LevelView::groups` (`GroupInfo`): the id, the members, the statement, `origin`, `parent` and `disabled`, as for a usage; a group that PRIORITY turns off is listed too.

## The usages of an object

`Object.usages` turns the usage table round: for each instance, net, usage and group, the usages and groups it is a member of in its level (`MemberOf`), in the order of the usage table, then of the failed applications. Each entry has:

- `usage`: the usage or group, an index into `objects`, or none for an application that failed and made no usage. `kind` is `"usage"` or `"group"`. `id` is the usage's id (`%dp1`, or `@file:line:col` for one without a name), and `definition` its definition, empty for a group.
- `roles`: the roles the object fills (`RoleOf`). `role` is the role's name. `set` says it is a set role (9.4) with the object as one of its members. `member` is how the role names the object, as the snapshot writes ids: `#M1`, `&vdd`, `%dp1`, `#M5:1` for an instance's terminal by number, or `%g1:p` for a usage's. `terminal` is a terminal's name, such as `d`.
- `file` and `line`: the statement's file and first line, as `Usage::file` and `first_line` have them.
- `source`, where the usage comes from:
  - `written`: a statement of the document's records;
  - `solver`: a record a solver wrote back (`type="generated"`, 2.8);
  - `rule`: a rule (10.5), with `rule` giving its package (empty for the document's own), file and line;
  - `body`: the body of the definition that the usage `made_in` applies (9.4).
- `state`, with `reason` for the failed and the overridden:
  - `in-effect`;
  - `failed`: the application failed and made no usage (7.2);
  - `overridden`: a fact its statement writes lost a conflict to one of higher priority (8.5);
  - `disabled`: its priority, or that of the usage it is made in, is `"disabled"` (14.8).

A group is only `in-effect` or `disabled`: GROUP takes no part in conflicts and has no priority but on and off (11.5). Its members have it with the role `members`, a set role. A reference to a set is spread in a set (5.2), so a group is never itself a member of another; a group is within another when all its members are among the other's, and then its own entry lists the smallest such groups, with no roles. In `%stage1 = {#M1 #M2 #M5} @GROUP; %core = {{%stage1} {#M3 #M4}} @GROUP`, `#M1` lists `%stage1` and `%core`, and `%stage1` lists `%core`. A usage that is a member of a group lists the group, as `%dp1` in `{%dp1 #M5} @GROUP`.

An instance lists the usages of its terminals too. The chain upward is the usage's own entry in `objects`: `%dp1`'s `usages` say that it is `input` of `%stage1`, and so on. The runtime gives what this needs in `ObjectInfo`:
- `origin` (`UsageOrigin`: written, solver, rule with its package and place, or body);
- `parent`, the usage it is made in;
- `disabled`.

It gives the failed applications in `LevelView::failed_usages`, each with the name it binds, its definition, the objects written for its roles and the error's message. A failed application is noted only for a statement of the level's own records, not for a definition's body or a rule. `rnl explain FILE REF` prints these lists (see the [CLI](../rnl-cli/README.md)). The snapshot gives the same lists by ids, as `ObjectView.usages` and `HostNet.usages` (`UsageOf`, with `kind`), and the groups as `LevelModel.groups` (`GroupView`: id, members by id, file and line, source, state, and `usages`, the groups it is within).

## The parameters of subcircuits

A viewer shows a subcircuit's parameters, and the values an instance gives them, without the language evaluating any: `${w}` still shows what is written (13.6), and nothing drawn depends on a parameter.

- `Level.params` (`SubcktParam`): a subcircuit's parameters, as its definition writes them (SPICE's `.subckt … params: w=1u`, with its `+` lines, or the `name=value` HSPICE writes without `params:`; Spectre's `parameters` in its body). Each has `name`, `default` (none when it writes none), `value` and `number`, and `from`: `"default"`, `"bound"` or `"unset"`.
- `Child.params` (`ParamValue`): the parameters an instance writes, each with the number it comes to in the level the instance is in. An instance of a subcircuit the netlist does not define has them too.
- `Child.effective` (`SubcktParam`): when the netlist defines the subcircuit, its parameters for that instance: those the instance writes, `from` `"instance"`, and the defaults of the others, evaluated with them, so a default such as `wp={2*wn}` follows the `wn` the instance gives.
- `BuildOptions::bind` (`Bind { subckt, params }`), the Request's `bind`, `rnl view --bind SUBCKT --param NAME=VALUE`: values, as text, for a subcircuit's parameters, for showing it as one instance would. Its `Level.params` have them, `from` `"bound"`, and what is written in it is evaluated with them. Nothing is remembered.

A value is evaluated in the subcircuit's scope: the values bound or given, then the defaults, the subcircuit's own `.param` values, those of the subcircuits it is written in, and the values the files set outside subcircuits (`.param`, Spectre's `parameters`). The evaluator takes numbers with their scale factors (SPICE's `meg`, `k`, `m`, `u` without case; Spectre's `M` mega and `m` milli by case), `+ - * / ^ **`, parentheses, braces and single quotes around an expression, and the common functions (`sqrt`, `abs`, `exp`, `log`, `log10`, `pow`, `pwr`, `min`, `max`, `int` and the like). Anything else, a string, a condition, a function the netlist defines, an unknown name, has no number, and nothing is said of it. Parameters whose defaults refer to each other have no number, with a hint; a `bind` that names a subcircuit the netlist does not have, or a parameter it does not have, is a warning.

## The constraints of a level

**Experimental: these shapes are not promised to stay as they are.**

With `BuildOptions::constraints` (`constraints: true` in a request of the [WebAssembly binding](../../bindings/runtime-wasm/README.md), `rnl view --constraints`), each level of the Document has `constraints`, the constraints after expansion that a solver takes in, with no solver needed: the structures expanded, one fact per coordinate or relation, in the order of 8.5. They are the facts of the level's `LevelProblem`, by the conversion that `rnl problem` prints too, so nothing here expands anything of its own. A package file has no problem and no `constraints`; any other level has them when asked for, with an empty `facts` when it has none. A document with records of the solver is read once more, as for `status`.

- `facts[k]`, whose index is its rank: the `kind` and what that kind relates, `priority`, `label`, `what`, the line that says it such as `ALIGN x {#M1 #M2}`, `reference` for one with a handle, `source`, and `chain`, the usages that made it by index in `usages`.
- A member is `{origin: k}`, `{object: k, pin, terminal}` or `{centre: [...]}`, with `k` an index in `objects`.
- `objects[k]` ties an object to this Document: `objects`, what it is in `Document.objects`, the instance, the instances of a bundle or the usage, which `hits[].objects` find on the drawing; and `id`, as `Usage.id`. An object that a rule makes, or one without a name, has them too. The facts are read as a solver reads the level, without its record of the solver (2.8), and the Document is drawn with it, so with such a record an object is found by its reference, as for the hints of a warm start; one that nothing can refer to has `id` null and empty `objects`, and is listed only. Points and texts have empty `objects`.
- `usages[k].object` is the usage in `Document.objects`, as `Level.usages[].object`, with or without a symbol; `routes` and `groups` are the level's ROUTEs and the sets given GROUP.
- `input` is the digest of the solver's input. A report of a solve (`rnl_cli::preview::LevelReport`, `rnl preview`) has `host`, the level's `Level.host`, and `input`: when the two `input`s are the same, the report's `facts[k]` is `constraints.facts[k]`; when they differ, the report is of another input and says nothing about these facts. The Document of a preview has its constraints already.

What is not in `facts`: a fact with priority `"disabled"` (14.8) and one that failed as it was read (8.5, 7.6) never reach a solver. A usage so turned off is in `Level.usages[]` with its `state`, and on its members in `Object.usages`. A constraint statement turned off on its own, such as `{#R1 #R2} @ORDER("y", priority="disabled")`, is not in the Document at all: `rnl dump` lists it in the level's `constraints`, with the status `disabled`. A statement that failed is in `Document.diagnostics` and in `SourceFile.failed`, and an application that failed in `Object.usages` with its state.

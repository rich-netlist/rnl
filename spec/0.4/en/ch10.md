## 10 Selections, rules and generation one by one

This chapter covers the selection keywords, the rules that use them, and generation one by one.

### 10.1 Selection keywords

There is one selection keyword for each kind of object selected, each with a fixed set of conditions. The result of a selection is a set (5.2).

Each selection keyword takes one scope object. `#` is the level in which the selection is evaluated (10.3). Given an object or a set, the selection looks among those objects: given a set of nets, for example, SELECT-TERMINAL selects the terminals on those nets (how the scope leads to the kind selected is described after the table). The scope cannot be left out, so a simple selection is also written with `#`: `# @SELECT-INSTANCE(name="R*") => @SET-SYMBOL $RESISTOR`.

| Keyword | Selects | Conditions |
|---|---|---|
| SELECT-INSTANCE | Host instances. With terminals in the scope, the instances they belong to; with nets, the instances that have a terminal on them | `name` (the instance name, such as `name="R*"`); `model` (the name in the model position of the instance line: a `.model` name or a subcircuit name); `type` (the type of the instance, from its `.model` or a DEVICE, such as `"nmos"`; takes `*`); `terminals` (the number of terminals of the instance, such as `terminals=3`); `symbol` and `drawn` (below) |
| SELECT-TERMINAL | Terminals of host instances, whether they have pins or not: a selection of the circuit | `name`, `model` and `type` of the instance; `terminal` (a terminal name or number); `net` (the name of the net it is on); `current` (the current direction, 15.2: `"in"`, `"out"` or `"unspecified"`) |
| SELECT-PIN | Pins of drawn objects: a selection of the drawing (9.2.4) | `name`, `model` and `type` of the object that owns the pin; `terminal` (a terminal or role name the pin binds); `net` (the name of its `::net`); `wired` (10.2) |
| SELECT-NET | Nets. With instances, terminals or wires in the scope, the nets they are on | `name`; `port` (whether it is a port of this level); `wired` (10.2); `global` (whether it is a global net, 6.3) |
| SELECT-WIRE | Wires. With nets in the scope, the wires drawn on them | `net` (the name of the net of the wire; a bus matches when one of its nets matches); `bus` (`true`: only buses, 13.1; `false`: only wires that are not buses, whose net slot receives a net rather than a set) |
| SELECT-LABEL | Labels, that is, TEXTs attached to objects (13.3). With objects in the scope, the labels attached to them | `key` (the key of the text; takes `*` and is case-sensitive; a label without a key matches no `key=`) |
| SELECT-ANNOTATION | Annotations, that is, graphics in the scene and TEXTs attached to points (13.4) | No condition other than `role` and `recursive` |
| SELECT-USAGE | `scope @SELECT-USAGE $D`: the usages of the definition `$D` in the scope, looking inward. With `#`, the usages of the level; with usages, these usages themselves and the usages inside them. Without `$D`, the usages of any definition | The definition is the last object (5.6) and may be left out. `symbol` and `drawn` (below) |
| SELECT-ANCESTOR-USAGE | `objects @SELECT-ANCESTOR-USAGE $D`: the usages of `$D` that have these objects as members, looking outward; indirect members count | The definition is the last object (5.6) and is required. No condition other than `recursive` |

Besides these, every selection keyword takes the condition `recursive`, and the first seven take `role`, which has a meaning only when the scope holds usages (both below).

- **One keyword for each kind.** Each selection keyword is named after the kind it selects, such as `&clk @SELECT-WIRE => @SET-STYLE $signal` for the wires of a net, or `#M1 @SELECT-LABEL` for the labels of M1. No selection takes objects of all kinds: to cover every kind, write one rule for each kind, as the standard package does to give every object its base style.
- **How the scope leads to the kind selected.** Each object in the scope takes one step towards the kind being selected; an object that has no such step selects nothing, which is not an error:
  - SELECT-INSTANCE: an instance is itself; a terminal leads to its instance; a net leads to the instances that have a terminal on it.
  - SELECT-TERMINAL: an instance leads to its terminals; a net leads to the terminals on it; a terminal is itself; a pin leads to the terminals it binds.
  - SELECT-PIN: a drawn object (an instance, a bundle, a usage with a symbol) leads to the pins of its own symbol, and with `role`, a usage leads instead to the pins that fill that role, as the other selections take members (below); a usage without a symbol leads to the pins among the objects that fill its roles; a terminal leads to the pins that bind it; a net leads to the pins whose `::net` is that net, the pins bound to roles filled by it included; a pin is itself. With `#`, every pin of the level.
  - SELECT-NET: a net is itself; an instance leads to the nets of its terminals; a terminal leads to its net; a wire leads to the nets it is drawn on.
  - SELECT-WIRE: a net leads to the wires drawn on it; a wire is itself. SELECT-LABEL: an object leads to the labels attached to it; a label is itself. SELECT-ANNOTATION takes only the annotations in the scope.
  - A step through terminals counts every terminal, with a pin or not: terminals belong to the circuit. What is drawn is selected through pins. So `&vss @SELECT-INSTANCE` includes an NMOS whose only terminal on vss is a bulk that its symbol does not draw. A port of this level, such as `#:inp`, leads to its net.
  - With usages as the scope, only the members of the kind being selected are taken; members are not used as a scope again (see below).
  - For example, the transistors controlled by the clock are `&clk @SELECT-INSTANCE`; only those whose gate is on clk are `&clk @SELECT-TERMINAL(terminal="g") => @SELECT-INSTANCE`; the nets of M1 are `#M1 @SELECT-NET`.
  - Note: a rule that adds grounds, wires, labels or styles to the drawing selects pins (SELECT-PIN), so what it adds fits what is drawn; a rule that checks the circuit selects terminals.
- **By symbol: `symbol` and `drawn`.** SELECT-INSTANCE and SELECT-USAGE take `symbol="$X"`, a string: the object is drawn with a symbol given through that `$` name, the name written in the SET-SYMBOL that gave it, compared as written and with the wildcard `*`, such as `symbol="$IO_PORT*"`; a symbol given through a `%` name or written anonymously matches no `symbol=`. An alias of a `$` name in that SET-SYMBOL is read as the original name (16.5), so the original is compared; the string of `symbol=` is not translated (16.5) and is written with the original name. Unlike the definition of SELECT-USAGE, which is recognized by what its name resolves to (9.5), this is a comparison of names; parameters hold only literals (3.7), so the name is written as a string, as other conditions write names. They also take `drawn` (`true`: the object is drawn, with a symbol given by a statement, a rule, a block symbol or the default block symbol (9.2.6); `false`: it is not, as a usage without a symbol). Every instance is drawn. These conditions read the symbols, so they work in generation rules and in the style queue, which come after the symbols are given (8.2); written in a selection of SET-SYMBOL, they are an error, since the symbol queue cannot select by the symbol it is giving. SELECT-PIN reads symbols too, with the same restriction, and so does any selection whose scope is a pin or steps through pins, such as `#R1::p @SELECT-TERMINAL`: in a selection of SET-SYMBOL, it is an error. So is a scope written with `::` and a name that is not a role name, a local name or a standard sub-object name of the object, such as `#X1::k`: whether it names a pin or a key of a text that the symbol brings is known only once the symbols are given (6.5).
- **This level, or also the levels below.** Every selection keyword has the condition `recursive`, `false` by default. A rule is evaluated in the level where it is written, and how far below it reaches is decided as follows; in each evaluation every selection and every set in it is evaluated in that level and holds only the members of that level (10.3).
  - **A rule with a selection written in it**, in its pipe or in a `{…}` written in it, reaches the levels below when one of these selections writes `recursive=true`, and only then; the sets it uses do not change this. So `# @SELECT-INSTANCE(recursive=true) => @SELECT-PIN(net="vss", wired=false) => $GROUND_STUB @ATTACH` adds grounds in this level and in every level below it, while `# @SELECT-NET(name="vdd") => @REMOVE-FROM $PORT_FILL_SET` acts in its own level only.
  - **A rule with no selection written in it**, which takes sets that depend on selections (10.4), reaches every level below its own that one of those sets reaches. A set reaches its own level and the levels that the statements adding the results of selections to it reach: the statement it is bound to, the sets among its items, and the ADD-TO statements that add to it, where an ADD-TO with no selection written in it counts as reaching as far as the set it adds, not the set it adds to. In a level that a set does not reach, it has no members, also when a rule that reaches there uses it. So with `$GROUND_NET_SET = # @SELECT-NET(name="0", recursive=true)`, the set has the net 0 of every level, `%g_set = {$GROUND_NET_SET}` reaches as far, and `$IO_PORT @ATTACH $PORT_FILL_SET` or `$SUPPLY_NET_SET @REMOVE-FROM $PORT_FILL_SET` acts in every level where these sets reach.
  - A single host object is simply referred to, such as `&vss`: host references resolve only in their own level, and a set of them, such as `{&vss}`, reaches no level below.
- **SELECT-USAGE and SELECT-ANCESTOR-USAGE.** Both recognize a definition by what its name resolves to (9.5), always select usages, and have no `role=`.
  - SELECT-USAGE looks inward, like the other selection keywords. With `#` as the scope, it selects the usages of the level being evaluated; with a usage or a set of usages, these usages themselves and the usages inside them, down to the innermost. Instances, nets and terminals in the scope are not usages and select nothing; a warning points to SELECT-ANCESTOR-USAGE for the usages they are in.
  - SELECT-ANCESTOR-USAGE looks outward: it selects the usages that have an object of the scope as a member, directly or indirectly (see the example below). The usages in the scope are not included themselves. With `#` as the scope, it is an error: a level is not a member of anything.
- **Usages as the scope.** With usages as the scope, the other selection keywords select the members of their kind in these usages, and `role=` takes only the members of that role. SELECT-PIN differs only for a usage with a symbol and without `role`, which gives the pins of its own symbol (above). Members that are usages are followed inward, down to the innermost:

  ```rnl
  $OTA = @DEFINE(roles=[["pair", "usage"], ["load", "usage"]]) {};
  %dp1 = #M1(left) #M2(right) #M5(tail) @AS $DIFFERENTIAL_PAIR_N;
  %cm1 = #M3(ref) #M4(out) @AS $CURRENT_MIRROR_P;
  %ota1 = %dp1(pair) %cm1(load) @AS $OTA;
  %all_set = %ota1 @SELECT-INSTANCE;                 /* {#M1 #M2 #M5 #M3 #M4} */
  %pair_set = %ota1 @SELECT-INSTANCE(role="pair");   /* {#M1 #M2 #M5} */
  %up_set = #M1 @SELECT-ANCESTOR-USAGE $OTA          /* {%ota1} */
  ```

  - The value of `role=` also accepts the `definition=` aliases of the definition of the usage (16.5). For the direct members only, use the role as a sub-object, such as `%dp1::tail`. The walk stops at a usage already visited. Members are the objects that fill roles, not the local objects of the body (9.4).
  - **Only members of the kind selected.** Members are not used as a scope to go further, and members of other kinds do not count. SELECT-TERMINAL takes only terminal members: after `$GROUND @ATTACH &0; $CURRENT_ARROW @ATTACH #M5:1`, `# @SELECT-USAGE => @SELECT-TERMINAL` is only {#M5:1}, not the terminals on net 0. The members of the differential pair %dp1 are instances, so `%dp1 @SELECT-TERMINAL` is empty. For the terminals of member instances, write `%dp1 @SELECT-INSTANCE => @SELECT-TERMINAL(terminal=2)` (the gates of all three transistors, the tail included); for the terminals on member nets, `… => @SELECT-NET => @SELECT-TERMINAL`. Each segment does one thing; to go further, add a segment. Objects given directly in the scope follow the rules above: a net gives the terminals on it, an instance its terminals.
  - **A role filled through a conversion** (5.2.4), such as a role of kind `"pin"` given a terminal, holds the object as written until the symbols are given, and the converted object from then on. So in the generation rules and later, `@SELECT-PIN(role="t")` selects the pin, whether the role was given the pin by its name or a terminal that stands for it.
- To find objects in the scene by condition, always use a selection keyword; `::` takes only parts of the object itself (6.5).
- **Bundles.** The members of a bundle cannot be selected; the bundle is selected instead (11.8). SELECT-INSTANCE selects the bundle itself by the conditions of its first member, once for each bundle. SELECT-TERMINAL selects the terminals of the bundle, and `net=` matches when it matches the net of any one member.
- **Conditions** are written by name, as `name=value`; an object is selected only when all the conditions written hold. For "or", write several rules. The conditions that compare names (`name`, `model`, `net`) take the wildcard `*`, which matches any number of characters, and compare by the case rules of the host, as DEVICE does (6.12). To select by element letter, write `name="R*"`. Spectre instance names do not start with an element letter; select them by `model`, such as `model="resistor"` (6.12).
- **`model`** compares the name written in the model position of the instance line: for M, Q, D and other elements, the `.model` name; for X instances, the subcircuit name, including PDK devices that the netlist does not define, such as `# @SELECT-INSTANCE(model="sky130_fd_pr__nfet_01v8")`; in Spectre, the master. It is the same as the `model=` of DEVICE (6.12). `type` compares the type of the instance: the type of its `.model`, or, for an instance whose host gives none, such as an X instance, the type a DEVICE gives (6.12); without either, the instance has no type and matches no `type=`. `type` takes the wildcard `*` as the conditions that compare names do: `type="*mos"` matches the types nmos and pmos, and `type="*"` selects the instances that have a type, whatever it is, which is how a rule or an assertion leaves out the devices whose type is not known.
- **`terminals`** compares the number of terminals of the instance, a whole number: the nodes that the host reads on its line, which have the numbers 1, 2, … (6.12), however many names DEVICE gives them. So `terminals=3` selects `Q1 c b e qn` and not `Q2 c b e s qn`. For an X instance it counts the nodes of its line, that is, the ports of the subcircuit; in Spectre, the nodes in the parentheses, so `S1 (com t1 t2) switch` has 3. It combines with the other conditions like them, such as `# @SELECT-INSTANCE(type="nmos", terminals=4) => @SET-SYMBOL $NMOS_4TERM`; a bundle is selected by its first member (11.8).
- Comparison follows 3.6: condition names and standard enumeration values are case-sensitive; values that name host things (names, model names, net names) follow the rules of the host.
- A net can be selected by name: `# @SELECT-NET(name="0")` selects it, and `# @SELECT-TERMINAL(net="0")` the terminals on it. Objects can also be selected by meaning: `# @SELECT-USAGE $DIFFERENTIAL_PAIR_N => @SELECT-INSTANCE(role="left")` selects the left transistor of every differential pair.
- There is no keyword for an intersection, such as the members of a set that belong to a usage; write it with REMOVE-FROM twice (5.2.2):

  ```rnl
  %s_set = {#M1 #M3 #M5};
  %s_set @SELECT-ANCESTOR-USAGE $DIFFERENTIAL_PAIR_N => @SELECT-INSTANCE => %dp_m_set;
  %out_set = {%s_set};
  %dp_m_set @REMOVE-FROM %out_set;    /* the members of %s_set in no differential pair */
  %in_set = {%s_set};
  %out_set @REMOVE-FROM %in_set       /* the members of %s_set in a differential pair */
  ```

- **Ground and supply nets** are given by sets that the standard package provides, `$GROUND_NET_SET` (net 0 by default) and `$SUPPLY_NET_SET` (empty by default). There are no net classes.
  - A package cannot contain host references (16.2), so the default content of such a set can only be written as a selection, such as `# @SELECT-NET(name="0", recursive=true)`.
  - The user adds and removes nets with ADD-TO and REMOVE-FROM:

    ```rnl
    &vss @ADD-TO $GROUND_NET_SET;                                       /* the vss of this level */
    # @SELECT-NET(name="vss", recursive=true) => @ADD-TO $GROUND_NET_SET;   /* the nets named vss of every level */
    # @SELECT-NET(name="vdd!", global=true, recursive=true) => @ADD-TO $SUPPLY_NET_SET  /* only the global vdd! */
    ```

    The second statement also adds local nets named vss in subcircuits. To leave a net out in one place only, copy the set and remove the net from the copy: `%g_set = {$GROUND_NET_SET}; &vss2 @REMOVE-FROM %g_set`.
  - A fill rule uses such a set as its scope, such as `$GROUND_NET_SET @SELECT-PIN(wired=false, recursive=true) => $GROUND_STUB @ATTACH`, which also takes the pins that virtual parts have on these nets; the standard package then takes out the pins of the parts it places itself, such as those of the grounds.
  - Writing `$GROUND_NET_SET = …` in one's own level hides the set of the package, and the rules of the package do not see the new one (6.8).
  - Grounds and supplies are not guessed from net names. An importer writes the power domain of a net in an editor file (such as `powerDomain`) as ADD-TO.
  - A solver may read the standard sets as hints (such as supplies at the top and grounds at the bottom), as it may read the definitions of the standard package; this is not required.
  - Note: there is no keyword for ground and supply nets (1.5 item 7): the uses of these sets, such as selecting terminals to add grounds or to change symbols, can all be written as rules in a package.
- **The empty node** (6.3) is not a net: SELECT-NET never gives it, a pin on it is selected by SELECT-PIN only through its object or `#`, not through a net or `net=`, and a wire on it by SELECT-WIRE without `net=`.
- **Global nets.** The condition `global=true` of SELECT-NET selects only global nets (6.3). Local nets with the same name in different levels are different nodes, and selecting by name selects all of them; to take only the global one, add this condition.

### 10.2 The condition `wired`

- A pin is `wired=false` when it is not one of the points of any explicit wire (an end or a point in between; a wire written to a terminal ends on the terminal's pin, 5.2.4), and it is in no tree of ROUTE-NET or ROUTE-OBJECT (13.7), since the solver draws the wires of a tree. A bus pin is one pin, wired when a wire ends on it through any of its terminals (9.2.4). Bus wires are explicit wires too (13.1). A wire to a terminal of a bundle connects that terminal of every member (11.8).
- A net is `wired=false` when no terminal of a host instance on it is touched by an explicit wire and no tree of ROUTE-NET or ROUTE-OBJECT is on it; the pins of virtual parts do not count.
- Which pins are in trees is fixed in two stages of 8.2. After step 4, once the symbols are given, from the statements of step 3: the rules of ROUTE-NET, ROUTE-OBJECT, UNROUTE-NET and UNROUTE-OBJECT, which are evaluated in step 5 (10.4), read these trees, such as `{&a &b} @SELECT-NET(wired=false) => @ROUTE-NET`, and do not see one another, so a rule never reads the trees it makes itself. After step 5, with the trees those rules make and change: the conditions of step 6 and of the later steps read these. So a generation rule, such as the fill of the standard package (16.3), counts the pins that a ROUTE rule joins as wired, and the pins that an UNROUTE rule takes out as not wired, unless a written wire touches them. The route statements in content generated in step 6, such as the body of a generated usage, make and change trees as well, but no condition sees them.
- A wire written on the empty node (13.1) counts as any other: the pins it ends on are wired.
- Only wires written explicitly count, not generated ones. Whether there are virtual parts makes no difference.
- Wires count as they are written, from step 3 of 8.2, also a wire that fails later because a terminal has no pin (7.1, 9.2.4). For a wire that is rewritten, the last rewrite counts (13.1).

### 10.3 Evaluating selections

- A selection is not expanded where it is written, and each evaluation looks at one level only. A rule (10.4) is evaluated once in the level where it is written and once in each level below that it reaches (10.1); in each evaluation, `#` is that level, and the selection selects only objects of that level. So `# @SELECT-INSTANCE(model="nch", recursive=true) => @ALIGN("y")` written at the top level aligns once in each drawing, and does not align instances of different drawings with each other.
- A selection is evaluated in the phase that uses it: appearance rules in the symbol queue and the style queue, the rules of the route keywords in step 5, generation rules in the generation phase (8.2). The same holds for sets (5.2).
- The kind that a selection selects is known when it is read. Giving it to a slot that does not take that kind is an error at once, also inside a set, such as `# @SELECT-TERMINAL(net="vss") => @SET-SYMBOL $NMOS`.
- SELECT-USAGE and SELECT-ANCESTOR-USAGE always select usages; when a selection goes from usages to their members, the kind selected is given by its keyword. So the kind of every selection is known when it is read.
- The result of a selection is a set and can be named with `%` or `$`. A set evaluated in a level takes only the members of that level: `&vss @ADD-TO $GROUND_NET_SET` written at the top level adds only the vss of the top level, which is not in the set when it is evaluated in a subcircuit (6.6).
- **The order of the result.** The members of the result of a selection are in this order, which matters wherever the order of a set does, such as for ORDER, DISTRIBUTE, TABLE and LINE, and for the results of a rule applied one by one (5.2.1):
  - With `#` as the scope, the objects of the level in the order of the scene:
    - instances in the order of their lines in the netlist, a bundle at the line of its first member; terminals by instance or bundle, then by number;
    - nets: the ports of the level in the order of the subcircuit line, then the other nets in the order in which they first appear on the instance lines;
    - pins by the object they belong to, first instances and bundles in the order of the lines (a bundle at the line of its first member), then usages in their order; within one object, in the order of the PIN statements of its symbol;
    - usages, wires, texts and graphics: first those created in step 3 of 8.2, in the order of their positions (8.5), what the body of a usage creates coming right after that usage, in the order of the body; then those created in later steps, step by step. Within one step, they are in the order of the positions of the statements or rules that create them, the results of one rule in the order of its input (5.2.1), and the texts that symbols bring by the object they belong to, the objects taken in the order given for pins, then in the order of the symbol. A text of the scene that overrides a text of the symbol by key (13.3) is one text, at the position of the first statement that writes it.
  - With any other scope, each member of the scope gives its results in turn, each in the order above, and an object already given is not given again. This holds for every selection keyword, SELECT-ANCESTOR-USAGE included.
  - Sets keep the order in which their members are written and added (5.2, 5.2.2): ADD-TO appends and keeps repeats, and UNION removes them.
- When the scope of a selection is written as host objects of its level, such as `&Q<0:3:2, 1> @SELECT-TERMINAL(name="R*", recursive=true) => @TEXT("${net}", key="netname")` at the top level, these objects do not exist when the rule is evaluated in a lower level: the selection is empty there and does nothing, with no warning, just as a set takes only the members of the level. The warning of 10.5 is given only for the other roles of generation rules.

### 10.4 Rules

- A statement that takes the result of a selection, directly or through a set that depends on one, is a rule. A set depends on a selection when it is bound to one, when it has one or such a set among its items, when it is made by UNION of such sets, or when ADD-TO or REMOVE-FROM changes it with the result of a selection or with such a set (5.2.2): its members are then known only in the phase that uses it. In the body of a usage, a set role depends on a selection when what fills it does.
- Any keyword but BUNDLE (11.8), WIRE (13.1), and RECTANGLE, CIRCLE and ELLIPSE written with two points (9.2.5), can take the result of a selection, one by one or as a whole as 5.2.1 says: `# @SELECT-INSTANCE(type="nmos") => @ORIENT("MY")`, `# @SELECT-INSTANCE(model="nch") => @ALIGN("y")`.
- SET-SYMBOL and SET-STYLE with the result of a selection as their object are appearance rules and go into the appearance queues (8.3). AS and ATTACH are generation rules (10.5), and so are TEXT attached to the result of a selection (13.3), RECTANGLE, CIRCLE and ELLIPSE written with a size whose point is that result (9.2.5), and the rules of LINE, ARC and BEZIER, which make drawn objects; their slot takes a set, so such a rule draws one figure through the whole result, in its order (5.2.1, 10.3). The rules of ROUTE-NET, ROUTE-OBJECT, UNROUTE-NET and UNROUTE-OBJECT are evaluated before them, in step 5: their conditions read the trees of the statements of step 3, and the generation rules see the trees they make (10.2). The rules of CURRENT are evaluated with the generation rules, in step 6; together they are the rules of step 6: current directions are fixed from the statements of step 3, and the conditions of step 6 do not see what these rules change (15.2). BUNDLE does not take the result of a selection: a bundle must exist before the symbols are given (11.8). Rules of other keywords, such as the constraints, PLACE and ORIENT, take effect in the step of their keyword and see the generated objects. With any other keyword, a rule is the same as a statement written for each selected object, or one written for all of them, and takes effect in the phase of its keyword.
- A rule applies to the level where it is written, and to the levels below that it reaches (10.1), through `recursive=true` in a selection written in it or, if it has none, through the sets it uses, evaluated once in each level and looking only at that level (10.3). A rule in a package counts as written in the level of the package's USE-PACKAGE, and a package at the root as used in the top level of its file (16.2), so it reaches the levels below only as 10.1 says, which is why the standard package writes `recursive=true` in its selections. A rule in the body of a general definition counts as written in the level of the usage (9.4).
- **Host objects of a level in a rule that reaches the levels below**: a rule that reaches the levels below and whose other slots name host objects of its level, such as `%clk_set %rest_set @DISTANCE("bottom-to-top", min=3)` with `%clk_set = {#VP1 #VP2}` and `%rest_set` bound to a selection with `recursive=true`, finds no such objects in a lower level: there the statement has no effect, and no warning is given. Only generation rules warn, as 10.5 says.

### 10.5 Generation one by one

"For each terminal on vss without a wire, place a ground and connect it with a wire":

```rnl
$GROUND_STUB = @DEFINE(roles=[["t", "pin"]], parameters=[["gap", 2]]) {
  %g = $GROUND @ATTACH ?t::net;
  ?t::net @WIRE {?t %g::pin};
  {?t %g::pin} @ALIGN("x");
  %g::pin ?t @DISTANCE("bottom-to-top", exact=?gap)
};
# @SELECT-INSTANCE => @SELECT-PIN(net="vss", wired=false) => $GROUND_STUB @ATTACH => %stubs_set
```

The standard package provides a `$GROUND_STUB` like this one, except that its gap is 1 by default and it gives only the least distance (`min=?gap`), so that a solver may draw the wire longer, as when it lines up the grounds of parts of different lengths, that it points the ground down (`@ORIENT("R0")`), and that its constraints are of priority `"low"`; the definition here hides it (6.8).

- When a single role of AS or ATTACH receives the result of a selection, the definition is applied once for each selected object, and the other roles are the same in every application (5.2.1, 9.4). A set role takes the result of a selection as a whole, and the definition is applied once; when all its roles are set roles, only in the levels where one of them holds something (9.4).
- Virtual parts are created one by one in the same way: `# @SELECT-NET(port=true) => $IO_PORT @ATTACH` gives each port net a port tag; with `$RLOAD`, a definition of two roles drawn as a resistor, `# @SELECT-NET(name="out*", recursive=true) => $RLOAD @ATTACH &vss` attaches one between each selected net and vss; since `&vss` belongs to this level, the rule takes effect only here, with the warning described below.
- The fill of the standard package adds grounds and supplies with a wire (`$GROUND_STUB`, `$SUPPLY_STUB`): once they are written back, the wire makes the pin no longer `wired=false`, and the fill skips it. A ground put on a pin by constraints alone, with no wire, leaves the pin `wired=false`, so the fill still adds one there; a wire of length 0 between the two pins (13.1) makes the pin wired.
- The pairing is within each application: the local names of a definition are new in each application, so the `%g` of one application is the ground made in that application.
- The result is a generated set. It can be named and given as a whole to SET-SYMBOL or SET-STYLE (such as `%stubs_set @SET-STYLE $grey`), but no single member of it can be referred to (5.7).
- **Writing one by hand.** To describe one of them on its own, create it by hand and wire it. Its pin is then no longer `wired=false`, and the fill skips it. There is no separate way to cancel a generation.
- **Snapshot.** All generation rules see the same snapshot, the result of steps 3 to 5 of 8.2 (after override by key, with the symbols of all objects and the trees of step 5), and do not see each other's results. So the same rule written twice generates two copies.
- Generated facts take the position of their generation rule in conflict resolution (8.5).
- Generated objects without a position are placed by the solver; to say how they are placed, use a definition with constraints.
- **Write-back.** A single generated object cannot be referred to (5.7). When the solver writes them back, it writes them as explicit statements, such as `$IO_PORT @ATTACH &out => @PLACE(40, 20) => %p_out` with the wire to it. The explicit object takes the place of the generated one only when the rule leaves out what is already written, as the fills of the standard package do by selecting only pins without wires (10.1) and as a fill by net does by writing the difference of two sets (below); a rule written otherwise makes the object again beside the explicit one, without a position. A rule whose objects the solver places should therefore leave out what is already written, in one of these two ways. The objects in the body of an explicit usage written this way that have no local name are referred to by number (5.9). The usage is written with the priority that the rule writes on its application, as written, or with `"disabled"` when it has that from the head of the record of the rule (14.8); otherwise it is written without a priority, so that its body keeps the priorities it had, and a record head with another priority is not written.
- Generation does not recurse: when the content expanded by a generation rule contains rules of step 5 or 6 (10.4), those fail, since each of these steps runs once. Its other rules take effect in the later steps as usual: SET-SYMBOL in the symbol queue of step 7; PLACE, ORIENT, LAYER, PRIORITY and constraints in step 8, so that the body of a generated usage can place and orient what its roles get; SET-STYLE in the style queue; assertions when they are checked (8.2, 15.3).
- When another role of a generation rule that reaches the levels below (10.1) is filled with an object of the level (a scene object or a host object), the rule takes effect only in the level where it is written, with a warning: these objects belong to that level, and the levels below do not have them. A role given a definition has no such limit.
- A SET-SYMBOL or SET-STYLE made by a generation belongs to the group of the rule that made it, at the position of the rule (8.3).
- A name bound to a selection or to a generated set cannot be bound again (6.6).
- **Fill by net.** There is no built-in rule "add none where one exists". A fill writes the difference of two sets; a package that adds port tags writes:

  ```rnl
  $PORT_FILL_SET = # @SELECT-NET(port=true, recursive=true);                                /* the nets that get a port tag */
  # @SELECT-USAGE(recursive=true) $IO_PORT => @SELECT-NET => @REMOVE-FROM $PORT_FILL_SET;   /* less those that have one */
  $IO_PORT @ATTACH $PORT_FILL_SET
  ```

  - The fill of the standard series 0.4 is written this way, with the set in `rnl-std-basic`, and it also puts the tags of each level in one column (12.4). It leaves the supply and ground nets in the set; a file that wants no tag where its stubs stand writes `$SUPPLY_NET_SET @REMOVE-FROM $PORT_FILL_SET; $GROUND_NET_SET @REMOVE-FROM $PORT_FILL_SET`.
  - A port tag written by hand takes the place of the generated one: after `$IO_PORT @ATTACH &inp => @PLACE(0, 20) => %p`, inp gets no generated port tag. The user can also take nets out of `$PORT_FILL_SET`, such as `# @SELECT-NET(name="vdd") => @REMOVE-FROM $PORT_FILL_SET`, or count the usages of their own port definition: `# @SELECT-USAGE $MY_PORT => @SELECT-NET => @REMOVE-FROM $PORT_FILL_SET`.
  - Generated port tags do not count: the generation rules use `$PORT_FILL_SET` in step 6, and the selections in the difference are evaluated on the state before step 6 (5.2).
  - Note: "one already exists" is not built in, because it is unclear for a definition with several roles, the user's own port definitions would not count, and a repeated layout definition only repeats constraints, which conflict resolution and priorities handle (8.5, 14.8).
- In a fill by terminal, it is still the wire of an object written by hand that takes the place of the generated one: a pin with a wire is no longer `wired=false`. There is still no way to cancel a generation: taking a net out of the set only changes the set.

## 6 Names and scope

### 6.1 Hierarchy of levels

- **Levels follow the text.** The RNL of a level applies to that level and to the levels that it contains in its text; which subcircuit instantiates which plays no part.
  - A file contains the subcircuits it defines and the files it includes.
  - An `.include` written in a subcircuit, and a `.subckt` definition nested in a subcircuit (a local definition in SPICE3 and ngspice), are below that subcircuit.
- From the top, the chain of levels down to a subcircuit is: the packages at the root (the packages of USE-PACKAGE in header records, the standard package first among them, 16.3) → the file level of the main file → … (the included files, one within another) → the file that defines the subcircuit → the subcircuit itself. For example:

  ```text
  packages at the root (such as the standard package)
  └─ file level of tb.sp (the top level)
     ├─ load                    a subcircuit defined in tb.sp
     ├─ file level of ota.sp    a file included by tb.sp
     │  ├─ ota                  ota instantiates cell
     │  └─ cell
     └─ file level of bias.sp
        └─ bias                 also instantiates cell, but neither the RNL of bias.sp nor that of bias reaches cell
  ```

- **The RNL of a subcircuit covers only the subcircuit.** In resolving conflicts its statements come after the content of the file levels, and so take precedence over it (8.5); but they are not passed to the subcircuits it instantiates, except to those defined inside it. When amp instantiates cell, the definitions and rules of amp do not reach cell.
- **An included file does not affect the level that includes it.** The definitions, rules and USE-PACKAGE of its file level apply only to its subcircuits and to the files it includes in turn. In the netlist, the devices it writes outside subcircuits belong to the level that includes it, but its RNL cannot change them. So a file is never changed by the files it includes.
- **The file level of an included file has no circuit of its own.** Only the file level of the main file is a circuit. Host references (`#M1`, `&vss`) at the file level of an included file fail (6.3); only definitions, rules, USE-PACKAGE and `scope` have effect there. A file opened on its own is the main file.
- **An included file inherits from the level that includes it.** The house style of the main file (its rules and the packages of its USE-PACKAGE) passes down into the subcircuits of library files. So one library file may be drawn differently under different main files, or when opened on its own, while its solver result is stored only once (chapter 17). To keep the symbols that a library uses free of the appearance rules of upper levels, use the standard package again with USE-PACKAGE in the library file or the subcircuit (16.2). To pin only the version of the standard package and still let the house style from above override it, write the USE-PACKAGE in the header record of the library file (16.3). Rules of the main file apply only to its top level unless their selection writes `recursive=true` (10.1); the rules of a house style that should reach the library files write it.
- **Verilog-A files.** A Verilog-A file that the netlist brings in with `ahdl_include` or `.hdl` sits where it is brought in, as an included file does, and each of its modules is a level below its file level, which has no circuit and no schematic and only gives the module its block symbol (2.9).
- **One schematic for each subcircuit.** A viewer does not expand subcircuits: an instance of a subcircuit is always drawn with its symbol, and the inside of the subcircuit is drawn and solved separately. Each subcircuit has one chain of upper levels, so in a document each subcircuit has exactly one schematic.
- **Packages.** The `$` definitions of a package take effect in the level where `@USE-PACKAGE` is written and in the levels below; its rules count as written in that level and reach the levels below with `recursive=true` (16.2, 10.4). The packages of USE-PACKAGE in a header record are placed at the root, the standard package among them when it is written or added by a setting of the tool (16.3). An include places a file below the level, and the file inherits from the level; a USE-PACKAGE places a package above the level, and the level inherits from the package.
- **Rules apply to their own level by default.** A rule written in a level is evaluated in that level only. When it reaches the levels below, through `recursive=true` in a selection written in it or, if it has none, through the sets it uses (10.1), it is evaluated also once in each level below, each time looking only at that level (10.4). This is what Principles 2.5 asks of rules: a rule can limit its effect to the current level or let the levels below inherit it, and applies to its own level by default, while `$` definitions are inherited by default (6.8).

### 6.2 Prefixes

| Prefix | Refers to | Resolved in |
|---|---|---|
| `#` | An instance of the host; `#` alone is this level | The host of this level |
| `&` | A net of the host; `&` alone is the empty node, no net at all (6.3) | The host of this level |
| `%` | A name given in this level: of a scene object, of an existing object such as `%tail = #M5`, or of a definition used only in this level | This level |
| `$` | A definition, or a set (6.6) | The level where it is bound, and the levels below |
| `?` | A role or a parameter of a definition; `?` alone is, in a symbol body, the object drawn with the symbol (13.3), and in the body of a general definition, the usage being expanded (9.4) | The body of a general definition or of a symbol |

`$X` and `%X` are two different names.

### 6.3 Host references

- `#M1` and `&vss` are resolved only in the host of this level, never in another level (Principles 2.5). Instances with the same name in different subcircuits are unrelated.
- A host reference that is not found fails (Principles 2.4). The file level of an included file has no circuit of its own, so every host reference there fails (6.1).
- A name may be followed directly by a subscript, which stands for one or several host names, such as `&D<3>` and `#XI0<3:0>` (6.11).
- The host adapter decides which nets a level has, following the semantics of the host:
  - Local nets: the nodes that the netlist lines of the level use, ports included.
  - Global nets: `0` is the global ground in every SPICE dialect. The aliases of ground that a simulator itself knows (such as `gnd` in ngspice, and `GND`, `GND!`, `!GND` and `GROUND` in HSPICE) are merged into `0` by the adapter for the dialect; after merging, `&gnd` and `&0` are the same handle. A name declared with `.GLOBAL vdd` (`global vdd` in Spectre) is the same node in every subcircuit. A name ending in `!`, such as `vdd!`, is a convention of Virtuoso schematics; what counts is the declaration.
  - A global net has one handle in each level that uses it: the copy in that level. A level whose netlist lines do not use it has no copy. So `&0` refers to the copy in the level where it is written: each schematic draws its own, the facts belong to that level, and descriptions in a lower level cannot change an upper level.
  - To mean the global net in every level, select it by name in an upper level with the condition `global=true` (10.1).
- **The empty node.** `&` written alone, with no name, says that there is no net: what is given it is connected to no electrical node of the circuit. It is written where a net is taken and none exists, as for the pins of virtual parts that draw a block diagram without netlist lines: `$INTEGRATOR @ATTACH &(in) &y(out)`, `& @WIRE {%sub1::y %int1::a}`.
  - It is not an object: it has no handle, cannot be bound to a name, cannot be a member of a set and is never selected. Two places that write `&` have nothing in common; a viewer that highlights a pin or a wire on the empty node highlights only that one.
  - Two places take it as it is: a role whose kind is `"net"` (9.4) and the net slot of WIRE (13.1). A pin bound to a role that it fills is on no net, and its `::net` is the empty node (12.1); `${net}` and `${p}` of it are the empty text (13.6).
  - Anywhere else that takes a net, it counts as an empty set of nets: ROUTE-NET joins nothing, ASSERT-NET holds trivially, a selection with it as its scope selects nothing, and ADD-TO adds nothing (5.2.1). Written out there, it gives a warning, as an empty set written out does; reached through a role, as in the body of a definition, it gives none. So a body that uses the net of a role needs no case of its own for it.
  - It is not a net of the host, so `&` followed by a name that the host does not have still fails as before.

### 6.4 Terminals

- `object:terminal` is a terminal: `#M1:1`, `#M1:d`, `#XU1:inp`, and a terminal of a bundle such as `%x:in` (11.8). `#:inp` is the port inp of this level. Only host instances, bundles and the ports of a level have terminals; a usage has none (12.1).
- A number is the terminal number of the host, counted from 1. A terminal written only with digits is a number, also when it is quoted (4.1), wherever a terminal is named: in `:` references, in `terminal=` of PIN, in `terminals=` of SET-SYMBOL, and in the `terminal` condition of selections. So a port name made only of digits, as in `.subckt amp 3 1 2`, is reached by its place, and `#X1:1` is the port named 3; a DEVICE name made only of digits is an error (6.12).
- A name is a terminal name of the host: a name given by `@DEVICE` in the header record (6.12), or a port name of the subcircuit. A name that cannot be written unquoted (3.6) is quoted, such as `#XU1:"in+"`. A terminal or port name may be followed directly by a subscript, such as `#X1:D<7:0>` and `#:D<7:0>` (6.11).
- Case: the port names of subcircuits and the terminal names given by DEVICE follow the rules of the host: SPICE ignores case, so `#M1:D` works too; Spectre does not.
- The `label=` of a pin is only for display and cannot be used to refer to a terminal: terminals belong to the netlist, and a reference to one does not depend on the symbol in use.
- **Terminals and pins**: a terminal belongs to the netlist; a pin belongs to the symbol of a drawn object (9.2.4). A terminal is drawn at the pins that bind it, and where a pin or a point is needed, a terminal stands for its pin (5.2.4). A pin is written through its terminal, such as `#M1:d`, or, when it has a name in its symbol, by that name as a sub-object, such as `#X1::vdd_t` (6.5); a number is never a pin name.
- A terminal that is not found fails. Whether a terminal has a pin in its symbol is checked after the symbols are decided (7.1).
- Apart from the port names of subcircuits, terminal names are given by DEVICE; 6.12 lists the standard names of the SPICE family.
- A subcircuit that the netlist does not define (such as the PDK device in `XM1 … sky130_fd_pr__nfet_01v8`) has terminal names only when the user gives them with DEVICE in the header record (6.12), or uses a package that holds DEVICE statements (16.2); otherwise only numbers can be used.

### 6.5 Sub-objects

- `object::name` is a sub-object. It is always an object, never a value. Its handle is the parent object and the name, so two names are two members wherever members are counted before the symbols are given (5.2.4): `{#R1::p #R1::q} @UNION` has two members, also when both names turn out to name one pin.
- The sub-objects are:
  - A key of a text: the sub-object that a TEXT with `key=` makes on the object it is attached to, such as `#M1::wl`. A text with a key in a symbol is a sub-object of each object drawn with the symbol (13.3). `::name` and `::value` are not standard sub-objects, only common keys (13.3).
  - `::position`: the origin of the object. `#M1::position @PLACE(…)` is `#M1 @PLACE(…)`. For a usage it is its own point (14.1), the origin of its symbol when it has one (12.1). Of a set it is the set of the `::position` of each member, nested sets followed inward: `{%dp1 %dp2}::position` is `{%dp1::position %dp2::position}`, the two own points, where `{%dp1 %dp2}` in a constraint stands for the six transistors (14.1). For a TEXT it is the position of the text itself (13.3); for a RECTANGLE, CIRCLE or ELLIPSE written in the centre form, the centre (13.4).
  - `::net` of a terminal: the net it is on, such as `#M5:1::net`, which is `&tail`. For the terminals of a bundle see 11.8: when the members are on different nets, it is the set of these nets. `::net` of a pin: the net of the terminal it binds, or of what fills the role it binds (12.1); for a bus pin, the set of these nets; a pin that binds nothing has none.
  - A named pin of the symbol of the object: `#X1::vdd_t` is the pin named vdd_t in the symbol of X1, `%g0::pin` the pin named pin in the symbol of the usage `%g0` (9.2.4).
  - A role name of a usage: what fills that role, such as `%dp1::left`, which is M1, and `%g0::p`, which is the net vss. For a set role it is that set. It is that object itself and not a second one: `{%dp1::left #M1} @UNION` has one member, and a PLACE written for `%dp1::left` has the key of M1.
  - A named local object in the body of a usage, such as `%c1::mid` (9.4).
- The standard sub-object names are reserved: no role name, parameter name or local name of a general definition, and no key of a text, can be the same as one of them (compared as written, 3.6). A local name cannot be a role name, and the key of a text cannot be a role name or a local name of the usage it is attached to. A local name may be a parameter name: a parameter is a value, and `::` does not take values. No parameter of a definition can be named `priority` either (14.8).
- **The name after `::` is looked up in this order**: the role names and local names of the usage itself; their `definition=` aliases; the standard sub-object names and their aliases; the names of the pins of the object's symbol; the keys of texts (aliases: 16.5). A pin name that is the same as a role name or a local name of the usage, or as a standard sub-object name, is an error when the symbol is given to the object; so is a key of a text that is the same as a pin name.
  - Keys come last, so a key cannot be spelled like a name that comes before it: a standard sub-object name or one of its aliases declared in this file (such as `"位置"` of `alias-zh`), a role name or local name of the usage, or a `definition=` alias of these names. Such a key is an error, like the clashes above (13.3).
- `::` takes only parts of the object itself; finding objects in the scene by conditions is always done with selection keywords. So "all usages of a definition" is written as a selection (10.1), not as a sub-object of the definition.
- Terminals use `:` and sub-objects `::`, so that sub-object names added in later versions cannot clash with the port names of a netlist.
- **Sub-object names**: there are two standard sub-object names, `position` and `net`, and both are reserved. All other sub-object names are dynamic: keys of texts, role names of usages, local names in the bodies of definitions, and the names of pins. Standard sub-object names added in later versions apply by version (16.1): in a file of an older version, a key with the same name stays valid.

### 6.6 Naming

- `%name = statement` and `$name = statement` name the result of a statement; in a pipe, `=> %name` and `=> $name` name the result of the segment to their left (5.5). A name is only another way to refer to an object and makes no object.
- `$name` binds a definition or a set, including the result of a selection. A `$` set evaluated in a level holds only the members of that level (10.3). Other scene objects belong to a level and cannot have a `$` name.
- `%name` can bind any object of this level: an object made by the statement, an existing object (`%tail = #M5`), a set (`%pair_set = {#M1 #M2}`), or a definition used only in this level.
- **A name is bound only once in a level.** Binding it again to the same object is allowed, such as `%x = #M1` written twice; binding it to another object is an error, and the name keeps its first valid binding. What a binding binds follows 5.5. A segment that keeps the handle of its input, such as PLACE or ORIENT, binds that handle, also when the segment fails, and such a binding is valid exactly when that handle is: when the input itself is a failed object, as after a BUNDLE that fails, the binding is not valid either (5.5). A segment that makes a new object binds it, and the binding is valid when that segment does not fail as the level is read and created (steps 1 to 3 of 8.2); when it fails later, at a check made after the symbols are given (8.2), it keeps the name, a later binding does not take it over, and the name refers to the failed object from then on. Only when none of its bindings is valid is the name bound to a failed object (7.2). A binding that is not valid does not hold the name, so a later binding to another object is not the error of binding twice: after the failed bundle of 5.5, `%s = #XI1` binds `%s` to XI1. This holds alike for statements that create objects, definitions, sets and the results of selections.
- Overriding applies to facts, not to names: to change an object made by RNL, write a statement that modifies it, such as `%g0 @PLACE(40, 38)` (5.8).

### 6.7 Scope of names

- The names committed by `@RNL` are published to the level: all records of the level share them, and a name can be used before the statement that binds it (Principles 2.9).
- A name bound in a nested set holds only in that set.
- A name bound in a definition body is local to the body (6.9).

### 6.8 Inheritance and hiding

- `$` definitions are inherited down the hierarchy of levels (6.1), never up: into the subcircuits of the file and into included files. A level does not see the `$` definitions of the files it includes; to provide definitions to upper levels, make a package and use it with USE-PACKAGE (16.2). The block symbol of a subcircuit is the only exception that goes up (9.2.6).
- A `$X` defined in a lower level with the same name as an inherited one hides the inherited definition in that level and the levels below, and gives a hint; the upper level still sees its own.
- The `$` definitions of a package used with USE-PACKAGE in a level count as one level above that level (16.2). When they hide definitions of the levels above or of the packages at the root, a hint is given, as for any hiding. A hint is also given when a package used in a header record defines a name of the standard package, or of a package placed at the root before it (16.3).
- `%` names hold only in their own level and are not inherited: not into the subcircuits of the file, and not across include. The `%` definitions of a package are private helpers of the package.

### 6.9 Names in definition bodies

- The names in a definition body are resolved where the definition is written, not again where it is applied; the one exception is a lone `#` in the body of a general definition (below).
- So hiding a definition changes only what the name refers to: the definitions already used inside other definitions stay as they are. For example, hiding `$DIFFERENTIAL_PAIR_N` in a lower level does not change the differential pair used in the body of a definition written in an upper level.
- A `%name` in a body is looked up first among the local names of the body, then among the definitions of the level. The scene objects of the level (points, wires and so on) cannot be referred to from a body; such a reference is an error. A set or the result of a selection that the level names with `%` is such an object too, whatever its members are when it is evaluated: to share one with bodies, name it with `$`, which a body may refer to and which is evaluated in the level of each usage (6.6, 10.3).
- **Notation in bodies**: roles and parameters are written `?name`. Local names are bound with `%name =` (or `=> %name` in a pipe) and referred to as `%name`. From outside, local names are reached through the usage (9.4).
- A definition body does not see the name being defined: in `$NMOS = @DEFINE-SYMBOL {$NMOS; …}`, the `$NMOS` in the body is the definition of that name outside (in an upper level or a package). This is how a lower level hides and extends an upper definition; without such an outer definition it is an error.
- Host references in the bodies of DEFINE-SYMBOL and DEFINE are errors: `#M1`, `&vss`, `#:inp` and `#M1:d` cannot be written there, nor a lone `#` in a symbol body. In the body of a general definition, a lone `#` means the level the usage is in, which is known only where the definition is applied (9.4); it is written there as the scope of a selection. A block symbol cannot be given from a body: `# @SET-SYMBOL` there is an error, since the block symbol of a level goes into the symbol queue before the usages of the level, and a usage may be generated after it (8.3, 9.2.6). Names in a body are resolved where the definition is written, but a general definition is applied in other levels and other files, where a host reference would still point into the level of the definition, so its meaning would not be unique. A general definition that needs host objects receives them through its roles.
- **When the body of a general definition is checked**:
  - Once for each definition: everything that does not depend on the arguments is checked then, including keywords, signatures (number of objects, parameter names and types), `$` and `%` names (resolved where the definition is written), host references, clashes of local names (9.4), and whether roles declared with a kind are used correctly: when the role t is declared `"instance"`, `?t::net` in the body is an error. Signatures are checked when the text is read (7.1); names can be resolved only after the whole level has been read, so the checks that need names are made when the level takes effect. Both are made only once for each definition, however many times it is applied.
  - For each application: what depends on the arguments, such as the objects that roles without a declared kind receive, or whether the symbol has a pin, is checked at each application and reported at the application, pointing also to the statement in the general definition.
  - Extent of the errors: a statement of the body found wrong (a local name that clashes included) is reported once, at the definition, and is left out of every expansion; the rest of the body works as usual (the body is tolerant, 9.1). A wrong role list or parameter list (repeated names, clashes with standard sub-object names, unknown kind names) makes the whole general definition fail, and with it every application that uses it.
  - A general definition that is never applied is checked too. These checks do not depend on applications, so they find errors in the unused definitions of a package.

### 6.10 Placeholders

- `?name` appears only in the body of a general definition, and the name must be in the role list or the parameter list; otherwise it is an error when the text is read.
- Where an object goes, it is a role, such as `?t` or `?t::net`; where a literal goes, it is a parameter, such as `min=?gap`, `[?w, 2]` and `(?x, 0)` (9.4). A role where a literal goes, or a parameter where an object goes, is an error when the text is read. Role names and parameter names are in one table and cannot repeat.
- A role placeholder may have a path, such as `?t::net`, and the placeholder of a set role may take member places, such as `?ref{1}` (5.2.3); a parameter placeholder has neither.

### 6.11 Subscripts

| Written | Stands for |
|---|---|
| `&D<3>` | The same as `&"D<3>"` |
| `&D<7:0>` | A list: `D<7>`, `D<6>`, …, `D<0>` |
| `&D<1,2:3>` | `D<1>`, `D<2>`, `D<3>` |
| `&D<0:6:2, 9>` | `D<0>`, `D<2>`, `D<4>`, `D<6>`, `D<9>` |
| `&D[3:0]` | `D[3]`, `D[2]`, `D[1]`, `D[0]` |
| `#XI0<3:0>` | Four instances |
| `#X1:D<7:0>` | Eight terminals of X1 |
| `#:D<7:0>` | Eight ports of this level |
| `&"D"<1:0>` | `D<1>`, `D<0>` |
| `&"D<7:0>"` | The node whose name is `D<7:0>`: nothing in quotes is parsed |

- A netlist has no buses: when tools such as Virtuoso write a netlist, they split a bus into single bits, such as `D\<3\>` in a Spectre netlist; bus ports of subcircuits and iterated instances are split too. A subscript is a short way of writing one or several such names. It only builds names and does not rely on the host knowing buses, so its meaning is unique.
- **Form**: a host name, quoted or not, followed directly by `<…>` or `[…]` that holds items separated by `,`. Each item is `i`, `a:b` or `a:b:s`, and the forms can be mixed. The numbers i, a, b and s are unsigned decimal integers, and s is at least 1. There is no white space between the name and the bracket; inside the brackets white space and comments are allowed (3.5).
- **Expansion**: the items are expanded in the order written and joined; repeats are kept. `a:b` runs from a to b, and `a:b:s` in steps of s without passing b: `<7:0>` is 7, 6, …, 0, and `<0:7:2>` is 0, 2, 4, 6. The step comes last, as in Virtuoso and Xschem, not as in MATLAB's `a:s:b`. A generated name is the name before the bracket, the opening bracket, the decimal number without leading zeros, and the closing bracket, in the kind of bracket written: `&D<07>` is `D<7>`, and `&D[3]` is `D[3]`.
- **One or a list**: one item that is a single number gives one reference: `&D<3>` is `&"D<3>"`. Anything else gives a list, which is a reference to a set, such as `&D<3:3>` and `&D<3,5>`. A list in a set is spread one level (5.2); as the only object of a statement it is first split one level (5.2.1), so `#XI0<3:0> @ALIGN("y")` aligns four instances; in a slot that takes a single object it works member by member; in the net slot of WIRE it is taken whole and makes a bus (13.1).
- **Where**: host names after `#` and `&`, and terminal names and port names in `#` references. RNL names (after `%`, `$` and `?`), role names and sub-object names take no subscript; a `<` or `[` right after them is an error. Members of a set are taken by their places with braces instead (5.2.3).
- **No point right after a name**: a `<` or `[` right after a name always starts a subscript, and when what follows does not fit the form, it is a syntax error; it is never read as a point. To write a point after a name, separate them, such as `&D (1, 2)`.
- **One expansion**: a name has at most one subscript, so a name such as `A<1>[2]` is written in quotes, `&"A<1>[2]"`. At most one subscript in a reference expands to a list: `#XI0<3:0>:a` and `#X1:D<7:0>` are allowed, `#XI0<1:0>:D<1:0>` is an error, and two subscripts that are each a single number are allowed, such as `#XI0<3>:D<1>`. When a reference that expands to a list is followed by `::`, the sub-object is taken for each member, such as `#XI0<3:0>::name`.
- **Nothing in quotes is parsed**: `&"D<7:0>"` refers to the node named `D<7:0>`; `&"D"<7:0>` expands. When a name in the netlist contains `<` or `[` that do not mark the bits of a bus, quote it to refer to it as it is.
- **The names compared are those the adapter reads** (3.6): `D\<7\>` in a Spectre netlist, where the backslash is Spectre's escape, is read by the adapter as `D<7>`, so `&D<7>` refers to it.
- Each member is resolved on its own. A member that is not found is a failed object, handled strictly or tolerantly as the slot that receives it says (7.3).
- Strings in parameters are not expanded, such as the `terminal=` of PIN (9.2.4) and the condition `name=` of a selection.
- Not accepted: the repetition of Virtuoso, `<*2>A` and `A<0:2*2>`, and its juxtaposition `A,B` (sets can already be written); `D[0..7]` of KiCad and Xschem, whose members are D0 … D7 without brackets.
- Iterated instances (such as `I0<3:0>` of Virtuoso: several host instances drawn as one) are written as bundles: `#XI0<3:0> @BUNDLE` (11.8).

### 6.12 Terminal names: DEVICE

```spice
* sky130 transistors, defined in the PDK and not in this netlist
* @RNL(type="header") {
*   @VERSION("0.4");
*   @DEVICE(name="X*", model="sky130_fd_pr__nfet_*", terminals=["d", "g", "s", "b"], type="nmos");
*   @DEVICE(name="X*", model="sky130_fd_pr__pfet_*", terminals=["d", "g", "s", "b"]);
*   @DEVICE(model="sky130_fd_pr__pfet_*", type="pmos")    /* adds the type to the names given above */
* }
XM1 out in 0 0 sky130_fd_pr__nfet_01v8 w=1 l=0.15
XM2 out in vdd vdd sky130_fd_pr__pfet_01v8 w=2 l=0.15
* @RNL { #XM1:d @CURRENT("in") /* XM1 is a sky130 NMOS; its terminal 1 is named d, and its type is nmos */}
.end
```

- **RNL names the terminals and gives the type.** `@DEVICE` describes a class of devices: `terminals` lists the names of their terminals in the order of the nodes on the netlist line, and `type` gives their type (below). It only gives names to the terminal numbers of the host, and changes neither the order of the terminals nor the interface of a subcircuit; it is a display alias, which Principles 2.2 allows. The names in one `terminals` list must differ by the case rules of the host and may not be made only of digits (6.4); for example, `"d"` and `"D"` compare equal in SPICE. In the header record of a package file, which may be used by files of either dialect, they must differ without regard to case. A list with two equal names, or with a name made only of digits, is an error, that DEVICE statement fails, and the instances keep the names that the earlier DEVICE statements and the adapter give them.
- **Only in the header record** (2.8): DEVICE written anywhere else is an error. The header record of a package file counts (16.2). An inline package cannot hold DEVICE; write it in the header record of the file.
- **Matching**: `name` is compared with the instance name, and `model` with the model name or subcircuit name written on the instance line (in Spectre, the master of the instance, such as `resistor` for a primitive); both may use the wildcard `*` (any number of characters) and are compared by the case rules of the host. Either may be left out, but not both, and a DEVICE matches an instance when those written match. A DEVICE gives `terminals`, `type` or both; one that has neither `name` nor `model`, or neither `terminals` nor `type`, is an error and fails. The conditions of selections that compare names take `*` by the same rules (10.1).
- **Type**: `type` is a string, such as `"nmos"`; the words of the table below are the standard ones. It is the type that the condition `type` (10.1), `${type}` (13.6) and the assertions (15.3) read, for an instance whose host gives it none, such as an X instance, including the PDK devices that the netlist does not define. An instance of a model card keeps the type of its model (below): a DEVICE whose type differs gives a warning and does not change it, as for the port names of subcircuits.
- **When several match, the later one counts, item by item**: for the terminal names and for the type separately, the last matching DEVICE that writes the item counts, so one DEVICE can give the names and a later one the type, and a later DEVICE that leaves an item out does not change it. The defaults of the adapter come first, then the DEVICE statements of the packages used by the level (in the order of the packages' positions, 16.2), then those in the header records of the outer files, then those of the included files; within one header record, in the order written, and of the header records of one file, the one without `language` first, then those with `language` in the order written, each acting only on the instances in sections of its language (2.8). So what a file writes overrides its packages, packages override the adapter, and specific statements should be written after general ones. The DEVICE statements of all packages come before those of the files, wherever their USE-PACKAGE is written: the header record is always at the start of the file, so placing a package at its USE-PACKAGE would let it override what the file itself writes. A DEVICE that gives `model` is not ranked as more specific; there is no separate rule of specificity.
- **Scope**: DEVICE in the header record of a file applies to that file and the files it includes; an included file can change only itself and the files it includes in turn (6.1). DEVICE in the header record of a package file applies to the levels that use the package (16.2). For example, a package for sky130 can hold DEVICE statements, symbols and the rules that choose the symbols, and a user who writes `@USE-PACKAGE(name="sky130-rnl")` gets terminal names, types and symbols.
- **Defaults of the adapter**: the standard element definitions of each dialect, which count as written at the outermost level. They need not be written in the file, and a tool may write them out. Tools for the same dialect must give the same definitions. They are the defaults of the version of the file in which the instance line stands (16.1), as a DEVICE in the header record of that file is. For the SPICE family:

  ```rnl header
  @DEVICE(name="M*", terminals=["d", "g", "s", "b"]);
  @DEVICE(name="Q*", terminals=["c", "b", "e", "s"]);
  @DEVICE(name="J*", terminals=["d", "g", "s"]);
  @DEVICE(name="Z*", terminals=["d", "g", "s"]);
  @DEVICE(name="D*", terminals=["a", "k"]);
  @DEVICE(name="R*", terminals=["p", "n"]);             /* and one each like it for C, L, V, I, B, F, H, W */
  @DEVICE(name="E*", terminals=["p", "n", "cp", "cn"]);  /* and one each like it for G, S */
  @DEVICE(name="T*", terminals=["p1", "n1", "p2", "n2"]); /* and one like it for O */
  @DEVICE(name="U*", terminals=["a", "b", "ref"])
  ```

  Instance names in Spectre do not start with an element letter, so the defaults are matched by `model`, the master of the instance. For the primitives of Spectre:

  ```rnl header
  @DEVICE(name="*", model="resistor", terminals=["p", "n"]);      /* and one each like it for capacitor, inductor, vsource, isource, ccvs, cccs, bsource, port */
  @DEVICE(name="*", model="diode", terminals=["a", "k"]);
  @DEVICE(name="*", model="vcvs", terminals=["p", "n", "cp", "cn"]); /* and one each like it for vccs, relay */
  @DEVICE(name="*", model="tline", terminals=["p1", "n1", "p2", "n2"]);       /* as T in SPICE */
  @DEVICE(name="*", model="transformer", terminals=["p1", "n1", "p2", "n2"])   /* as T in SPICE */
  ```

- **Subcircuits defined in the netlist** (including those in library files brought in by include or lib): the port names are those of the definition, which is a fact of the host (Principles 2.2). DEVICE does not change them; a DEVICE that matches such an instance with different names gives a warning. DEVICE names only devices without terminal names: primitives, and subcircuits that the netlist does not define (PDK devices), for which the user, or an LLM, writes the DEVICE. A DEVICE without `terminals` can still give a subcircuit defined in the netlist its type.
- **Number of names**: when an instance has more nodes than `terminals` has names, the extra terminals have numbers only; when it has fewer, a reference to an extra name fails.
- **Case**: the terminal names given by DEVICE are compared by the rules of the host (6.4).
- Numbers always work, and so do the port names of subcircuits that are not made only of digits, and `#:port`.

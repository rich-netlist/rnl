## 16 ファイル、バージョン、パッケージおよび別名

本章ではファイルの言語バージョン、パッケージとパッケージファイル、標準パッケージ、未知の内容、および別名を扱う。

### 16.1 バージョン

```rnl
* @RNL(type="header") { @VERSION("0.4")}
```

- **1ファイルにつき1つの言語バージョン。** 異なるバージョンのRNLは別々のファイルに書き、インクルードで結合する（6.1）。
- **ヘッダーレコードで宣言する。** VERSIONはファイルの最初のレコードであるヘッダーレコード（`type="header"`）内にのみ記述できる（2.8）。バージョンは1度だけ宣言できるため、1つのファイルが2つのバージョン値を持つことはない。それ以外の場所に書かれたVERSIONはエラーであり無視される。
- **読み取り順序：**
  1. ホストアダプタがコメントを渡す；
  2. すべてのレコードが外形によって切り出され、それらのレコードヘッダーが読み取られる（この手順はバージョンに依存しない）；
  3. 最初のレコードがヘッダーレコードであるとき、そのVERSIONが読み取られる；
  4. 他のレコードがそのバージョンで構文解析される。
- **バージョンに依存しない部分。** コメントキャリア、`@RNL` の入り口、レコードヘッダーの形式、およびヘッダーレコード内のVERSIONの形式は将来のどのバージョンでも変わらない（さもなくばパーサがバージョンを見つけられないためである）。新しいホストへの対応はキャリアを追加するだけで既存のものを変更しない（2.2）。ヘッダーレコードの残りの部分は宣言されたバージョンで読み取られる。
- **ヘッダーレコードがない場合。** ヘッダーレコードは省略してよく、その中のVERSIONも省略してよい。その場合、インクルードファイルはそれをインクルードしたファイルのバージョンをとり、主ファイルはヒント付きでツールのデフォルトバージョンをとる。ツールはファイルを保存する際にヘッダーレコードとバージョンを書き出さなければならないため、手書きのファイルでは省略できるがツールが書き出したファイルには含まれる。パッケージファイルはヘッダーレコードを持たなければならず（16.2）、VERSIONがなければ主ファイルと同様にツールのデフォルトバージョンをとる。インラインパッケージはそれが書かれたファイルのバージョンをとる（16.2）。
- **未サポートバージョン。** ツールがファイルのバージョンをサポートしていない場合、そのファイルのRNLは一切解釈されず、エラーが報告され、保存時にはファイルはそのまま保持される。他のファイルは通常どおり解釈される。
- 実装はサポートするバージョンを宣言しなければならない（原則 2.3）。言語バージョン、パッケージのバージョン（USE-PACKAGEの `version=`）、およびホストのバージョンは3つの異なるものである。パッケージバージョンの記述と照合方法は16.2にある。本バージョンのファイルは本バージョンのパッケージのみを使用する：異なる言語バージョンを宣言するパッケージファイルや別名パッケージ、あるいは宣言せずにより古いバージョンで読まれるものは、それに直接または他のパッケージ経由で到達するUSE-PACKAGEまたはUSE-ALIASESにおいてエラーとなる（16.2、16.5）。
- **バージョン番号。** バージョンは `"1.0"` や `"1.2"` のように2つの符号なし10進整数 `"major.minor"` として書かれる。パッチ番号、日付、プロファイルはない。`"1.0"` より前のバージョンはドラフトであり `"0.minor"` と書かれる。0.xバージョン同士では互換性を保証せず、各々が独立したメジャーバージョンとして数えられる。`"1"` や `"v1.2"` のような不正な形式のバージョンは欠落ではなく未サポートバージョンとして扱われ、ファイルが別バージョンで誤読されないようにする。
- **ファイルは自身が宣言するバージョンで読まれる。** ツールは各標準語がどのバージョンで追加されたかを知っていなければならない：より古いバージョンを宣言するファイルでは、後から追加された語は標準語ではない。したがって後から追加された標準サブオブジェクト名は古いファイル内の同綴りのkeyに影響せず（6.5）、新しい属性名は同名のホストパラメータに影響せず（13.6）、ASとATTACHの新しい標準パラメータは同名の定義パラメータに影響しない（9.4）。
- **1つのメジャーバージョン内では、新しいマイナーバージョンは追加のみを行い意味を変えない。**
  - 許容されるもの：キーワード、パラメータ、値、標準語、サブオブジェクト名、属性名の追加、および以前は失敗していた形式への意味の付与。付録 Cの項目や本標準が純粋な緩和と呼ぶもの、また解釈全体が失敗するケース（1.5項目3）を許容的にすることもこの種のものである。
  - 新しいメジャーバージョンなしには許容されないもの：妥当な形式の意味の変更、何かの削除、デフォルト値の変更、妥当な形式をエラーにすること。
  - 古いファイルは新しいツールでも意味を保つ。古いツールでは、新しいファイルのうち古いバージョンにある部分は通常どおり読まれ、新しい部分は未知の内容（16.4）となり、ファイルのバージョンがツールのサポート対象より新しい旨の警告が出る。ツールはそのファイルを描画しない選択をしてもよいが、理解したふりをしてはならない。
- **異なるメジャーバージョン。** ツールがサポートしないメジャーバージョンのファイルは解釈されずそのまま保持される（上記参照）。そのパッケージも使用されない：そのファイルのRNLは一切解釈されず、ビューアは自身のデフォルト外観でネットリストを描画し、バージョンがサポートされていない旨を報告する。ツールは複数のメジャーバージョンをサポートしてもよい。ファイルを新しいメジャーバージョンへ移す作業は明示的な移行であり、ツールがファイルとそのヘッダーレコードを書き換える。ツールが古いファイルを新しいメジャーバージョンの規則で黙って読み取ってはならない。本標準の各新しいメジャーバージョンには移行ノートが付属する。
- **サポートバージョン。** ツールはメジャーバージョンごとに `"1.0"`–`"1.3"` のようにどのマイナーバージョンまでをサポートするかを示す。`"1.3"` のサポートは `"1.0"` から `"1.2"` までを読み取れることも意味する。
- **バージョンの引き上げ。** ツールが新しいバージョンにしかない形式をファイルへ書き込むとき、ヘッダーレコードのバージョンを引き上げる。その前に、間に追加された標準語がファイル内にすでにある名前（テキストのkey、ロール名、定義パラメータ、ホストパラメータ）と同綴りでないかを検査し、バージョンを引き上げると意味が変わり得るため該当する各名前について警告を出すが、バージョンはそのまま引き上げる。
- **バージョン0.3および0.2。** 本バージョンはバージョン0.3を置き換える。バージョン0.3および0.2のファイルは別のメジャーバージョンのファイルであり（上記）、本標準はそれらを記述しない。それらはバージョン0.3を読み取るアップグレードツールによって0.4へ移行される：バージョンを引き上げ、ファイルを標準シリーズ 0.4へ移してヘッダーレコードに固定されていた標準パッケージの任意のバージョンの代わりに `@USE-PACKAGE(name="rnl-std-all", version="0.4")` を書き、付録 Dの定めに従ってファイルを書き換え、シリーズ 0.4にない定義の使用など書き換えられないものを報告する。

### 16.2 パッケージとUSE-PACKAGE

```rnl fragment
@USE-PACKAGE(name="acme-style", version="1.2");                               /* looked up in the package directories of the tool */
@USE-PACKAGE(name="acme-style", version="1.2", path="lib/acme-style.rnl");    /* reads this package file */
@USE-PACKAGE(name="acme-style", version="1.2") {…}                            /* an inline package */
```

**パッケージがどこで有効になるか。**

- パッケージの `$` 定義は、そのUSE-PACKAGEが書かれたレベルおよびその下位レベルで有効になる。そのルールはそのレベルに書かれたものとして数えられる：そのレベルで適用され、下位レベルにはそのルール内に書かれた選択の `recursive=true`、またはそれがなければそのルールが使うセットを通じて到達するときのみ適用される（10.1、10.4）。本バージョンには自身のレベルにのみ適用されるUSE-PACKAGEはない。サブサーキット内に書かれたパッケージはそのサブサーキットにのみ、ファイルレベルに書かれたパッケージはそのファイルのサブサーキットとそのファイルがインクルードするファイルに（6.1）、ヘッダーレコードに書かれたパッケージはファイルレベルと同じレベルに適用されるがルートに置かれる（16.3）。
- ルートのパッケージは、ヘッダーレコードに書かれたかツールの設定で追加されたかにかかわらず（16.3）、そのファイルのトップレベル（主ファイルではそのトップレベル）で使用されたものとして数えられる。したがってヘッダーレコードで使われるハウススタイルパッケージのルールは、標準パッケージが書くように `recursive=true` を付けたときのみサブサーキットへ届く。
- **順序上の位置。** パッケージの内容はそのUSE-PACKAGEの位置に、パッケージ内部ではテキスト順に置かれる（定義から展開された事実がASまたはATTACH文の位置をとるのと同様である）。競合解決（8.5）および外観キュー（8.3）はこの位置を用いる。レベルの文より前に使われたパッケージはデフォルトの組として働き、それらの後に使われたパッケージのルールは先の文を上書きできる。ヘッダーレコード内のUSE-PACKAGEはルートに置かれる（16.3）。

**パッケージ内の名前。** 位置のみがUSE-PACKAGEに従い、パッケージの名前は自身固有のものである。

- パッケージ内の名前は、最初にそのパッケージ自身の定義の中から、次にそれが参照するパッケージ（下記の「他パッケージを参照するパッケージ」を参照）の中から、次にそのUSE-PACKAGEのレベルで有効になっている標準パッケージの中から探索される。そのレベルや上位レベルのユーザーの定義の中や、他のパッケージの中では探索されない。定義本体（6.9）と同様に、USE-PACKAGEのレベルの同名定義がそれを捕捉することはない。したがってインラインパッケージの名前は同じ内容を持つパッケージファイルと同様に見つかり、そのテキストをそのようなファイルへ切り出すことができる。またパッケージファイルはツールの設定が追加する標準パッケージとともに単独で検証できる（16.3）。標準パッケージおよびそれが直接または間接に参照するパッケージは、自身と自身が参照するパッケージのみを見、標準パッケージは見ないため、探索が自身へ戻ってくることはない。
- パッケージの `$` 定義は公開されており、USE-PACKAGEのレベルの1つ上のレベルに属するものとして数えられる：そのレベルの同名定義はパッケージのものを隠蔽してヒントを出し（6.8）、1つのレベルでの二重束縛にはならない。パッケージの `$` 定義が上位レベルまたはルートのパッケージの定義を隠蔽するときもヒントが出される（6.8）。
- パッケージの `%` 定義はそのパッケージに対して非公開である。

**パッケージが含むもの。**

- パッケージは定義、`$` セット、およびルールを保持する。パッケージファイルのヘッダーレコードはVERSIONとPACKAGEを保持し、さらにそれを使うレベルに適用されるUSE-PACKAGE、DEVICE（6.12）、SOLVER-CONFIG（14.10）、およびそのファイルのみに適用されるALIASとUSE-ALIASESを保持してよい（16.5）。USE-PACKAGEは他パッケージを参照し（下記）、1つの言語用のヘッダーレコードに置くこともできる（2.8）。別名パッケージはヘッダーレコードのみを持つパッケージファイルであり、USE-ALIASESで読み込まれる（16.5）。
- パッケージはインクルードファイルのファイルレベルと同様に自身の回路を持たない（6.1）：
  - 特定のホストオブジェクトを名指しする文（`#M1`、`&vss`、`#:inp`）は失敗する。単独の `#` は一般定義の定義本体（9.4）と同様に依然としてルールが評価されるレベルである；
  - ルールではなく単一のシーンオブジェクトを描く文（`(0, 0) @RECTANGLE …` など）は描かれるレベルを持たないためエラーである；
  - ヘッダー以外のレコードにおけるレコードヘッダーの `scope=` と `type="generated"` はエラーである（2.8）；
  - パッケージのヘッダーレコード以外のレコード内のUSE-PACKAGEはエラーである：他パッケージへの参照はヘッダーレコード内にのみ記述する。
- インラインパッケージの定義本体も同じ規則に従うがヘッダーレコードを持たない：パッケージの名前とバージョンはそのUSE-PACKAGEのパラメータであり、DEVICEとSOLVER-CONFIGはそのファイル自身のヘッダーレコードに書かれる。インラインパッケージは他パッケージを参照できない。パッケージコレクションをファイルへ凍結するには、その展開された内容を意味を保つ変更とともに定義本体へ順に書き込む（16.3）。

**パッケージファイル。** パッケージファイルの読み取り方は例とともに2.7に示されている。そのヘッダーレコードは `@PACKAGE(name=…, version=…)` によりファイルがどのパッケージでどのバージョンかを宣言する。PACKAGEのないファイルはパッケージではなく、それに対するUSE-PACKAGEはエラーである。1つのパッケージは1つのファイルである：複数ファイルに分割されたパッケージにはそれらの間の順序が必要になるが、本バージョンはそれを提供しない。パッケージファイルはVERSIONで自身の言語バージョンを宣言し、それはそれを使うファイルの言語バージョンでなければならない（16.1）。そうでなければそのUSE-PACKAGEはエラーとなり、そのパッケージの名前を使う文は名前が見つからないため失敗する。

**探索。**

- 定義本体を持つUSE-PACKAGEはインラインパッケージであり、探索されない。
- `path=` がある場合、そのファイルが読み取られる。パスはそのUSE-PACKAGEが書かれたファイルのディレクトリからの相対パスであり、区切り文字には `/` を用い、URLではなくローカルファイルを指す。ファイルが存在しない場合、あるいはそのPACKAGEが別のパッケージ名や下記の規則が受け入れないバージョンを名指している場合は、警告付きで名前による探索が行われる。ファイルが存在するがパッケージでない場合（PACKAGEがない、またはPACKAGEの `version=` の書式が誤っている）、他のパッケージでないファイルと同様に（上記）そのUSE-PACKAGEは失敗する。
- それ以外の場合は、ツールに設定されたパッケージディレクトリ内でそのPACKAGEの名前とバージョンによって探索される。標準パッケージはツールに付属するかパッケージディレクトリにインストールされている。パッケージディレクトリはツールの設定でありファイルには書かれない。同じバージョンのコピーが複数ある場合は、その設定内のディレクトリの順序が決める。
- 診断にはどのファイルとどのバージョンが使用されたかが示される。
- パッケージが見つからない場合、そのUSE-PACKAGEは失敗し（エラー）、そのパッケージの名前を使う文もともに失敗する（7.3）。診断には欠落したパッケージが原因として示される。
- `name=` は必須である。文字列全体として比較され大小文字を区別する。パッケージ名は小文字の英字、数字、および `-` を使うべきである。
- `path=` を用いることでネットリストとそのパッケージファイルをまとめて保持し、全体として移動できる。本バージョンにはそれらのためのマニフェスト形式はない。

**パッケージバージョン。**

- パッケージバージョンは言語バージョンと同様に `"major.minor"` と書かれ、各0.xは独立したメジャーバージョンとして数えられる（16.1）。
- 書かれたバージョンが存在すればそれが使われる。存在しなければ同じメジャーバージョン内のより新しいバージョンのうち最小のものが、パッケージのバージョンが異なり描画が変わり得る旨の警告付きで使われる。そのメジャーバージョンに古いバージョンしかないか、1つもない場合はパッケージが見つからない扱いとなる。古いバージョンは名前を欠いている可能性があるため使われない。`path=` で指定されたファイルも同じ規則で検査される。
- `version=` がない場合、見つかった最新バージョンがヒント付きで使われる。USE-PACKAGE、USE-ALIASES、またはPACKAGEで16.1の定めに従わない `version=` はエラーであり探索されない：そのUSE-PACKAGEやUSE-ALIASESは失敗し、PACKAGEにそれを持つパッケージファイルはパッケージではない（上記）。インラインパッケージの `version=` はバージョンを識別するだけで探索はされず、誤って書かれた場合はやはりエラーとなってそのインラインパッケージが失敗する。
- 名前とバージョンで見つかったパッケージは1つの文書内で1度だけ読み取られる：同じバージョンは使われる場所にかかわらず同じ定義の組である。パッケージはそれが参照するパッケージと有効になっている標準パッケージの名前を使用箇所で見つける：それらのバージョンとインライン内容は下記の規則により、ファイルが使用するパッケージではレベルに最も近いUSE-PACKAGEによって、他パッケージ経由でのみ取り込まれるものではレベルの連鎖上の最新バージョンによって決まる。パッケージが使われる2箇所でこれらが異なる場合、それぞれについて1度ずつ読み取られ、2つのバージョンと同様に別の定義の組となる（9.5）。各インラインパッケージは自身のコピーである：2つのインラインパッケージはテキストが同じであっても異なるため、それらを2箇所で見つけるパッケージはそれぞれについて1度ずつ読み取られる。異なるバージョンにおける同名の定義は2つの異なる定義である（9.5；16.3の例を参照）。
- パッケージ作成者は言語の規則に従うべきである（16.1）：1つのメジャーバージョン内では既存の名前、ロール、パラメータ、ピンを削除または変更しない（描画は変わってよい）。これはツールが検査できない規約である。
- 本バージョンにはパッケージの内容ダイジェスト（USE-PACKAGEの `digest=` パラメータなど）はない。描画を完全に同じに保つにはバージョンを固定するか、ファイル内にパッケージをインラインで記述する。レコードヘッダーの `hash` をどう計算するかはツール次第である（第17章）。

**他パッケージを参照するパッケージ。** パッケージは他のパッケージを参照できるため、大きなパッケージを部品に分割し、いくつかのサイズに組み直すことができる。標準パッケージはこの方法で構築されている（16.3）。ファイルのヘッダーレコードのみを持ち他パッケージの参照のみを行うパッケージを*パッケージコレクション*と呼び、本標準では通常単にパッケージと呼ぶ。

- **形式。** パッケージファイルのヘッダーレコード内に、参照する各パッケージについて `@USE-PACKAGE(name=…, version=…)` を書く。`path=` はそのパッケージファイルのディレクトリからの相対パスであり、探索とバージョンは上記のとおりである。参照は定義本体を持たない：定義本体を持つものは、インライン内容がバージョンを持たず下記の最新バージョンの選択に参加できないためエラーである。
- **順序。** パッケージが使われると、そのヘッダーレコードが参照するパッケージが参照順に先に展開されてその前に置かれ、他のパッケージを参照する被参照パッケージも同様に先に展開される。その後にそのパッケージ自身の内容が来る。1つの展開内では各パッケージは1度だけ、最初の場所に置かれる。したがってパッケージコレクションの内容は、それが参照するパッケージの内容が順々に並んだものとなる。
- **名前。** 被参照パッケージの `$` 名はそれを参照するパッケージ内で可視であり、その利用者にも引き継がれる。パッケージ自身の `$` 名と同様に、それらはUSE-PACKAGEのレベルの1つ上のレベルに属するものとして数えられる。複数の被参照パッケージが `$X` を定義する場合、後の参照が前のものを隠蔽し、パッケージ自身の定義はそれらすべてを隠蔽する。1つのレベルで複数のパッケージを使う場合と同様に、各隠蔽はヒントを出す。本バージョンはパッケージ自身の内部使用のための参照と利用者へ引き継がれる参照を区別しない。`%` 名は各パッケージに対して非公開に留まる。
- **有効になるのは1つのみ。** パッケージは下記の「どのUSE-PACKAGEが有効になるか」のとおり名前で数えられ、展開される場所において他パッケージ経由で取り込まれるものも含む。
  - ファイルが直接使用するパッケージでは、他パッケージがそのパッケージを参照している場合であっても、レベルに最も近いファイル内のUSE-PACKAGEがそのバージョンとインライン内容で有効になる（「どのUSE-PACKAGEが有効になるか」を参照）。そのメジャーバージョンがそれを参照するパッケージが要求するものと異なる場合は警告が出される：参照側パッケージが持たない名前を使う可能性があるためである。
  - 他パッケージ経由でのみ取り込まれるパッケージでは、1つのレベルの連鎖上のすべての参照のうち同一メジャーバージョン内で最新のバージョンが使われ、バージョンが異なる場合はヒントが出る。同一メジャーバージョン内では新しいバージョンは追加のみを行うため、古い参照にも応えられる。異なるメジャーバージョンの参照はエラーである：後に展開される参照が失敗し、その名前を使う文もともに失敗する（7.3）。
- **置換または除外**は「有効になるのは1つのみ」から導かれ、追加の規則はない。同名の空のインラインパッケージはそれを除外し（自動補完をオフにする `@USE-PACKAGE(name="rnl-std-fill") {}` など）、同じ名前のもとでの別のバージョンや別のインライン内容はそれを置き換える。除外されたパッケージが他パッケージによって使われていた場合、それらの中のその名前を使う文は失敗する。
- **循環。** 循環をなす参照はエラーであり、循環を閉じる参照が失敗する。どの参照がそれになるかは展開が始まる場所による。循環内の複数のパッケージが直接使われる場合、循環はそれぞれについて1回ずつ報告される。
- **診断が報告される場所。** バージョンが異なる旨のヒントとメジャーバージョンが異なる旨の警告は、ファイル内に書かれたUSE-PACKAGE上で報告される（パッケージ内部のヒントと警告はユーザーに表示されない；7.6）。失敗する参照のエラーはその参照上で報告され、ファイル内のどのUSE-PACKAGEがそれを取り込んだかを示す。
- 別名パッケージは参照できない（16.5）。パッケージファイルのヘッダーレコード内のUSE-ALIASESは通常どおりそのファイルのみに適用される。

**複数のパッケージにおける同じ `$` 名。**

- 1つのレベルで使われる複数のパッケージが `$X` を定義する場合、後に使われた方が前のものをヒント付きで隠蔽する。
- 名前は次の順で探索される：このレベル → このレベルで使われたパッケージ（後のものが先） → 上のレベル → 上のレベルで使われたパッケージ → … → ルートのパッケージ（後に置かれたものが先）。
- 本バージョンにはパッケージ修飾名やパッケージの別名・レベルタグ（`$acme.DIFFERENTIAL_PAIR` や `as=` など）はない。注記：将来のバージョンでそれらを追加する場合、文末でよく使われる名前の後の `.`（`align #M1 and #M2.` など）とは別の形式が必要になる。

**どのUSE-PACKAGEが有効になるか。** ルートからあるレベルまでのレベルの連鎖上で、1つのパッケージが有効になるのは1度だけである。このレベルに最も近いレベルに書かれたUSE-PACKAGEがそのバージョンとインライン内容で有効になる。同じレベル内では後のものがより近いと数えられ、ヘッダーレコード内のものはファイルレベルの先頭に書かれたものとして数えられる。他パッケージ経由で取り込まれたパッケージは、それを取り込むUSE-PACKAGEの位置に、上記の「他パッケージを参照するパッケージ」のとおり選ばれたバージョンで書かれたものとして数えられる。パッケージはそのUSE-PACKAGEの位置に、そのUSE-PACKAGEがヘッダーレコード内にある場合はルートに置かれる。

注記：そうでなければグラウンドの自動補完のようなパッケージの生成ルールが下位レベルでもう1度走り、オブジェクトを2重に生成してしまうことになる。

**パッケージの再使用。** サブサーキットまたはライブラリファイルは、そのファイルレベルまたはサブサーキット内で標準パッケージを再度使用してよい。その場合、標準パッケージの外観ルールは上のレベル（主ファイルなど）から流れ下るルールの後に置かれてそれらを再び上書きし、そのUSE-PACKAGEの1つ上のレベルに属すると数えられるパッケージの `$` 名が上のレベルからの同名定義を隠蔽する。このレベルで使われるシンボルはそのとき上のレベルの外観ルールの影響を受けなくなる（6.1）。

- これが影響するのはシンボルと名前のみである。上のレベルから流れ下る幾何ルールおよび生成ルールは依然として適用され、それらのために解が古くなったときは再求解を促すヒントが出される（第17章）。
- バージョンのみを固定しつつ上のレベルのスタイルによる上書きを許すには、ヘッダーレコード内にUSE-PACKAGEを書く（16.3）。

**インラインパッケージ。** USE-PACKAGEは定義本体を持ってよく、それがパッケージの内容となる。その場合、ファイルがパッケージを携行し、探索は一切行われない：

```rnl
@USE-PACKAGE(name="acme-style", version="1.2") {
  $NMOS_ACME = @DEFINE-SYMBOL {$NMOS; (-1, 0) @CIRCLE(radius=2.5)};
  # @SELECT-INSTANCE(type="nmos", recursive=true) => @SET-SYMBOL $NMOS_ACME
}
```

- インラインパッケージは定義本体のないUSE-PACKAGEと同じ意味を持つ：パッケージの名前とバージョン、USE-PACKAGEの位置への配置、「パッケージ内の名前」のとおりの名前探索、1つ上のレベルとして数えられる `$` 名、非公開の `%` 名、パッケージ名で数える「有効になるのは1つのみ」がすべて上記のとおり成り立つ。定義本体は囲むことで消費される（5.4）。インラインパッケージはそれが書かれたファイルの言語バージョンを持つ（16.1）。
- インラインパッケージがパッケージファイルと異なるのは、その内容がネットリスト内に書かれる点とヘッダーレコードを持たない点のみである：言語バージョンはファイルのものであり、`version=` はバージョンを識別するのみであり、DEVICE、SOLVER-CONFIG、ALIASを宣言できず、他パッケージを参照できない。各インラインパッケージは自身のコピーである。したがってインラインパッケージを外へ切り出すと名前の探索方法は保たれるが、どの定義が同一であるかは必ずしも保たれない：同じ名前とバージョンのパッケージファイルがすでに使われている場所では2つが1つの定義の組になり（上記）、SELECT-USAGEのように定義で選択するルール（9.5）がより多くの適用オブジェクトに届くようになり得る。
- インラインパッケージは通常2つの目的でのみ使用される：同名の空のインラインパッケージによってパッケージを除外すること（16.3）、および完全な展開後の内容を定義本体に収めて自己完結させ、パッケージ一式をファイルへ凍結することである。
- 標準パッケージを拡張するかその一部を置き換えるには、それが使う標準パッケージをヘッダーレコードで参照するパッケージファイルを書き（上記の「他パッケージを参照するパッケージ」を参照）、ネットリストから `path=` でそれを指す。標準パッケージのサブパッケージを置き換える内容付きインラインパッケージは標準パッケージの一部として数えられ、自身のみを見るため、標準パッケージの他のサブパッケージの名前を使うことはできない。

**その他の規則。**

- パッケージの処理はコードを実行したりネットワークへ暗黙にアクセスしたりしてはならない（原則 2.7）。
- ビューアが回路図をどう表示するか、およびユーザーの好み（ダーク背景や印刷など）によって外観を変更できるかは本標準の範囲外である。どのスタイルもパラメータも値を与えないプロパティはレンダラのデフォルトをとる（9.3、原則 2.7）。

### 16.3 標準パッケージ

- 標準パッケージは本標準の一部ではない。他のパッケージと同様にRNLで記述され別途公開される。その意味定義、仮想部品、その他の内容はそのパッケージ自身によって定義される。
- 標準パッケージ内の名前には `$DIFFERENTIAL_PAIR_N` のような必須の接頭辞はない。ユーザーが同じ名前の定義を書けば、隠蔽によって標準のものを置き換えられる（6.8）。
- **パッケージコレクション。** 標準パッケージ `rnl-std-all` はヘッダーレコードのみを持つ：これは本シリーズの唯一のコレクションであり、下記の2つのオプションパッケージを除く本シリーズの他のすべてのパッケージを参照する。ファイルはコレクション全体を用いるか、必要なパッケージを1つずつ記述する。
  - `rnl-std-style`（スタイルとデフォルトのスタイルルール）、`rnl-std-basic` と `rnl-std-semiconductors`（シンボルと定義：グラウンド・電源・ポートタグなどの仮想部品、およびグラウンド・電源・バイアスネットのセットを含む）、およびインスタンスにシンボルを与える2つの方言のルールパッケージ（素子文字とモデル型による `rnl-std-spice`、マスタとモデル型による `rnl-std-spectre`；下記の方言を参照）。これらはネットリストを描画するだけで何も追加しない。`rnl-std-basic` のヘッダーレコードは `@SOLVER-CONFIG(junction="$JUNCTION")` を保持しているため、ソルバーは標準定義で黒丸を描く（13.2、14.10）。
  - `rnl-std-fill` は配線のないピンにグラウンド、電源、バイアスマーク、ネットラベルを各々スタブ上で追加するルールを保持し（10.5）、`rnl-std-basic` を参照する。これはピンを選択するため、仮想部品がネット上に持つピン（自身が配置した部品のものを除く）も補完される。シリーズ 0.4では `$PORT_FILL_SET` にあるすべてのポートネットに、レベルごとに縦1列でポートタグを与え（12.4）、ファイルやパッケージがROUTE-NETやROUTE-OBJECTで指示しない限りどのネットも配線として描かず、グラウンド・電源・バイアスネットは `@UNROUTE-NET(priority="high")` で除外されているため、それらを配線として描きたいファイルは `@ROUTE-NET(priority="high")` またはWIREを書く（13.7）。手書きまたは文やルールのROUTE-NET・ROUTE-OBJECTによって配線を持つピンには自動補完はグラウンドや電源シンボルを与えず、それを望むファイルは明示的に取り付ける（10.5）。routeキーワードのルールは自動補完より前に評価されるため、自動補完はそれらが作ったツリーを参照する（8.2、10.2）。セット `$GROUND_FILL_SET`、`$SUPPLY_FILL_SET`、`$BIAS_FILL_SET`、`$LABEL_FILL_SET`、`$PORT_FILL_SET` は自動補完がこれから追加するものを保持する：求解がスタブとタグを書き戻すと（14.8）、それらはもはやそのピンやネットを保持しないため、ファイルはそれらの上に他のルール（そのピンに対するTEXTなど）を構築しない。
  - `rnl-std-semantics` は差動対やカレントミラーなどの回路構造、信号フローや電力フロー、および `$MIRRORED_LAYOUT` などのレイアウトの定義を保持する。それらの定義本体内の制約はすべて優先度 `"low"` である（9.5、14.8）。表明も配線も行わず配置のみを行う定義は回路について何も述べず、その名前は `$MIRRORED_LAYOUT` のように `_LAYOUT` で終わる。`$DIFFERENTIAL_PAIR_N` や `$CURRENT_MIRROR_P` のように構造名の末尾にある `_N` と `_P` はトランジスタの極性を表し、型が分かっているトランジスタに対して構造がその極性を表明し（15.3）、それに合わせた描画（n型はソースまたはエミッタを下向き、p型は上向き）を与える。
  - 特定分野のパッケージは `rnl-std-functional`（アンプ、コンパレータ、変換器など）、`rnl-std-rf`、`rnl-std-logic`、および `rnl-std-signal-flow` である。
  - パッケージ間で名前は重複しないため、ユーザーはある名前がどのパッケージに由来するかを知る必要がない。
  - オプションの `rnl-std-45deg` はブリッジ、交差結合対、斜め巻線など45度で描かれたシンボルを保持する。コレクションには含まれないため、使いたいファイルはそれに対するUSE-PACKAGEを書く。
  - オプションの `rnl-std-no-labels` はすべてのラベルを自分で書くファイルのために標準シンボルのデフォルトラベルを非表示にする。コレクションには含まれない。シリーズ 0.4では描画されたオブジェクト（`drawn=true`、10.1）のみを選択してその名前・値・モデルのラベルと、適用オブジェクトのシンボルが描くネット名に、スタイル `textvisible=false` を与え（9.3）、ファイルはそのうちの1つに `textvisible=true` を書くことで再び表示できる（13.3）。オプションの `rnl-std-no-instance-labels` は描画されたインスタンスだけに同じことをするため、適用オブジェクトのラベル（グラウンド、電源、ポートタグ、ネットラベルが描くネット名など）は残る。これもコレクションには含まれない。将来さらにパッケージが追加されることもある。標準シリーズ全体は1つのバージョン番号のもとでまとめてリリースされ、コレクションはその各パッケージのバージョンを固定する。
  - これが標準シリーズ 0.4の構成である。その `rnl-std-all` は各言語用のヘッダーレコードを持つ（2.8）。
- **暗黙の読み込みはしない。** バージョン0.4のファイルが標準パッケージ `rnl-std-all` を使用するのは、他のパッケージと同様にUSE-PACKAGEがそれを記述したときのみである（16.2）。ツールは主ファイルのヘッダーレコードがいかなる形式でも `rnl-std-all` を書いていないときにそれを追加する設定（コマンドラインの `--include-std` オプションやビューアの設定など；デフォルトで有効でもよい）を提供してよい。この設定が有効なとき、ツールは `language` なしのヘッダーレコードが最初に `@USE-PACKAGE(name="rnl-std-all", version="…")`（ファイルの言語バージョンで書かれた標準シリーズのうちツールが持つ最新バージョン）を書いているかのようにファイルを読み取り、主ファイルへ書き出す際にはそのUSE-PACKAGEをヘッダーレコードへ書き出すことで、どのツールでもファイルが同じように描画されるようにする。あるファイルのヘッダーレコードに固定されたバージョンはそのファイルとそのファイルがインクルードするファイルで使われる（下記）。
  - 注記：標準パッケージも他のパッケージと同様の1つのパッケージである。RNL向けに書かれていないネットリストが標準シンボルで描かれるのはこのような設定を通じてのみであり、`$GROUND` など標準パッケージの定義を使うファイルがUSE-PACKAGEを書かなければそれらの名前は見つからない。見つからない各名前は通常どおりエラーとなる。使用されていない標準シリーズのパッケージがその名前を定義している場合、そのパッケージを名指ししUSE-PACKAGEとツールの設定を指し示すヒントがファイルにつき1回出される。
- **他方言のルールパッケージ。** 2つの方言ではインスタンスの名前が意味するものが異なる：SPICEでは `I0` は電流源である一方、Spectreではインスタンスの名前は何も意味せず、Virtuosoはサブサーキットのインスタンスを `I0` と名付ける。標準シリーズ 0.4はこれを `language` で表す：そのコレクション `rnl-std-all` は両言語が共有する内容用の `language` なしのヘッダーレコード、`rnl-std-spice` を使う `language="spice"` のヘッダーレコード、および `rnl-std-spectre` を使う `language="spectre"` のヘッダーレコードを持つ（2.8）。したがってSpectreファイル内でもSPICE区間はSPICEの規則で、Spectre区間はSpectreの規則でシンボルを見つける。
  - シリーズ 0.4を凍結するツールは、各言語の部分をその言語のヘッダーレコード内のインラインパッケージとして書き、共有部分を `language` なしのヘッダーレコードに書く：インラインパッケージはレコードではなく文を保持するため、自身で `language` を持てないためである。
- **ルートのパッケージ。** 主ファイルまたはインクルードファイル（Verilog-Aファイルを含む；2.9）のヘッダーレコードはUSE-PACKAGEを保持してよい：

  ```rnl
  * @RNL(type="header") { @VERSION("0.4"); @USE-PACKAGE(name="rnl-std-all", version="0.4")}
  ```

  - その範囲はファイルレベルのUSE-PACKAGEの範囲と同じである：それを書いたファイルとそのファイルがインクルードするファイル。インクルードファイルに書かれたものはそのファイルとそれがさらにインクルードするファイルに適用され、それをインクルードした側のファイルには適用されない（6.1）。
  - それはルートに置かれる：すべてのレベルのルールの前であり、ブロックシンボルよりも前である（8.3、グループ1）。その `$` 名もルートにあるため、主ファイルなどのレベル内の同名定義は引き続きそれを隠蔽する。代わりにファイルレベルのUSE-PACKAGEは自身の位置に置かれる：それはパッケージを再使用する（16.2）ため流れ下るルールを上書きし、その `$` 名は1つ上のレベルに属するものとして数えられる。ヘッダーレコードに書かれたパッケージは「このファイルはこのバージョンに依存し、上のレベルのスタイルが依然としてそれを上書きしてよい」ことを意味し、ファイルレベルに書かれたパッケージは「このファイルは自身の描画を定めるためにこのパッケージを使う」ことを意味する。
  - どのUSE-PACKAGEが有効になるかは16.2のとおりである：そのレベルに最も近いレベルに書かれたもの（ヘッダーレコード内のものはファイルレベルの先頭に書かれたものとして数える）。
  - ルートのパッケージの順序：ヘッダーレコードのどこに書かれた場合でも、またツールの設定で追加された場合でも、標準パッケージ `rnl-std-all` が最初に来て、次に他のパッケージがそれぞれを最初に書いたファイル（最も外側のファイルから内側へ）およびそのヘッダーレコードの順に並ぶ。内側のファイルのヘッダーレコードが同じパッケージを再度書いた場合、そのファイルのレベルで使われるバージョンまたはインライン内容のみが変わり、場所は変わらないため、バージョンを固定しても順序は変わらない。
  - 標準パッケージ、またはルートにそれより前に置かれたパッケージの `$` 名を定義するヘッダーレコード内のパッケージは、その定義を隠蔽してヒントを出す（6.8）。
  - バージョンを固定するかは作成者の選択である。主ファイルは固定すべきである。バージョンを固定しないインクルードファイルはそれをインクルードするファイルに従う。インクルードファイルは特定のバージョンに依存するときのみ固定すべきである。古いバージョンのファイルを引き上げる際に書き込む固定を除き、ツールがインクルードファイルへ勝手にバージョンを追加してはならない（16.1）。
  - 主ファイルのファイルレベルのUSE-PACKAGEでバージョンを固定すべきではない：そこではパッケージがブロックシンボルの後に置かれ、またそのファイルが別の場所でインクルードされたときにそのUSE-PACKAGEがパッケージを再使用して（16.2）ファイルの意味を変えてしまうためである。
- **例。** `tb.sp` のヘッダーレコードが `@USE-PACKAGE(name="rnl-std-all", version="1.2")` と書き、`tb.sp` がインクルードする `ota.sp` のヘッダーレコードがバージョン `"1.0"` を書いているとする。
  - `tb.sp` のトップレベルと `tb.sp` で定義されたサブサーキットは `"1.2"` を使い、`ota.sp` 内のサブサーキットは `"1.0"` を使う。`tb.sp` のスタイルルールは依然として `ota.sp` へ流れ込み、`"1.0"` のデフォルトを上書きする。
  - `$GROUND` の適用オブジェクトにグラウンドシンボルを与えるルールなどのデフォルト選択は標準パッケージ内のルールによって行われる。各バージョンはそれを使うレベル内で自身の `$GROUND` を選択するため、`ota.sp` は通常どおり描画される。
  - 2つのバージョンの同名定義は2つの異なる定義である（16.2）。したがって `# @SELECT-USAGE(recursive=true) $GROUND => @SET-SYMBOL $MY_GND` のように定義で選択する `tb.sp` のルールは `"1.2"` の `$GROUND` の適用オブジェクトのみを見つけるため、`ota.sp` は自身のバージョンを固定していない場合にのみそれに従う。`# @SELECT-INSTANCE(type="nmos", recursive=true) => …` のようにホストのプロパティで選択するルールは影響を受けない。
  - 自身のシンボルを `tb.sp` のルールから自由にするには、`ota.sp` はファイルレベルでパッケージを使う（16.2）。
- **標準パッケージの一部のみを使う。** ツールの設定が追加するのはパッケージ名 `rnl-std-all` のみである。
  - 一部のパッケージを外すには、同名の空のインラインパッケージで除外する：`@USE-PACKAGE(name="rnl-std-fill") {}` は自動補完をオフにする。同じ名前のパッケージが有効になるのは1度だけであり、2度になることはない。
  - 一部だけを使うには、ツールの設定がコレクションも追加してしまわないよう空の `rnl-std-all` とともに1つずつ記述する：

  ```rnl
  * @RNL(type="header") {
  *   @VERSION("0.4");
  *   @USE-PACKAGE(name="rnl-std-all") {};
  *   @USE-PACKAGE(name="rnl-std-style", version="0.4");
  *   @USE-PACKAGE(name="rnl-std-basic", version="0.4");
  *   @USE-PACKAGE(name="rnl-std-spice", version="0.4")
  * }
  ```

- **標準パッケージを拡張する、または一部を置き換える。** 使う標準パッケージをヘッダーレコードで参照するパッケージファイルを書き、自身の追加内容を書く（16.2、インラインパッケージ）。標準パッケージに付け加えるだけの定義やルールはネットリスト内に直接書いてもよいが、標準パッケージが持つルールを除去または置換できるのは同名のパッケージのみである。
- **標準パッケージ全体を凍結する、または除外する。** ヘッダーレコード内に同名のインラインパッケージを書く。これはパッケージ名で数える「有効になるのは1つのみ」から導かれ、追加の規則はない：
  - `@USE-PACKAGE(name="rnl-std-all", version="1.2") {…}` は標準パッケージをファイル内へ凍結し、ファイルを自己完結させる。定義本体はそのパッケージ群を展開した後の内容が展開順に並んだものである（16.2）。1つの定義本体にまとめられると2つのパッケージが衝突することがある：両方で使われている非公開の `%` 名、または一方が他方から隠蔽する `$` 名である。凍結を行うツールは各参照が自身のパッケージ内で見つけていたものをそのまま見つけられるよう衝突する名前をリネームし、凍結パッケージのヘッダーレコードのDEVICE文とSOLVER-CONFIG文を（インラインパッケージはそれらを保持できないため）ファイルのヘッダーレコードへ、その順序でファイル自身のものの前に書き出す（2.8、6.12、14.10）：各々は自身が経由して使われる言語用のヘッダーレコードへ、言語なしで用いられるパッケージについては `language` なしのヘッダーレコードへ書き出される（`language` 付きのヘッダーレコード経由でのみ使われるパッケージのSOLVER-CONFIGは効力を持たないためコピーされない；14.10）。するとそれらのコピーは凍結されたものの後に来ていたパッケージより後ろに来ることになる。そのようなパッケージがコピーの書くSOLVER-CONFIGのkeyや、コピーされたDEVICEも一致するインスタンスに対するDEVICE項目（端子名や型）を書いている場合、ツールは、そのパッケージが同じファイルのヘッダーレコードで使われているなら衝突するコピーを保持するヘッダーレコードのそのコピーの後かつファイル自身のものの前にその文を書き出し、インクルードファイルやレベル内で使われているならその衝突を報告する。報告される衝突を除き、凍結されたパッケージは同じ意味を持つ；
  - `@USE-PACKAGE(name="rnl-std-all") {}` はツールの設定が追加する場合でも標準パッケージを一切使用しない。その場合、すべてのインスタンスは既定のブロックシンボルを持ち（9.2.6）、外観の残りはレンダラのデフォルトに委ねられる（原則 2.7）。
- 太線のバス、バスのタップシンボル、バスの幅を示すマークなどの規約も標準パッケージの内容である。標準パッケージがなければ、すべてのインスタンスは既定のブロックシンボルを持ち（9.2.6）、レンダラが描画スタイルを決定する（原則 2.7）。

### 16.4 拡張と未知の内容

- **未知の内容**（原則 2.3）。未知のキーワード、パラメータ、値はエラーである：その文は失敗し、それに依存する文もともに失敗し（5.5、7.3）、残りは通常どおり解釈される（7.6）。レコードヘッダーの未知のフィールドは例外であり、警告のみを出す（2.8）。SOLVER-CONFIGでは、ソルバーが知らないkeyは警告を出し、採用されない値はそのkeyだけが失敗する（14.10）。その場合、描画は不完全になり得るため、診断はその旨を伝えなければならない。
- **保存時に保持する。** 原則 2.3はそのような内容を変更せず保持することを推奨しており、本標準はそれを必須とする：
  - ツール自身のものではないレコードは変更せず（第17章）、ホストテキストと通常のコメントはそのまま残す；
  - ツールが自身のレコードを書き換える際、その中の自身が知らない文や失敗する文は、その自由テキストとともに同じ順序のまま保持される；
  - バージョンがサポートされていないファイルは丸ごとそのまま保持される（16.1）；
  - ツールが書き換えるレコードはバイト単位で同一のまま保つ必要はない。
- **本バージョンに拡張機構はない。** 新しい意味、仮想部品、描画方法は新しいキーワードとしてではなくパッケージ内の定義、シンボル、スタイルとして記述する（1.5項目7）。実装が理解しなければならない新しい機構は本標準の新しいバージョンを待つ。エディタのロック状態や表示状態などツール固有のデータはRNLレコード内に書かず、ツール独自のファイルまたはレコード外の通常のコメントに入れる。
  - 注記：本バージョンではまずすべてのツールが同じRNLを読めるようにする。現時点でベンダー方言を作ると言語が分裂してしまい、新しい意味はすでにパッケージで記述できるためである。
  - 注記：将来のバージョンでは、ヘッダーレコードで宣言されるベンダー接頭辞と `.` 付きのキーワード（`@ACME.ROUTE` など）として拡張を追加することがあり得る：ツールが知らない必須拡張はファイル全体を未解釈のまま残し、任意拡張はヒント付きでスキップされるであろう。そのようなキーワードは現在では未知のキーワードとしてエラーであるため、後からこれを追加することは純粋な緩和である（16.1）。ベンダー接頭辞には標準キーワードの名前を使うことは許されないであろう。
- 拡張のために予約された形式はない：標準キーワードの直後の `.` は自由テキストであるため、`@BUNDLE.LOCK` はBUNDLEに自由テキスト `.LOCK` が続いたものであり、文末の `{#M1 #M2} @GROUP.` は妥当である（3.5）。
- **認識されるが解釈されないもの。** 本バージョンでこの種の内容に当たるのは、レコードヘッダーの未知のフィールド（2.8）およびソルバーが知らないSOLVER-CONFIGのkey（14.10）である。将来のバージョンで拡張が追加された場合、任意拡張が2番目の種類になる。

### 16.5 別名

```rnl
* @RNL(type="header") {
*   @VERSION("0.4");
*   @USE-PACKAGE(name="rnl-std-all", version="0.4");
*   @USE-ALIASES(name="alias-zh");
*   @ALIAS("@at", "@PLACE")
* }
* @RNL {#M1 @位于(10, 20); {#M1 #M2} @对齐("y"); #M3 @at(x=4); #M1(左管) #M2(右管) #M5(尾管) @视作 $"差分对"}
```

- 別名（alias）は、大文字・小文字の別の使い方との互換性のため、あるいは中国語など他の自然言語のスタイルでRNLを書くために、標準語に別の綴りを与える。
- **別名の由来：**
  - 少数の独自別名のためにヘッダーレコード内に直接書かれたALIAS文；
  - ヘッダーレコード内の `@USE-ALIASES(name=…, version=…, path=…)` で読み込まれる別名パッケージ。1つの言語の別名を1つのパッケージにまとめることで、ファイルがそれらを繰り返す必要がなくなり、どこでも言い回しが統一される。標準の中国語別名パッケージは `alias-zh` であり、標準パッケージとともに公開されツールに付属する（16.3）。
  - 両者を併用してよく、複数の別名パッケージを読み込んでもよい。それらはまとめて下記の対応規則で検査される。
  - 別名はそれを宣言したファイルのみに適用され、インクルードを通じて継承されない。別名を使うインクルードファイルやパッケージファイルは自身のヘッダーレコードでそれらを宣言する。同じ標準語が異なるファイルで異なる別名を持ってよい。シンボル内に書かれたテキストのkeyは、そのシンボルが書かれたファイルの別名に対して検査される（6.5、13.3）。
  - ヘッダーレコード自体は常に標準の綴りで読まれ、別名を認識しない：USE-ALIASESとALIASが読み込まれるまでは別名が判明しておらず、またヘッダーレコードは主にツールが書くためである。したがってヘッダーレコードにのみ書けるキーワード（VERSION、ALIAS、USE-ALIASES、DEVICE、PACKAGE）の別名は役に立たない。
- **別名パッケージ：**
  - 別名パッケージとは、ヘッダーレコードにVERSION、PACKAGE、およびALIAS文のリストのみを保持し、他のレコードを持たないパッケージファイルである（16.2）。探索とバージョン選択は16.2と同様に行われる。
  - 別名パッケージでないファイルに対するUSE-ALIASES、または別名パッケージに対するUSE-PACKAGEはエラーである。別名パッケージが見つからない場合、そのUSE-ALIASESはエラーとなり、その別名を使う文もともに失敗し（7.3）、診断には欠落した別名パッケージが原因として示される。
  - 注記：別名パッケージをUSE-PACKAGEで読み込まないのは、USE-PACKAGEが任意のレベルに書けて定義やルールを扱い位置で順序付けられるのに対し、別名はファイルテキストの読み取り方を扱いファイル単位でのみ適用できるためである。切り離しておくことで、ハウススタイルパッケージがテキストの読み取り方を変えることができないようにしている。
  - 別名パッケージの内容はそれが参照するものに追従する：標準パッケージの名前が変わると、`alias-zh` もともに変わりそのバージョンが引き上げられる。
- **形式。** `@ALIAS("alias", "original")`：別名が先である。2つのパラメータは `alias` と `original` であり、通常は位置指定で与えられる。3番目のパラメータ `definition` は名前指定でのみ与えられる（下記）。
- **原語（original）：**
  - 本標準が定義するキーワードまたは標準語（その標準の綴りで）。キーワードは `"@PLACE"` のように `@` 付きで書き、他の語は `"axis"` や `"low"` のようにそれなしで書く。別名も同じ方法で書く：キーワードの別名は `@` を持ち、他の別名は持たない。`@` によってキーワードと同綴りの標準語が区別され、別名は宣言されたとおりの形でテキスト中に現れる。
  - `$` 名。`@ALIAS("$接地补位集", "$GROUND_FILL_SET")` のように別名と原語の双方が `$` を持つ。テキスト中では `$"接地补位集"` と書き（`$` の後の非ASCII名には引用符が必要、3.6）、`$GROUND_FILL_SET` として読まれる。`%` 名は別名を持たない：記述者は他の言語で自身の名前を直接付けられ、パッケージ内の `%` 名は非公開だからである。
  - `definition=` で宣言される定義内の名前（`@ALIAS("左管", "left", definition="$DIFFERENTIAL_PAIR_N")` や `@ALIAS("间距", "gap", definition="$GROUND_STUB")` など）。このような別名はその定義内でのみ探索される：適用時のロール名（`#M1(左管) #M2(right) #M5(tail) @AS $DIFFERENTIAL_PAIR_N`）、ASおよびATTACHで渡されるパラメータ名（`$GROUND_STUB @ATTACH(间距=3) …`）、および `::` を通じてその適用オブジェクトから取り出されるローカル名（`%c1::"中点"`）である。`definition` の値自体を別名で書いてもよい。ASとATTACH自身のパラメータである `priority` を除き、これらの場所では標準語の別名は使われない。
    - 別名は名前に付随する：その `$` 名をたどり、別名が `$` 名の綴りを置き換えるのと同様に、下位レベルが同名の定義でその定義を隠蔽した箇所にも適用される。
    - 別名が宣言される時点では原語がその定義と照合されることはなく、定義が適用されるときに、見つからない名前が通常どおりエラーとなる（「ロール in_p がない」など）。
    - `::` の後の名前は6.5の順序で探索される：適用オブジェクト自身の名前、それらの `definition=` 別名、標準サブオブジェクト名とその別名、オブジェクトのシンボルのピン名、テキストのkey。
    - 選択条件 `role=` の値、および `${…}` 内でロールに沿って下るパスもこれらの別名を認識し、各ステップの適用オブジェクトの定義内で探索される（`$DIFFERENTIAL_PAIR_N` の適用オブジェクト `%dp1` に対する `%dp1 @SELECT-INSTANCE(role="左管")` や `${左管::w}` など）。スコープが複数定義の適用オブジェクトを保持する場合、各々が自身の定義内で探索され、原語も引き続き動作する。
- **別名を持てるもの：** 次の項目に挙げるものを除く標準語リストのすべての語：キーワード、組み込みキーワードのスロット名、パラメータ名と値、種別名、サブオブジェクト名、属性名、スタイルプロパティ、`true` と `false`（5.3）、および上記の `$` 名と定義内の名前。
- **別名を持てないもの：** 外形（すなわち `@RNL`、レコードヘッダーのフィールド名と `type` の値、および `@VERSION`）、ならびに `@ALIAS` と `@USE-ALIASES` 自身。
- **その他の名前。** 名前とはすでにオブジェクトの別名である：`$"差分对" = $DIFFERENTIAL_PAIR_N` の後では、`$"差分对"` は同じ定義である。このような名前はテキストの一部であって再び取り出すことはできず、ロール名やパラメータ名には届かない。他言語の名前の完全な組には別名を用いる。
- **対応関係：**
  - 1つの原語は複数の別名を持ってよいが、1つのスコープ内では1つの別名は1つの原語のみを表す。各定義の `definition=` 別名はそれぞれ1つのスコープをなす。
  - 別名はファイルが宣言するバージョンのどの標準語と同じ綴りであってもならず、別の原語のために再度宣言してはならない。`definition=` 別名はその定義が持つロール名・パラメータ名・ローカル名と同じ綴りであってもならず、ASとATTACH自身のパラメータである `priority` の別名と同じ綴りであってもならない。
  - 別名を原語として使うことはできず、別名をその原語と同じにすることもできない。ファイルのバージョンが引き上げられ、新たに追加された標準語がある別名と同じ綴りを持つ場合、警告が出されつつバージョンはそのまま引き上げられる（16.1）。すると新しいバージョンではその別名が標準語と同じ綴りになるため、上記の規則によりエラーとなる。
  - 別名パッケージはそれを使うファイルの言語バージョンを宣言しなければならない（16.1）。そうでなければそのUSE-ALIASESはエラーである。
- **別名は綴りを追加するのみ。** 標準の綴りは常に機能し、1つのファイル内で両者を混在させてよい。
- **別名はトークン単位でのみ置換する：**
  - 別名はトークン全体を置き換える。テキストマクロではないため位置や診断が正しく保たれる；
  - `@` のない標準語はその綴りによって別名を得るため、同じ綴りの語（パラメータ名 `x` と値 `"x"` など）は別名を共有する；
  - `$` 名の別名は綴りを置き換える：`$"接地补位集" = {…}` と書いた記述者はそのレベルで `$GROUND_FILL_SET` を定義したことになり、ヒント付きで標準パッケージのものを隠蔽する（6.8）。
- **字句規則：**
  - キーワードの別名は `@` の直後に続く（任意の文字体系の）文字、数字、およびアンダースコアであり、`-` を含まない：それらが1つのトークンをなし、`@` の前には（`对 &b，@选出元件` はエラーであり `对 &b， @选出元件` と書かなければならないように、中国語の句読点の後でも）空白が必要である（2.3）。文字・数字・アンダースコア以外の任意の文字（空白、あるいは `，` や `。` のような任意の文字体系の句読点）が別名を終わらせる。したがって `@对齐两个器件` は1つの未知のキーワードすなわちエラーとなり、その診断は `@对齐` の後に空白が抜けていないかを尋ねなければならない。特定の言語向けの規則は存在しない：どの文字体系であれ文字・数字・アンダースコアでないものが別名を終わらせ、括弧外の非ASCII文字は自由テキストである（3.3）。トークンの読み取りに宣言が不要となるよう、宣言された別名によってトークンが分割されることはない。
  - 引用符なしの非ASCII語が現れるのは `@` の直後と括弧内の2箇所のみである。`@` の直後では、その語は宣言された別名でなければならず、そうでなければエラー（「非ASCII名には引用符が必要」）となる。括弧内（パラメータ名、組み込みキーワードのスロット名、`true` と `false`、ロール名）では、宣言された別名は別名であり、定義のロール名またはパラメータ名の位置にある別名でない語はその名前自身であり（3.6）、それ以外の場所にある別名でない語はエラーである。その他の場所では3.6が適用される：ホスト名、RNL名、端子名、および `::` の後の名前は引用符がないときはASCII文字のみをとり、`::` の後に使われる別名も `#M1::"位置"` のように引用符で囲む。
  - 括弧内にある引用符なしの別名が、同じ場所で使える定義のパラメータ名またはロール名と同じ綴りである場合、意味が一意にならないためエラーとなる。括弧内の引用符付きの語は常に名前であり、決して別名ではない。`$` 名の別名と `::` の後の別名はいずれにせよ引用符付きで書かれる（3.6）。
  - 列挙値の別名は文字列内に書かれ、値が列挙であるパラメータ内でのみ機能する。`${…}` 内の属性名も別名を認識する（13.6）。TEXTの `text` などの他の文字列は置換されない。
- **診断と翻訳：**
  - 診断はファイルに書かれたとおりの語を、その標準の綴りとともに示す。
  - 翻訳器は双方向に機械的に動作する。別名へ翻訳するときはヘッダーレコードにUSE-ALIASESを書き、自己完結ファイルでは代わりに使用された別名をALIAS文として書く。1つの原語に複数の別名があるときは最初に宣言されたものがとられる。標準の綴りへ戻すときはUSE-ALIASESとALIASを除去し、何も失われない。
  - 自由テキスト、コメント、文字列は（列挙値と `${…}` 内の属性名を除き）翻訳されない。
  - LLM、ソルバー、エディタは標準の綴りで書く。別名で書かれたファイルを変更するときも、それらが追加する文は標準の綴りであり、混在は妥当である。

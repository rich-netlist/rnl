## 3 字句構造

### 3.1 文字

- トークンはASCII文字で構成される。
- 非ASCII文字は、文字列（クォートされた名前を含む）、自由テキスト、コメント、別名、およびクォートなしのロール名・パラメータ名にのみ現れる。自由テキストとコメント以外では、クォートなしの非ASCII語は `@` の直後と括弧の内部にのみ現れる：`@` の直後では宣言済みの別名でなければならず、括弧の内部では別名、あるいはロール名またはパラメータ名そのものである（3.6、16.5）。
- **エンコーディング。** ホストアダプタはホストの規則に従ってテキストをデコードし、RNLは文字単位で処理する。RNLを書き出すツールはホストファイルのエンコーディングや改行コードを変更してはならず、バイト順マーク（BOM）を追加してはならない。また、ホストのエンコーディングで表現できない文字を書き出してはならず、代わりに警告を出す。新規ファイルではUTF-8を使用すべきである。
- **ホストコメント内の非ASCII文字。** アダプタは、コメント内の非ASCII文字が検証済みのホストを明示しなければならない。それ以外のホストでは、非ASCII文字に対してヒントが出される。

  注記：対応状況はホストによって異なる。ngspice（バージョン42以降）、WRspice（タイトル行を除く）、Xyce、および近年のLTspiceはコメント内の非ASCII文字を受け入れる。HSPICE、PSpice、Eldoのドキュメントには記載がない。SpectreのマニュアルはネットリストをASCIIファイルと記述しており、QSPICEはWindows-1252を使用する。BOMを追加してはならないもう1つの理由として、古いバージョンのngspiceはBOMをインクルードファイルの最初のトークンに連結してしまい、WRspiceは1行目がBOMで始まると読み込みを停止する点が挙げられる。

### 3.2 トークン

| トークン | 形式 |
|---|---|
| キーワード | `@` に続けて大文字の名前を書いたもの（`@PLACE` など）、または宣言済みの別名（16.5） |
| 参照 | 接頭辞に続く名前。必要に応じて端子やサブオブジェクトを伴う（`#M1`、`#M1:d`、`%dp1::left` など；第6章）。あるいは `#`、`?`、`&` 単体（6.2）。ホスト名や端子名の直後に `&D<3>`、`&D<7:0>` のような添字を付けてもよい（6.11）。セットへの参照の直後に `%a{1}`、`?ref{2:end}` のようなメンバー位置指定を付けてもよい（5.2.3）。ソルバーのレコード内では、`%#` に符号なし整数を続けた番号（`%#3` など）も含む（5.9） |
| 点 | `(x, y)`。キーワードやオブジェクトに密着せず、空白・コメント・`{`・`;`・`=>`・`=` の後に置かれる（3.8） |
| 丸括弧・角括弧 | パラメータおよびロールの `(` `)`。キーワードまたはオブジェクトに密着する（3.5） |
| 波括弧 | セットの `{` `}` |
| 区切り記号 | `;`（メンバーの区切り）、`=>`（パイプおよび命名）、`=`（メンバー先頭での命名） |

括弧内（パラメータ・ロール・点の `()`、および配列の `[]`）には、文字列、数値、`,`、`=`、`_`、名前（パラメータ名、ロール名、`true`、`false`）、および一般定義の定義本体ではパラメータプレースホルダ `?name`（6.10）も現れる。添字の `<>` および `[]` の内部には符号なし整数、`,`、`:` のみが現れ（6.11）、メンバー位置指定の波括弧の内部には符号なし整数、`end`、`-`、`,`、`:` のみが現れる（5.2.3）。

### 3.3 自由テキスト

- 括弧の外では、以下に列挙するものを除き任意の文字が自由テキストになり得る。これにはすべての非ASCII文字（中国語の句読点 `：`、`、`、`；`、`（`、`）` など）および `-`、`:`、`'`、`!`、`+`、`/`、`*`、`|` が含まれる。例外は以下のとおり：
  - `@`、`#`、`&`、`%`、`$`、`?`、`"`、`;`、`=`、`{`、`}`、`(`、`)`：括弧の外ではトークンの開始または一部となる（3.2）。後ろに名前が続かない `&` 単体は空ノードである（6.3）。`?` はプレースホルダを開始し（6.10）、単独の `?` はシンボル定義本体ではそのシンボルで描画されるオブジェクトを（13.3）、一般定義の定義本体では展開中の適用オブジェクトを指す（9.4）。
  - `[`、`]`、`<`、`>`：配列および添字の括弧（3.7、6.11）。
  - `/*`：コメントを開始する（3.4）。
- 位置規則により意味の一意性が保たれる：
  - 参照の直後にあり、後に名前またはクォートが続く `:` または `::` は、通常どおり端子またはサブオブジェクトを表す（6.4、6.5）。後に名前が続かない場合、`Input pair: %dp1 = …` や `#M1: the left one` のように `:` は自由テキストとなる。
  - 名前の直後の `<` または `[` は添字となる（6.11）。
  - 空白なしで参照の直後に続く `{` はメンバー位置指定を開始し（5.2.3）、空白の後ではセットを開始する。
  - キーワード名の中では、`-` の後に文字が続く場合にのみそれが名前の一部となる（キーワード：3.6）。`@GROUP- the pair` はGROUPの後に自由テキストが続く形となる。
- 自由テキストは括弧の外の任意の2つのトークンの間、およびメンバーの先頭に書くことができる。
- **自由テキストは文の一部である。** その中に書かれた参照は単なる説明ではなく、その文のオブジェクトとなる：`Unlike #M2, #M1 @PLACE(x=0)` はM2もx = 0に配置する。単なる説明のためのテキストはコメント（3.4）に書くか、`;` で次のメンバーと区切った独立のメンバーとして記述する（自由テキストのみからなるメンバーは空メンバーとなり無視される；4.1）。
- 本標準は自由テキストを検査せず、自由テキストは意味に影響しない（原則 2.8）：`do not move #M2 @PLACE(x=30)` もやはりM2を移動させる。実装は否定語などに対して独自の警告を出してもよい（7.6）。
- 同様に、誤記された `#M1.d` では `.d` が自由テキストとなり、参照はドレインではなくM1自体を意味する（下記の警告が出る）。
- 括弧の内部に自由テキストはない。
- **警告。** 以下の誤りは黙って通過する可能性があるため、警告を出す（7.6）：
  - 自由テキスト中の単語が、このレベルのホストインスタンス名、可視のRNL名（接頭辞なし）、またはキーワード名と一致する場合（`#M1 #M2 M3 @ALIGN("y")` の `M3` や、`WIRE {…}` の `WIRE` など）：`#`、`%`、`$`、または `@` が抜けている可能性が高い。ネット名は in や out のような一般語であることが多いため検査しない。
  - 参照の直後に `.` と名前が続く場合（`#M1.d` など）：端子は `:` で記述する。
  - 参照の直後に `-`、`!`、`'`、`+`、`/`、`*`、`\`、`^`、`~`、`|` が続く場合（`&vdd!` や `#X1-a` など）：名前にその文字が含まれており `&"vdd!"` のようにクォートが必要である可能性が高い（3.6）。クォートなしでは参照は黙って `vdd` や `X1` を意味してしまう。
  - 自由テキスト中の `|`：パイプは `=>` で記述する（4.2項目3）。
  - 参照の直後の `:` または `::` に非ASCII語が続く場合（`%c1::中点` など）：`::` の後の非ASCII文字を含む名前には `%c1::"中点"` のようにクォートが必要である（3.6）。クォートなしでは `::` とその語が自由テキストとなり、参照は `%c1` のみを意味する。
- この種の他の誤りの大半はすでにエラーとなる：括弧内に自由テキストはないため `@ORIENT(MY)` はエラーであり、`#M1 @PLACE 1 2` はシグネチャに一致せず、`#M1 (in_p)` は空白後の括弧が点を開始するため `(in_p)` が点として不正でエラーとなり（3.5）、`R1 -> R2` の `>` は自由テキストになれない。
- 記述者向けのガイドは標準語リストから生成される（5.3）。ソルバーおよびエディタが書き出すレコードには自由テキストを含めてはならない。

### 3.4 コメント

`/* … */` は空白が許される任意の場所（括弧内を含む）に記述できる。コメントは入れ子にならず、内部には任意の文字を書ける。参照や `@`、`#`、`;` などの文字を含む説明はコメント内に記述する（3.3）。

### 3.5 空白と隣接

- 空白とはスペース、タブ、および改行である。トークンを行をまたいで分割することはできず、文字列も行をまたげない。
- 空白およびコメントは以下の箇所には許されない：接頭辞と名前の間、または `%#` と番号の間、`:` と `::` の前後、名前と添字の間（6.11）、参照とそのメンバー位置指定 `{` の間（5.2.3）、キーワードとそのパラメータ括弧の間および `@RNL` とレコードヘッダーの括弧の間（2.4）、オブジェクトとそのロール括弧の間。
- 空白またはコメントの後の `(` は点を開始する（3.8）。そのため `#M1 @PLACE (10, 20)` はPLACEの後に点がある形となり、PLACEにはパラメータがないためエラーとなる。`#M1 (in_p)` はM1の後に正しく書かれていない点がある形となり、同様にエラーとなる。診断は空白の削除を提案する。
- クォートの有無にかかわらず、名前の直後の `<` または `[` は常に添字を開始する（6.11）。点は `(x, y)` と書かれるため添字とは衝突しない。名前の後に点を書くには、`&D (1, 2)` のように間に空白を入れる。添字の内部には、`&D<1, 2:3>` のように空白およびコメントを書くことができる（6.11）。
- キーワードの直後の `.` は自由テキストとなる（`{#M1 #M2} @GROUP.` のピリオドなど）。`@BUNDLE.LOCK` はBUNDLEの後に自由テキスト `.LOCK` が続く形となる（16.4）。

### 3.6 名前

- **クォートなしの名前**は1文字以上のASCII英字、数字、およびアンダースコアからなり、最長一致で切り出される。
- **ホスト名**（`#` および `&` の後）と端子名はホスト方言の規則に従う（原則 2.1）：どの名前が有効か、大小文字を区別するか、`&0` のように数字で始められるかなど。SPICEは大小文字を区別せず、Spectreは区別する。その他の文字を含む名前は `#"M1<0>"`、`&"vdd!"`、`#XU1:"in+"` のようにクォートで囲んで記述する。クォート内のテキストは文字列と同様に記述される（3.7）。名前の直後に添字を続けることができる：`#M1<0>` は `#"M1<0>"` であり、`&D<7:0>` はネットのリストである（6.11）。クォート内の `<` や `[` は名前の一部であり、添字として構文解析されない。
- **RNL名**（`%`、`$`、`?` の後の名前、ロール名、および一般定義のパラメータ名）：
  - 大小文字を区別する：`$DIFFERENTIAL_PAIR` と `$differential_pair` は別の名前である。
  - `%`、`$`、`?` の後では、`%1st` のように数字で始めてもよい。接頭辞のない位置（`(role)` および `parameter=`）では、クォートなしの名前はASCII英字、数字、アンダースコアおよび任意の非ASCII文字からなり、数値に見えないようASCII数字で始まらない：`#M1(正输入)`、`@AS(间距=3) $X`。いずれの位置も括弧内であり自由テキストが存在しないため（3.3）、他の語が名前に取り込まれることはない。
  - クォートで囲んでも意味は同じである：`$"a"` は `$a` であり、クォートはエスケープのためだけに働く。その他の文字を含む名前や非ASCII名は、`%"差分对"`、`%"input pair"`、`?"正输入"`、`%dp::"正输入"` のようにクォートで記述する。ロールおよびパラメータ名の位置では非ASCII名をクォートなしで書いてよいが（上記）、空白やASCII記号を含む場合は `#M1("input pair")` のようにクォートが必要である。ロールおよびパラメータ名の位置において、クォートされた名前は常にその名前自身であり、別名とはみなされない。これは `$` 名および `::` の後の名前には当てはまらない（非ASCII別名はいずれにせよクォート付きで書かれるため；16.5）。
  - Unicode正規化は行わず、記述された文字どおりに1文字ずつ比較される。空の名前はエラーである。
  - 添字をとらない（6.11）：直後の `<` または `[` は `%p<1, 2>` のようにエラーとなる。点は空白で区切って `(1, 2)` のように書く。
- **別名**（16.5）はヘッダーレコードで宣言するか別名パッケージから読み込む。キーワードおよび標準語の別名は非ASCII文字を含んでもよく、クォートなしで書けるのは `@` の後と括弧の内部のみである。`$` 名の別名は `$` 名と同様に記述し、非ASCIIの場合は `$"接地补位集"` のようにクォートする。`#`、`&`、`%`、`$`、`?`、`::` の後のクォートなしの名前は上記のとおりASCIIのみであるため、`#M1和#M2` は `#M1`、自由テキスト `和`、および `#M2` になる。
- **キーワード**は大文字のみで、単語を `-` で連結する（`@AS`、`@SET-SYMBOL` など）。大文字にすることで自由テキスト内でも見つけやすくなる。`@at` は、ヘッダーレコードで別名として宣言されていない限り未知のキーワードとなる（16.5）。
- **標準語**は大小文字を区別し、本標準の綴りどおりに記述される：パラメータ名、レコードヘッダーのフィールド名、サブオブジェクト名、選択条件名、および列挙値（`"x"`、`"low"`、`"MY"` など）。ホストのものを名指す値（選択条件内の名前、モデル名、ネット名）はホストの規則に従う。他の綴りは別名を通じて受け入れることができる（16.5）。
- **`true` と `false`** は予約語であり、小文字のみである。ロール名やパラメータ名には使えない。

### 3.7 リテラル

- **数値**は10進数である。符号や先頭のゼロを持ってもよく、小数点前のゼロや小数点後の桁を省略してもよく、指数部を持ってもよい：`0`、`+1`、`01`、`.5`、`1.`、`-2.5E-4`。`01` は8進数ではなく1である。単位や工学接尾辞（`2u` や `10k` はエラー）、16進数、`NaN`、`Infinity` は存在しない。桁数に制限はない。ある実装がその値を保持できない場合、その文はその実装において実装上限に達した旨のエラーで失敗し、値が黙って変更されることはない。座標は許容差を用いて比較される（11.7）。
- **文字列**は二重引用符で囲んで書き、行をまたぐことはできない。引用符の間の文字はそのまま解釈され、`"` 自体のみ `"say ""hi"""` のように `""` と記述する。バックスラッシュエスケープは存在しない：`\` は通常文字であり、`\n` や `\uXXXX` はない。非ASCII文字は直接記述する。文字列内に改行は書けず、テキスト内の改行はマークアップ `\\` で記述する（13.6）。TEXTには独自のバックスラッシュコマンドがあるが（13.6）、それらはTEXTが文字列内容を読み取る方法であり、文字列リテラルのエスケープではない。レコードヘッダー内の文字列も同じ方法で書かれる。これは外殻形式に属し、変更されない（16.1）。
- **配列**は `[value, value, …]` と書く。要素はリテラルであり、配列は入れ子にできる。
- **真偽値**は `true` と `false` である。
- 他のリテラルはない。列挙値は `axis="x"` のように文字列で書く。`null`、マップ、構築された値などは存在しない。
- 式は存在しない：演算子はエラーとなる。

### 3.8 点

- 点は `(x, y)` と書き、xとyは数値または `_` である（一般定義の定義本体ではパラメータプレースホルダも可；6.10）。`_` はその軸を自由なまま残し、制約またはソルバーによる決定に委ねる。
- 点を記述すると点オブジェクトが生成される（5.1）。
- 点に対する算術演算はない。相対位置は制約として記述する（第14章）。一般定義の定義本体では、リテラル座標は適用オブジェクト自身の点からのオフセットとなる（9.4）。
- 点の `(` の前には空白またはコメントがあるか、`{`、`;`、`=>`、`=` の直後に位置する。キーワードまたはオブジェクトに密着する括弧は、そのパラメータまたはロールを保持する（3.5）。名前の直後の `<` はいかなる場合も添字となる（6.11）。

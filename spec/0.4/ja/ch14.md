## 14 レイアウトの意図

### 14.1 共通規則

- 制約は制約オブジェクトを作る。名前付きの制約は `%row1 = {#M1 #M2} @ALIGN("y")` のように参照でき、検索や編集に役立つ。制約は匿名であってもよい。
- **語彙**：位置に対する原子制約はALIGN、ORDER、DISTRIBUTE、DISTANCEのみであり、他にPLACE、ORIENT、GROUP、および表として書かれた順序であるTABLE（14.11）がある。その他の関係は一般定義として記述される：対称（14.7）、中央揃え（3メンバーのDISTRIBUTE）、行と列（ALIGNとORDER）、信号フロー（14.6）、鏡像対、比例する間隔（複数のexactなDISTANCE）。LEFTやABOVEはなく（それらは方向付きのORDERまたはDISTANCEである）、RATIO、NEAR、INSIDEもない。相対的な向き（同じ向き、鏡像反転）はORIENT-RELATION（14.9）である。対のゲート同士が向かい合うか外側を向くかは依然としてORIENT、または端子上のORDERで固定する（14.3）。シンボルが重ならないこと、間隔定数、およびグリッドはソルバーに属し（11.7）、制約の語彙の一部ではない。
- **図面全体に対する相対位置はない**：「最左」「最右」「最上」を表すキーワードはなく、図面全体やシンボル外形の範囲もない。あるオブジェクト群に対する相対的なORDERまたはDISTANCEを記述すれば、ソルバーがそこからレイアウトを求める。右端のポートに対しては `{#M6 #M7 #CL} %pout @DISTANCE("left-to-right", min=2)`、あるいはM7がすでに最右であるなら `{#M7 %pout} @ORDER("left-to-right")` と書く。
- **メンバーは最も下位のオブジェクト**：インスタンス、バンドル、端子とピン、点、TEXT（自身の位置による、13.3）、中心で書かれたRECTANGLE・CIRCLE・ELLIPSEの中心、およびシンボルで描画される適用オブジェクト（各々自身の点による）。シンボルを持たない適用オブジェクトはそれ自体はメンバーではなく、そのメンバーを表す：ロールを埋めるオブジェクトであり、シンボルを持たない適用オブジェクトであるメンバーはGROUP（11.5）と同様に最も下位のオブジェクトまで内側へたどられ、その中のネットは除外される。その自身の点は `%u::position` と書く（6.5）。配線、ネット、制約、定義はメンバーになれない：これらを渡すと制約は失敗する。配線上の位置はまず点として記述しなければならない（13.1）。セットはメンバーではない：自身の位置を持たないためである（下記）。
- **どの点が数えられるか**：インスタンスはその原点すなわちシンボルの原点（PLACEが配置する位置でもある）で数えられ、端子またはピンはそのピンの位置（素子の位置にシンボル内のピン位置の剛体変換を加えたものであり単独では動かせない）で、点はそれ自身で、シンボルを持つ適用オブジェクトまたは任意の適用オブジェクトの `::position` は自身の点（下記）で、TEXTは自身の位置で、中心で書かれたRECTANGLE・CIRCLE・ELLIPSEはその中心で数えられる。シンボルの外接枠の中心は使われない：3端子と4端子のMOSシンボルでは外接枠が異なり、それらの行が揃わなくなってしまうためである。ピンで揃えるには端子を記述する。視覚的な対称性には原点がシンボルの対称軸上にある必要があり、それはシンボルライブラリ次第である。
- **適用オブジェクト自身の点**：すべての適用オブジェクトは（シンボルを持たないものも含めて）自身の点を持つ。この点は `(_, _)` のように自由な状態で始まり、PLACE、制約、そのシンボルのピンへの配線、およびその定義本体がその点に書いた事実によって結び付けられる。自由に残された部分はソルバーが配置する。シンボルを持つ適用オブジェクトはこの点にシンボルの原点を置いて描画され（12.1）、それに対する制約はこの点に作用する。シンボルを持たない適用オブジェクトへの制約はそのメンバーに作用する（上記）。その点を制約するには `%u::position` と書く：`{%dp::position #X1} @ALIGN("y")` はX1を差動対の中央と同じ高さに置くが、`{%dp #X1} @ALIGN("y")` はX1と差動対の3つのトランジスタを同じ高さに置くことになる。定義本体は単独の `?` に `{?members::position ?} @ALIGN("y")` のような事実を書いた箇所で、この点をメンバーに結び付ける（9.4）。適用オブジェクトの点がどの描画要素にも事実で結び付けられていない場合、`%u::position` への制約は目に見える効果を持たず、ヒントがその旨を伝える。
- **セットは位置を持たない**：セットはメンバーのリストにすぎず、中心も範囲も持たない。ALIGN、ORDER、またはDISTRIBUTEのメンバーリスト内でセットである項目（書かれた `{…}` またはセットへの参照；5.2）はその項目においてその最も内側のメンバーそれぞれを表す：文は、そのような各項目から1メンバーずつとる各組み合わせにつき1つの制約となる。`{#M1 {#M2 #M3} #M4} @ORDER("top-to-bottom")` は `{#M1 #M2 #M4}` と `{#M1 #M3 #M4}` であり、M2とM3がそれぞれM1とM4の間にあり、M2とM3同士の間では順序付けられない。シンボルを持たない適用オブジェクトである項目も同様にそのメンバーを表す（上記）。DISTANCEのスロット内のセットはその各メンバーを表し、各ペアにつき1つの制約となる（14.5）。空のセットである項目は除外される。1つのオブジェクトを2度とる組み合わせは除外される：1つの素子を共有する2つの構造を `{%stage1 %stage2} @ORDER("left-to-right")` として順序付けた場合、メンバーの他のすべてのペアは順序付けられ、その共有素子がそれ自身に対して順序付けられることはない。
  - そのように作られた制約は書かれた文の優先度、名前、位置を持つ（8.5、14.8）。名前はそれらのセットを束縛する。意味をなすにはメンバー数が少なすぎる組み合わせはヒントを出す。
  - 実装は1つの文が表す制約の数に上限を設けてもよい。上限を超えると文は失敗し、実装上限である旨のエラーを出す（1.6）。
  - 唯一のオブジェクトであるセットはまず1レベル展開される（5.2.1）：`%row_set @ORDER("left-to-right")` と `{%row_set} @ORDER("left-to-right")` はどちらもそのセットのメンバーを順序付ける。
- **方向は明示的に書く。** ALIGNは射影 `"x"` または `"y"` をとり（14.2）、ORDER、DISTRIBUTE、DISTANCEは4方向のいずれか1つをとる（14.3）。方向を未定のままにする形式はない：どちら向きに描いてもよい関係は一方の向きに対する1つの事実として書き、両方の描画を許すべき定義は標準パッケージの `$BRANCH` と `$BRANCH_HORIZONTAL` のように2つの定義として提供される。選択肢を提供する事実はORIENT（11.2）とORIENT-RELATION（14.9）の向きのリストのみである。
- 制約はネットリストを変更しない。競合時には、原子制約は全体として採用または全体として破棄される（8.5）。
- 4つの原子制約、ORIENT-RELATIONおよびTABLEはパラメータ `priority=` をとる（14.8）。

### 14.2 ALIGN

`{…} @ALIGN("y")`：メンバーは射影 `axis` において等しい：`"y"` は同じy（行）、`"x"` は同じx（列）を与える。`axis` は必須であり、位置指定で与えられ、1つの射影である：射影のリストは誤ったパラメータ値であり、制約は失敗する。メンバーが2つ未満のとき、制約は自明に成り立ち失敗しない：選択やセットがいくつのメンバーを持つかは文を書く時点では不明なためである。

### 14.3 ORDER

```rnl
%rc_set = {#R2 #C2};
{#M1 #M1:2 #M2:2 #M2} @ORDER("left-to-right");  /* M1 on the left, the two gates face each other */
{#R1 {%rc_set} #M1} @ORDER("left-to-right")     /* R2 and C2 each between R1 and M1 */
```

- `{…} @ORDER(direction)`：メンバーは方向の射影において狭義単調である。メンバーが2つ未満のときは自明に成り立つ。
- **方向**：パラメータ `direction` は必須であり、位置指定の1番目で与えられる。その値は次のとおり：
  - `"left-to-right"`、`"right-to-left"`：xの増加、xの減少；
  - `"bottom-to-top"`、`"top-to-bottom"`：yの増加、yの減少（yは上向き、11.7）。

  DISTRIBUTEとDISTANCEも同じ値をとる。軸のみを固定する値はない：`"x"` と `"y"` は誤ったパラメータ値であり、制約は失敗する。
- セットである項目はその各メンバーを表す（14.1）：2番目の例は R1, R2, M1 と R1, C2, M1 を順序付け、R2とC2の間は順序付けない。
- ORDERは点に対する事実である：メンバーの外接枠ではなく点を比較する。ORDERに沿ってシンボルの外接枠同士を離しておくことは、すべての事実の後にランク付けされるソルバーの基準である（8.5）。事実が外接枠の重なりを強制するときは重なり、ヒントが出されてもよい。
- ORDERは狭義である：隣接するメンバーは少なくとも1座標単位だけ異なる（11.7）。これは隣接するメンバーの各ペア間の `min=1` を持つその方向のDISTANCEの短縮形である（14.5）。等しい座標にはALIGNを用いる。

### 14.4 DISTRIBUTE

```rnl
{#R1 #R2 #R3} @DISTRIBUTE("left-to-right")     /* R1, R2 and R3 from left to right, in equal steps */
```

- `{…} @DISTRIBUTE(direction)`：メンバーはORDER（14.3）と同様にその方向に狭義に順次並び、その射影における隣接メンバー間の差が等しい。間隔は外接枠間の隙間ではなくメンバーの点同士の間である。セットである項目はその各メンバーを表す（14.1）。
- **方向**：パラメータ `direction` は必須であり、位置指定の1番目で与えられ、ORDER（14.3）の値をとる。
- 2メンバーではDISTRIBUTEはORDERと同じであり、2メンバー未満では自明に成り立つ。

### 14.5 DISTANCE

```rnl
#M1:2 #M1 @DISTANCE("left-to-right", min=1);      /* the gate is on the left */
#R1 #R2 @DISTANCE("left-to-right", exact=8)       /* R2 exactly 8 units to the right of R1 */
```

```rnl
%stage1_set = {#M1 #M2 #M5};
%stage2_set = {#M3 #M4};
%stage1_set %stage2_set @DISTANCE("left-to-right", min=1)     /* all of stage 2 is to the right of all of stage 1 */
```

- `A B @DISTANCE(direction, min=…, max=…)`：Aがスロット `from` を埋め、Bがスロット `to` を埋める。各々はオブジェクトまたはセットである。
- **方向**：パラメータ `direction` は必須であり、位置指定の1番目で与えられ、ORDER（14.3）の値をとる。その軸のみが制約され、これはユークリッド距離ではない。
  - 増加方向（`"left-to-right"`、`"bottom-to-top"`）は B − A を制約する；
  - 減少方向（`"right-to-left"`、`"top-to-bottom"`）は A − B を制約する。
- **セット**：スロット内のセットはその各メンバーを表し（14.1）、シンボルを持たない適用オブジェクトも同様であり、DISTANCEはAのすべてのメンバーからBのすべてのメンバーへ、各ペアにつき1つの制約として成り立つ。同一オブジェクト同士のペアは除外される。したがって `%stage1_set %stage2_set @DISTANCE("left-to-right", min=1)` はステージ2のすべてをステージ1のすべての右側に置き、入り混じってはならない2つのセットはこのように記述する。一方が空のセットのときはペアが存在せず、何も起きない。
- `min`、`max`、`exact` の少なくとも1つを書かなければならず、`min` は `max` より大きくてはならない。DISTANCEは順序も表明する：その方向においてBがAより前になることはない。したがって上下限は負ではなく、負の `min`、`max`、または `exact` は誤ったパラメータ値であり制約は失敗する。書かれなかった `min` は0であるため、`max=10` は0から10までの距離で成り立つ。
- `exact=` は正確な距離であり、等しい `min` と `max` の短縮形である：増加方向では B − A = exact、減少方向では A − B = exact となる。`min` や `max` と同時に書くことはできない：それは不正なパラメータであり文は失敗する。ツールは正確な距離を `exact` で書き出す（4.3）。

### 14.6 信号フロー

信号フロー（原則 2.4）は一般定義の適用オブジェクトとして記述され、専用のキーワードはない。標準パッケージがその定義を提供するか否か、およびどの名前で提供するかは標準パッケージ次第である（16.3）。例ではセットとして与えられる経路を名指す標準シリーズ 0.4の `$SIGNAL_FLOW` を用い、その前に信号源（source）を、後に負荷（load）を名指すこともできる。これは意味定義であり、何も配置しない。

```rnl
%rc_set = {#R2 #C2} @GROUP;
{#R1 {%rc_set} #M1} @AS $SIGNAL_FLOW                                    /* the signal goes from R1 through the block of R2 and C2 to M1 */
{#:inp #:inn}(source) {#R1 {%rc_set} #M1}(path) #CL(load) @AS $SIGNAL_FLOW   /* from the two inputs of the level to the load CL */
```

- 信号フローは緩やかな概念である：すべての回路が厳格な一方向を持つわけではない。ソルバーはそれを優先傾向として読み取ってもよい。図面上で各段を順番に並べるにはORDERまたはTABLEを書く（14.3、14.11）。
- 複数のオブジェクトからなる経路の1つの段は、`{%rc_set}` のように独立した `{…}` として書く。GROUP（11.5）はソルバーにそれを1つのまとまりとして扱わせるだけであり、省略してもよい。
- 信号源と負荷はそれぞれ順序を持たないグループであり、差動信号の2つの入力などがその例である。それらはデバイス、構造、`#:inp` のようなそのレベルのポート（6.4）、その他の端子、またはネットであってもよい。ロールの印がない場合、それらのオブジェクトは1行目のように経路を表す。
- 電力の流れ——電源から、電力を変換またはスイッチする各段を経て、電力を消費する各部へ至る経路——も、同様に `$POWER_FLOW` で記述される。

### 14.7 対称性

対称性は一般定義の適用オブジェクトとして記述する。対称軸は単なる自由な点であり、キーワードは不要である。標準シリーズ 0.4はロール `left`、`right`、`axis` を持つ `$MIRRORED_LAYOUT`（leftとrightが同じ高さ、axisがその中央、rightはleftを左右反転した向き）と、それを縦向きにしたロール `top`、`bottom`、`axis` を持つ `$MIRRORED_VERTICAL_LAYOUT` を提供する。いずれの適用オブジェクトも自身の点は両側の中央にあり（14.1）、その適用オブジェクトへの制約によってペア全体が移動する。標準パッケージのすべての定義と同様に、これらの制約の優先度は `"low"` である（9.5）。軸は1つのオブジェクトである：複数の素子が軸上に立つ場合は、まずそれらを自身の点で数えられる1つの適用オブジェクトにするか（14.1）、それらのうちの1つを与える。

```rnl
%ax = (_, _);
%sym12 = #M1(left) #M2(right) %ax(axis) @AS $MIRRORED_LAYOUT
```

- `$MIRRORED_LAYOUT` は実際の向きを固定しない：ゲートが内側を向くか外側を向くかには依然として片側にORIENTが必要である（14.9）。両側が同じ向きを持つ対称な対に対しては、ORIENT-RELATIONを除いた別の一般定義を書く。

### 14.8 優先度：PRIORITY

```rnl id=dpl
$DP_LAYOUT = @DEFINE(roles=["in_p", "in_n"]) {
  {?in_p ?in_n} @ALIGN("y", priority="low")                    /* a default layout, the first to give way */
};
%dp2 = #M1(in_p) #M2(in_n) @AS(priority="high") $DP_LAYOUT;     /* this pair keeps the default layout strictly */
#M1 @PLACE(12, 20, priority="high")                             /* fixes the position of M1 */
```

```rnl use=dpl
# @SELECT-USAGE(recursive=true) $DP_LAYOUT => @PRIORITY("disabled")    /* a house-style package turns the default layout off, to apply its own */
```

- **4つの値**：`"disabled"`、`"low"`、`"normal"`、`"high"`。優先度のない事実は、ユーザーのレコード、パッケージ、定義本体のいずれに書かれても `"normal"` である。
- **重み付けではなく順位付け**：競合時にはまず優先度が比較され、高い方が採用される。同じ優先度では後に書かれた方が採用される（8.5）。制約を重み付きで合算することはしない。

  注記：重み付けでは、低優先度の10個の制約が高優先度の1つの制約を上回ってしまうおそれがあり、また制約がどれだけ破られたかの測り方はソルバーごとに異なるためである。
- **採用されたすべての事実はハードである**：`"low"` とは「できるだけ近づける」ではなく「競合時に最初に破棄される」を意味する。ソルバーは優先度にかかわらず採用されたすべての事実を満たさなければならず、見栄えの良い回路図にするための実装独自の目標は、言語のすべての記述の後で、採用された事実の範囲内でのみ最適化される。
- **`"disabled"`**：その事実は順序付けの前に取り除かれ、ソルバーに渡されない。これは失敗ではない：オブジェクトは依然として存在し、それに依存する記述は影響を受けず、警告も出ず、後に書かれた優先度が再びそれを有効にできる。
- **記述方法**：
  - PLACE、ORIENT、4つの原子制約、ORIENT-RELATION、TABLE、ROUTE-NET、ROUTE-OBJECT、UNROUTE-NET、UNROUTE-OBJECT、AS、およびATTACHはパラメータ `priority=` をとり、その優先度は事実に付随する。`priority` はASおよびATTACHの唯一の標準パラメータであり、定義のパラメータはこの名前を持てない。
  - PRIORITY文は後から優先度を変更する。これは自身のハンドルを持つオブジェクトのみをとる：制約、適用オブジェクト、およびGROUP付きのセット（有効・無効の切り替えのみ、11.5）。GROUP付きのセットはグループ自体として扱われ、他のセットはメンバーごとに扱われる（5.2.1）。インスタンスや他のオブジェクトを渡すと失敗する（種別の誤り）：PLACEはM1のハンドルを次へ渡すため `#M1 @PLACE(…) => @PRIORITY(…)` はエラーであり、優先度はPLACEのパラメータとして書く。
  - レコードヘッダー `@RNL(priority=…)` は、このパラメータをとりそれを書いていないレコード内の文と、TEXTの `dx`・`dy` にデフォルトを与える（13.3）。ASとATTACHには `"disabled"` のみを与えるため、無効化されたレコードはその定義本体を含め適用オブジェクトを他の文と同様に無効にする。`"high"`、`"normal"`、`"low"` を持つヘッダーのもとでは、適用オブジェクトは自身の文またはPRIORITY文が優先度を与えたときにのみ優先度を持ち、そうでなければルールが作った場合と同様に定義本体の優先度を保つため、ソルバーが書き出した適用オブジェクト（10.5）も生成されたものが意味したとおりの意味になる。適用オブジェクトが書いた優先度は依然としてその定義本体を上書きする（下記）。
- **上書きの順序**（低から高へ）：レコードヘッダーのデフォルト、文自身のパラメータ、PRIORITY文（複数ある場合は後のものが勝つ；パッケージ内のものはUSE-PACKAGEの位置による）、囲む適用オブジェクトの優先度、適用オブジェクトの外から `::` を通じてローカルオブジェクトに直接書かれたPRIORITY文（複数ある場合は後のものが勝つ）。これらのいずれも与えられない場合、優先度は `"normal"` である。
- **適用オブジェクトの優先度は下へ伝わる**：適用オブジェクトの優先度（自身のパラメータまたはその上のPRIORITY文）はそれが展開するすべての事実（入れ子の適用オブジェクトのものも含む）に適用され、それら自身の優先度を上書きする。入れ子の場合は優先度を持つ最も外側の適用オブジェクトが決める。内部の一部だけを調整するには、外から `::` を通じてそのローカルオブジェクトに直接書く（9.4）：これは適用オブジェクトの優先度より具体的であるためそれを上書きし、より具体的なものが勝つ。囲む定義の定義本体内で書かれたそのような文も、依然としてその囲む適用オブジェクトの優先度に従う。レコードのすべての文は直接変更できるため、レコードヘッダーはデフォルトを与えるにすぎない。
  - 厳密には：適用オブジェクトの優先度はその定義の定義本体内に書かれたすべてのPRIORITY文を支配し、それらは効力を持たなくなる。外から `::` を通じてローカルの適用オブジェクトに直接書かれたPRIORITYも同様に支配する：その適用オブジェクトが優先度を持つ最も外側のものとして数えられ、その文がその適用オブジェクトの展開するすべてを決める。何も支配していない文同士では、最も内側のオブジェクトに書かれたものが勝ち、同じオブジェクト上ではそのオブジェクトを作る定義本体の外から書かれたものがその定義本体内で書かれたものに勝ち、その次に後のものが勝つ。
  - 例えば、`%o1` が無効化されており、最上位に `%o1::in @PRIORITY("high")`、`%o1` の定義の本体内に `%in::row @PRIORITY("low")` がある場合、`row` の事実は `"high"` になる：定義本体内の文は `%o1` の優先度に支配され、最上位の文が `in` に対してそれを上書きするためである。`%o1` に優先度がなければ、より内側のオブジェクトに書かれた `"low"` になる。どちらの場合も `"low"` にするには外から `%o1::in::row @PRIORITY("low")` と書く。
- **ソルバーの出力**：ソルバーはその結果をPLACE、ORIENTなどとして `"high"` を付けて、そのレベル自身のテキストの最後のレコード（`@RNL(type="generated", priority="high") {…}` など）に書き出す。サブサーキットでは、それがインクルードファイルにあっても `.subckt … .ends` の内部にあり、トップレベルでは主ファイルのファイルレベルにある（第17章）。ソルバーが求解するときは `type="generated"` のレコードを除いてレベルが解釈される（2.8）ため、古い結果が次回の求解を制約することはない。求解後、ソルバーはそれらを削除して新しい結果を末尾に書き出す。
  - 求解と求解の間に書かれた、ソルバーの結果と競合する通常優先度の新しい文は破棄され、次回の求解後にのみ有効になる。ビューアはレコードヘッダーのハッシュによって再求解を提案してもよい。このような破棄を1つずつ報告する必要はない。
  - エディタでのドラッグ操作は、やはりそのレベル自身のテキスト内の、ソルバーのレコードの後に `"high"` を持つPLACEとして書き出される。これが位置を固定するため、以降のすべての求解はそれをハード制約として扱う。解除するにはその文を削除する。
- **ソルバーが書く内容。** ソルバーのレコードは、ソルバーが決定しテキストが自由のまま残していたすべての位置、向き、および経路を保持しなければならない：名前またはkeyを持つオブジェクトはそれによって、他は番号によって（5.9）、配線の経路はWIREによって（13.1）、ルールが生成したオブジェクトは明示的な文として（10.5）書き出す。そこに書かれなかった決定は結果ではない：そのオブジェクトはレベルが求解されなかったかのように自由なまま留まる。したがって求解を行わないビューアはソルバーが描いたのとまったく同じようにレベルを描画する。生成ルールが直接作ったkeyのないテキストの位置など、参照できないものをソルバーが決定することはない。そのようなテキストはビューアが配置する（13.3）。ルールが生成した適用オブジェクトを書き出せない場合（その定義がパッケージの非公開定義であり（16.2）、シンボルもテキストも持たず、他のどのオブジェクトや配線もその点によって配置されない場合など）、その自身の点も書き出されない：そのような点はソルバーを補助するだけであり、描画されるものは何もその上に立たず、自由のまま残しても描画は変わらないため、書き残された決定とはみなされない。
- **ソルバーの結果はRNLである。** ソルバーがソルバーとビューアの間のメッセージなど別の形式で結果を他ツールへ渡すとき、その形式はソルバーのレコードが保持できるもののみを保持しなければならない。それによりすべての結果をそのようなレコードとして保存できる。
- **ソルバーの目的関数**は、採用されたすべての事実を満たすレイアウトの中から選択するのみである。採用された事実は優先度にかかわらずハードである。目的関数は言語の一部ではない：目的関数の種類や順序はソルバーごとに異なり、本標準はそれらに共通の語彙を定義できない。1つのデフォルトは定まっている：妨げるものがなく他の配線と併合されない `"auto"` 配線はデフォルト経路（13.1；折れ曲がり点数を第1、長さを第2とする）に解かれる。ソルバーのオプションはハッシュが覆う入力の一部である（第17章）。結果を再現できるようにするため、ファイルはそれらをSOLVER-CONFIGで保持する（14.10）。

### 14.9 向き関係：ORIENT-RELATION

```rnl
#M1 #M2 @ORIENT-RELATION("MY");                  /* M2 is drawn as M1 flipped left-right */
#M5 {#M7 #M8} @ORIENT-RELATION("R0");            /* two facts: M7 and M8 each have the orientation of M5 */
#M3 #M4 @ORIENT-RELATION(["R0", "MY"])           /* M4 as M3, or as M3 flipped left-right */
#M1::g #M2::g @ORIENT-RELATION("R180")           /* the gates of M1 and M2 face opposite ways */
```

- `A B @ORIENT-RELATION(relation)`：2つのスロット `from` と `to`、各々1つのオブジェクトをとる。関係はORIENT（11.2）の8つの向きコードの1つ、またはそれらのリストであり、位置指定で与えられる。Bの向きはAの向きにその関係の変換を続けたものである。変換は図面の座標系でとられるため、A自身が回転しているかどうかにかかわらず `"MY"` は常に垂直線に対して左右反転する。
- **関係のリスト**（`["R0", "MY"]` など）は1つの事実を作り、AとBの間に列挙された関係のいずれかが成り立つときに成り立つ。これは全体として採用または破棄され（8.5）、ソルバーがどちらの関係を描画するかを選ぶ。リストには少なくとも1つのコードが含まれる。1コードのリストはそのコード単独と同じである。
- **1つのオブジェクト対1つのオブジェクト。** 一方のスロット内のセットはメンバーごとに処理され（5.2.1）、各メンバーにつき1つの事実を作る：`#M5 {#M7 #M8} @ORIENT-RELATION("R0")` はM7とM8のそれぞれにM5の向きを与え、したがって3つすべてが同じ向きになる。両方のスロットに2つ以上のメンバーを持つセットを書くことはエラーである：順序どおりにペアを組む解釈も全ペアを関連付ける解釈も成り立ち得るためである（5.2.1）。
- メンバーすべてが同じ向きを持つことを表す単一セットの形式はない：このキーワードは2つのものの間の関係を表すため、1つのセットでは何に関係が適用されるかが明確にならないためである。単一のオブジェクトはシグネチャに一致しないためエラーである。単一のセットは5.2.1に従ってまず1レベル展開されるため、`{#M1 #M2} @ORIENT-RELATION("MY")` は `#M1 #M2 @ORIENT-RELATION("MY")` となる。展開しても2つのオブジェクトにならない場合はエラーである。
- メンバーはORIENT（11.2）と同様に向きを持つオブジェクト（インスタンス、バンドル、シンボルを持つ適用オブジェクト）、あるいは両者がピン（端子はそのピンを表す；5.2.4）である。点、ネット、配線、またはシンボルのない適用オブジェクトはエラーであり、ピンとオブジェクトを関連付けることもエラーであり、制約は失敗する。一方のスロットが空のセットを受け取ったときは関連付けるものがなく、何も起きない（5.2.1）。
- **ピン。** 各スロットにピンがある場合、関係は図面内での2つのピンの向き同士の間で成り立つ（11.2）：Bの向きはAの向きをその関係で回転させたもの（逆向きに向き合うピンの `"R180"` など）であり、鏡像コードは点を回転させるのと同様に向きを変える。関係はコードのみで書く：11.2の語は回転ではなく方向の名前のため、ここに書くと誤ったパラメータ値となり制約は失敗する。`direction=` が書かれていないピンはその事実を失敗させる（9.2.4）。
- これは制約である：制約オブジェクトを作り、名前を付けられ、`priority=` をとり、PRIORITYで変更でき（14.8）、競合時には1単位として採用または破棄される（8.5）。メンバーごとに処理される場合、各メンバーにつき1つの制約を作り、名前はそれらのセットを束縛する（5.2.1）。1コードのORIENTを持つメンバーはすでに向きが固定されており、他のメンバーについてはソルバーがその関係と各メンバーのORIENTリストを満たす向きの中から選択する（11.2）。
- これは実際の向きを固定しない：2つのMOSトランジスタが鏡像対称であるとき、ゲートが内側を向く場合と外側を向く場合のどちらも `"MY"` を満たす。決定するにはさらに1つのORIENTまたは端子上のORDER（14.3）を書き、決定せずに絞り込むにはリスト付きのORIENTを書く（11.2）。

### 14.10 ソルバー設定：SOLVER-CONFIG

```rnl header
@SOLVER-CONFIG(spacing_x=2, spacing_y=1, layout="lines", lines_weights=[1, 4])    /* the default of the file */
```

```rnl
@SOLVER-CONFIG(spacing_x=1)                                                       /* this level: overrides the key spacing_x */
```

- SOLVER-CONFIGはファイルを同じ設定で再求解できるよう、ソルバーに設定を与える。事実は作らない：ソルバーは採用されたすべての事実を満たすレイアウトの中から選択するためだけに設定を使用する（14.8）。
- **形式**：RNLリテラル（数値、文字列、`true` と `false`、およびそれらの配列；3.7）による名前付きパラメータ。入れ子の設定はない。本標準が名指しするkey（下記）を除き、keyは標準語ではなく各ソルバーが独自のものを定義する。コアはパラメータをRNLリテラルとして読み取り、書かれたとおりに下記の順序でソルバーへ渡し、どれも統合して消すことはしない。値については、本標準が名指しするkeyのものだけを検査する。それ以外のkeyと値はソルバーが判断し、知らないkeyには警告を出して無視する。ソルバーは、自身の一部の設定のもとでのみkeyを受け付けることもある。例えば、あるレイアウトは使い別のレイアウトは使わない目的関数がそうである。そのkeyを使わない設定のもとでは、そのkeyは同じように警告付きで無視される。
- **本標準が名指しするkey**：`spacing_x` と `spacing_y`（グループと同様にソルバーのデフォルト間隔に加算されるグリッド単位のレベル間隔；11.5）、および `junction`（ソルバーが分岐点に黒丸を描く定義であり、`"$JUNCTION"` のように文字列として書かれた `$` 名；レベルレコードのSOLVER-CONFIGではそのレベルで探索される `%` 名も可（6.6）で、これにより1つのサブサーキット用に定義された変種がその中に留まる；黒丸を描かない場合は `""`；13.2）。すべてのソルバーが `junction` をとる。本バージョンが名指しするのはこれらのみであり、ソルバーがとってよいkeyがこれらだけという意味ではない：例にある `layout` や `lines_weights` などソルバーが他にどのkeyを持ち何を意味するかはそのソルバー次第であり、ソルバーが文書化する。レベルの間隔を持つソルバーはこの2つの名前でそれを受け取る。
- **どこに**：DEVICEと同様にそのファイルとそのファイルがインクルードするファイルのレベルに対して `language` なしのヘッダーレコード内に（2.8、6.12）、そのパッケージを使うレベルに対してパッケージファイルのヘッダーレコード内に（16.2）、そしてそのレベルに対してレベルのレコード内に書く。オブジェクトは持たない。パッケージの内容、インラインパッケージ、`language` 付きのレコード、またはソルバーのレコード内に書かれた場合は効力を持たず警告が出される。したがって `language` 付きのヘッダーレコードを通じてのみ使われるパッケージは設定を与えない。
- **順序**：設定はkeyごとに後のものが前のものを上書きする：ソルバーのデフォルト、レベルが使用するパッケージのヘッダーレコード（DEVICEと同様に記述位置の順；6.12）、外側のファイルのヘッダーレコード、次にインクルードファイルのヘッダーレコード、レベルのレコード、最後にコマンドラインやビューアのページなどでツールに渡された設定の順である。ツールは括弧内のものと同じテキスト形式でそれらを受け取るため、双方向にコピーできる。
- **採用されない値**（数値をとるところに文字列がある場合など）は、そのkeyに限ってエラーとなる（16.4）：そのkeyはその場所では書かれなかったものとして扱われ、それ以前の値が有効のままとなり、同じ文の他のkeyは通常どおり適用される。値は、それが適用される各レベルで判断される：あるレベルで定義を指さないヘッダーレコードの `junction` は、そのレベルに限って採用されず、他のレベルは引き続きそれを用いる。コアは本標準が名指しするkeyの値を判断し、採用しないものは除く。ソルバーは自身のkeyの値を判断する。したがってソルバーが受け取る設定は上記の順序の一覧であり、そこには同じkeyが複数回現れることがあり、各keyについてソルバーは受け入れる最後の値を採用する。
- **時間や探索量の制限**（8.5）は、コマンドラインやビューアのページなどツールだけが与え、ファイルが与えることはない。制限は求解を行うマシンに依存するからである。ソルバーの制限を設定するkey、たとえば組み込みソルバーの `limit`、`seconds`、`work` はそのツール専用のkeyであり、どのレコード内であってもSOLVER-CONFIGに書くと、未知のkeyと同じく警告付きで無視され、ツールが与えた制限またはソルバーの既定値が有効のままとなる。
- パッケージのものを含め、あるレベルで有効になっている設定は、ソルバーのハッシュが覆う入力の一部である（第17章）。

### 14.11 表：TABLE

```rnl
@TABLE layout: {
  {#M1 #M2 #M3}
  {#M4 {#M5 #M6} #M7}
}
```

- TABLEは入れ子の `{…}` で書かれた表としてオブジェクトを配置する：例は上から下に2行を持ち、1行目は左から右にM1、M2、M3、2行目は左から右にM4、M5とM6のセル、M7であり、そのセル内ではM5がM6の上にある。表は複数行にわたって書いてよい。標準形式はキーワードを先に書き、「@TABLE layout: {…}」と読む（4.3）。そこにある語 `layout:` は自由テキストであり（3.3）、TABLEの表をとるスロットは `rows` である（付録 A）。
- **読み方**：外側のリストは上から下へ1行ずつ進み、その中に入れ子になった各リストは自身を保持するリストに対して直角に進む（上から下へ進むリストの内部では左から右、左から右へ進むリストの内部では上から下）。`transpose=true` は外側のリストを左から右へ進める。TABLEに渡されたセットは書かれたとおりの外側のリストであり、先に展開されない（5.2.1項目2）ため、`@TABLE layout: {{#M1 #M2 #M3}}` は1行となり、`@TABLE layout: %port_set` はそのセットの各項目を独立した行に置く。
- **項目**：オブジェクトである項目は1つのセルであり、セットである項目（表の中に書かれた `{…}` またはセットへの参照）は1レベル内側のリストである。これがTABLEの規則である：TABLE内のセットは各メンバーそれぞれを表す項目ではない（14.1）。シンボルで描画される適用オブジェクトは自身の点によって1つのセルとなる。シンボルを持たない適用オブジェクトはそのメンバーを収める1つのセルとなり（14.1）、そのすべてが次の項目より前に置かれる。`%u::position` と書けばその自身の点が1つのセルとなる。
- **事実**：TABLEは1つの幾何的事実であり、競合時には全体として採用または破棄される（8.5）。これが成り立つのは、表のすべてのリストにおいてある項目の各点が次の項目の各点よりもそのリストの方向に厳密に前（ORDERと同様に少なくとも1座標単位前；14.3）にあるときである。チェッカーはそれをそのようなORDER群へ展開してもよい。ソルバーには、外側のリストおよびその中に入れ子になったリストの方向とともに1つの項目として渡される。
- **グループ**：表全体のオブジェクトは同じセット上の `@GROUP` と同様に1つのグループをなす（11.5）。その行や列は独立したグループではない。
- TABLEは整列を行わない：行が同じ高さである必要も、列が同じxである必要もない。それらを揃えるにはALIGNを書く。1つのセルが複数の行や列にまたがることはない。
- 表内の空のリストは除外され、その両隣が隣接する項目となる（14.1）。1セルの表は自明に成り立ち、グループを作らない。1つの表の2つのセルに同じオブジェクトがあると自分自身より前に来なければならなくなるためTABLEは失敗する。ネットやピンのない端子のように位置を特定できないメンバーがある場合も同様に失敗する（14.1）。
- TABLEは `priority=` をとり（14.8）、名前を付けられる制約オブジェクトを作る。

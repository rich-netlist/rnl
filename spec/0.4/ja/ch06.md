## 6 名前とスコープ

### 6.1 レベルの階層

- **レベルはテキスト構造に従う。** あるレベルのRNLは、そのレベルおよびテキスト上その中に含まれるレベルに適用される。どのサブサーキットがどれをインスタンス化しているかは関係しない。
  - ファイルは、その中で定義されたサブサーキットと、それがインクルードするファイルを含む。
  - サブサーキット内に書かれた `.include`、およびサブサーキット内に入れ子にされた `.subckt` 定義（SPICE3およびngspiceのローカル定義）は、そのサブサーキットの下位に位置する。
- 最上位からあるサブサーキットまでのレベルの連なりは、ルートのパッケージ（ヘッダーレコード内のUSE-PACKAGEのパッケージ群、記述されている場合は標準パッケージが先頭；16.3）→ 主ファイルのファイルレベル → …（入れ子になったインクルードファイル）→ そのサブサーキットを定義するファイル → サブサーキット自身、となる。例えば：

  ```text
  packages at the root (such as the standard package)
  └─ file level of tb.sp (the top level)
     ├─ load                    a subcircuit defined in tb.sp
     ├─ file level of ota.sp    a file included by tb.sp
     │  ├─ ota                  ota instantiates cell
     │  └─ cell
     └─ file level of bias.sp
        └─ bias                 also instantiates cell, but neither the RNL of bias.sp nor that of bias reaches cell
  ```

- **サブサーキットのRNLはそのサブサーキットのみを対象とする。** 競合解決においてその文はファイルレベルの内容より後に来るため優先される（8.5）が、自身がインスタンス化するサブサーキットへは引き継がれない（内部で定義されたものを除く）。ampがcellをインスタンス化しても、ampの定義やルールはcellには届かない。
- **インクルードファイルはそれをインクルードしたレベルに影響しない。** インクルードファイルのファイルレベルの定義・ルール・USE-PACKAGEは、その内部のサブサーキットとそれがさらにインクルードするファイルにのみ適用される。ネットリスト上ではサブサーキットの外に書かれた素子はインクルード元レベルに属するが、インクルードファイルのRNLがそれらを変更することはできない。したがって、あるファイルが自身のインクルードするファイルによって改変されることは決してない。
- **インクルードファイルのファイルレベルは自身の回路を持たない。** 回路を持つファイルレベルは主ファイルのファイルレベルだけである。インクルードファイルのファイルレベルにおけるホスト参照（`#M1`、`&vss`）は失敗する（6.3）。そこでは定義、ルール、USE-PACKAGE、および `scope` のみが効力を持つ。単独で開かれたファイルは主ファイルとなる。
- **インクルードファイルはインクルード元レベルから継承する。** 主ファイルのハウススタイル（そのルールおよびUSE-PACKAGEのパッケージ群）はライブラリファイル内のサブサーキットへ下方向に伝わる。そのため、同じライブラリファイルでも別の主ファイルのもとで開くか単独で開くかによって異なる描画になり得る一方、そのソルバー結果は1つだけ保存される（第17章）。ライブラリが使用するシンボルを上位レベルの見た目に関するルールの影響から守るには、ライブラリファイルまたはサブサーキット内で標準パッケージを再度USE-PACKAGEで指定する（16.2）。標準パッケージのバージョンのみを固定しつつ上位からのハウススタイルによる上書きを許すには、ライブラリファイルのヘッダーレコードにUSE-PACKAGEを記述する（16.3）。主ファイルのルールは、選択に `recursive=true` と書かない限りトップレベルにのみ適用される（10.1）。ライブラリファイルにまで届かせるべきハウススタイルのルールにはこれを記述する。
- **Verilog-Aファイル。** ネットリストが `ahdl_include` または `.hdl` で取り込むVerilog-Aファイルは、インクルードファイルと同様にその取り込み位置に配置され、その各モジュールはそのファイルレベルの下位の1レベルをなす。このレベルは回路も回路図も持たず、モジュールにブロックシンボルを与えるためだけに存在する（2.9）。
- **各サブサーキットに1つの回路図。** ビューアはサブサーキットをインライン展開しない：サブサーキットのインスタンスは常にそのシンボルで描画され、サブサーキットの内部は別に描画・求解される。各サブサーキットは上位レベルの連鎖を1通りだけ持つため、1つの文書内で各サブサーキットはちょうど1つの回路図を持つ。
- **パッケージ。** パッケージの `$` 定義は `@USE-PACKAGE` が書かれたレベルおよびその下位レベルで有効になり、そのルールはそのレベルに書かれたものとして扱われ `recursive=true` で下位レベルに到達する（16.2、10.4）。ヘッダーレコード内のUSE-PACKAGEのパッケージ群は、記述された場合またはツールの設定で追加された場合は標準パッケージとともにルートに配置される（16.3）。インクルードはレベルの下位にファイルを配置してファイルがレベルから継承するのに対し、USE-PACKAGEはレベルの上位にパッケージを配置してレベルがパッケージから継承する。
- **ルールはデフォルトでは自身のレベルにのみ適用される。** あるレベルに書かれたルールはそのレベルでのみ評価される。自身に書かれた選択の `recursive=true`、またはそれがなければ使用するセットを通じて下位レベルに到達する場合（10.1）は、下位の各レベルでもう1度ずつ、毎回そのレベルのみを見て評価される（10.4）。これが原則 2.5のルールに対する要請である：ルールは自身のレベルのみに限定することも下位レベルへ継承させることもでき、デフォルトでは自身のレベルのみに適用される一方、`$` 定義はデフォルトで継承される（6.8）。

### 6.2 接頭辞

| 接頭辞 | 指すもの | 解決場所 |
|---|---|---|
| `#` | ホストのインスタンス。`#` 単体はこのレベル自身 | このレベルのホスト |
| `&` | ホストのネット。`&` 単体は空ノード、すなわちネットなし（6.3） | このレベルのホスト |
| `%` | このレベルで付けられた名前：シーンオブジェクト、`%tail = #M5` のような既存オブジェクト、またはこのレベル内でのみ使う定義 | このレベル |
| `$` | 定義、またはセット（6.6） | 束縛されたレベルおよびその下位レベル |
| `?` | 定義のロールまたはパラメータ。`?` 単体はシンボル定義本体ではそのシンボルで描画されるオブジェクト（13.3）、一般定義の定義本体では展開中の適用オブジェクト（9.4） | 一般定義またはシンボルの定義本体 |

`$X` と `%X` は異なる名前である。

### 6.3 ホスト参照

- `#M1` と `&vss` はこのレベルのホスト内でのみ解決され、他のレベルでは決して解決されない（原則 2.5）。異なるサブサーキット内の同名のインスタンスは無関係である。
- 見つからないホスト参照は失敗する（原則 2.4）。インクルードファイルのファイルレベルは自身の回路を持たないため、そこでのホスト参照はすべて失敗する（6.1）。
- 名前の直後に添字を続けることができ、`&D<3>` や `#XI0<3:0>` のように1つまたは複数のホスト名を表す（6.11）。
- どのネットがそのレベルに存在するかは、ホストの意味論に従ってホストアダプタが決定する：
  - ローカルネット：そのレベルのネットリスト行が使用するノード（ポートを含む）。
  - グローバルネット：すべてのSPICE方言で `0` はグローバルグラウンドである。シミュレータ自身が知っているグラウンドの別名（ngspiceの `gnd`、HSPICEの `GND`・`GND!`・`!GND`・`GROUND` など）は、方言用アダプタによって `0` に統合され、統合後は `&gnd` と `&0` が同じハンドルとなる。`.GLOBAL vdd`（Spectreでは `global vdd`）で宣言された名前はすべてのサブサーキットで同じノードになる。`vdd!` のような `!` 終わりの名前はVirtuoso回路図の慣習にすぎず、効力を持つのは宣言である。
  - グローバルネットは、それを使用する各レベルごとに1つのハンドル（そのレベル内のコピー）を持つ。ネットリスト行でそれを使用しないレベルにはコピーがない。したがって `&0` はそれが書かれたレベル内のコピーを指し、各回路図は自身のものを描き、事実はそのレベルに属し、下位レベルの記述が上位レベルを変更することはできない。
  - すべてのレベルにおけるグローバルネットを指すには、上位レベルで条件 `global=true` を付けて名前で選択する（10.1）。
- **空ノード。** 後ろに名前のない単独の `&` は、ネットがないことを示す：これが渡されたものは回路のどの電気的ノードにも接続されない。これはネットをとる箇所でネットが存在しない場合、例えばネットリスト行を持たないブロック図を描く仮想部品のピンに対して書かれる：`$INTEGRATOR @ATTACH &(in) &y(out)`、`& @WIRE {%sub1::y %int1::a}`。
  - これはオブジェクトではない：ハンドルを持たず、名前に束縛できず、セットのメンバーになれず、選択されることもない。2箇所に `&` と書いても両者に共通点はない。空ノード上のピンや配線をハイライト表示するビューアは、その1箇所だけをハイライトする。
  - これをそのまま受け取るのは2箇所だけである：種別 `"net"` のロール（9.4）とWIREのnetスロット（13.1）。これが入ったロールに束縛されたピンはどのネットにも属さず、その `::net` は空ノードとなり（12.1）、その `${net}` と `${p}` は空テキストとなる（13.6）。
  - ネットを受け取るそれ以外のすべての箇所では、これはネットの空セットとして数えられる：ROUTE-NETは何も結ばず、ASSERT-NETは自明に成り立ち、これをスコープとする選択は何も選ばず、ADD-TOは何も追加しない（5.2.1）。そこに直接書いた場合は空セットを直接書いたときと同様に警告が出るが、定義本体内などでロールを通じて渡された場合は警告が出ない。したがってロールのネットを使う定義本体で空ノード用の分岐を別途用意する必要はない。
  - これはホストのネットではないため、`&` に続けてホストが持たない名前を書いた場合は従来どおり失敗する。

### 6.4 端子

- `object:terminal` は端子を表す：`#M1:1`、`#M1:d`、`#XU1:inp`、および `%x:in` のようなバンドルの端子（11.8）。`#:inp` はこのレベルのポートinpである。端子を持つのはホストインスタンス、バンドル、およびレベルのポートのみであり、適用オブジェクトは端子を持たない（12.1）。
- 数字は1から数えるホストの端子番号である。端子が指定されるあらゆる場所（`:` 参照、PINの `terminal=`、SET-SYMBOLの `terminals=`、選択の `terminal` 条件）において、数字のみからなる表記は（クォートされていても；4.1）番号である。したがって `.subckt amp 3 1 2` のように数字のみのポート名にはその位置番号で到達し、`#X1:1` がポート名3となる。また数字のみのDEVICE名はエラーとなる（6.12）。
- 名前はホストの端子名である：ヘッダーレコードの `@DEVICE` で与えられた名前（6.12）、またはサブサーキットのポート名。クォートなしで書けない名前（3.6）は `#XU1:"in+"` のようにクォートする。端子名またはポート名の直後に `#X1:D<7:0>` や `#:D<7:0>` のように添字を続けてよい（6.11）。
- 大小文字：サブサーキットのポート名およびDEVICEで与えられた端子名はホストの規則に従う：SPICEは大小文字を無視するため `#M1:D` も動作し、Spectreは無視しない。
- ピンの `label=` は表示専用であり、端子の参照には使えない：端子はネットリストに属するため、参照は使用中のシンボルに依存しない。
- **端子とピン**：端子はネットリストに属し、ピンは描画オブジェクトのシンボルに属する（9.2.4）。端子はそれを束縛するピン位置に描画され、ピンまたは点が必要な箇所では端子が自身のピンを代表する（5.2.4）。ピンは `#M1:d` のようにその端子を通じて書くか、シンボル内で名前を持つ場合は `#X1::vdd_t` のようにサブオブジェクトとしてその名前で書く（6.5）。数字がピン名になることはない。
- 見つからない端子は失敗する。端子が自身のシンボル内にピンを持つか否かは、シンボルが決定された後に検査される（7.1）。
- サブサーキットのポート名以外の端子名はDEVICEによって与えられる。6.12にSPICE系の標準名を示す。
- ネットリストが定義を持たないサブサーキット（`XM1 … sky130_fd_pr__nfet_01v8` のようなPDK素子など）は、ユーザーがヘッダーレコードでDEVICEにより名前を与えるか（6.12）、DEVICE文を保持するパッケージを使用した場合（16.2）にのみ端子名を持ち、そうでなければ番号のみが使用できる。

### 6.5 サブオブジェクト

- `object::name` はサブオブジェクトである。これは常にオブジェクトであり、値ではない。そのハンドルは親オブジェクトと名前の組であるため、シンボルが与えられる前にメンバー数を数える場面（5.2.4）では2つの名前は2つのメンバーである：`{#R1::p #R1::q} @UNION` は、後から両方の名前が1つのピンを指すと判明した場合でも2メンバーを持つ。
- サブオブジェクトには以下のものがある：
  - テキストのkey：`key=` 付きのTEXTが取り付け先のオブジェクト上に作るサブオブジェクト（`#M1::wl` など）。シンボル内のkey付きテキストは、そのシンボルで描画される各オブジェクトのサブオブジェクトとなる（13.3）。`::name` と `::value` は標準サブオブジェクトではなく、よく使われるkeyにすぎない（13.3）。
  - `::position`：オブジェクトの原点。`#M1::position @PLACE(…)` は `#M1 @PLACE(…)` と同じである。適用オブジェクトでは自身の点（14.1；シンボルを持つ場合はそのシンボルの原点；12.1）である。セットでは各メンバーの `::position` のセットとなり、入れ子のセットは内側へたどられる：`{%dp1 %dp2}::position` は2つの自身の点からなる `{%dp1::position %dp2::position}` であるが、制約内の `{%dp1 %dp2}` は6個のトランジスタを表す（14.1）。TEXTではテキスト自身の位置（13.3）、中心形式で書かれたRECTANGLE・CIRCLE・ELLIPSEではその中心である（13.4）。
  - 端子の `::net`：それが接続するネット（`#M5:1::net` は `&tail`）。バンドルの端子については11.8を参照（メンバーが異なるネットにある場合はそれらのネットのセット）。ピンの `::net`：それが束縛する端子、またはそれが束縛するロールを埋めるもののネット（12.1）。バスピンの場合はそれらのネットのセット。何も束縛しないピンはこれを持たない。
  - オブジェクトのシンボルの名前付きピン：`#X1::vdd_t` はX1のシンボル内の vdd_t という名前のピンであり、`%g0::pin` は適用オブジェクト `%g0` のシンボル内の pin という名前のピンである（9.2.4）。
  - 適用オブジェクトのロール名：そのロールを埋めるもの（`%dp1::left` はM1、`%g0::p` はネットvss）。セットロールの場合はそのセットである。これは2つ目の別オブジェクトではなくそのオブジェクト自体であるため、`{%dp1::left #M1} @UNION` は1メンバーとなり、`%dp1::left` に対して書かれたPLACEはM1のキーを持つ。
  - 適用オブジェクトの定義本体内の名前付きローカルオブジェクト（`%c1::mid` など；9.4）。
- 標準サブオブジェクト名は予約されている：一般定義のロール名・パラメータ名・ローカル名、およびテキストのkeyは、いずれもこれらと同じ（記述どおりの比較；3.6）であってはならない。ローカル名はロール名と同じであってはならず、テキストのkeyは取り付け先の適用オブジェクトのロール名またはローカル名と同じであってはならない。ローカル名はパラメータ名と同じであってよい（パラメータは値であり、`::` は値をとらないため）。定義のパラメータに `priority` という名前を付けることもできない（14.8）。
- **`::` の後の名前は次の順序で検索される**：適用オブジェクト自身のロール名とローカル名、それらの `definition=` 別名、標準サブオブジェクト名とその別名、オブジェクトのシンボルのピン名、テキストのkey（別名：16.5）。ピン名が適用オブジェクトのロール名・ローカル名または標準サブオブジェクト名と同じである場合は、そのシンボルがオブジェクトに与えられた時点でエラーとなり、テキストのkeyがピン名と同じである場合も同様である。
  - keyは最後に検索されるため、それより前に来る名前（標準サブオブジェクト名、このファイルで宣言されたその別名（`alias-zh` の `"位置"` など）、適用オブジェクトのロール名・ローカル名、またはそれらの名前の `definition=` 別名）と同じ綴りにすることはできない。そのようなkeyは上記の衝突と同様にエラーとなる（13.3）。
- `::` はそのオブジェクト自身の部分のみを取り出す。シーン内のオブジェクトを条件で探す場合は常に選択キーワードを用いる。したがって「ある定義のすべての適用オブジェクト」は、定義のサブオブジェクトではなく選択として書く（10.1）。
- 後のバージョンで標準サブオブジェクト名を追加してもネットリストのポート名と衝突しないよう、端子には `:`、サブオブジェクトには `::` を用いる。
- **サブオブジェクト名**：標準サブオブジェクト名は `position` と `net` の2つであり、両者とも予約されている。その他のサブオブジェクト名はすべて動的である：テキストのkey、適用オブジェクトのロール名、定義本体内のローカル名、およびピンの名前。後のバージョンで追加される標準サブオブジェクト名はバージョンごとに適用されるため（16.1）、旧バージョンのファイルでは同名のkeyも引き続き有効である。

### 6.6 命名

- `%name = statement` と `$name = statement` は文の結果に名前を付ける。パイプ内では `=> %name` と `=> $name` がその左側のセグメントの結果に名前を付ける（5.5）。名前は単にオブジェクトを参照する別手段にすぎず、オブジェクトを作らない。
- `$name` は定義またはセット（選択の結果を含む）を束縛する。あるレベルで評価された `$` セットはそのレベルのメンバーのみを保持する（10.3）。その他のシーンオブジェクトはそのレベルに属するため `$` 名を持てない。
- `%name` はこのレベルの任意のオブジェクトを束縛できる：文が作ったオブジェクト、既存のオブジェクト（`%tail = #M5`）、セット（`%pair_set = {#M1 #M2}`）、またはこのレベル内でのみ使う定義。
- **名前は1つのレベル内で1度だけ束縛される。** `%x = #M1` を2回書くように同じオブジェクトへ再度束縛することは許されるが、別のオブジェクトへ束縛するとエラーになり、名前は最初の有効な束縛を保持する。束縛が何を束縛するかは5.5に従う。PLACEやORIENTのように入力ハンドルを保持するセグメントはそのハンドルを束縛し（そのセグメントが失敗したときも同様）、そのような束縛は入力ハンドルが有効である場合にのみ有効である：失敗したBUNDLEの後のように入力自体が失敗オブジェクトである場合、束縛も有効ではない（5.5）。新しいオブジェクトを作るセグメントはそれを束縛し、レベルの読み込み・生成時（8.2のステップ1〜3）に失敗しなければその束縛は有効である。その後のシンボル割り当て後に行われる検査（8.2）で失敗した場合も名前はそのまま保持され、後の束縛がそれを奪うことはなく、以降その名前は失敗オブジェクトを指す。その名前に対する有効な束縛が1つもない場合にのみ、名前は失敗オブジェクトに束縛される（7.2）。有効でない束縛は名前を占有しないため、後の別オブジェクトへの束縛は二重束縛エラーにならない：5.5の失敗したバンドルの後で `%s = #XI1` と書けば `%s` はXI1に束縛される。これはオブジェクトを作る文、定義、セット、および選択結果のいずれについても同様に成り立つ。
- 上書きは事実に対して適用され、名前に対してではない：RNLが作ったオブジェクトを変更するには、`%g0 @PLACE(40, 38)` のようにそれを変更する文を書く（5.8）。

### 6.7 名前のスコープ

- `@RNL` によってコミットされた名前はそのレベルに公開される：そのレベルのすべてのレコードがそれらを共有し、名前を束縛する文より前でその名前を使用できる（原則 2.9）。
- 入れ子になったセット内で束縛された名前はそのセット内でのみ有効である。
- 定義本体内で束縛された名前はその定義本体に対してローカルである（6.9）。

### 6.8 継承と隠蔽

- `$` 定義はレベルの階層を下方向に継承され（6.1）、上方向へは決して継承されない：すなわちファイル内のサブサーキットやインクルードファイルへ引き継がれる。あるレベルが自身がインクルードしたファイルの `$` 定義を見ることはない。上位レベルへ定義を提供するにはパッケージを作成し、USE-PACKAGEで使用する（16.2）。上方向へ伝わる唯一の例外はサブサーキットのブロックシンボルである（9.2.6）。
- 下位レベルで継承された定義と同名の `$X` を定義すると、そのレベルおよびその下位レベルで継承定義が隠蔽され、ヒントが出る。上位レベルでは依然として自身の定義が見える。
- あるレベルでUSE-PACKAGEにより使用されるパッケージの `$` 定義は、そのレベルの1つ上のレベルとして数えられる（16.2）。それらが上位レベルやルートのパッケージの定義を隠蔽する場合、通常の隠蔽と同様にヒントが出る。ヘッダーレコードで使用されたパッケージが、標準パッケージまたは自身より前にルートに置かれたパッケージの名前を定義している場合もヒントが出る（16.3）。
- `%` 名はそのレベル内でのみ有効であり、ファイル内のサブサーキットにもインクルード先にも継承されない。パッケージ内の `%` 定義はパッケージのプライベートな補助定義である。

### 6.9 定義本体内の名前

- 定義本体内の名前はその定義が書かれた場所で解決され、適用される場所で再解決されることはない。唯一の例外は一般定義の定義本体内の単独の `#` である（下記）。
- したがって、定義を隠蔽しても変わるのはその名前が指す先だけであり、他の定義の内部ですでに使われている定義はそのまま残る。例えば、下位レベルで `$DIFFERENTIAL_PAIR_N` を隠蔽しても、上位レベルに書かれた定義の本体内で使われている差動対は変わらない。
- 定義本体内の `%name` は、まずその定義本体のローカル名から探され、次にそのレベルの定義から探される。そのレベルのシーンオブジェクト（点、配線など）を定義本体から参照することはできず、そのような参照はエラーとなる。そのレベルが `%` で命名したセットや選択結果も、評価時のメンバーが何であるかにかかわらずこのようなシーンオブジェクトである：定義本体と共有するには `$` で命名する（こちらなら定義本体から参照でき、各適用オブジェクトのレベルで評価される；6.6、10.3）。
- **定義本体内の表記**：ロールとパラメータは `?name` と書く。ローカル名は `%name =`（パイプでは `=> %name`）で束縛し、`%name` として参照する。外部からは適用オブジェクトを通じてローカル名に到達する（9.4）。
- 定義本体からは今まさに定義している名前自身は見えない：`$NMOS = @DEFINE-SYMBOL {$NMOS; …}` の定義本体内の `$NMOS` は外側（上位レベルまたはパッケージ）の同名定義である。これにより下位レベルで上位の定義を隠蔽して拡張できる。外側にそのような定義がなければエラーとなる。
- DEFINE-SYMBOLおよびDEFINEの定義本体内におけるホスト参照はエラーである：`#M1`、`&vss`、`#:inp`、`#M1:d` はそこに書けず、シンボル定義本体内では単独の `#` も書けない。一般定義の定義本体内では、単独の `#` は適用オブジェクトが置かれるレベルを意味し（定義が適用されたときにのみ決まる；9.4）、選択のスコープとして書かれる。定義本体内からブロックシンボルを与えることはできない：そこでの `# @SET-SYMBOL` はエラーである（レベルのブロックシンボルはレベルの適用オブジェクトより先にシンボルキューに入る一方、適用オブジェクトはその後に生成され得るため；8.3、9.2.6）。定義本体内の名前は定義が書かれた場所で解決されるが、一般定義は他のレベルや他のファイルで適用されるため、ホスト参照を書くと定義側のレベルを指したままになり意味が一意にならなくなってしまう。ホストオブジェクトを必要とする一般定義は、ロールを通じてそれらを受け取る。
- **一般定義の定義本体の検査時期**：
  - 定義ごとに1回：引数に依存しないものはすべてこの時点で検査される。これにはキーワード、シグネチャ（オブジェクト数、パラメータ名と型）、`$` 名および `%` 名（定義が書かれた場所で解決）、ホスト参照、ローカル名の衝突（9.4）、および種別が宣言されたロールが正しく使われているか（ロール t が `"instance"` と宣言されているときに定義本体で `?t::net` と書くとエラー）が含まれる。シグネチャはテキスト読み込み時に検査され（7.1）、名前はレベル全体を読み終えた後にのみ解決できるため名前を必要とする検査はレベルが有効になるときに行われる。いずれの検査も、定義が何回適用されても定義ごとに1回だけ行われる。
  - 各適用ごと：引数に依存する部分（種別宣言のないロールが受け取ったオブジェクト、シンボルがピンを持っているかなど）は適用のたびに検査され、一般定義内の該当文も併せて指し示しつつ適用箇所で報告される。
  - エラーの影響範囲：誤りが見つかった定義本体の文（衝突するローカル名を含む）は定義箇所で1度だけ報告され、すべての展開から除外されるが、定義本体の残りの部分は通常どおり動作する（定義本体は許容的；9.1）。ロールリストまたはパラメータリストに誤りがある（名前の重複、標準サブオブジェクト名との衝突、未知の種別名）場合は一般定義全体が失敗し、それを使用するすべての適用も失敗する。
  - 1度も適用されない一般定義も検査される。上記の検査は適用に依存しないため、パッケージ内の未使用定義のエラーも検出できる。

### 6.10 プレースホルダ

- `?name` は一般定義の定義本体内にのみ現れ、その名前はロールリストまたはパラメータリストに存在しなければならない。そうでなければテキスト読み込み時にエラーとなる。
- オブジェクトが置かれる箇所ではロール（`?t` や `?t::net` など）であり、リテラルが置かれる箇所ではパラメータ（`min=?gap`、`[?w, 2]`、`(?x, 0)` など）である（9.4）。リテラルの箇所にロールを、あるいはオブジェクトの箇所にパラメータを書くと、テキスト読み込み時にエラーとなる。ロール名とパラメータ名は1つの表で管理され、重複できない。
- ロールプレースホルダは `?t::net` のようにパスを持つことができ、セットロールのプレースホルダは `?ref{1}` のようにメンバー位置指定をとることができる（5.2.3）。パラメータプレースホルダはそのどちらも持たない。

### 6.11 添字

| 表記 | 意味 |
|---|---|
| `&D<3>` | `&"D<3>"` と同じ |
| `&D<7:0>` | リスト：`D<7>`、`D<6>`、…、`D<0>` |
| `&D<1,2:3>` | `D<1>`、`D<2>`、`D<3>` |
| `&D<0:6:2, 9>` | `D<0>`、`D<2>`、`D<4>`、`D<6>`、`D<9>` |
| `&D[3:0]` | `D[3]`、`D[2]`、`D[1]`、`D[0]` |
| `#XI0<3:0>` | 4つのインスタンス |
| `#X1:D<7:0>` | X1の8つの端子 |
| `#:D<7:0>` | このレベルの8つのポート |
| `&"D"<1:0>` | `D<1>`、`D<0>` |
| `&"D<7:0>"` | 名前が `D<7:0>` であるノード：クォート内は構文解析されない |

- ネットリストにはバスが存在しない：Virtuosoなどのツールがネットリストを出力するとき、バスはSpectreネットリストの `D\<3\>` のように単一ビットに分割され、サブサーキットのバスポートや反復インスタンスも分割される。添字はそのような1つまたは複数の名前を簡潔に書くための記法である。これは名前を組み立てるだけであり、ホストがバスを知っていることに依存しないため、意味が一意になる。
- **形式**：クォートの有無にかかわらず、ホスト名の直後に `,` で区切られた項目群を保持する `<…>` または `[…]` を続ける。各項目は `i`、`a:b`、または `a:b:s` であり、混在させてよい。数値 i、a、b、s は符号なし10進整数であり、s は1以上である。名前と括弧の間に空白は入れられない。括弧の内部には空白およびコメントを記述してよい（3.5）。
- **展開**：項目は記述順に展開されて連結され、重複は保持される。`a:b` はaからbまで進み、`a:b:s` はbを超えない範囲で刻み幅sで進む：`<7:0>` は 7, 6, …, 0、`<0:7:2>` は 0, 2, 4, 6 である。刻み幅はMATLABの `a:s:b` ではなく、VirtuosoやXschemと同様に末尾に来る。生成される名前は、括弧の前の名前、開き括弧、先頭ゼロなしの10進数、閉じ括弧（書かれた括弧の種類を使用）を連結したものである：`&D<07>` は `D<7>`、`&D[3]` は `D[3]` となる。
- **単一またはリスト**：単一の数値1項目のみの場合は1つの参照になる：`&D<3>` は `&"D<3>"` である。それ以外はすべてリスト（セットへの参照）になる：`&D<3:3>` や `&D<3,5>` など。セット内のリストは1段階展開され（5.2）、文の唯一のオブジェクトである場合はまず1段階分解される（5.2.1）ため、`#XI0<3:0> @ALIGN("y")` は4つのインスタンスを整列させる。単一オブジェクトをとるスロットではメンバーごとに作用し、WIREのnetスロットでは全体がそのまま受け取られて1本のバスを作る（13.1）。
- **記述場所**：`#` および `&` の後のホスト名、ならびに `#` 参照内の端子名およびポート名。RNL名（`%`、`$`、`?` の後）、ロール名、サブオブジェクト名は添字をとらず、直後の `<` または `[` はエラーとなる。セットのメンバーは代わりに波括弧の位置指定で取り出す（5.2.3）。
- **名前の直後に点は置けない**：名前の直後の `<` または `[` は常に添字を開始するため、その内容が形式に合わなければ構文エラーとなり、点として解釈されることはない。名前の後ろに点を書くには、`&D (1, 2)` のように空白で区切る。
- **展開は1つまで**：1つの名前は最大1つの添字を持つため、`A<1>[2]` のような名前は `&"A<1>[2]"` のようにクォートで書く。1つの参照の中でリストに展開される添字は最大1つである：`#XI0<3:0>:a` と `#X1:D<7:0>` は許され、`#XI0<1:0>:D<1:0>` はエラーであり、`#XI0<3>:D<1>` のように両方とも単一数値である2つの添字は許される。リストに展開される参照の後に `::` が続く場合、`#XI0<3:0>::name` のように各メンバーに対してサブオブジェクトが取得される。
- **クォート内は構文解析されない**：`&"D<7:0>"` は `D<7:0>` という名前のノードを指し、`&"D"<7:0>` は展開される。ネットリスト内の名前にバスのビットではない `<` や `[` が含まれている場合は、そのままの名前として参照するためにクォートする。
- **比較される名前はアダプタが読み取った名前である**（3.6）：バックスラッシュがSpectreのエスケープであるSpectreネットリスト中の `D\<7\>` は、アダプタによって `D<7>` と読み取られるため、`&D<7>` でこれを参照する。
- 各メンバーは個別に解決される。見つからないメンバーは失敗オブジェクトとなり、それを受け取るスロットの定めに応じて厳格または許容的に扱われる（7.3）。
- パラメータ内の文字列（PINの `terminal=`（9.2.4）や選択の `name=` 条件など）は展開されない。
- 非対応の記法：Virtuosoの繰り返し記法 `<*2>A` や `A<0:2*2>` および並列記法 `A,B`（セットがすでに書けるため）、KiCadやXschemの `D[0..7]`（メンバーが括弧なしの D0 … D7 になるため）。
- 反復インスタンス（Virtuosoの `I0<3:0>` のように、複数のホストインスタンスを1つとして描画するもの）はバンドルとして記述する：`#XI0<3:0> @BUNDLE`（11.8）。

### 6.12 端子名：DEVICE

```spice
* sky130 transistors, defined in the PDK and not in this netlist
* @RNL(type="header") {
*   @VERSION("0.4");
*   @DEVICE(name="X*", model="sky130_fd_pr__nfet_*", terminals=["d", "g", "s", "b"], type="nmos");
*   @DEVICE(name="X*", model="sky130_fd_pr__pfet_*", terminals=["d", "g", "s", "b"]);
*   @DEVICE(model="sky130_fd_pr__pfet_*", type="pmos")    /* adds the type to the names given above */
* }
XM1 out in 0 0 sky130_fd_pr__nfet_01v8 w=1 l=0.15
XM2 out in vdd vdd sky130_fd_pr__pfet_01v8 w=2 l=0.15
* @RNL { #XM1:d @CURRENT("in") /* XM1 is a sky130 NMOS; its terminal 1 is named d, and its type is nmos */}
.end
```

- **RNLが端子に名前を付け型を与える。** `@DEVICE` はある素子のクラスを記述する：`terminals` はネットリスト行上のノード順にそれらの端子名を列挙し、`type` はその型（下記）を与える。これはホストの端子番号に名前を与えるだけであり、端子の順序もサブサーキットのインターフェースも変更しない（原則 2.2が許容する表示上の別名である）。1つの `terminals` リスト内の名前はホストの大小文字規則のもとで互いに異ならなければならず、数字のみで構成されてはならない（6.4）。例えばSPICEでは `"d"` と `"D"` は等しいとみなされる。どちらの方言のファイルから使われるか分からないパッケージファイルのヘッダーレコード内では、大小文字を区別せずに互いに異ならなければならない。同名が2つあるリスト、または数字のみの名前を含むリストはエラーとなり、そのDEVICE文は失敗し、インスタンスはそれ以前のDEVICE文およびアダプタが与えた名前を保持する。
- **ヘッダーレコード内にのみ記述可**（2.8）：それ以外の場所に書いたDEVICEはエラーである。パッケージファイルのヘッダーレコードも有効である（16.2）。インラインパッケージはDEVICEを保持できないため、ファイルのヘッダーレコードに記述する。
- **照合**：`name` はインスタンス名と照合され、`model` はインスタンス行に書かれたモデル名またはサブサーキット名（Spectreではプリミティブの `resistor` などのインスタンスのマスタ）と照合される。いずれもワイルドカード `*`（任意の0文字以上）を使うことができ、ホストの大小文字規則で比較される。一方は省略できるが両方は省略できず、書かれた条件が一致するときにDEVICEはそのインスタンスに一致する。DEVICEは `terminals`、`type`、またはその両方を与える。`name` と `model` のいずれもないもの、または `terminals` と `type` のいずれもないものはエラーとなり失敗する。名前を比較する選択条件も同じ規則で `*` をとる（10.1）。
- **型**：`type` は `"nmos"` のような文字列であり、下表の語が標準である。これはXインスタンス（ネットリストに定義のないPDK素子を含む）のようにホストが型を持たないインスタンスに対して、条件 `type`（10.1）、`${type}`（13.6）、および表明（15.3）が読み取る型である。モデルカードのインスタンスは自身のモデルの型を保持する（下記）：異なる型を指定するDEVICEは警告を出し、サブサーキットのポート名と同様に型を変更しない。
- **複数一致する場合は項目ごとに後のものが有効になる**：端子名と型のそれぞれについて個別に、その項目を書いた最後の一致DEVICEが有効になる。したがってあるDEVICEが名前を与え、後のDEVICEが型を与えることができ、項目を省略した後のDEVICEが前の設定を上書きすることはない。まずアダプタのデフォルトが来、次にレベルが使用するパッケージのDEVICE文（パッケージ位置の順；16.2）、次に外側のファイルのヘッダーレコード内のもの、次にインクルードファイルのものが来る。1つのヘッダーレコード内では記述順であり、1つのファイルのヘッダーレコード間では `language` なしのものが先、次に `language` 付きのものが記述順に来（各々その言語区間内のインスタンスにのみ作用する；2.8）。したがって、ファイルに書いたものがパッケージを上書きし、パッケージがアダプタを上書きし、より限定的な文は一般的な文より後に書くべきである。USE-PACKAGEがどこに書かれているかにかかわらず、すべてのパッケージのDEVICE文はファイル自身のものより前に来る（ヘッダーレコードは常にファイル先頭にあるため、パッケージをUSE-PACKAGEの位置に置くとファイル自身の記述を上書きできてしまうためである）。`model` を指定したDEVICEがより特異的として優先されることはなく、特異性による別ルールはない。
- **スコープ**：ファイルのヘッダーレコード内のDEVICEは、そのファイルおよびそれがインクルードするファイルに適用される。インクルードファイルは自分自身と自身がさらにインクルードするファイルのみを変更できる（6.1）。パッケージファイルのヘッダーレコード内のDEVICEは、そのパッケージを使用するレベルに適用される（16.2）。例えばsky130用パッケージにDEVICE文、シンボル、およびシンボル選択ルールをまとめておけば、`@USE-PACKAGE(name="sky130-rnl")` と書くだけで端子名・型・シンボルが揃う。
- **アダプタのデフォルト**：各方言の標準素子定義であり、最上位レベルに書かれたものとして数えられる。ファイルに記述する必要はなく、ツールが出力してもよい。同じ方言向けのツールは同じ定義を与えなければならない。それらは16.1の定めに従い、インスタンス行が存在するファイルのバージョンのデフォルト（そのファイルのヘッダーレコードのDEVICEと同様）となる。SPICE系では以下のとおり：

  ```rnl header
  @DEVICE(name="M*", terminals=["d", "g", "s", "b"]);
  @DEVICE(name="Q*", terminals=["c", "b", "e", "s"]);
  @DEVICE(name="J*", terminals=["d", "g", "s"]);
  @DEVICE(name="Z*", terminals=["d", "g", "s"]);
  @DEVICE(name="D*", terminals=["a", "k"]);
  @DEVICE(name="R*", terminals=["p", "n"]);             /* and one each like it for C, L, V, I, B, F, H, W */
  @DEVICE(name="E*", terminals=["p", "n", "cp", "cn"]);  /* and one each like it for G, S */
  @DEVICE(name="T*", terminals=["p1", "n1", "p2", "n2"]); /* and one like it for O */
  @DEVICE(name="U*", terminals=["a", "b", "ref"])
  ```

  Spectreのインスタンス名は素子文字で始まらないため、デフォルトはインスタンスのマスタである `model` で照合される。Spectreのプリミティブでは以下のとおり：

  ```rnl header
  @DEVICE(name="*", model="resistor", terminals=["p", "n"]);      /* and one each like it for capacitor, inductor, vsource, isource, ccvs, cccs, bsource, port */
  @DEVICE(name="*", model="diode", terminals=["a", "k"]);
  @DEVICE(name="*", model="vcvs", terminals=["p", "n", "cp", "cn"]); /* and one each like it for vccs, relay */
  @DEVICE(name="*", model="tline", terminals=["p1", "n1", "p2", "n2"]);       /* as T in SPICE */
  @DEVICE(name="*", model="transformer", terminals=["p1", "n1", "p2", "n2"])   /* as T in SPICE */
  ```

  - `switch` は各ノードに対応する1つの端子を持ち、Spectreがその位置に番号を振る通りに、共通端子を `t0`、各接点を `t1` から `tn` として命名される。
  - マスタが `model` 文の名前であるモデルカードのインスタンスは、そのモデルのマスタが属するファミリの名前を受け取る。条件 `type`（10.1）のためのその型はSPICEの語で記述される：

  | ファミリ | モデルのマスタ | 端子 | 型 |
  |---|---|---|---|
  | MOS | `bsim1`, `bsim2`, `bsim3`, `bsim3v3`, `bsim4`, `bsim6`, `bsimbulk`, `bsimsoi`, `bsimcmg`, `bsimimg`, `b3soipd`, `mos0`, `mos1`, `mos2`, `mos3`, `mos9`, `mos11`, `mos705`, `mos902`, `mos903`, `psp102`, `psp103`, `psp104`, `pspnqs102`, `pspnqs103`, `ekv`, `hisim`, `hisim2`, `hisimhv`, `hvmos`, `bta_soi`, `ucsd_hvmos`, `hisim_hv`, `utsoi`, `letisoi`, `bsimcmg_va` | `d g s b` | `nmos`、またはモデルの `type` が `p` あるいは `pmos` のとき `pmos` |

  | リレー | `relay` | `p n cp cn` | `sw` |
- **ネットリスト内で定義されたサブサーキット**（includeやlibで取り込まれたライブラリファイル内のものを含む）：ポート名は定義のものであり、ホストの事実である（原則 2.2）。DEVICEはそれを変更しない：そのようなインスタンスに異なる名前で一致するDEVICEは警告を出す。DEVICEが名前を与えるのは端子名を持たない素子、すなわちプリミティブとネットリストが定義を持たないサブサーキット（PDK素子。これに対してはユーザーやLLMがDEVICEを書く）のみである。`terminals` を持たないDEVICEであれば、ネットリスト内で定義されたサブサーキットにも型を与えることができる。
- **名前の個数**：インスタンスのノード数が `terminals` の名前数より多い場合、余分な端子は番号のみを持つ。少ない場合、余分な名前への参照は失敗する。
- **大小文字**：DEVICEが与えた端子名はホストの規則で比較される（6.4）。
- 番号は常に機能し、数字のみではないサブサーキットのポート名や `#:port` も同様である。

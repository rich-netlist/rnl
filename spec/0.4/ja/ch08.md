## 8 有効化

### 8.1 レベルは完全に読み込まれた後に有効になる

- インタプリタはホストネットリスト全体を構文解析し、すべてのレコードを読み込む。その後、各レベルが8.2のフェーズ順に有効になる。
- 1つのレベル内では、文の順序は1.5項目2が定める場合にのみ影響し、名前および参照の解決方法には影響しない（原則 2.9）。
- 2つのレベルのどちらが他方を上書きするかは、テキスト内の出現順ではなくレベルの階層によって決まる（原則 2.9、8.3）。

### 8.2 フェーズ

1. **読み込み**：字句構造、文法、およびシグネチャ。
2. **名前と定義**：`$` 名、`%` 名、およびホスト参照が解決され、DEFINE-SYMBOLとDEFINE-STYLEの定義本体が評価される。
3. **オブジェクト生成**：明示的に書かれたシーンオブジェクト（点、配線、ラベル、バンドル、図形、制約、適用オブジェクト）およびセットが生成され、一般定義の定義本体が展開される。定義本体内のルールは適用オブジェクトのレベルのルールに合流する（9.4）。選択はこの時点では展開されない。
4. **シンボルキュー**：SET-SYMBOLが有効になり、ステップ3のオブジェクトにシンボルを割り当てる。このキュー内のルールの選択は、この時点で初めて各レベルにおいて評価される。
5. **ツリー**：ROUTE-NET、ROUTE-OBJECT、UNROUTE-NET、UNROUTE-OBJECTのルール（10.4、13.7）が各レベルで1回ずつ、パッケージ、上位レベル、このレベルの順に評価される。これらの条件はステップ3の文が作ったツリーを読み取り、互いに他の結果を見ない。これらが作ったツリーはステップ6以降から参照可能になる（10.2）。
6. **1つずつの生成**：選択の結果をオブジェクトとするASとATTACH、選択の結果に取り付けられたTEXT（10.5、13.3）、選択の結果を点とするサイズ指定付きのRECTANGLE・CIRCLE・ELLIPSE（9.2.5）、LINE・ARC・BEZIERのルール、およびCURRENTのルール（10.4）が、同じ順序で各レベルで1回ずつ評価される。
7. **生成オブジェクトへのシンボル割り当て**：新しいオブジェクトに対して同じシンボルキューがもう1度実行され、生成された内容の中のSET-SYMBOL文とルールも使用される（10.5）。ステップ3のオブジェクトのシンボルはステップ4の後で確定している（ツリーと `wired` がそれらから計算されるため；10.2）：生成された内容の中のSET-SYMBOLがそのようなオブジェクトに到達しても効力を持たず、警告が出される。生成は生成前の状態のシンボルを参照する。
   シンボルが確定したこの時点で表明（15.3）が検査される。
8. **ジオメトリ**：PLACE、ORIENT、および制約が解決順序に従って1つずつ取り込まれ、すでに取り込まれたものと競合するものは破棄される（8.5、14.8）。その後、レイアウトが求解される。このステップはピンの位置とシンボルの外接枠を必要とするため（9.2.3）、シンボル割り当ての後に行われる。シンボルを持たない適用オブジェクトに適用されたORIENTはここで失敗する一方、PLACEと制約は適用オブジェクト自身の点をとる（14.1）。位置も制約も持たないオブジェクトはソルバーによって配置され、ソルバーはその位置を書き戻す（14.8）。
9. **スタイルキュー**：SET-STYLEが8.3の2つのティアに従って有効になる。この時点で初めて、シンボルの図形が未指定のまま残したスタイルプロパティや `fill=` の色が、所有元オブジェクトのスタイルから具体的な値を得る。
10. **レンダリング**。

- これらのフェーズは1.5項目4の内部順序である：ある記述は自身のフェーズが始まる前の状態を読み取り、自身の効果も同一フェーズ内の他の記述の効果も含まれない。
- セットはそれを使用するフェーズで評価される（5.2）：同じセットでも、ステップ6で使われるときは生成オブジェクトを含まず、ステップ9で使われるときはそれらを含む。
- 選択条件は、それより前のフェーズで確定した情報のみを読み取る：
  - ホスト情報、オブジェクトの種別、適用オブジェクト、端子上の文として書かれた電流方向、および明示的な配線はステップ3で確定する。CURRENTのルール（ステップ6）とピン上のCURRENT（シンボル確定後）が設定する方向は、スタイルキューや15.2の検査などステップ7以降から参照可能になる。
  - シンボルキュー内の選択は、オブジェクトが使用するシンボルを条件として選択することはできない。
  - 生成ルールはシンボルを参照できる。
- 端子が自身のシンボル内にピンを持っているかはステップ7の後に検査される（7.1）。「`"pin"` 種別のロールにピンを持たない端子を渡した適用」のように、シンボル割り当て後の検査で失敗が判明した文は、それ以前のステップには書かれたとおりに関与しており、それらのステップを再計算することはなく、その時点以降効力を持たなくなる。配線も同じように数えられる（10.2）。
- 求解とレンダリングの方法自体は本標準では規定しない。規定するのはそれらの入力のみである（原則 1）。

### 8.3 外観キュー

- キューは2つある：シンボルキューはSET-SYMBOLを受け取り、スタイルキューはSET-STYLEを受け取る。
- 1つのレベルに対して、各キューは次のグループからこの順序で構成される：
  1. ルートのパッケージのルール：標準パッケージが先、次にヘッダーレコード内のUSE-PACKAGEの他のパッケージ（16.3）。あるパッケージがこのレベルまたは上位レベル（ファイルレベルまたはサブサーキット）でUSE-PACKAGEにより再度使われた場合、代わりにそのUSE-PACKAGEの位置に置かれる（16.2）。
  2. サブサーキットが自身の `#` に割り当てるシンボル、すなわちそのブロックシンボル（シンボルキューのみ；9.2.6）。
  3. 上位レベルのルール（最も外側から内側へ）。
  4. このレベルに書かれたすべてのSET-SYMBOLまたはSET-STYLE文（ルールと個別オブジェクトへの文の双方）。
  5. `scope` によって外部からこのレベルに書かれたSET-SYMBOLまたはSET-STYLE（より外側のレベルのものほど後；2.6）。
- 各グループ内ではテキスト順となる。他のパッケージの内容はそのUSE-PACKAGEの位置に置かれる（16.2）：上位レベルで使われたパッケージはそのレベルと一緒になり、このレベルで使われたパッケージはこのレベルのテキスト内のUSE-PACKAGEの位置に入る。1つずつの生成によって作られたSET-SYMBOLとSET-STYLEは、それを生成したルールのグループ内の、そのルールの位置に属する。
- **2つのティア**：
  - 直接（Direct）：このオブジェクトを直接名指しするSET-SYMBOLおよびSET-STYLE。すなわち、入力がそのハンドル、名前、またはそこへの `::` パスであるもの、あるいはそれをメンバーとして列挙する `{…}` で書かれたセットであるもの（そのセットに名前が付いている場合も含む）。オブジェクトの定義時に書かれたスタイルパラメータ（9.2.5、9.3）も、そのオブジェクトを作る文の位置でSET-STYLEが書かれたかのようにここに数えられる。
  - 引き継ぎまたは選択（Passed on or selected）：メンバーが選択や1つずつの生成を通じて受け取ったもの、所有元オブジェクトが自身のシンボルの図形へ引き継ぐもの（9.2.5）、オブジェクトが自身に取り付けられたテキストへ引き継ぐもの（11.3）、適用オブジェクトが自身のシンボルおよび定義本体内で作られた描画可能オブジェクトへ（さらに入れ子の適用オブジェクトへと下方向に、ただしロールを埋めるメンバーへは引き継がない；12.1項目4）引き継ぐもの。引き継がれた事実は元の文の位置を保持する。
  - 各プロパティ（シンボルキューではシンボル）について、まず直接の事実が考慮され、位置上最後のものが採用される。直接の事実がない場合は引き継ぎまたは選択の事実が考慮され、位置上最後のものが採用される。どちらもない場合、インスタンスは既定のブロックシンボルを取り（9.2.6）、適用オブジェクトは描画されず（12.1）、スタイルプロパティはレンダラのデフォルトを取る（9.3）。位置は上記のキューの順序に従う。
  - これにより、エディタが単一のオブジェクトに対して変更したシンボルやスタイルが、後に書かれたルールによって上書きされることはない。一方、個別に変更されていないオブジェクトに対しては、ルール、パッケージ、およびテーマが引き続き支配する。
- レコードヘッダーの `type` と `author` は順序に影響しない（2.8）。
- シンボルは丸ごと置き換わるが、スタイルはプロパティ単位でマージされる。スタイルを適用することは、それが定義する各プロパティを1回ずつ書くのと同じであるため、`linewidth` のみを定義するスタイルは線幅だけを変更する。
- ルールはそれが書かれたレベルに適用され、自身に書かれた選択の `recursive=true`、またはそれがなければ使用するセットを通じて下位レベルに到達する場合は下位レベルにも適用される（10.1）が、上位レベルには決して適用されない。パッケージのルールはそのUSE-PACKAGEのレベルに書かれたものとして、またルートのパッケージのものはそのファイルのトップレベルで使われたものとして数えられ（10.4、16.2）、毎回そのレベルのオブジェクトのみを見て各レベルで1回ずつ評価される。

### 8.4 キーによる上書き

キーを持つ事実（5.8）はキー単位で互いに上書きし合い、後のものが有効になる（原則 2.9）。上書きは正当な記述方法でありエラーではない。ヒントを出すか否かは実装に委ねられる。PLACEとORIENTは幾何的事実であり、8.5によって解決される（5.8）。

### 8.5 競合

幾何的事実同士は、`{#M1 #M2} @ALIGN("y")`、`#M1 @PLACE(y=0)`、`#M2 @PLACE(y=10)` のように、どの2つをとっても互いに矛盾していなくても全体として解を持たないことがある。どの事実を破棄するかは以下によって決まる。

- **幾何的事実**とは、4つの基本制約（ALIGN、ORDER、DISTRIBUTE、DISTANCE）、向き関係ORIENT-RELATION（14.9）、TABLE（14.11）、PLACEの各座標、TEXTの `dx` と `dy`（13.3；同一軸上ではこれらとPLACEが位置順で置き換え合うため、ここで解決されるわけではない）、およびORIENTである。シンボル（SET-SYMBOL）は含まれない（ジオメトリより前に確定している；8.2）。実装独自の基準（素子同士が重ならない、グリッドなど）も含まれない：それらはソルバー自身の考慮事項であり、言語のすべての記述の後に位置する。記述が素子同士の重なりを強制する場合、それらは重なる。
- **解決の単位**：
  - 1つの基本制約文は1つの単位であり、競合時は全体がまとめて破棄される（ORIENT-RELATIONも同様）。メンバーの一部だけに対して保持されることはない。これは失敗扱いと整合している：基本制約のメンバーは厳格な入力である（7.3）。単一オブジェクトをとるスロットがセットを受け取ってメンバーごとに1回ずつ作用する場合、それぞれの記述が1つの単位となる（5.2.1）。メンバーリストが表す各制約（組み合わせごと（14.1）またはDISTANCEのペアごと（14.5）に1つ）も同様である。1つのTABLEは1つの単位である（14.11）。
  - 1つのPLACEは2つの単位（xに1つ、yに1つ）であり、別々に破棄できる。TEXTの `dx` と `dy` も同様にそれぞれ1つの単位である。それらはまず同一テキストの同一軸上のPLACEと位置順で置き換え合い（13.3）、残ったものが解決に参加する。
  - ORIENTは1つの単位である：このオブジェクトの向きが指定値、またはリスト内の値のいずれかに等しいことを表す（11.2）。ピンのORIENTは、そのオブジェクトの向きが、ピンを書かれた方向または方向のいずれかに向けるものであることを表す。ORIENTがなければ制約はない：ソルバーが向きを選択して書き戻し（14.8）、解を持たないレンダラは `"R0"` で描画する。向きは端子の位置を計算するための8つの値を持つ変数であり、競合検査は向きを直接試すことができ、端子の相対位置へ書き換える必要はない。
  - 一般定義は制約ではない：適用オブジェクトから展開された各事実がそれぞれ独立した単位となり、個別に順序付けられ破棄される。
- **自己矛盾する事実**：各事実はまず単独で検査される。DISTANCEであるオブジェクトから自身への距離を `min=4` とするような（9.5）、単独で解を持たない事実は自己矛盾している：それは失敗し（7.6）、解決には参加しない。単独で解を持つ事実のみが順序付けられて取り込まれる。
- **解決順序**：幾何的事実は1つの順序に並べられる。まず `priority` によって `"high"`、`"normal"`、`"low"` の順に並べ（14.8）、同じ優先度の場合は位置によって後のものを先にする。位置の順序は以下のとおり：
  - レベルとテキスト順：ルートのパッケージ（16.3）、上位レベルの内容、このレベルの文、`scope` で外部からこのレベルに書かれた文（より外側のレベルほど後；2.6）。他のパッケージの内容は、このレベルに最も近いUSE-PACKAGEの位置に置かれる（16.2）。
  - 一般定義から展開された事実はASまたはATTACH文の位置をとり、1つずつ生成された事実はその生成ルールの位置をとる（10.5）。
  - 1つの文が複数の事実を作る場合、展開によるものは定義本体の順序、メンバーごとに1回作用する文によるものはメンバーの順序に従い、PLACEではxがyより先に来る。いずれの場合も後のものが先になる。パイプの各セグメントはそれぞれ独立した記述であり、後のセグメントは後に書かれたものとなる（5.5）：`#R1 @PLACE(0, 0) => @PLACE(5, 5)` の事実は y = 5、x = 5、y = 0、x = 0 の順になり、`#M1 @PLACE(0, 0) => @ORIENT("R90")` ではORIENTがPLACEより先に来る。
- **解決**：事実は解決順序に従って1つずつ取り込まれる。毎回、それまで取り込まれた事実群が解を持つか検査し、解がなければその事実を破棄する。結果は一意である：この順序において辞書式に最大の整合部分集合となる。許容差（11.7）の範囲内でそれらすべてを満たす実数座標と、自由な各向きに対する8値のいずれかが存在するとき、事実群は解を持つ。整数点であることはソルバーの目標にすぎない。
- **制限**：ある種の事実は順番に試さなければならない複数の選択肢のいずれかで成り立つため（向きのリスト（11.2、14.9）や自由な向き）、解の有無の検査には時間がかかる場合がある。したがって実装は、大きな回路で時間がかかりすぎないよう、検査に費やす時間または計算量に適切な制限を設けるべきである。この制限はユーザーが設定できるソルバーのオプションであり（14.8）、ツールが与えるもので、ファイルが与えるものではなく（14.10）、その計測方法や値は本標準では固定しない。ある事実の検査が制限内に終わらなかった場合、その事実は未判定である旨の警告付きで破棄される（7.6）。その場合、結果は上記で定義したものと異なる場合があり、実行ごとに異なる場合もある。制限がない場合、およびどの検査も制限に達しない場合、結果は上記で定義したとおりとなる。
- 取り込まれた事実はすべてソルバーにとってハード制約となり、破棄された事実はそれ以降効力を持たない。優先度 `"disabled"` の事実は順序付けの前に除外される（14.8）。
- 注記：本節が定めるのはどの事実が採用されるかであり、それをどう見つけるかではない。同じ事実群が採用される限り、実装は一連の事実をまとめて検査し解がないときにだけ破棄すべき事実を探してもよく、新しい事実とオブジェクトを共有する事実だけを検査してもよい。
- 求解を行う実装は本節の定めに従って競合を解決しなければならず、その結果は取り込まれたすべての事実を満たさなければならない。求解を行わない実装は明示的なジオメトリのみを描画し、文間の競合を検査することは要求されない（原則 2.4）。
- 破棄は正当な解決であり、ヒントを出す（実装はこれを警告へ引き上げてもよい）。ヒントを出す場合は、破棄された事実と合わせると解を持たなくなり、かつどの事実も省くことができない取り込み済み事実のすべての集合を、各事実を書いた文によって名指しする（7.6）。そのような集合に事実が含まれる文にも、それによって破棄された事実を名指しするヒントを出し、記述者がどの文のせいで効力を失ったか分かるようにする。これらの集合をすべて見つける処理が制限時間内に終わらない場合、ヒントはその一覧が完全ではない旨を示す。`"low"` の事実が破棄されることは想定内であるため、そのヒントは省略してよい（7.6）：実装はそれが競合した事実の集合を列挙しなくてもよく、それらの中の文にヒントを出さなくてもよい。
- 競合は失敗ではない（7.5）。文間の高レベルな意味の矛盾やネットリストとの整合性を検査することは要求されない（原則 2.4）。

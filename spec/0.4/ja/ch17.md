## 17 変更モデル

- RNLは現在の状態のみを記述し、そこに至った編集手順は記述しない：
  - 元に戻す操作や削除操作はなく、削除とはテキストを編集することである；
  - 相対移動はなく、エディタは新しい絶対値を書き出す。
- **誰がどのレコードを変更するか。** ソルバーは `type="generated"` を持つレコードを置き換える。他のツールは、エディタが自身が書いた変更を整理するときや、新しいインポートが前回のインポートの書いたものを置き換えるときのように、`author` が自身であるレコードのみを変更しなければならない。ツールは `author` のない作成済みレコードに触れてはならない（2.8）。
- 後に追記された記述は順に前の記述を上書きする（8.4）。幾何的事実については優先度が先に比較される（8.5）。`type` と `author` は順序に影響しない（8.3）。
- **出力はサブサーキットとともに置く。** ソルバーの出力とユーザーがエディタで行った変更は、そのレベル自身のテキストに書き込まれる：サブサーキットではそれがインクルードファイルにあっても `.subckt … .ends` の内部に、トップレベルでは主ファイルのファイルレベルに置かれる。ソルバーは自身の出力を `priority="high"` 付きでそのレベル自身のテキストの末尾に書き込む。求解の際、`type="generated"` のレコードは解釈から除外され（2.8）、その後にそれらを置き換える（14.8）。ソルバーは自身が下したすべての決定を書き戻さなければならない（14.8）。`scope=` は作成者が外部に書くことを選んだ文のためのものにすぎない（2.6）。読み取り専用ファイルを保存するか否かはツール次第である。
- **Verilog-Aファイル。** モジュール階層レベルには求解すべきものがなく、ソルバーの出力は置かれない。Verilog-Aファイル内でツールが変更するのは、ヘッダーレコードおよびモジュール内の `//` で書かれたブロックシンボルのレコードのみである（2.9）。
- **古くなった解はヒントを出すのみ。** 上位レベルやパッケージが変更されると（例えば主ファイルがシンボルを変えたとき）、ライブラリ内のサブサーキットの解が古くなることがある。古い解も引き続き有効になる。レコードヘッダーの `hash` が現在の入力と一致しないことを見つけたビューアは、再求解を促すヒントを出す（2.8）。
  - ハッシュは継承後のレベルの実際の入力（流れ下って有効になるルール、選ばれたシンボル、パッケージのバージョン、およびソルバーのオプション）から計算され、`type="generated"` のレコードおよびメタデータフィールドは含まない。それはサブサーキット自身のテキストのみからではなく、またファイル単位でもなく、レベル単位で計算される。そうしなければ主ファイルでの変更が見落とされてしまうためである。
  - ハッシュは解釈を変更しない。そのアルゴリズムはツールに属する。値には `"sig1:…"` のようにアルゴリズムを示すタグを付けるべきであり、そのアルゴリズムを知らないツールはそれを比較しない。
  - 注記：一致しないハッシュによって古い解が使われなくなるなら、アルゴリズムが言語の一部となってすべてのツールが同じ方法でそれを計算しなければならなくなり、求解を行わないビューアがそのレベルを描画できなくなってしまう。
  - 番号が例外である：名前のないオブジェクトを作る文が変更されると番号の検査が一致しなくなり、そのレベルが再求解されるまで番号を使う文は効力を失う（5.9）。この検査はそのレベルのテキストとそれが使う定義のテキストのみを覆うため、どのツールも同じ方法で計算でき、古い解の残りの部分は引き続き描画される。
- **生成されたオブジェクト。** ソルバーがルールの生成するオブジェクトを配置・配線したとき、ソルバーはそれらを配線とともに明示的な文として自身のレコードに書き出す。明示的なオブジェクトが優先され、自動補完ルールは同じオブジェクトを再び生成しなくなる（10.5）。それらの定義本体内でローカル名を持たないオブジェクトは番号で参照される（5.9）。
- **ソルバーが作ったものを変更する。** ソルバーが書き出したオブジェクトに付けた名前はそのレコード内でのみ束縛されており、そのレコードはレベルが求解される際に除外される（2.8）。したがって別のレコード内の文がその名前を使うと求解時には何も見つからず、ソルバーはそれを考慮に入れることができない。そのようなオブジェクトを単独で記述するには、エディタは10.5のとおり自身のレコードにそれを手書きし、その変更を追加する（`%g_r4 = $GROUND_STUB @ATTACH #R4:2; %g_r4::g @PLACE(30, -4, priority="high")` など）：スタブの配線がピンを配線済みにするため自動補完はそれをスキップし、次回の求解ではそのオブジェクトを書き出さなくなる。それまでの間は、ソルバーのレコード内のオブジェクトもあわせて描画される。変更対象のオブジェクトがポートタグなど生成された適用オブジェクト自身である場合、ホストオブジェクトからの選択（`&out @SELECT-ANCESTOR-USAGE $IO_PORT => @PLACE(40, 20, priority="high")` など）は求解時にも描画時にもそれに到達する。適用オブジェクトのローカルオブジェクトはその適用オブジェクトを通じては選択できず、名前によるかそのレベルのオブジェクトとしてのみ選択できる（9.4）。
- レコードヘッダーのフィールドはそのレコード内のすべての文に適用される（2.8）。
- **例：エディタでの変更。** 以下はホストのコメント接頭辞を含む完全な断片である。ヘッダーレコードの後、設計者が最初のレコードを書き、ソルバーが2番目のレコードを書き、ユーザーがエディタでVINを左へドラッグしたことでエディタが3番目のレコードを追記した：

  ```spice
  * Common-source stage
  * @RNL(type="header") { @VERSION("0.4"); @USE-PACKAGE(name="rnl-std-all", version="0.4")}
  .model nch nmos level=1
  M1 out in 0 0 nch W=4u L=1u
  RD vdd out 5k
  VDD vdd 0 1.8
  VIN in 0 DC 0.6 AC 1
  * @RNL {
  *   {#RD #M1} @ALIGN("x");
  *   #M1 #RD @DISTANCE("bottom-to-top", min=2);
  *   &vdd @ADD-TO $SUPPLY_NET_SET
  * }
  * @RNL(type="generated", priority="high", author="rnl-solver 0.3", hash="sig1:5be1c09a") {
  *   #M1 @PLACE(10, 0); #RD @PLACE(10, 8); #VIN @PLACE(0, -2); #VDD @PLACE(20, 4)
  * }
  * @RNL(author="rnl-editor 0.1") { #VIN @PLACE(x=-4, priority="high")}
  .end
  ```

  - ドラッグ操作はソルバーのレコードの後に優先度 `"high"` を持つ新しいレコードとして追記される。両者ともhighであるため後のものが採用され、ソルバーが書いたxはヒント付きで破棄される（8.5）。以降そのレベルが再求解されるたびに、新しいxが固定位置となる（14.8）。
  - 設計者のレコード内に書き込んでも機能しない。そこにある文はデフォルトで `"normal"` でありソルバーの `"high"` を上書きできない。また `"high"` として書いても、ソルバーのレコードの方が後に来るため、同じ優先度内では後の事実が採用されてやはり負ける。この誤りはエラーではなく、解決に関するヒントを出すのみである。その位置が有効になるのは次にレベルが求解されるとき（設計者の文が制約の1つになるとき）であり、それまでは図面は変化しない。
  - 位置指定のパラメータは名前指定のパラメータより前に来る（4.2項目9）：`@PLACE(-4, -2, priority="high")` は `@PLACE(x=-4, y=-2, priority="high")` と同じであり、`@PLACE(x=-4, -2)` はエラーである。
  - 設計者が書いたもの（シンボルの変更、改名、制約の削除）を変えるには、設計者のレコードを直接編集する。ソルバーのレコードには手を加えず、次にレベルが求解されるときに丸ごと置き換えられる。
- 文を一時的に無効にするには `/* … */` で囲む。
- **ラウンドトリップ。** RNLは、任意のエクスポートと再インポートの後に図面が同一に保たれることを保証しない（原則 1）。エクスポータは座標レベルで厳密なRNLを書き出す選択をしてもよい（原則 3）。本バージョンは厳密なRNLが何であるかも、ラウンドトリップの基準も定義しない。

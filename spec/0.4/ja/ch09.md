## 9 定義

### 9.1 共通規則

- 定義には3つの種類がある：DEFINE-SYMBOLはシンボルを作り、DEFINE-STYLEはスタイルを作り、DEFINEは一般定義を作る。シンボルとスタイルは個別定義である（1.4.4）。いずれも定義本体としてセットをとり、定義本体内の文は1つずつ許容的である（7.3）。
- 定義はオブジェクトである。`$name =` または `%name =` で名前が付けられ（6.6）、キーワードがそのために定めたスロットにオブジェクトとして渡される（5.6）。
- 定義をコミットしてもその名前が公開されるだけである。定義それ自体は描画されず、使用されたときにのみ効果を発揮する：シンボルはSET-SYMBOLが割り当てたとき、スタイルはSET-STYLEが割り当てたとき、一般定義はASまたはATTACHが適用したときである。
- 文の中に入れ子にされずレコードのメンバーとして直接書かれ、かつ名前を持たない定義は決して使用されず、警告を出す。文の中に入れ子にされた無名定義は通常どおり使用される。
- **インクルード（取り込み）**：DEFINE-SYMBOLまたはDEFINE-STYLEの定義本体内に同種の定義への参照を書くと、その位置にその定義の内容が取り込まれる。keyを持つメンバーは後に書かれたものが前のものを上書きし、keyを持たないメンバーは累積する。`base=` パラメータは存在しない。他のインクルードやシンボル定義本体内に描かれる適用オブジェクトのシンボルを経由するものも含め（9.2.7）、内容を作成中の定義自身へと戻るインクルードは循環（サイクル）を閉じる：そのインクルードは失敗し、診断はその連鎖を列挙し、定義本体の残りの部分は有効になる。定義の内容はその定義自身を起点として作られるため、`$A` が `$B` を取り込み `$B` が `$A` を取り込む場合、`$A` は自身の内容と `$A` を除いた `$B` の内容になり、`$B` はその逆になる。
- 一般定義同士は互いに取り込むことはなく、それぞれの定義本体内でASとATTACHによって組み合わされる。派生と拡張も同じ方法で行われ、継承関係は存在しない（9.4）。

### 9.2 シンボル：DEFINE-SYMBOL

#### 9.2.1 評価

- シンボルは値である：その定義本体は定義された場所で評価され、内部の文はシンボルのローカル座標でピンと図形を生成する。これらが定義の内容となり、シーンにはコミットされない。
- メンバーの順序が描画順となる。
- ローカル座標はシーンと同じ単位と軸（xが右向き、yが上向き）を持ち、(0, 0) がシンボルの原点である（6.5）。本バージョンに拡大・縮小はない（11.7）。定義本体内の点は両軸とも数値を指定しなければならず、`_` は使えない。

#### 9.2.2 定義本体内の文

- 定義本体に含めることができるのは、図形、ピン、名前付きのローカル点（`%tip = (0, 0.7)` など）、他のシンボルの取り込み、描画目的のみで適用された適用オブジェクト（ATTACHまたはAS；9.4）とそれらに対するSET-SYMBOLおよびORIENT（9.2.7）、ならびに所有元オブジェクト `?`（このシンボルで描画されるオブジェクト）に取り付けられたTEXTとそれを配置するPLACE（13.3）のみである。
- それ以外の文は失敗して破棄され（定義本体は許容的）、ホスト参照も同様に失敗する。
- ピンはDEFINE-SYMBOLの定義本体内にのみ書くことができる。図形はシーン座標でシーン内に書くこともでき、その場合は注釈（annotation）となる（13.4）。

#### 9.2.3 パラメータ

- `box=[x1, y1, x2, y2]`：ローカル座標で軸平行なシンボルの外接枠。インスタンスの向きに合わせて変換される。言語自体はこれを使用しないが、通常はビューアが選択枠として、またソルバーがシンボル同士を離すための境界として使用する。具体的な使い方は実装に委ねられる。書かれていない場合は、テキストを除くシンボル内のすべての図形の外接枠となる（テキストの大きさはフォントとレンダラに依存するため）。

#### 9.2.4 ピン

```rnl
$RES_BOX = @DEFINE-SYMBOL {
  %p = (0, 3) @PIN(terminal=1, label="P", direction="up");
  %n = (0, -3) @PIN(terminal=2, label="N", direction="down");
  @LINE {%p (0, 1.5)};
  @LINE {(0, -1.5) %n};
  (0, 0) @RECTANGLE(width=1.2, height=3)
}
```

- **ピンはシンボルのオブジェクトである**：各PIN文は1つのピン（端子を束縛し得る1点）を作る。定義本体内では、上のリード線が `%p` で始まり `%n` で終わっているように、名前付きのピンを点として使用できる。そのローカル名は、`#R1::p` のようにそのシンボルで描画される各オブジェクトのサブオブジェクト名にもなる（6.5）。ローカル名を持たないピンは名前がなく、束縛する端子を通じて到達する（5.2.4）。
- **名前は1度だけ束縛される**：取り込まれたシンボルのピンを含め、ピン名は1つのシンボル内で1度だけ束縛される（9.2.7、6.6）。2つのピンに同じ名前を束縛するとエラーになる。ピン同士が置き換わることはなく、すべてのPIN文がそれぞれ固有のピンを作る。
- ピンは整数点上に配置すべきである（11.7）：インスタンスが整数点に配置されたとき、そのピンとそこに接続される配線も整数点に落ちるようにするためである。それ以外の位置でもエラーではないが、実装はヒントを出してもよい。シンボル内の図形はこの対象ではない。
- `terminal=`：ピンが束縛する端子（名前または番号）。これらがシンボルの端子名である。SET-SYMBOLはこれらをオブジェクトの端子に照合する（11.3）：名前はDEVICE（6.12）またはサブサーキットのポート名で与えられたその名前の端子へ、番号はその位置の端子へ対応付ける。端子を持たない適用オブジェクトでは、名前がその定義内の同名ロールに照合され、番号はどのロールも束縛しない（11.3、12.1）。`terminal=` は省略してもよい：その場合ピンは何も束縛せず、スイッチの接点を図形として描くときのように描画専用となる。
- **1つの端子に対する複数のピン**：大きなブロックの両側に電源ピンを置く場合のように、1つの端子を複数のピンで描画してよい。それぞれが独立したピンであり自身の名前で到達でき、ピンの代わりに端子が書かれた箇所では最後に書かれたピンを代表する（5.2.4）。各ピンはそれぞれ独立に配線済みか否かが判定される（10.2）。
- **バスピン**：`terminal=` には配列を渡すことができ、サブサーキットのバスポートなど複数の端子に対して1つのピンを作れる：`(-4, 0) @PIN(terminal=["D<3>", "D<2>", "D<1>", "D<0>"], label="D<3:0>", direction="left")`。配列は少なくとも1つの要素を持ち、各要素は番号または名前である。パラメータ内の文字列は添字を展開しないため（6.11）、名前は1つずつ列挙する。
  - これらの端子はすべてこのピンに描画される：そのいずれか1つに接続された配線または制約はこのピンに接続され、このピンは配線済みとなる（10.2）。
  - 同じ座標に複数のピンを置いても代用にはならない：座標が等しいだけでは接続されず（13.1）、配線はそのうちの1つのピンにしか接続されないため、残りは `wired=false` のままとなり、標準パッケージの自動補完ルールがそれらにラベルやグラウンドを追加してしまう。
- `label=`：ピンに表示されるテキスト。表示専用であり名前ではない：ピンは `%p = (0, 3) @PIN(…)` の `p` のようにシンボル内で束縛された名前で `#R1::p` のように参照し、端子は `#R1:1` のように端子名で参照する。`label="P"` を書いても `#R1::P` や `#R1:P` が生まれるわけではない（6.4、6.5）。これを表示するか否かおよびどこに表示するかはビューアに委ねられる。`\overline{CS}` のようなテキストマークアップを使用できる（13.6）。
- **描画されない端子はピンを持たない。** ピンを持たない端子は描画上の意味を持たない：それに接続する配線や制約は失敗する（「シンボルにこの端子のピンがない」）。また自動補完でも選択されない（10.1）。ピンを持つ端子を隠す記法はない。バルクを省くにはバルクピンのない3端子シンボルを使用する。
- `direction=`：配線がそのピンから出ていく方向：`"right"`、`"up"`、`"left"`、または `"down"`。シンボルのローカル座標で書かれ、向きに合わせて回転・反転する（11.2）。これは自動配線がピンから出る方向、端子における電流の流れる向き（15.2）、あるいは向きを選ぶ際の参考といったソルバーやビューアへのヒントであり、これ自体は制約ではなく競合に参加しない。ただしピンに対して書かれたORIENTおよびORIENT-RELATIONはこれを制約する（11.2、14.9）。省略してもよく、その場合ピンは方向を持たない：実装は図形から方向を推測してヒントとしてよいが、そのピンに対するORIENTおよびORIENT-RELATIONは失敗する。
- リード長（lead length）パラメータはない：リード線はシンボル内でLINEによって描画する。
- 電気的種別（electrical type）はない：ピンにも端子にも入力や出力といったパラメータはなく、ネットリストにもそのような情報はない。必要な場合はユーザーが意味定義の適用オブジェクトで表現する。Virtuosoなどのツールへのエクスポータは独自の設定により一般定義を電気的種別に対応付ける。
- ピンは単なる点である：リード線を描くか否かはシンボル次第であり、ピンの点をどう示すか（小さな四角、点、または無表示）はビューア次第である。したがってリード線のないピンに特別な記法は不要であり、LINEを書かずにPINだけを書けばよい。例えば、エディタが隠しているバルクピンに配線が接続されている図面は、バルクのPINを保持しつつバルクのリード線を描かないシンボルとしてインポートされる。標準パッケージのものを含め通常のシンボルはリード線を描く。

#### 9.2.5 図形

位置は点オブジェクト、スカラー値はパラメータである。表中の *point* は任意の点オブジェクトを表す。

| 形式 | 意味 |
|---|---|
| `@LINE {point point …}` | 2点は線分、3点以上は折れ線。最後の点が最初の点と同じ位置にある場合、図形は閉じられ、継ぎ目は角（join）として描画される |
| `@RECTANGLE {point point}` | 矩形。2点は対角の頂点（順序不問） |
| `(0, 0) @RECTANGLE(width=4, height=2)` | 矩形。点は中心、`width` と `height` は幅と高さ |
| `@CIRCLE {point point}` | 円。1点目は中心、2点目は円周上の点 |
| `(0, 0) @CIRCLE(radius=1)` | 円。点は中心 |
| `@ELLIPSE {point point}` | 楕円。2点は外接枠の対角の頂点 |
| `(0, 0) @ELLIPSE(width=4, height=2)` | 楕円。点は中心、`width` と `height` は外接枠の幅と高さ |
| `@ARC {point point point}` | 1点目から2点目を通って3点目に至る円弧 |
| `@BEZIER {point point point point …}` | 3n+1個の点による3次ベジェ曲線：始点、および各セグメントにつき2つの制御点と終点。隣接するセグメントは終点を共有する |
| `(1, 0) @TEXT("…")` | 点に取り付けられたテキスト：シンボルの固定テキストであり、インスタンスごとに変えることはできない |
| `? @TEXT("${name}", key="name") => @PLACE(1, 0)` | 所有元オブジェクト（このシンボルで描画されるオブジェクト）に取り付けられたテキストであり、その属性を読み取る。keyが `name` なのでM1では `#M1::name` となり、シーン内の同じkeyのテキストがパラメータ単位で上書きする（13.3） |

- **2つの形式**：RECTANGLE、CIRCLE、ELLIPSEはサイズパラメータが書かれているか否かで区別される。サイズ指定（RECTANGLEとELLIPSEでは `width` と `height`、CIRCLEでは `radius`）がある場合、オブジェクトスロットは中心である1点を受け取り、セットが渡された場合は点ごとに1つの図形を描く（5.2.1）。`# @SELECT-PIN => @RECTANGLE(width=0.4, height=0.4, fill="linecolor")` のように選択の結果が渡された場合は、TEXTと同様に8.2のステップ6で1つずつ生成されるためシンボルを参照できる。2点指定で書かれた図形は選択を受け取れない（10.4）：選択がいくつの点を返すか読み込み時には不明であり、この形式はちょうど2点をとるためである。サイズ指定がない場合、オブジェクトスロットは2点からなるセットを受け取り、点数が異なれば図形は失敗する。サイズを片方だけ書いた場合はパラメータ誤りとなり図形は失敗する。2点指定形式では点はオブジェクトであるため、名前を付けたりピンの位置にしたりでき、図形はその点に追従する。
- 矩形と楕円は軸平行である。傾いた矩形は閉じたLINEで描く。
- **塗りつぶし**：TEXT以外のすべての図形は `fill=` をとる。開いたLINE、ARC、BEZIERは、最後の点から最初の点へ引いた直線で閉じた領域として塗りつぶされ、この閉じる直線自体は描画（ストローク）されない。塗りつぶされたARCは弦と弧で囲まれた弓形となる。MOSのゲート、矢印の先端、接続点の黒丸のように、枠線なしで塗りつぶす図形は `fill="linecolor", linestyle="none"` と書く（9.3）。
- **矢尻**：LINE、ARC、BEZIERは `arrow=` をとる：`"none"`（デフォルト）、`"start"`、`"end"`、または `"both"`（`@LINE(arrow="end") {%from %to}` など）。先端は始点または終点にあり、その端における線の向きを指す：LINEでは最初または最後の線分、ARCでは端点における円弧の接線、BEZIERでは隣接する制御点から端点へ向かう直線（両者が一致する場合は一致しない次の点）。矢尻の長さは `arrowsize`（9.3）で指定され、形状は実装に委ねられる。端点は点オブジェクトであるため、制約で点が動けば矢尻も任意の角度で追従する（点に描画される矢印の適用オブジェクトが8方向しか持たないのとは異なる）。WIREは `arrow=` をとらない。
- **スタイルパラメータ**：図形はスタイルプロパティを直接パラメータとしてとることができる（9.3）：LINE、ARC、BEZIERは `linecolor`、`linestyle`、`linewidth`、`cap`、`join`、`fillcolor`、`arrowsize` をとり、RECTANGLE、CIRCLE、ELLIPSEは最初の6つをとり、TEXTは `textcolor`、`size`、`font`、`bold`、`italic`、`textvisible` をとる。直接書かれたプロパティはその図形の直接スタイルとなり、所有元オブジェクトから引き継がれるスタイルより優先される（8.3）ため、シンボル内で書いた色はテーマを変えても変化しない。書かれていないプロパティは所有元オブジェクトのスタイルから補われるため、テーマ変更時にシンボルを書き換える必要がない。塗りつぶしは `fill=` で指定する：`"none"`（デフォルト）、`"linecolor"`（`linecolor` の色）、または `"fillcolor"`（`fillcolor` の色）。
- **提供されないもの**：SVGパス文字列、POLYGON（閉じたLINEを使う）、独立した矢印図形（線端の矢尻には上記を、それ以外では塗りつぶした閉じたLINEまたは点に描画する矢印適用オブジェクトを使う；9.2.7）、角丸矩形、楕円弧（BEZIERで近似する）、および画像。
- **テキスト**：TEXTはさらに `size=`（フォントサイズ；11.7）、`halign=`（水平揃え：`"start"`（デフォルト）、`"middle"`、`"end"`）、`valign=`（垂直揃え：`"baseline"`（デフォルト）、`"top"`、`"middle"`、`"bottom"`）、および `rotate=`（0、90、180、または270；デフォルト0）を持つ。シンボル定義本体内では、`?` に取り付けられたTEXTは所有元オブジェクトの属性を参照し、点に取り付けられたものは固定テキストとなる。シーン内では、TEXTは取り付け先に応じて注釈またはラベルとなる（13.3、13.4）。テキストマークアップは13.6で説明する。
- **ベースライン**：`valign="baseline"` の場合、アンカー（anchor）は1行目のベースライン上にあり、後続行は下方向へ進む（SVG、PostScript、および大半のエディタと同様）。`"top"`、`"middle"`、`"bottom"` はテキストボックス全体を揃える。ベースラインがデフォルトである。
- **テキストの向き**：アンカーはテキスト自身の位置である（13.3）。テキストボックスは `halign` と `valign` に従ってアンカーの横に配置され、アンカーを中心に反時計回りに `rotate` 度（`30` など任意の数値）回転する。シンボル内のテキストはさらにインスタンスの向き（回転と鏡像反転の双方）で変換される。デフォルトである `upright=true` では、ボックス内の文字は正立して読めるように保たれる：水平テキストは左から右へ、垂直テキストは下から上へ読み、字形（グリフ）は決して鏡像反転されない。向き変換後の最終角度が90度より大きく270度以下のテキストは、アンカーを中心に180度回転される。したがって `rotate=180` は0として、270は90として表示され、テキストボックスはアンカーの反対側に移る。インスタンスが鏡像反転されたとき、アンカーは通常どおり鏡像反転され、テキストボックスも鏡像反転の方向においてアンカーの反対側へ移動するが、文字自体は反転しない。これはすべての揃え方に当てはまる：`start` と `end` が入れ替わり、`top` と `bottom` も入れ替わる。`valign="baseline"` のテキストも同様に回転され、アンカーの上に立っていた分だけアンカーの下にぶら下がる。`fix_rotate=true` のテキストは文字の向きを保持し、ボックスの側だけがインスタンスの向きに従う（13.3）。`upright=false` の場合、テキストは読みやすさのために反転されることがなく、文字は鏡像字形を含めて回転と鏡像反転にそのまま従う（`→` のようにテキストで書いた矢印などの記号に適する）。この2つは組み合わさる：`fix_rotate` が最終角度を決め（シーンでは `rotate`、そうでなければオブジェクトとともに変換された `rotate`（鏡像反転で符号が反転））、`upright` がその角度を読むために180度回すかどうかを決める。`fix_rotate=true` のテキストも決して鏡像反転されない。例えばNMOSの名前は (1.5, 1.5) にアンカーを持ち `halign="start"` で右へ伸びるが、`"MY"` ではアンカーが (−1.5, 1.5) に移りテキストは本体から離れて左へ伸び、`"R90"` ではアンカーが (−1.5, 1.5) に移りテキストは下から上へ縦に走る。シーン内のテキストはインスタンスとともに回転しない。
- **ラベルを縦1列に配置**：シンボルが `?` に取り付けたテキストのうち、同じx座標を持ち、同じ `halign`、`valign`、`rotate`、`fix_rotate`、`upright` を持ち、かつ内容が空でないものは、上から下へ読む縦1列（column）をなす（抵抗の名前とその下の値など）。オブジェクトの向きによって縦1列が逆さま（`"MX"`、`"R180"`）または右から左へ読む横向き（`"R270"`、`"MXR90"`）になる場合、テキスト同士が位置を入れ替え、最初のものが最後の位置に入るなどして、その向きでも上から下・左から右の順で読めるようにする。ボックス上の名前と中央の式のように揃え方が異なるテキスト同士は列をなさず、シーンから位置が与えられたテキスト（13.3）もこれに加わらない。

#### 9.2.6 ブロックシンボル

サブサーキット `.subckt ota5t … .ends` の内部に記述する：

```rnl subckt
%ota5t = @DEFINE-SYMBOL(box=[-4, -4, 4, 4]) {
  (-4, 1) @PIN(terminal="inp");
  (-4, -1) @PIN(terminal="inn");
  (4, 0) @PIN(terminal="out");
  @LINE {(-4, -4) (-4, 4) (4, 0) (-4, -4)};
  ? @TEXT("${name}", key="name") => @PLACE(-1, 0)
};
# @SET-SYMBOL %ota5t
```

- サブサーキットが自身の `#` に割り当てるシンボルは、そのサブサーキットがどこでインスタンス化されても適用されるインスタンスのデフォルト外観、すなわちブロックシンボル（block symbol）である。ピンは名前によってサブサーキットのポートに対応する。
- これは定義が下方向にのみ有効になるという原則 2.5の例外であり、そのサブサーキットをインスタンス化するレベルへ適用される。
- サブサーキットのバスポートはネットリスト内ではすでに単一ポートに分割されているが（6.11）、ブロックシンボルではバスピンを用いて1つとして描画する（9.2.4）。
- シンボルキューにおいて、ブロックシンボルはルートのパッケージのルールの後、各レベルのルール（レベル内で使われるパッケージを含む）の前に位置するため、上位レベルからルールや個別インスタンスへのSET-SYMBOLで置き換えることができる（8.3）。
- ファイルレベルをインスタンス化するインスタンスは存在しないため、ファイルレベルに `# @SET-SYMBOL` を書いても効力を持たない。
- Verilog-Aのモジュールも同様に、Verilog-Aファイル内のモジュールに `# @SET-SYMBOL` を書くことでブロックシンボルを与える。そのピンは名前によってモジュールのポートに対応し、ベクタポートは各ビットごとに1つの端子に対応する（2.9）。
- **既定のブロックシンボル。** ルール・文・ブロックシンボルのいずれもシンボルを与えなかったインスタンスは、その端子から作られる既定のブロックシンボルで描画される：
  - **ピン。** 端子ごとに1つのピンを持つ。ファイルが読み込むサブサーキットまたはモジュール（2.9）のインスタンスでは、ピンは定義の順序でのポートであり、各ピンはそのポートの名前で名付けられる（例：`terminal="inp"`）。それ以外のインスタンス、例えば定義がファイルに読み込まれないセルや、どのルールでも種別を判別できない素子のインスタンスでは、ピンはその行上のノードであり、各ピンはその番号で名付けられる（例：`terminal=1`）。ピンの前半は左側、残りは右側に置かれ、ピン数が奇数のときは左側が1つ多い。各ピンは箱の内側に、そのポートの名前、なければその端子の名前（6.12）、それもなければその番号でラベル付けされる。
  - **箱。** 箱は、一辺の長さが左側のピン数の2倍（ただし最小2）の正方形で、その中心がシンボルの原点である。ピンは2間隔で並び、箱の外側を向く：左側のピンは上の角から1下がった位置から下へ並び、右側のピンはその辺の中央に揃えて並ぶ。したがって端子が1つのインスタンスは一辺2の箱を持ち、ピンは左辺の中央にある。端子が3つのものは一辺4の箱で、ピンは (−2, 1)、(−2, −1)、(2, 0) にある。すべてのピンは整数単位上にある。
  - **テキスト。** 箱の上にインスタンスの名前（`key="name"`）、下に `${model}`（`key="model"`）、すなわちサブサーキットまたはモデルの名前（13.6）が置かれる。
  - **キュー内の位置。** シンボルキュー全体（8.3）の後、ブロックシンボルのグループの外に位置する。したがってインスタンスにシンボルを与えるルールや文はこれを置き換え、そのサブサーキットのブロックシンボルも同様である。`drawn` に対してはシンボルとして数えられ、`symbol=` には一致しない（10.1）。
  - こうして、すべてのインスタンスはシンボルを持ち、与えられたシンボルが省く場合を除いて、各端子に対応するピンを持つ（9.2.4）。
- サブサーキットが複数の `# @SET-SYMBOL` 文を持つ場合、それらはシンボルキューの同じグループ内でテキスト順に並び、後のものが有効になる（8.3）。実装は警告を出してもよい。

#### 9.2.7 変種とフラグメント

```rnl
$NMOS_BULK = @DEFINE-SYMBOL(box=[-3, -3, 2, 3]) {
  $NMOS;
  %b = (1, 0) @PIN(terminal=4, label="B", direction="right");
  @LINE {(0, 0) %b}
}
```

- 定義本体内で別のシンボルを取り込んでから追加を行うと変種を作れる：ピンと図形は累積し、取り込まれたシンボルのピン名も変種の名前として数えられる（9.2.4）。ピンを移動したい場合は、標準パッケージが行っているように共通部分をフラグメントに分け、各シンボルでピンを書く。
- そのレベル内でのみ使うフラグメントは `%MOS_CHANNEL = @DEFINE-SYMBOL {…}` のように `%` で命名し、別のシンボル定義本体が `%MOS_CHANNEL;` のように取り込む。
- 図形にはkeyがないため取り込みは追加のみを行い、取り込んだ図形を削除することはできない。描画要素を減らすには別のシンボルを定義する：共通部分をフラグメントに分け、各シンボルに必要な部分だけを取り込む（`$NMOS3 = @DEFINE-SYMBOL {%MOS_BODY}` と `$NMOS_4TERM = @DEFINE-SYMBOL {%MOS_BODY; %BULK}` など）。
- **定義本体内の適用オブジェクト**：矢尻のように異なる位置や向きで必要となる図形は、点に描画される適用オブジェクトとして記述する：

  ```rnl
  $ARROWHEAD = @DEFINE(roles=[["p", "point"]]) {};
  $ARROWHEAD_SYM = @DEFINE-SYMBOL {
    @LINE(fill="linecolor", linestyle="none") {(0.4, 0) (-0.4, 0.3) (-0.4, -0.3) (0.4, 0)}
  };
  $ISRC_DOWN = @DEFINE-SYMBOL {
    (0, 3) @PIN(terminal=1, direction="up");
    (0, -3) @PIN(terminal=2, direction="down");
    @LINE {(0, 3) (0, 1.5)};
    @LINE {(0, -1.5) (0, -3)};
    (0, 0) @CIRCLE(radius=1.5);
    @LINE {(0, 0.9) (0, -0.5)};
    $ARROWHEAD @ATTACH (0, -0.6) => @SET-SYMBOL $ARROWHEAD_SYM => @ORIENT("R270")
  }
  ```

  - 第1ロールには定義本体内のローカル座標の点が入る。適用オブジェクトはその点に自身のシンボルで描画され、その点の周りに自身の向きで回転し、その後囲むシンボル全体とともに変換される。入れ子の適用オブジェクトの変換は外側から順に合成されるため、矢尻は素子とともに向きを変える。
  - 描画専用：外部のルールはシンボル定義本体の内部を見ることができないため、シンボルは定義本体内でSET-SYMBOLにより割り当てる。これを持たない適用オブジェクトは描画されず、警告が出る。シンボル内では一般定義の定義本体は展開されず、制約や配線は意味を持たない。ここでのORIENTはシンボルの内部データであり、競合に参加せず優先度も持たない。
  - ここでのSET-SYMBOLが、取り込みや他のこのような適用オブジェクトを通じて現在作成中のシンボル自身に戻る場合、取り込みと同様に循環を閉じる（9.1）：そのSET-SYMBOLは失敗してその適用オブジェクトは描画されず、定義本体の残りは有効になる。
  - 第1ロールを埋める点に適用オブジェクトを描画する振る舞いは、ソルバーがレイアウトを行わないシンボル定義本体内でのみ成り立つ。シーン内では同じ記法が自身の点を持つ適用オブジェクトを作り（12.1項目5）、ルールでシンボルを割り当てることができる。ハウススタイルパッケージのルールはシンボル内部には届かない。
- ピン名と数式：ピン名を表示するか否かはビューア次第である（9.2.4）。数式は属性を参照する単なるTEXTであり（13.6）、特別な規則はない。テキストマークアップは13.6で説明する。

#### 9.2.8 シンボルとオブジェクトの照合

シンボルは素子用と適用オブジェクト用に分かれているわけではない。あるシンボルをオブジェクトに使えるかは、そのピンがそのオブジェクトの端子に一致するかで決まる。

- **シンボルを持たないインスタンス。** シンボルを持たないインスタンスは存在しない：文もルールもインスタンスにシンボルを与えなかった場合、それは既定のブロックシンボル（9.2.6）を持ち、各端子に対応するピンを備え、他のインスタンスと同様に描画され求解される。モデルカードが読み込まれなかったトランジスタに対して標準パッケージが行うように、種別を判別できない素子を誤った素子として描画するくらいならシンボルを与えないでおくという判断をパッケージが行うこともある。その場合、その素子は各ノードに対応するピンを持つ箱として描画される。

### 9.3 スタイル：DEFINE-STYLE

```rnl
$ink = @DEFINE-STYLE(linecolor="#202020", textcolor="#202020", fillcolor="#ffffff", size=1.2) {};
$accent = @DEFINE-STYLE(linecolor="#1f4fd8", linestyle="bold") {$ink};
$shade = @DEFINE-STYLE(fillcolor="#1f4fd833") {}
```

- 括弧内のパラメータはそのスタイル自身のプロパティであり、最後に有効になる。セット内では他のスタイルのみを参照でき、その位置にそれらのプロパティが取り込まれ、後のものが前のものを上書きする。ベーススタイルのないスタイルは `{}` と書く。
- スタイルはSET-STYLEが割り当てたときにのみ有効になる（11.3）。同じプロパティは図形、TEXT、WIREのパラメータとして直接書くこともでき（9.2.5、13.1）、値は8.3の2つのティアで採用される。
- スタイルが定めるのは線種・色のみである：位置、向き、形状（シンボルや図形の点）、およびテキストの内容はスタイルの一部ではない。
- **プロパティ**：

| グループ | プロパティ | 値 |
|---|---|---|
| 線 | `linecolor` | 色。`fill="linecolor"` の色にも使われる |
| | `linestyle` | `"solid"`（デフォルト）、`"dashed"`、`"dotted"`、`"dash-dot"`、`"double"`（2本の平行実線）、`"bold"`、`"none"`（線なし） |
| | `linewidth` | 座標単位での線幅（11.7）。`0` は拡大率によらず一定の細さのヘアラインであり、デフォルト値 |
| | `cap` | 線端の形状：`"butt"`、`"round"`、`"square"` |
| | `join` | 角の形状：`"miter"`、`"round"`、`"bevel"` |
| 塗り | `fillcolor` | `fill="fillcolor"` の色 |
| テキスト | `textcolor` | テキストの文字色。未指定時は `linecolor` |
| | `size` | 座標単位での文字サイズ（11.7） |
| | `font` | フォント名（ヒントにすぎない。このフォントを持たないビューアは自身のフォントを使う） |
| | `bold`、`italic` | テキスト全体の太字または斜体（`true` または `false`）。マークアップ `\textbf` と `\textit` で部分的に適用することもできる（13.6） |
| | `textvisible` | 文字表示可否（textvisible）：テキストを表示するか否か（`true`（デフォルト）または `false`）。`false` のテキストは描画されず、領域も占有せず、ピックもできない（衝突判定、シンボルの外接枠、9.2.5の縦1列から除外される）。内容、key、位置、属性参照は維持され通常どおり評価される。ビューアは非表示テキストを表示する機能を提供してもよい。ラベルを隠すパッケージはスタイルを定義してそれを与える（`$hidden = @DEFINE-STYLE(textvisible=false) {};` と `# @SELECT-LABEL(recursive=true) => @SET-STYLE $hidden`）。単一のテキストに直接指定することもできる（`#M1 @TEXT("note", key="memo", textvisible=false)`） |
| その他 | `arrowsize` | 座標単位での線端の矢尻の長さ（9.2.5） |

- 線には色、線種、幅、線端、角の5つのプロパティしかない。`"bold"` は線幅の2倍（幅が0ならヘアラインの2倍）を描画する。破線の長さや間隔、二重線の間隔は線幅に比例して実装が決める。将来の言語バージョンで `linestyle` に値が追加される場合がある（16.1）。
- `"none"` は線を描かず、線端の矢尻も描かない（矢尻は線に属するため；9.2.5）。`fill="linecolor"` は依然として `linecolor` の色をとるため、枠線なしで塗りつぶす図形は `fill="linecolor", linestyle="none"` と書き、その色は引き続きテーマ変更に追従する。配線と図形の双方がこれをとることができる。これを指定した配線は見えない配線になるが、依然として配線である（13.1）。
- **色**はCSSの16進数表記で書く：`"#RRGGBB"` または `"#RRGGBBAA"`、あるいは短縮形の `"#RGB"` と `"#RGBA"`。アルファ値は末尾に来る：`00` が完全透明、`FF` が不透明であり、省略時は不透明である。線と塗りはそれぞれ独自の色を持つため、上記の `$shade` が塗りのみを半透明にしているように透明度も別々に設定される。本バージョンは色名や `rgb()` を受け付けない。色は文字列である。
- 本バージョンでは、パターン塗り・グラデーション・影、テキスト以外のオブジェクトの可視性（表示・非表示の切り替えはビューアの役割である；16.2。`textvisible` がテキストのみを対象としているのは、後からそのような可視性を独自の名前で追加できるようにするためであり、その場合テキストは両方がtrueのとき表示される）、およびテーマやプロファイルのようなオブジェクト（テーマはUSE-PACKAGEで取り込むスタイルとルールのパッケージである；16.2）は提供しない。
- スタイルもパラメータもプロパティ値を与えない場合は、レンダラ自身のデフォルトが使われる。これはエラーではない（原則 2.7）。標準パッケージは可搬なデフォルト外観を提供し（16.3）、ユーザーが書いたルールと文がそれを上書きする。
- 未知のプロパティは構文エラーと同様に扱われる（原則 2.3）。

### 9.4 一般定義：DEFINE

```rnl id=gdef
$TAIL_MID = @DEFINE(roles=["a", "b", "t"]) {
  %mid = (_, _);
  {?a %mid ?b} @DISTRIBUTE("left-to-right");
  {%mid ?t} @ALIGN("x")
};
$CHAIN_ROW = @DEFINE(roles=["source", "{chain}", "load"]) {
  {?source ?chain ?load} @ORDER("left-to-right")
};
$GND_BELOW = @DEFINE(roles=[["t", "pin"]], parameters=[["gap", 2]]) {
  %g = $GROUND @ATTACH ?t::net;
  ?t::net @WIRE {?t %g::pin};
  {?t %g::pin} @ALIGN("x");
  %g::pin ?t @DISTANCE("bottom-to-top", exact=?gap)
};
%c1 = #M1:3(a) #M2:3(b) #M5:1(t) @AS $TAIL_MID;
#R1(source) {#R2 #R3}(chain) #R4(load) @AS $CHAIN_ROW;
# @SELECT-INSTANCE => @SELECT-PIN(net="vss", wired=false) => $GND_BELOW @ATTACH(gap=3)
```

- 一般定義はロールリスト、パラメータリスト、および定義本体からなる。定義本体ではロールとパラメータを `?name` で参照する（6.10）。定義が何を行うかはその内容によって決まる（9.5を参照）。
- **適用**：ASとATTACHは定義のロールをオブジェクトで埋め、適用オブジェクトを作る。この2つのキーワードは同じ働きをし、定義をどこに書くかだけが異なる：
  - ASは定義を最後に置き、「これらのオブジェクトを、これこれとして扱う」と読む。意味やレイアウトに用いる（`#M1(left) #M2(right) #M5(tail) @AS $DIFFERENTIAL_PAIR_N` など）。
  - ATTACHは定義を最初に（明示的に書かれたオブジェクト群の前に）置き、標準形式では定義の後ろにキーワードを置く（`$GROUND @ATTACH &vss` など）。「これこれを、これらのオブジェクトに付与する」と読み、仮想部品や自動補完に用いる（第12章、10.5）。
  - もう一方のキーワードを選んでもエラーにはならず読みにくくなるだけだが、定義を誤った位置に書くとエラーになる（4.2項目7）。パイプで渡されたオブジェクトは直接ロールに対応付けられるため、その場合2つのキーワードは同じに見える。使い分けは定義の目的に従う。
  - 選び方の目安：オブジェクト群が一体となってそのもの（回路構造、レイアウト、またはそれらのオブジェクトからなる局所的な描画法）を構成する場合はASを用い、オブジェクトに対してそのもの（グラウンド、ポートタグ、未接続マーク、接続点の黒丸、インスタンスごとのラベル、または自動補完）を付け加える場合はATTACHを用いる。標準文は `#M1(left), #M2(right) and #M5(tail) are treated @AS $DIFFERENTIAL_PAIR_N` および `$GROUND is @ATTACH to &vss` である（4.5）。
- **ロールリスト**：パラメータ `roles` は、各要素がロール名または `[name, kind]` のペアである配列。DEFINEのどちらのパラメータも名前指定でのみ渡せる。
  - リストは空 `roles=[]` でもよい：定義は単独で適用され（`$PORT_LIST @ATTACH` など）、適用オブジェクトは主オブジェクトを持たないが、依然として自身の点を持つ（14.1）。
  - `"{name}"` と書かれた要素はセットロールであり、セット全体をとる。その他は単一ロールである（5.2.1項目4）。
  - セットロールに単一オブジェクトが渡された場合はそのオブジェクト1つだけからなるセットとして受け取り、空セットも妥当である（定義本体内のメンバー不足の制約は自明に成り立つ；第14章）。
  - 単一ロールにセットが渡された場合はメンバーごとに1回ずつ定義を適用し、空セットでは0回となる。1つの適用において、複数メンバーのセットを受け取れる単一ロールは最大1つである（そうでなければ文が失敗する；5.2.1）。
  - ロールがすべてセットロールである定義を適用するルールは、そのすべてが空であるレベルでは適用オブジェクトを作らない：ルールは到達する各レベルで評価され（10.4）、適用オブジェクトはそのセットロールに何かが入っているところでのみ作られる。これは、空セットを渡された単一ロールが定義を0回適用するのと同じである。ルールでない文は、セットロールが空でも適用オブジェクトを作る。したがって標準シリーズ 0.4 の自動補完は、ポートタグを得るレベルでのみ、そのレベルのポートタグの縦1列を作る（12.4）。
  - セットロールの `?name` が `{…}` 内に書かれた場合、それはそのセット内の1項目となる（5.2）：制約内ではその項目位置における各メンバーを表すため（14.1）、上例のORDERはR2とR3のそれぞれをR1とR4の間に配置する。
  - メンバーの中にセットを含むセットがセットロールに渡された場合、そのまま受け取り、どう使うかは定義本体が決める。
  - セットロールは端子に対応しない（6.4）。
  - 1つの適用において、各ロールは1度しか付与できない。セットロールに複数のオブジェクトを渡すには、上の `{#R2 #R3}(chain)` のようにセットとして記述する。
  - **種別**：`[name, kind]` と書かれた要素はそのロールが受け取るオブジェクトの種別を宣言し、名前のみの要素は任意の種別を受け取る。種別名は標準語リストのものである（5.3）：`"instance"`、`"terminal"`、`"pin"`、`"net"`、`"point"`、`"wire"`、`"usage"`、`"bundle"`、`"text"`、`"annotation"`、`"label"`。ロール宣言では、`"instance"` はバンドルも受け取り、`"terminal"` はバンドルの端子も受け取る（11.8）。配列を指定すると `["p", ["net", "terminal"]]` のように複数の種別のいずれかを受け取ることを意味する。いずれかの種別のオブジェクトはそのまま受け取られ、いずれにも該当しないがいくつかへ変換可能なオブジェクト（5.2.4）は配列順で最初の種別へ変換される（そのため `["net", "terminal"]` に `#R1::p` を渡すとそのピンのネットになる）。`"net"` をとるロールは空ノード（単独の `&`）も受け取り、そのロールがどのネットにも属さないことを示す（6.3）。セットロールはこれを受け取らない（空ノードはセットのメンバーになれないため）。セットロールの種別は `["{members}", "instance"]` のように各メンバーに適用される。特定の定義の適用オブジェクトだけを表す種別はない。
  - ロールが誤った種別のオブジェクトを受け取った場合、適用全体が失敗し、診断にはどのロールが、何を受け取り、何をとるはずだったかが示される。セットロールの1メンバーが誤った種別のときも同様である。選択によって1つずつ適用が行われる場合は、誤ったオブジェクトを受け取った適用のみが失敗する。
  - 注記：空の定義本体を持つ定義では、ロールに何が入ったかを他の文が検査することはないため、宣言された種別だけがロールの誤用を検出する。空でない定義本体では、展開後の各文も個別に検査される（9.5）。種別の宣言により、定義箇所の時点で定義本体内のロール使用法を検査することも可能になる（6.9）。
  - **省略可能なロールと個数**：単一ロールは必ず埋めなければならないが、セットロールは未指定のまま残すことができ、その場合は空セットになる。順序指定で渡したオブジェクト数がロール数より少ない場合、残りのロールはすべてセットロールでなければならない。ロール付与で渡した場合、書かれなかったセットロールは空セットになる。最小個数や最大個数の制限はなく、メンバー不足の制約は自明に成り立つ（第14章）。形状が異なる変種は別の定義として書く（下記の派生と拡張を参照）。同じオブジェクトが2つのロールを埋めるケースや期待される接続関係といった妥当性規則は9.5で扱う。
- **パラメータリスト**：パラメータ `parameters`（省略可）。各要素はパラメータ名または `[name, default]` である。
  - パラメータは `$GND_BELOW @ATTACH(gap=3)` のようにASおよびATTACHの括弧内で、パラメータリスト順の位置指定または名前指定で渡す（併用時は位置指定が先；4.2項目9）。標準形式は名前指定で書く（4.3）。パラメータリストにない名前を書くと適用は失敗する。選択によって1つずつ適用が行われる場合、すべての適用が同じパラメータを使用する。
  - 定義本体内のリテラルを書ける場所（パラメータの値、配列の要素、点の座標）には、代わりにパラメータプレースホルダを書くことができる。したがって定義本体内では「パラメータはリテラルのみをとる（4.1）」という規則が「リテラルまたはパラメータプレースホルダ」となり、展開後に再びリテラルに戻る。ASとATTACH自体のパラメータはリテラルのみをとることができ、オブジェクトを渡すことはできない（オブジェクトはロールを通じて渡す）。
  - 渡されず、かつデフォルト値も持たないパラメータは、使われた箇所で書かれなかったものとして扱われる：`@TEXT(?label, size=?size)` の `size=?size` のような名前指定パラメータなら書かれなかったことになり、テキストはTEXT自身のデフォルトサイズまたは自身のスタイルのサイズをとる（11.3）。点の座標なら `_` になる。位置指定パラメータまたは配列の要素に使われていた場合は定義された意味を持たず、その文が失敗する。そのため必須パラメータ用の印は不要である。
  - パラメータは数値やテキストのような量を渡すためのものであり、構造が異なる変種は別の定義として書くべきである（ただし言語がこれを強制するわけではない）。パラメータは定義本体へ渡されるだけであり、パラメータの値によって適用オブジェクトを選択することはできない。
- ロール名とパラメータ名は1つの表で管理され、すべて異ならなければならない。いずれも標準サブオブジェクト名にはできない（6.5）。パラメータに `priority` という名前を付けることはできない（ASおよびATTACHの標準パラメータであるため；14.8）。
- **適用オブジェクト自身**：一般定義の定義本体内で単独の `?` は、自身の点によって展開中の適用オブジェクト自身を表す（14.1）。`{?members::position ?} @ALIGN("y")` は適用オブジェクトの点をそのメンバーと同じ高さに置くため、別の構造における軸周りのDISTRIBUTEなど、その点に対する制約がメンバーごと一緒に移動させる。`::position` により、シンボルを持たない適用オブジェクトであるメンバーも1つの点のまま保たれる（14.1）。単独の `?` はロールではなくオブジェクトである。これは適用オブジェクトと同様にパスをとる（6.5）：`?::position` は自身の点（定義本体内の配線や図形がここで終端できる；5.2.4）であり、`?::` に続けてそのシンボルのピン名を書けばそのピン（pinという名前のピンなら `?::pin`）となる。
- **定義本体内のルール**：定義本体はルール（選択およびそこからパイプで渡される文；10.1）を保持してもよい。それらは適用オブジェクトが置かれたレベルの、そのASまたはATTACH文の位置に書かれたルールとして振る舞い（8.5、10.4）、そこに書かれたルールと同様に8.2のステップで有効になる：シンボルキューのSET-SYMBOL、ステップ5のrouteキーワードのルール、ステップ6の生成、スタイルキューのSET-STYLE。定義本体内では `#` はそのレベルである（10.3）。自身がステップ6で生成された適用オブジェクトの定義本体内では、ステップ5または6のルール（10.4）は失敗し、その他のルールは10.5のとおり後のステップで有効になる。
- 定義本体内で束縛された `%` 名はローカル名である：適用のたびにそれらのための新しいオブジェクトが作られ、外部からは適用オブジェクトを通じて参照される（下記）。対称軸のように複数の適用間で共有されるオブジェクトはロールを通じて渡す。
- 適用はオブジェクトにロールを付与して（`#M1(a) #M2(b) … @AS $T`、`$T @ATTACH #M1(a) #M2(b) …`）書いても、ロールリスト順に並べて（`#M1 #M2 … @AS $T`）書いてもよい。単一ロールが埋められていない場合、またはロール数より多くのオブジェクトが渡された場合は文全体が失敗する。埋められていないセットロールは空セットになる。
- 1回の適用は1つの適用オブジェクトを生成し、これは定義と各ロールを埋めるものを記録し、名前を付けることができる（`%c1` など）。文を削除すればそこから展開された記述も消える。適用オブジェクトはキーを持たない：各適用は別個のオブジェクトである（5.8）。
- **展開**：
  - プレースホルダは引数およびパラメータ値に置き換えられる。
  - ローカル名は「適用オブジェクト + ローカル名」という新しいハンドルに置き換えられ、`%c1::mid` のように記述される。無名の適用オブジェクトは診断においてその文の位置で示される。
  - 定義本体の外側に由来する名前は定義の適用箇所で再解決されない（6.9）。
  - 展開結果はASまたはATTACH文の位置でコミットされ、競合解決においてもこの位置をとる（8.5）。
- **定義本体内の座標**：一般定義の定義本体内のリテラル座標（`(1, 0)` のような点、またはPLACE内）は、そのレベルの軸に沿った適用オブジェクト自身の点（14.1）からのオフセットである：`(1, 0)` はその点から右へ1単位であり、`(0, 0)` はその点自身 `?::position` である。`_` は自由のまま残り、座標内のパラメータプレースホルダは置換後にオフセットになる。定義本体を移動させるのは点だけである：適用オブジェクトに対するORIENTはそのシンボルを回転・反転させるのであって、定義本体が描画・配置するものを回すわけではない（11.2）。したがって定義は `(0, 0)` で交差する2本のLINEのような目印を自身の点の周りに描き、自身の点をピンに結びつけることができる（12.1項目5）。自身の定義本体内で単独の `?` にPLACEを書くと（自身からのオフセットになるため）失敗する。定義本体の外（ソルバーのレコード内など）では位置はレベルの座標である（14.8）。
- 入れ子の適用オブジェクトは段階的にたどることができる（`%c1::inner::mid`）。また適用オブジェクトが別の定義のロールを埋めることもできる：独自の定義 `$OTA = @DEFINE(roles=[["pair", "usage"], ["load", "usage"]]) {}` に対して `#M1(left) #M2(right) #M5(tail) @AS $DIFFERENTIAL_PAIR_N => %cm1 @AS $OTA` は、pairロールが差動対の適用オブジェクトで、loadロールがカレントミラー `%cm1` で埋められた増幅器である（5.5）。
- **循環適用**：展開の内部にある適用が、直接または他の定義を経由して、現在展開中の上位の適用オブジェクトと同じ定義を再び適用する場合、循環を閉じる。その適用は失敗し、診断はその連鎖全体を列挙し、残りは通常どおり有効になる。以下ではM1に `$A` を適用すると `$B` が展開され、その中の `$A` の適用が循環 `$A → $B → $A` を閉じて失敗するが、`$B` 内のORIENTは引き続きM1を反転する：

  ```rnl error
  $A = @DEFINE(roles=["x"]) {?x @AS $B};
  $B = @DEFINE(roles=["x"]) {
    ?x @AS $A;               /* closes the cycle $A → $B → $A: this application fails */
    ?x @ORIENT("MY")
  };
  #M1 @AS $A
  ```

- **外部からのローカルオブジェクトの参照**：

  ```rnl use=gdef
  $DP_BLOCK = @DEFINE(roles=["in_p", "in_n"]) {
    %pair = {?in_p ?in_n} @GROUP
  };
  %dp1 = #M1(in_p) #M2(in_n) @AS $DP_BLOCK;
  %c1::mid @PLACE(x=20);              /* moves the midpoint of c1 */
  {%c1::mid #M9:1} @ALIGN("x");       /* aligns the drain of M9 with the midpoint of c1 */
  %dp1::pair @PRIORITY("disabled")    /* turns off only the group expanded for dp1 */
  ```

  - 定義本体のすべての名前付きローカルオブジェクトは、適用オブジェクトを通じて `usage::local_name` のように外部から参照できる。名前のないものは、ソルバーのレコードから番号で参照する場合を除き到達できない（5.9）。名前を付けるか否かは「オブジェクトを参照するには名前を付ける」（5.7）と同様に定義作成者の選択であり、別個のエクスポートリストはない。
  - パスは連鎖できる：`%st1::dp::mid` はst1の定義本体内のローカル適用オブジェクトdpのmidである。ロール経由でたどることも同じようにできる：`%st1::pair::mid` はロールpairを埋める適用オブジェクトのmidである。
  - これらは通常の参照である：事実を追加でき（PLACE、SET-STYLE、TEXT、PRIORITYなど）、他の文で使用でき、他の定義のロールを埋めることもできる。展開内の事実との競合は8.5で解決される。外部からローカル名を再束縛することはできない：`%c1::mid = …` はエラーである。
  - 名前：適用オブジェクト上で `::` を通じて到達される名前は一意でなければならない。したがってローカル名はロール名や標準サブオブジェクト名と同じであってはならず（定義時に検査される）、適用オブジェクト上のテキストのkeyもこれらの名前のいずれとも同じであってはならない（6.5、13.3）。ローカル名はパラメータ名と同じであってよい（パラメータは値であり、`::` は値に到達しないため）。
  - 優先度：外部からローカルオブジェクトに直接書かれたPRIORITY文は、適用オブジェクトの優先度を上書きする（14.8）。
  - 到達不能なもの：無名の適用オブジェクトのローカルオブジェクト（ソルバーのレコードからの番号による参照を除く；5.9）、および選択によって1つずつ生成された適用オブジェクトのローカルオブジェクト。適用オブジェクトをスコープとする選択は、そのロールのメンバーのみを選択し、ローカルオブジェクトは選択しない（10.1）：適用オブジェクト経由では、ローカルオブジェクトは名前によってのみ到達できる。レベルをスコープとする選択は（下記の `# @SELECT-USAGE $FILTER` のように）そのレベルのオブジェクトとして他のオブジェクトと同様にそれらを選択する。ルールができないのは、自身が書いていない定義のローカルオブジェクトを名指しすることである。
  - したがってローカル名は定義のインターフェースの一部である：定義がローカル名を変更すると、外部からの参照はそれを見つけられなくなって失敗し（第7章）、ソルバーの結果もそれとともに古くなり、ヒントが再求解を促す（第17章）。標準パッケージは自身の定義のどのローカル名に依存できるかを明記する。
- **定義本体内の表記**：ロールとパラメータは `?name`、ローカル名は `%name` と書く（6.9、6.10）。
- **派生と拡張**：合成（composition）によってのみ行われ、継承関係はない（9.1）。派生定義の定義本体はベース定義を適用し、自身の文を追加する：

  ```rnl
  $FILTER = @DEFINE(roles=["in", "out"]) {};
  $LOWPASS = @DEFINE(roles=["in", "out", "r", "c"]) {
    %f = ?in(in) ?out(out) @AS $FILTER;
    {?r ?c} @ORDER("left-to-right")
  }
  ```

  - 内容の追加は定義本体内の文で、数値的な変種はパラメータで行う。下位レベルで定義を隠蔽して拡張するには、定義本体内で同名の外側定義を参照する（6.9）。
  - ベース定義による選択に特別な規則は不要である：派生定義から展開されたFILTERの適用オブジェクトはシーン内に存在するため、`# @SELECT-USAGE $FILTER` はそれを選択し、`$FILTER` 向けに書かれたルールはローパスフィルタに対しても動作する（ただしその内部のFILTER適用オブジェクトに対してのみ作用し、派生定義が追加した文には作用しない）。
  - ベース定義の一部を取り除く専用機構はない：派生定義の定義本体内で `%f::x @PRIORITY("disabled")` と書いて一部を無効化することはできるが、外側の適用オブジェクトの優先度がそれを上書きしてしまう（14.8）。確実に一部を省くには、ベース定義をより小さな定義に分割するか、別の定義を書く。

### 9.5 一般定義の用途

定義が何を行うかはキーワードではなくその内容によって決まる：

```rnl
$PAIR = @DEFINE(roles=["in_p", "in_n"]) {};                /* meaning: roles only */
$SIDE_BY_SIDE = @DEFINE(roles=["a", "b"]) {               /* layout: constraints in the body */
  {?a ?b} @ALIGN("y");
  {?a ?b} @ORDER("left-to-right")
};
$PROBE = @DEFINE(roles=[["p", "net"]]) {};                 /* virtual part: a rule gives its usages a symbol (chapter 12) */
$PROBE_SYM = @DEFINE-SYMBOL {(0, 0) @PIN(terminal="p"); (0, 0) @CIRCLE(radius=0.5)};
# @SELECT-USAGE $PROBE => @SET-SYMBOL $PROBE_SYM
```

標準パッケージでは、`$CURRENT_MIRROR_N`、`$MIRRORED_LAYOUT`、`$GROUND` がこれら3種類にあたり、`$DIFFERENTIAL_PAIR_N` はロールを持ち、さらに定義本体にデフォルトレイアウトを持つ（下記）。

- これらはいずれも同じ種類のもの——1つの適用オブジェクト（どの定義が適用され各ロールを何が埋めるかの記録）と定義本体から展開された記述群——である。2つの部分で使い手が異なる：
  - 定義本体から展開された制約はソルバーによって処理され、満たされなければならず、競合時には8.5で解決される。
  - 適用オブジェクト自体は人間やLLMが読み取るため、およびRNL自身の選択やルールのためにある（10.1）。

  したがってレイアウト定義の適用オブジェクトも意味を担っている。`$PAIR` のように空の定義本体を持つ定義はロールのみを通じて意味を記録し、その意味は標準パッケージまたは作成者が述べる。意味を記録する定義も定義本体に描画を持たせてよい（下記）。
- 意味を表す適用オブジェクトはコメントではない：参照は見つからなければならず、ロールは一致しなければならず、基本的妥当性が検査され（原則 2.4）、選択やルールがそれを利用できる。単にどう描画されるかが規定されていないだけである。
- 「それが何であるか」と「どう描くか」は1つの定義に書いても、2つに分けて書いてもよい。定義は優先度 `"low"` のデフォルト描画を定義本体に持たせることができる：記述者自身の事実がそれより優先され、適用オブジェクトの優先度がそれを無効化または引き上げる（`%dp1 @PRIORITY("disabled")`、あるいはその定義のすべての適用オブジェクトに対して `# @SELECT-USAGE $DIFFERENTIAL_PAIR_N => @PRIORITY("disabled")` とするなど。適用オブジェクト自体はそれらが何であるかを記録し続ける；14.8）。意味から描画への変換はパッケージ内のルールとして書くこともでき、パッケージを切り替えることで描画が変わる：`# @SELECT-USAGE(recursive=true) $DIFFERENTIAL_PAIR_N => @AS $DP_LAYOUT`（レイアウト用の適用オブジェクトを削除しても意味側の適用オブジェクトには影響しない）。標準パッケージは自身の定義の定義本体にデフォルト描画を書いており、そのすべての制約は優先度 `"low"` である（差動対のテールを対の中央の下に置く、`$BRANCH` のメンバーを上から下へ縦1列に並べるなど；16.3）。
- **描画は常にRNLで記述する**：ある意味が特定の方法で描画されるのは、その定義の定義本体または上記のようにルール（パッケージ内であってもよい）で適用されたレイアウト定義においてRNLがそう書いているからである。特定の意味に対するレンダラの暗黙の慣習に依存してはならない。定義が描画を持つか否かはパッケージ次第であり、本標準はそれ以上の規定を設けない。RNLが記述しない部品がどう配置されるかは実装に委ねられる（原則 1）が、それは特定の意味に対する描画慣習ではなく依存できない。記述のないオブジェクトのデフォルトのスタイルをレンダラが決めること（原則 2.7）、およびシンボルを持たないインスタンスが既定のブロックシンボルを持つこと（9.2.6）はまた別の話である。
- **語彙は標準パッケージに属する**：最初の意味定義群と標準の仮想部品群は標準パッケージの内容であり、言語標準の一部ではない（16.3）。標準パッケージの定義がその意味とロールをどう定めるかも標準パッケージに委ねられる。ユーザー定義の意味はその定義本体であり、その名前は人間が読むためのものにすぎない。
- **基本的妥当性**（原則 2.4）：定義の構文は、2つのロールが同じオブジェクトで埋められたか否かを検査しない。1回の適用の基本的妥当性とは、参照が見つかること、ロールが正しい種別を受け取ること、単一ロールが埋められていること（9.4）、および展開後の各文がそれ自体として妥当であることである。

  ```rnl error
  $DP_LAYOUT = @DEFINE(roles=[["in_p", "instance"], ["in_n", "instance"]]) {
    {?in_p ?in_n} @ALIGN("y");
    ?in_p ?in_n @DISTANCE("left-to-right", min=4)
  };
  #M1(in_p) #M1(in_n) @AS $DP_LAYOUT      /* the expanded DISTANCE asks M1 to be at least 4 from itself */
  ```

  - この例では展開されたDISTANCEが自己矛盾している：診断付きで失敗し、それだけが破棄され（5.5、7.3）、ALIGNは通常どおり成り立つ。上の `$PAIR` のように定義本体が空の定義はそのような埋め方を検出できない：`#M1(in_p) #M1(in_n) @AS $PAIR` はエラーを報告しない。
  - 両端が同じネット上にある仮想部品には明確な意味があるため、「同じオブジェクトが2つのロールを埋める」ことを一般的にエラーとすることはできない。
  - 2つのロールが異なることを要求するようなさらなる検査は、表明として記述する（15.3）。
- **キーワードと一般定義**（1.5項目7）：実装自身が理解しなければならず他の記述では書けないものがキーワード（基本制約、GROUP、WIRE、TEXT、CURRENTなど）であり、一般定義の定義本体に書けるものが一般定義（差動対、カレントミラー、グラウンドと電源、信号フローなど；14.6）である。DEFINE-SYMBOL、DEFINE-STYLE、SET-SYMBOL、SET-STYLEもキーワードである：シンボル定義本体はローカル座標であり定義箇所で評価され、スタイルのプロパティはリテラルであり、SET-SYMBOLとSET-STYLEは既存オブジェクトの1つのプロパティを設定してすべてのオブジェクトが存在した後にキューで決定されるのに対し、ASとATTACHは毎回新しいオブジェクトを生成する。
- 定義は名前の文字列ではなく、その名前が解決する先の定義実体によって識別される：下位レベルが独自の `$DIFFERENTIAL_PAIR_N` を定義した場合、それは別の定義であり、標準の `$DIFFERENTIAL_PAIR_N` 向けに書かれたパッケージのルールはそれを認識しない。

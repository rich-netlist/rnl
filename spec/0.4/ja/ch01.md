## 1 概要

### 1.1 適用範囲

RNL（Rich Netlist）は、ホストネットリストのコメント内に記述される。ネットリストが定義する回路がどのように理解され、回路図として表現されるか——すなわち、どのシンボルを用いるか、部品をどこに配置するか、どのように向き付け・整列・配線・ラベル付け・スタイル設定するか、また部品のまとまりが何を意味するか——を記述する（原則 1）。

素子、型、パラメータ、接続およびサブサーキットのインターフェースは、ホストネットリストのみによって定義される。RNLはそれらを参照するだけであり、変更することはできない。RNLは、図面が示唆する電気的意味を検証しない（原則 2.2）。

本標準は以下を定義する：

- ホストネットリストのコメント、およびそれが取り込むVerilog-AファイルのコメントからRNLをどのように抽出するか（第2章）。
- RNLテキストの字句構造および構文（第3章、第4章）。
- テキストがどのようなオブジェクトを記述し、名前がどのように解決され、失敗がどのように処理され、各記述がどのように協調して有効になるか（第5章〜第8章）。
- 各種記述の語彙（第9章〜第17章）。
- 本書とともに `rnl-words-0.4.json` として公開される標準語リスト（5.3、付録 A）。

本標準は、レイアウトアルゴリズムや一意な描画結果（レンダリング）を定義しない（原則 1）。また、ホストネットリストの解析方法も定義しない（原則 2.1）。標準パッケージ `rnl-std-all` および `alias-zh` などの別名パッケージはRNLで記述されている。本標準はパッケージの動作を定義し（16.2、16.3、16.5）、パッケージ自体の内容は別途公開される。

本書は本言語のバージョン0.4を定義する。0.x系のバージョン間では互換性を保証しない（16.1）。

### 1.2 本標準の構成

本標準は抽象モデルとテキスト構文からなる。抽象モデルはオブジェクト、事実、入力の取り込み方および有効になるフェーズであり（第5章〜第8章）、テキスト構文はその記述形式である（第2章〜第4章）。ツール間ではこのテキストを交換する。

付録 A はキーワードのシグネチャ一覧であり、標準語リストから生成され、規範的である。付録 B は標準文を示し、付録 C は将来のバージョン向けに予約された事項を示し、付録 D はバージョン0.3からの変更点を示す。これら3つは参考情報（informative）である。注記および例も参考情報である。それ以外はすべて規範的である。

### 1.3 概要例

```spice
* Five-transistor OTA, input stage
* @RNL(type="header") { @VERSION("0.4"); @USE-PACKAGE(name="rnl-std-all", version="0.4")}
.model nch nmos level=1
.subckt ota5t inp inn out vdd vss vbias
M1 x    inp   tail vss nch W=2u L=0.5u
M2 out  inn   tail vss nch W=2u L=0.5u
M5 tail vbias vss  vss nch W=4u L=1u
* @RNL {
*   %dp1 = #M1(left), #M2(right) and #M5(tail) treated @AS $DIFFERENTIAL_PAIR_N;
*   {#M1 #M2} @ALIGN("y"), i.e., same y;
*   #M5 is at @PLACE(20, 6) => it @ORIENT("R0");
*   %g0 = $GROUND is @ATTACH to &vss;
*   net &vss, through {#M5:3 %g0::pin}, has a @WIRE
* }
.ends ota5t
.end
```

- `* ` でSPICEのコメントが始まる。`@RNL {…}` は1つのレコードであり、波括弧の内部には `;` で区切られたメンバーが並ぶ（第2章）。ファイル先頭のヘッダーレコードは言語バージョンを宣言する（16.1）。
- `#M1`、`&vss`、`#M5:3` はそれぞれホストのインスタンス、ネット、端子を参照する。`%dp1` と `%g0` はこのレベルのRNL名である。`$DIFFERENTIAL_PAIR_N` と `$GROUND` は、ヘッダーレコードが使用する標準パッケージ内の一般定義（9.4）である（16.3）。`%g0` は `$GROUND` の適用によって作られる適用オブジェクトであり、標準パッケージがそれにグラウンドシンボルを与えるため、グラウンドとして描画される（第12章）。
- `@AS`、`@ALIGN`、`@PLACE`、`@ORIENT`、`@ATTACH`、`@WIRE` はキーワードである。パラメータはキーワードに隣接する丸括弧内に記述し、リテラルのみをとる。ASは、その後に書かれた定義のロールを、その前に書かれたオブジェクトで埋める。ATTACHは、その前に書かれた定義を、その後に書かれたオブジェクトに付与する（9.4、第12章）。
- `(left)` はロールを表す。`%dp1 =` は文の結果に名前を付ける。`=>` は1つのセグメントの結果を次のセグメントへ渡し、直後に名前のみが続く場合は直前のセグメントの結果に名前を付ける（5.5）。
- `and`、`treated`、`, i.e., same y`、`is at`、`it`、`is … to`、`net`、`, through`、`, has a` は自由テキストであり、意味を変えない（3.3）。標準文は、文が英語の文のように読めるよう、トークンの間にこのような語句を挿入する（4.5、付録 B）。これらを取り除くとレコードは次のようになる：

```rnl
%dp1 = #M1(left) #M2(right) #M5(tail) @AS $DIFFERENTIAL_PAIR_N;
{#M1 #M2} @ALIGN("y");
#M5 @PLACE(20, 6) => @ORIENT("R0");
%g0 = $GROUND @ATTACH &vss;
&vss {#M5:3 %g0::pin} @WIRE
```

### 1.4 用語と表記規約

#### 1.4.1 要件を表す語

- **しなければならない**（must）、**してはならない**（must not）：文書または実装に対する必須要件。
- **すべきである**（should）、**すべきでない**（should not）：推奨。別様に行う理由がある場合もあるが、まずその理由を理解した上で判断すべきである。
- **してもよい**（may）：許容される事項。

言語自体の意味は現在形で記述される（「文は失敗する」「後のものが優先される」など）。

#### 1.4.2 失敗と診断

- **失敗**（fail）した項目（レコードヘッダーのフィールド、文、レコード、またはファイル；7.6）は効力を持たず、失敗した文はその値として失敗オブジェクトを持つ（7.2）。原因を問わず、すべての失敗は**エラー**である（7.6）。
- **警告**（warning）は、妥当ではあるが記述者の意図と異なる可能性のある項目を示す。本標準に別段の定めがある場合（制限時間内にソルバーが判定できなかった事実など；8.5）を除き、通常どおり有効になる。**違反**（violation）は、ファイルが回路に関して記述した文（表明など）が成り立たないことを報告するものであり、何も失敗しない（15.3、15.4）。**ヒント**（hint）は、よくある上書き・隠蔽・解決のうち、誤りである可能性もあるものを示す。各ケースは7.6に列挙されている。本標準で警告またはヒントを出すと述べている箇所では、実装はそれを報告すべきである。
- **解釈が失敗**したときは、何も描画されずエラーが報告される（1.5項目3、7.6）。

#### 1.4.3 表記法

- 本文中では、キーワードを `@` なしの大文字で表記する：PLACE、SET-SYMBOL。構文および例では `@` を付けて表記する。
- 標準語、名前およびリテラルは等幅フォントで表記する：`priority`、`"high"`、`instance`、`$GROUND`。
- 括弧内の節番号は本標準内の参照を表す：(9.4)。「原則 2.4」はRNL原則 `rich-netlist.md` の2.4節を指す。
- 例は標準形式（4.3）で、自由テキストを主題とする場合を除き自由テキストなしで記述する。エラーと記された例は誤りを示す。
- 例は標準パッケージを用いる。ヘッダーレコードを示していない例は、主ファイルのヘッダーレコードに `@USE-PACKAGE(name="rnl-std-all", version="0.4")` が書かれているものとして読む（16.3）。

| シンボル | symbol | DEFINE-SYMBOLが作るもの：インスタンス、バンドル、または適用オブジェクトに対して描画される図形・ピン・テキスト（9.2） |
| 有効になる | take effect | レベルが完全に読み込まれた後、その事実がフェーズごとに順次シーンへと反映されること（第8章） |
| トークン | token | キーワード、参照、点、丸括弧・角括弧、波括弧、`;`、`=>`、`=`。それ以外は自由テキストまたはコメントである（3.2） |
| 端子 | terminal | ネットリスト行におけるインスタンスの接続箇所：`#M1:d` や番号による `#M1:1`。`#:inp` はそのレベルのポート `inp` である（6.4） |
| 適用オブジェクト | usage | 1回の適用によって作られるオブジェクト。使用した定義と各ロールを埋めるオブジェクトを記録し、シンボルを持つ場合は描画される（9.4、9.5）。制約内では、シンボルを持たない適用オブジェクトはそのメンバーを表す（14.1） |
| 仮想部品 | virtual part | シンボルを持つ適用オブジェクト。描画されるがネットリストには含まれない部品（グラウンド、電源、ポートタグ、接続点の黒丸など；第12章） |
| 標準語リスト | word list | ある言語バージョンのすべての標準語とキーワードシグネチャの機械可読一覧。本バージョンでは `rnl-words-0.4.json`（5.3、付録 A） |

### 1.5 基本原則

本標準の規則は以下の原則に従う。項目1〜6は原則 2.9を精緻化したものであり、項目7は語彙の分割方針を示す。

1. **すべては記述である。** RNLテキストは記述の集合である。インタプリタは結果を出す前にすべての記述を収集する。何も「実行」されず、名前はそれを束縛する文よりも前で参照できる。
2. **記述位置は単なる順序データにすぎない。** 記述がどこに書かれたか（そのレベルとテキスト内の位置）が影響するのは次の3つの場合のみである：記述同士が矛盾するときに後のものを採用する（幾何的事実は優先度を先に比較する；8.3、8.4、8.5）、描画順（11.6）、およびセット内のメンバーの順序（5.2）。それ以外の場合、結果は記述順序に依存しない。パイプの各セグメントはそれぞれ固有の位置を持ち、後のセグメントは前のセグメントより後に書かれたものとして扱われる（5.5）。
3. **矛盾。**
   - 解釈できない記述（構文エラー、見つからない名前、誤った種別など）または自己矛盾する記述は失敗する（原則 2.4、2.9；第7章）。
   - 解釈は可能だが互いに矛盾する記述は、本標準が明確な解決策を定める箇所（keyによる上書き（8.4）、外観キュー（8.3）、幾何的事実の解決（8.5）など）で解決される。その際、ヒントが出される場合がある。
   - 明確な解決策がまだ定められていない箇所では、解釈全体が失敗する（7.6）。本バージョンにはそのようなケースは存在しない（7.5）。将来のバージョンで解決策を定めて許容的にすることはあるが、現在動作するファイルが影響を受けることはない。
4. **各記述は有効になる前の状態を参照する。** 記述は所属フェーズの開始時点の状態を読み取る。自分自身の効果および同じフェーズの他の記述の効果は含まれない（8.2）。
5. **オブジェクトと名前。** キーワードを持つすべての文とすべての `{…}` は、ハンドルと事実からなる新しいオブジェクトを作る。参照はオブジェクトを作らないが、位置指定によるメンバー取り出し（5.2.3）のみ新しいセットを作る。名前はオブジェクトを参照するだけであり、1つのレベルで1度だけ束縛される。上書きが適用されるのは事実に対してであり、名前に対してではない（5.1、6.6）。
6. **可読性のための制限は設けない。** 読みにくくても一意な意味を持つ形式は許容される。節度は記述者に委ねられる。一意な意味を持たない形式のみがエラーとなる。
7. **キーワードと定義。** 実装自身が理解しなければならず、他の記述では表現できないものがキーワードである。一般定義の定義本体内で既存の記述を用いて表現できるものは定義であり、その名前は単なるヒントにすぎない（9.5）。

### 1.6 適合性

**文書。** ホストネットリストは、そのレコードが第2章〜第4章の定めに従って読み取られ、第5章〜第17章の定めに従って解釈されたときに、使用するパッケージ内のエラーを含めてエラーが1つもなければ、RNL 0.4に適合する（7.6）。警告、ヒントおよび違反は適合性に影響しない。違反は回路がファイルの主張を満たしていないことを示すものであり、ファイルの記述誤りを示すものではない。パッケージファイルは、単独で検証されたときに同様に適合する（16.2）。ヘッダーレコードで別の言語バージョンを宣言しているファイルは、本バージョンの規律を受けない（16.1）。

**実装**とは、インタプリタ（検証のみに用いられるインタプリタはlintとも呼ばれる）、ビューア、ソルバー、エディタなど、RNLを読み書きするツールを指す。適合する実装は以下のすべてを満たす：

1. 第2章の定めに従ってホストのコメントからRNLを抽出し、第3章および第4章に従って読み取る。
2. 第5章〜第17章が定める効果を、標準語リストのシグネチャに従って各記述に与える（5.3）。
3. すべてのエラーをその位置および原因とともに報告する（7.6）。エラーの重要度を下げたり無効化したりすることはできない。
4. 本標準が列挙する警告およびヒントを報告すべきであり、違反は必ず報告しなければならない（7.6）。
5. 独自のチェックを追加してもよいが、警告またはヒントとしてのみ許容される。本標準が有効にする項目を失敗させたり、本標準が失敗させる項目を有効にしたりしてはならない。
6. 処理を停止する、または入力全体を拒否するようなより厳格なモードを提供してもよいが、それをデフォルトにしてはならない。
7. ユーザーに診断を提示する。提示方法の詳細は実装に委ねられる（7.6）。
8. サポートする言語バージョンを宣言し、サポートしないバージョンのファイルを16.1の定めに従って扱う。
9. 未知のキーワード、パラメータおよび値をエラーとして扱う（16.4）。
10. ファイルが標準パッケージを記述している場合、16.3の定めに従ってルートのパッケージに配置する。
11. RNLを書き出す際、新しい文は標準形式で書き出し、ユーザーが書いた文の順序を変更しない（4.3）。ファイルを保存する際にはヘッダーレコードとバージョンを書き出す（16.1）。未知の文や失敗した文、ホストテキスト、通常のコメントおよび未サポートバージョンのファイルはそのまま保持し（16.4）、第17章が変更を許すレコードのみを変更する。
12. 求解する際、8.5の定めに従って競合を解決し、下したすべての決定を書き戻し、ソルバーのレコードが保持できる形式でのみ他のツールへ結果を受け渡す（14.8）。
13. 使用するリソースに上限を設けてもよい（シンボルの入れ子深さ（9.2.7）、適用オブジェクトの展開深さ（9.4）、インクルードファイルやサブサーキットの深さ、あるいはオブジェクト数など）。その上限を超える入力に対しては、位置とともに実装上限に達した旨のエラーを報告しなければならない。入力を黙って切り詰めたり、本標準が定めるものとは異なる結果を描画または求解したりしてはならない。シンボルの入れ子深さは少なくとも64階層をサポートする。求解中の事実チェックに関する制限はこの種の上限ではなく、ソルバーのオプションであり、未判定のまま残された事実は警告付きで破棄される（8.5）。

本標準は、制約を満たす複数の配置からソルバーがどのように1つを選択するか、またRNLが未規定のまま残した部分をビューアがどのように描画するかは定義しない。それらに委ねられる箇所は本文中に明記されている（例えば13.1）。

**適合性テスト**は、エラー（その位置および各失敗の影響範囲）と、結果として得られるシーンを検証する。警告は任意の確認項目として検証してもよいが、ヒントは検証対象としない（7.6）。

## 7 失效與診斷

### 7.1 檢查的兩個階段

- **讀取時**：詞法結構；文法；內建關鍵字的簽名，亦即物件數量、種類與參數（含陣列形狀）；以及一般定義的定義本體中每個 `?name` 是否位於其角色列表或參數列表中且處於合適的位置（6.10）。一般定義的定義本體中不依賴引數的簽名錯誤亦會於此時回報（6.9）。
- **生效時**：
  - 完整讀取整個層級之後，解析名稱與宿主引用，並檢查名稱所指物件的種類；
  - 一般定義的定義本體中的名稱對每個定義解析一次，不會在每次套用時重新解析（6.9）；
  - 檢查 AS 與 ATTACH 的物件數量、角色名稱、角色宣告的種類以及參數（9.4）；
  - 每次套用分別檢查其展開結果中依賴引數的部分；
  - 一旦指派符號之後，檢查連線與約束所連接的端子在其符號中是否有對應接腳、ORIENT 所作用的用例是否有符號、透過實例或用例存取的接腳名稱（如 `#R1::p` 或 `%g::pin`）是否為其符號的接腳，以及往返接腳的轉換是否能夠完成（5.2.4）。

### 7.2 失效物件

- 失效的敘述產生一個失效物件，其上附有診斷資訊：原因、位置與上游原因。
- 失效物件在成員之間保留其位置，其餘成員亦保留各自的位置。因此當宿主網表沒有 M9 時，`{#M1 #M2 #M9} @ALIGN("y")` 會整體失效，不會變成僅對齊 M1 與 M2。
- 當名稱綁定至失效物件（包含讀取時即失效的定義）時，引用該名稱的敘述同樣會收到該失效物件。依賴於失效描述的敘述會隨之失效，不論書寫順序為何（原則 2.9），唯獨在賦予符號後的檢查才發現失效的敘述不會撤回它先前已經參與的步驟（8.2）；這些同樣構成錯誤，其診斷須說明上游原因（7.6）。
- 將名稱第二次綁定至另一個物件構成錯誤，該名稱保留其第一個有效綁定；僅當沒有任何綁定有效時，該名稱才綁定至失效物件（6.6、5.5）。

### 7.3 嚴格與容錯輸入

- 簽名會為每個輸入宣告其屬於嚴格或容錯：
  - 嚴格：當輸入包含失效物件時，整條敘述失效；
  - 容錯：移除失效成員並記錄一筆診斷，其餘部分照常生效。
- 預設情況下，吸收型輸入為嚴格；封裝型輸入（定義的定義本體）與提交型輸入（`@RNL`）為容錯（5.4）。
- AS 與 ATTACH 的引數為嚴格；其展開後的敘述則為容錯：失效的敘述各自被捨棄。
- 在管線與巢狀中，失效僅影響依賴它的描述（5.5）：當嚴格輸入包含失效物件時，該敘述失效，但巢狀於其中且不依賴該失效的敘述仍照常生效；當敘述對每個成員各運作一次時，每個成員各為一項描述並各自失效。

### 7.4 錯誤復原

- 語法錯誤會使發生錯誤的整個成員失效，直到下一個 `;` 或外層集合結束為止。
- 當字串或 `/* */` 註解未閉合，或大括號不匹配時，便無法找到該筆記錄的結尾（2.4）：該筆記錄不完整，整筆記錄失效。成員內部的括號若未閉合——例如參數、陣列、角色、點或下標的括號——僅為該成員的語法錯誤：該記錄中的其餘成員照常讀取。
- 當記錄在完整之前遭切斷時，整筆記錄失效，診斷會說明該記錄不完整（2.4）。
- 錯誤復原絕不越過其所在記錄：其餘記錄照常讀取（原則 2.9）。

### 7.5 衝突不是失效

- 衝突在完整讀取整個層級之後，依定義的方法處理：依 key 覆寫（8.4）、外觀佇列（8.3）與幾何事實取捨（8.5）。
- 尚未定義處理方式的衝突會使整份解譯失效（1.5 第 3 項；7.6）。本版本沒有這類情況：集合的循環依賴在使循環閉合的那條敘述處失效（5.2.2）。

### 7.6 診斷

- **檢查與解譯是同一個過程。** 解譯器讀取輸入並給出最終場景與一組診斷；僅用於檢查時，它亦稱為 lint。本標準僅定義這一組診斷。編輯器為了即時回饋所做的局部檢查（例如語法醒目顯示）不屬於此處意義上的診斷：本節不適用於它們，它們亦不能取代診斷。
- **項目。** 失效作用於一個項目：記錄標頭的欄位、敘述、記錄、檔案或整份解譯。具體屬於哪一種會在每個失效的定義處說明（見下方失效範圍）。
- **四種回報**：
  - **錯誤**：某個項目失效，無論原因在於該項目自身、另一項目，或上游所依賴的事物。錯誤包含原則 2.4 的基本錯誤（語法錯誤、未知詞彙、簽名不符、找不到引用、種類錯誤、自相矛盾、不受支援的版本）、本標準定義的其他失效（例如將 ORIENT 套用至沒有符號的用例，或端子在符號中沒有接腳；12.1、9.2.4），以及由它們引發的連帶失效（7.2）。
  - **警告**：項目合法且照常生效（除非本標準另有規定，例如檢查未於時限內完成而遭捨棄的事實，8.5），但可能並非作者本意，例如為接收單一物件的槽位直接寫出空集合，如 `{} @PLACE(1, 2)`（5.2.1）；直接寫作記錄成員且未巢狀於敘述中的未命名定義（9.1）；觸及下方層級的產生規則（10.1）中某個角色填入了僅本層級才有的物件（10.5）；記錄標頭中的未知欄位（2.8）；套件版本遭另一版本取代（16.2）；連線連到不在該連線所命名網路上的端子（13.1）；或幾何事實因檢查未能在求解器限制內完成而遭捨棄（8.5）。
  - **提示**：常見的覆寫、遮蔽或取捨結果，但也可能是誤寫，例如較低層級或其中使用的套件遮蔽了上層級或根層級套件的定義（6.8）；較後 USE-PACKAGE 的套件遮蔽較早 USE-PACKAGE 的套件（16.2）；在衝突取捨中遭捨棄的幾何事實（8.5）；因未寫明版本而改用套件的最新版本（16.2）；主檔案未宣告版本而依工具預設版本讀取（16.1）；未使用標準套件時找不到標準套件的名稱（16.3）；或求解器記錄中的編號已過時（5.9）。
  - **違規**：檔案對電路所做的陳述並不成立：斷言的檢查未成立（15.3、15.4），或某個網路上的 CURRENT 敘述將所有電流指向同一方向（15.2）。不會有任何項目失效，檢查及其回報也不會改變繪圖中的任何內容：斷言的繪圖效果與未寫時相同，供檢查讀取的 CURRENT 敘述亦繼續生效。回報是提供給作者與檢查檔案的工具閱讀的。檢視器可使用自訂名稱顯示它。
- **失效範圍**在每個失效定義處說明：欄位（寫錯的記錄標頭已知欄位視同未寫，2.8）；敘述（多數情況）；記錄（未閉合的字串或註解、不匹配的大括號、遭切斷的記錄、找不到 `scope` 目標；7.4、2.4、2.6）；檔案（不受支援的版本，16.1）；整份解譯（尚未定義處理方式的衝突，1.5 第 3 項：解譯中止且不繪製任何內容；後續版本可將此類情況改為容錯；本版本沒有此情況）。
- **要求**：
  - 錯誤須予以回報，違規亦須回報：回報正是撰寫斷言的目的（15.3）。警告與提示為本標準所列者，實作應予以回報。
  - 實作可以新增自訂檢查，但僅限作為警告或提示；不得使項目因此失效，否則不同實作會繪製出不同的結果。
  - 實作須讓使用者能看到診斷；呈現方式由實作自行決定（原則 2.9）。
  - 實作可以提供更嚴格的模式，例如中止或拒絕整份輸入（原則 2.9），但不得作為預設行為。實作可允許使用者調高或調降警告、提示與違規的嚴重程度；錯誤不得調降，因為錯誤即為失效。
  - 相容性測試檢查錯誤（其位置與失效範圍）、違規（哪一項檢查未成立，以及針對哪些成員）以及最終場景；警告可作為選用預期項目；提示不予測試。
  - 附註：警告是對作者意圖的推測，會隨經驗調整；若將其列為強制要求，將會把這些推測寫死在標準中。原則 2.4 同樣僅強制要求基本錯誤。
- **內容**：診斷須提供：
  - 位置：檔案、行號與欄號或範圍；哪一筆記錄、敘述、欄位或引用（原則 2.8）；
  - 原因：預期是什麼以及實際收到什麼，例如「in_p 接收 instance，卻收到 net」（9.4）；找不到名稱時，給出最接近的名稱；
  - 上游原因：每條連帶失效的敘述須說明其上游原因，呈現方式可將這類敘述歸納在根本原因之下，以免一處筆誤在整張圖面上引發數十筆錯誤。當一條規則在許多物件上失效時，這些失效可合併為一筆列出所有物件的診斷，例如套件對每顆 MOS 寫了 `W/L=${w}/${l}` 而部分實例沒有 `w`；
  - 來源：由一般定義展開的敘述，同時給出套用處與定義中的原始敘述；由規則產生的敘述，給出該規則與評估該規則的層級；位於套件中的敘述，給出該套件的名稱、版本與檔案（16.2）。
- 本標準不規定診斷的措辭與語言。本版本沒有標準診斷代碼；實作可自行為診斷編號，但編號並不定義容錯等級。
- **套件**：在使用某個套件的文件中，套件內容中的錯誤照常回報並歸屬於該套件；關於套件內容的警告與提示僅在單獨檢查該套件本身時才給出。套件所寫斷言的違規會在使用它的文件中回報——因為它們針對的是該文件的電路——並點名套件中的斷言以及套用它的用例或規則。附註：使用者無法修改套件，而套件作者刻意撰寫的廣泛規則否則會讓使用者被大量警告淹沒。
- 檔案本身不能抑制診斷或要求更嚴格的模式。
- 未知關鍵字、參數與值皆為錯誤，如同語法錯誤（原則 2.3）：該敘述失效（16.4），但 SOLVER-CONFIG 除外，其中不被接受的值只使其 key 失效（14.10）。在本版本中，會被識別但不予解譯、且僅給出警告的內容，只有記錄標頭的未知欄位（2.8）與求解器不認識的 SOLVER-CONFIG key（14.10）。

## 14 布局意图

### 14.1 共同规则

- 约束产生一个约束对象。命名的约束可以引用，便于定位、编辑，如 `%row1 = {#M1 #M2} @ALIGN("y")`；约束也可以匿名。
- **词汇**：位置的原子约束只有 ALIGN、ORDER、DISTRIBUTE、DISTANCE 四种，加上 PLACE、ORIENT、GROUP 和 TABLE（14.11，即写成表格的排序）。别的关系写成普通定义：对称（14.7）、居中（三个成员的 DISTRIBUTE）、行列（ALIGN 加 ORDER）、信号流向（14.6）、镜像对、按比例的间距（几条精确的 DISTANCE）。没有 LEFT、ABOVE（它们就是带方向的 ORDER 或 DISTANCE），也没有 RATIO、NEAR、INSIDE。相对朝向（同向、互为镜像）写 ORIENT-RELATION（14.9）；一对器件的栅极相向还是朝外，仍用一个 ORIENT 或端子上的 ORDER 定（14.3）。符号不重叠、间距常数、网格归求解器（11.7），不属于约束的词汇。
- **没有相对整张图的位置**："最左""最右""最上"没有关键字，也没有整张图或符号外框的范围。写成相对一组对象的 ORDER 或 DISTANCE，求解器据此找出布局。如端口在最右边：`{#M6 #M7 #CL} %pout @DISTANCE("left-to-right", min=2)`，或者在 M7 本来就在最右时写 `{#M7 %pout} @ORDER("left-to-right")`。
- **成员是最底层的对象**：元件、叠画、端子和引脚、点、TEXT（取文字自己的位置，13.3）、按中心写的 RECTANGLE、CIRCLE 或 ELLIPSE 的中心，以及带符号画出的用例（各自取自身的点）。没有符号的用例本身不是成员，而是代表它的成员：填它角色的各个对象，其中没有符号的用例同 GROUP（11.5）一样继续向里展开到最底层的对象，并略去其中的网络。它自身的点写作 `%u::position`（6.5）。导线、网络、约束和定义不能作成员：收到时这条约束失效。导线上的位置应先写成点（13.1）。集合不是成员：它没有自己的位置（见下）。
- **取哪一点**：元件取它的原点，即它的符号的原点，PLACE 放的也是它；端子或引脚取引脚的位置，是器件位置加上符号里引脚位置的刚性变换，不能单独移动；点取它自己；有符号的用例或任意用例的 `::position` 取它自身的点（见下）；TEXT 取文字自己的位置；按中心写的 RECTANGLE、CIRCLE 或 ELLIPSE 取中心。不取符号外框的中心：三端、四端 MOS 符号的外框不同，排成一行会错位。要按引脚对齐就写端子。视觉上的对称要求原点落在符号的对称轴上，这归符号库。
- **用例自身的点（own point）**：每个用例都有自己的一个点，没有符号的用例也一样。这个点起初是自由的，如同 `(_, _)`，由事实来绑住：PLACE、约束、连到它符号引脚的导线，以及它定义的体写在它上面的事实；剩下来自由的由求解器定。有符号的用例画在符号原点处于这个点的位置（12.1），写在它上面的约束作用于这个点。写在没有符号的用例上的约束作用于它的成员（见上）；要约束它的点，写 `%u::position`：`{%dp::position #X1} @ALIGN("y")` 把 X1 放在差分对中心的高度上，而 `{%dp #X1} @ALIGN("y")` 会把 X1 和差分对的三个晶体管放在同一高度上。定义体在单独的 `?` 上写事实的地方（9.4），如 `{?members::position ?} @ALIGN("y")`，把这个点和它的成员绑在一起。用例的点没有任何事实绑在画出来的东西上时，写在 `%u::position` 上的约束没有可见效果，并给提示说明。
- **集合没有位置**：集合只是一个成员列表，没有中心，也没有范围。在 ALIGN、ORDER 或 DISTRIBUTE 的成员列表里，若是集合的项（直接写的 `{…}` 或集合引用，5.2），在该位置上分别代表它的每一个最里层成员：这条语句展开成对每个这样的项各取一个成员的每一种组合，每种组合一条约束。`{#M1 {#M2 #M3} #M4} @ORDER("top-to-bottom")` 就是 `{#M1 #M2 #M4}` 和 `{#M1 #M3 #M4}`，使 M2、M3 各自都在 M1 和 M4 之间，而 M2、M3 之间不定次序。是无符号用例的项也以同样方式代表它的成员（见上）。DISTANCE 槽位里的集合分别代表它的每一个成员，每一对一条约束（14.5）。空集合的项略去。同一对象取两次的组合略去：共用一个器件的两个结构按 `{%stage1 %stage2} @ORDER("left-to-right")` 排序时，对其余每一对成员排次序，而不让那个共用器件与自己排次序。
  - 这样生成的约束都取所写语句的优先级、名字和位置（8.5、14.8）；起名字时把这组约束绑在一起。成员太少而说不出什么的组合给一个提示。
  - 实现可以限制一条语句能代表的约束条数；超出实现上限（limit of the implementation）时，这条语句失效，报错说明已达实现上限（1.6）。
  - 当集合是唯一的对象时，先拆开一层（5.2.1）：`%row_set @ORDER("left-to-right")` 和 `{%row_set} @ORDER("left-to-right")` 都排序这个集合的成员。
- **方向要明确写出**。ALIGN 收一个投影，`"x"` 或 `"y"`（14.2）；ORDER、DISTRIBUTE 和 DISTANCE 收一个方向，四选一（14.3）。没有把方向留空的写法：两种方向都能画的关系，写成某一种方向的一条事实；要同时允许两种画法的定义，分成两个定义，如标准包的 `$BRANCH` 和 `$BRANCH_HORIZONTAL`。唯一提供备选的事实，是 ORIENT（11.2）和 ORIENT-RELATION（14.9）的朝向列表。
- 约束不改变网表。冲突时一条原子约束整条保留或整条丢弃（8.5）。
- 四种原子约束、ORIENT-RELATION 和 TABLE 都收参数 `priority=`（14.8）。

### 14.2 ALIGN

`{…} @ALIGN("y")`：成员在 `axis` 这一投影上相等，`"y"` 是 y 相同（排成一行），`"x"` 是 x 相同（排成一列）。`axis` 必写，可以按位置写，只能是一个投影：投影列表是错误的参数值，这条约束失效。成员不到两个时这条约束自然成立，不失效：筛选和集合有几个成员，写语句的时候不知道。

### 14.3 ORDER

```rnl
%rc_set = {#R2 #C2};
{#M1 #M1:2 #M2:2 #M2} @ORDER("left-to-right");  /* M1 on the left, the two gates face each other */
{#R1 {%rc_set} #M1} @ORDER("left-to-right")     /* R2 and C2 each between R1 and M1 */
```

- `{…} @ORDER(direction)`：成员沿方向所在的投影严格单调。成员不到两个时自然成立。
- **方向**：参数 `direction`，必写，按位置写在最前。取值：
  - `"left-to-right"`、`"right-to-left"`：沿 x 递增、递减；
  - `"bottom-to-top"`、`"top-to-bottom"`：沿 y 递增、递减（y 向上，11.7）；

  DISTRIBUTE 和 DISTANCE 的取值与此相同。没有只定在哪一轴上的值：`"x"` 和 `"y"` 是错误的参数值，这条约束失效。
- 是集合的项分别代表它的每一个成员（14.1）：第二个例子分别排 R1、R2、M1 和 R1、C2、M1；R2 和 C2 之间不定次序。
- ORDER 是关于点的事实：它比的是成员的点，不是它们的外框。沿 ORDER 把符号外框分开是求解器的准则，排在全部事实之后（8.5）；当事实迫使外框重叠时它们就重叠，可以给提示说明。
- ORDER 是严格的：相邻成员至少差一个坐标单位（11.7）。它简写相邻每对成员之间、沿同一方向且 `min=1` 的一条 DISTANCE（14.5）。要坐标相等，用 ALIGN。

### 14.4 DISTRIBUTE

```rnl
{#R1 #R2 #R3} @DISTRIBUTE("left-to-right")     /* R1, R2 and R3 from left to right, in equal steps */
```

- `{…} @DISTRIBUTE(direction)`：成员沿方向严格依次排列（同 ORDER，14.3），并且相邻成员在该投影上的差相等。比的是成员那一点之间的步长，不是外框之间的间隙；是集合的项分别代表它的每一个成员（14.1）。
- **方向**：参数 `direction`，必写，按位置写在最前，取值同 ORDER（14.3）。
- 只有两个成员时，DISTRIBUTE 与 ORDER 相同；不到两个时自然成立。

### 14.5 DISTANCE

```rnl
#M1:2 #M1 @DISTANCE("left-to-right", min=1);      /* the gate is on the left */
#R1 #R2 @DISTANCE("left-to-right", exact=8)       /* R2 exactly 8 units to the right of R1 */
```

```rnl
%stage1_set = {#M1 #M2 #M5};
%stage2_set = {#M3 #M4};
%stage1_set %stage2_set @DISTANCE("left-to-right", min=1)     /* all of stage 2 is to the right of all of stage 1 */
```

- `A B @DISTANCE(direction, min=…, max=…)`：A 填槽位 `from`，B 填槽位 `to`；各是一个对象或一个集合。
- **方向**：参数 `direction`，必写，按位置写在最前，取值同 ORDER（14.3）。只约束这一轴，不是欧氏距离。
  - 沿递增方向（`"left-to-right"`、`"bottom-to-top"`）约束 B − A；
  - 沿递减方向（`"right-to-left"`、`"top-to-bottom"`）约束 A − B。
- **集合**：槽位里的集合分别代表它的每一个成员（14.1），没有符号的用例也一样，DISTANCE 对 A 的每一个成员到 B 的每一个成员分别成立，每一对一条约束；对象与自身的配对略去。所以 `%stage1_set %stage2_set @DISTANCE("left-to-right", min=1)` 把第 2 级全部放在第 1 级全部的右边，两个不能交错的集合就这么写。一边是空集合时没有配对，什么也不做。
- `min`、`max`、`exact` 至少应写一个；`min` 不应大于 `max`。DISTANCE 同时也定下了顺序：B 在这个方向上绝不在 A 前面。因此界限不能为负，负的 `min`、`max` 或 `exact` 是错误的参数值，会让约束失效；不写 `min` 时默认为 0，所以 `max=10` 表示距离从 0 到 10 之间都成立。
- `exact=` 是精确的距离，就是 `min`、`max` 相等的简写：沿递增方向时 B − A = exact，沿递减方向时 A − B = exact。它不能与 `min` 或 `max` 同写：同写是无效的参数，这条语句失效。工具写精确距离时写 `exact`（4.3）。

### 14.6 信号流向

信号流向（原则 2.4）写成普通定义的用例，没有关键字。标准包提供不提供这样的定义、叫什么名字，归标准包（16.3）；例子用标准系列 0.4 的 `$SIGNAL_FLOW`，它点明一条写成集合的路径，并且可以在前面写出来源、在后面写出负载。它是语义定义，本身不摆位置。

```rnl
%rc_set = {#R2 #C2} @GROUP;
{#R1 {%rc_set} #M1} @AS $SIGNAL_FLOW                                    /* the signal goes from R1 through the block of R2 and C2 to M1 */
{#:inp #:inn}(source) {#R1 {%rc_set} #M1}(path) #CL(load) @AS $SIGNAL_FLOW   /* from the two inputs of the level to the load CL */
```

- 信号流向是软的概念：不是所有电路都有严格的方向。求解器可以把它当作偏好；要把各级按次序摆在图上，写 ORDER 或 TABLE（14.3、14.11）。
- 路径上由几个对象组成的一段，单独写成一个 `{…}`，如 `{%rc_set}`。GROUP（11.5）只让求解器把它当作一块，可以不写。
- 来源与负载各自成一组，没有顺序之分，例如差分信号的两个输入。它们可以是元件、结构、这一层的端口如 `#:inp`（6.4）、其他端子，或网络。不标角色时，写出的对象就是路径，如第一行所示。
- 功率流——从电源经转换或开关它的各级，流向使用它的各部分——用 `$POWER_FLOW` 按同样写法表示。

### 14.7 对称

对称写成普通定义的用例。对称轴只是一个自由点，不需要关键字。标准系列 0.4 提供 `$MIRRORED_LAYOUT`，角色是 `left`、`right`、`axis`：left 和 right 同高，轴在两者的正中，right 的朝向是 left 左右翻过来的；还有 `$MIRRORED_VERTICAL_LAYOUT`，角色是 `top`、`bottom`、`axis`，把同样的关系竖过来摆。这两种用例自身的点都在两侧之间的中心（14.1），因此对用例施加约束会带动这一对一起移动。同标准包的每个定义一样，这些约束的优先级都是 `"low"`（9.5）。轴是一个对象：几个器件立在轴上时，先把它们做成一个用例，这个用例按它自身的点算（14.1），或者只给其中之一。

```rnl
%ax = (_, _);
%sym12 = #M1(left) #M2(right) %ax(axis) @AS $MIRRORED_LAYOUT
```

- `$MIRRORED_LAYOUT` 不定实际的朝向：栅极朝内还是朝外，仍要给一边写 ORIENT（14.9）。要两边同向的对称，另写一个普通定义，不带其中的 ORIENT-RELATION。

### 14.8 优先级：PRIORITY

```rnl id=dpl
$DP_LAYOUT = @DEFINE(roles=["in_p", "in_n"]) {
  {?in_p ?in_n} @ALIGN("y", priority="low")                    /* a default layout, the first to give way */
};
%dp2 = #M1(in_p) #M2(in_n) @AS(priority="high") $DP_LAYOUT;     /* this pair keeps the default layout strictly */
#M1 @PLACE(12, 20, priority="high")                             /* fixes the position of M1 */
```

```rnl use=dpl
# @SELECT-USAGE(recursive=true) $DP_LAYOUT => @PRIORITY("disabled")    /* a house-style package turns the default layout off, to apply its own */
```

- **四档**：`"disabled"`、`"low"`、`"normal"`、`"high"`。没写优先级的事实都是 `"normal"`，不论写在用户的记录里、包里还是定义体里。
- **分级，不加权**：冲突时先比优先级，高的保留；优先级相同，后写的保留（8.5）。约束不做加权求和。

  注：加权时，十条低优先级的约束能压过一条高优先级的；而且各求解器量"违反了多少"的办法也不同。
- **每条保留下来的事实都是硬的**：`"low"` 的意思是"冲突时先丢弃"，不是"尽量接近"。保留下来的事实，不论优先级是哪一档，求解器都必须满足；实现自己的美观目标只在保留下来的事实之内优化，排在语言的全部描述之后。
- **`"disabled"`**：这条事实在排序之前去掉，不交给求解器。这不是失效：对象照样存在，依赖它的描述不受影响，不给警告，后写的优先级可以把它重新打开。
- **写法**：
  - PLACE、ORIENT、四种原子约束、ORIENT-RELATION、TABLE、ROUTE-NET、ROUTE-OBJECT、UNROUTE-NET、UNROUTE-OBJECT、AS、ATTACH 都收参数 `priority=`，优先级跟着这条事实。`priority` 是 AS、ATTACH 唯一的标准参数；定义的参数不能叫这个名字。
  - PRIORITY 语句用来事后改优先级。它只收有自己句柄的对象：约束、用例，以及带 GROUP 的集合（只能开关，11.5）。收到带 GROUP 的集合时作用于分组本身；别的集合逐个成员处理（5.2.1）。收到元件或别的对象时失效（种类不对）：`#M1 @PLACE(…) => @PRIORITY(…)` 是错误，因为 PLACE 沿用 M1 的句柄；优先级要写成 PLACE 的参数。
  - 记录头 `@RNL(priority=…)` 给记录里收这个参数、又没写它的语句一个默认值，也给 TEXT 的 `dx`、`dy`（13.3）。给 AS、ATTACH 的只有 `"disabled"`，所以关掉的记录连同其中的用例和它们的体一起关掉，和记录里别的语句一样。记录头是 `"high"`、`"normal"` 或 `"low"` 时，用例只在它自己的语句或 PRIORITY 语句给了优先级时才有优先级，否则它的体保持各自的优先级，和规则生成它时一样，所以求解器写出的用例（10.5）和生成的那个意思相同。用例明写的优先级照旧盖过它的体（见下）。
- **覆盖的次序**，从低到高：记录头的默认值；语句自己的参数；PRIORITY 语句（几条之间后写的生效；包里的按 USE-PACKAGE 的位置）；外层用例的优先级；从用例外面经 `::` 直接写在它的某个局部对象上的 PRIORITY 语句（几条之间后写的生效）。这些都没有时，优先级是 `"normal"`。
- **用例的优先级向下传**：用例的优先级（它自己的参数，或写在它上面的 PRIORITY 语句）作用于它展开出的全部事实，包括嵌套的用例展开出的，并盖过它们自己的优先级；嵌套时，最外层带优先级的用例说了算。要只调里面的一部分，就从外面经 `::` 直接写在那个局部对象上（9.4）：它比用例的优先级更具体，所以盖过用例的优先级，越具体的越优先。这种语句若写在外层定义的体里，仍受外层用例的优先级管。记录里的每条语句都能直接改，所以记录头只给默认值。
  - 完整地说：用例的优先级管住它的定义体里写的全部 PRIORITY 语句，这些语句不再起作用。从外面经 `::` 直接写在局部用例上的 PRIORITY 也这样管住：那个用例算作带优先级的最外层，这条语句对它展开出的全部事实说了算。没被管住的语句之间，写在最里层对象上的胜出；写在同一对象上的，从产生这个对象的定义体外面写的，胜过写在这个体里的；再比后写的胜出。
  - 例如 `%o1` 为 disabled，顶层写 `%o1::in @PRIORITY("high")`，`%o1` 的定义体里写 `%in::row @PRIORITY("low")`：`row` 的事实是 `"high"`。体里那句受 `%o1` 的优先级管，而顶层那句为 `in` 盖过了这个优先级。`%o1` 若没有优先级，结果是 `"low"`：体里那句写在更里层的对象上。要两种情形都是 `"low"`，从外面写 `%o1::in::row @PRIORITY("low")`。
- **求解器的输出**：求解器把结果写成 PLACE、ORIENT 等，用 `"high"`，放在这一层自己的文字的最后一个记录里，如 `@RNL(type="generated", priority="high") {…}`。子电路写在它的 `.subckt … .ends` 之内，哪怕它在被引入的文件里；顶层写在主文件的文件层（第 17 章）。求解器求解时，不把 `type="generated"` 的记录算进解释（2.8），所以旧结果不会约束下一次求解；求完后删掉它们，在最后写上新的结果。
  - 两次求解之间，新写的 normal 语句若与求解结果冲突，会被丢弃，下一次求解后才生效。查看器可以按记录头的散列值建议重新求解；这类丢弃不必逐条报告。
  - 编辑器里的拖动写成 `"high"` 的 PLACE，同样写在这一层自己的文字里，放在求解器的记录之后。这就把位置固定住了：以后每次求解都把它当硬约束。要放开，删掉那条语句。
- **求解器写回什么**。求解器的记录应包含它定下的、文本里没定的每个位置、朝向和走法：有名字或 key 的对象用名字或 key，别的用编号（5.9），导线的走法用 WIRE 改写（13.1），规则生成的对象写成显式语句（10.5）。没写进记录的决定不算结果：那个对象仍是自由的，如同这一层没求过解。所以不求解的查看器画出的，正是求解器画的那张图。求解器引用不到的，它不去定，如生成规则直接产生的、没有 key 的文字的位置；这样的文字由查看器放（13.3）。规则造出的用例无法写出时——如它的定义是包私有的（16.2）、没有符号也没有文字，且没有别的对象或导线按它的点定位——它自身的点也不写回：这样的点只供求解器辅助求解，图面上没有任何画出来的东西落在上面，留作自由不改变任何图面，也不算漏写的决定。
- **求解器的结果就是 RNL**。求解器以别的形式把结果交给别的工具时，比如求解器与查看器之间的消息，这种形式应只含有求解器的记录能含有的东西，使任何结果都能存成这样一条记录。
- **求解器的优化目标**只在满足全部保留下来的事实的摆法里挑；保留下来的事实不论优先级都是硬的。优化目标不属于语言：目标的种类和次序因求解器而异，本标准定不出它们的共同词汇。只定了一条默认规则：没有遮挡也没有并到别的导线里的 `"auto"` 导线解成它的默认走法（13.1），它先算拐点数、再算长度。求解器选项是散列值所覆盖的输入的一部分（第 17 章）；文件用 SOLVER-CONFIG 保存它们，以便结果能够复现（14.10）。

### 14.9 朝向关系：ORIENT-RELATION

```rnl
#M1 #M2 @ORIENT-RELATION("MY");                  /* M2 is drawn as M1 flipped left-right */
#M5 {#M7 #M8} @ORIENT-RELATION("R0");            /* two facts: M7 and M8 each have the orientation of M5 */
#M3 #M4 @ORIENT-RELATION(["R0", "MY"])           /* M4 as M3, or as M3 flipped left-right */
#M1::g #M2::g @ORIENT-RELATION("R180")           /* the gates of M1 and M2 face opposite ways */
```

- `A B @ORIENT-RELATION(relation)`：两个槽位 `from`、`to`，各是一个对象。关系是 ORIENT 的八个朝向码之一（11.2），或它们的列表，按位置写。B 的朝向等于先按 A 的朝向变换、再做这个关系的变换。变换在图的坐标系里做，所以 `"MY"` 总是关于竖直线左右翻，与 A 本身转没转无关。
- **关系的列表**，如 `["R0", "MY"]`，是一条事实，当 A 和 B 之间满足所列的某个关系时成立。它作为一个整体保留或丢弃（8.5），由求解器挑选画哪一种关系。列表里至少有一个朝向码；只写一个朝向码的列表与直接写这个码相同。
- **一对一**。某一个槽位里的集合逐个成员处理（5.2.1），每个成员一条事实：`#M5 {#M7 #M8} @ORIENT-RELATION("R0")` 让 M7 和 M8 各自取 M5 的朝向，于是三者同向。两个槽位同时收到不止一个成员的集合是错误：按次序配对和两两之间全配对都说得通（5.2.1）。
- 没有"只给一个集合、集合里朝向都相同"的写法：关键字说的是两者之间的关系，只给一个集合时看不出关系作用在什么上。只写一个对象与签名不符，是错误。只写一个集合时，照 5.2.1 先拆一层，所以 `{#M1 #M2} @ORIENT-RELATION("MY")` 就是 `#M1 #M2 @ORIENT-RELATION("MY")`；拆出来不是两个对象时是错误。
- 成员是有朝向的对象，与 ORIENT 相同（11.2）：元件、叠画、有符号的用例；或者两个都是引脚（见下），端子代表它的引脚（5.2.4）。点、网络、导线、没有符号的用例，以及一个引脚配一个对象，都是错误：这条约束失效。一个槽位收到空集合时，没有可配的关系，什么也不做（5.2.1）。
- **引脚**。两个槽位都是引脚时，关系成立在两个引脚在图上的方向之间（11.2）：B 的方向等于 A 的方向按关系旋转变换后得到的结果，如朝向相反的引脚写 `"R180"`，带镜像的朝向码像变换点那样变换方向。关系只写朝向码：11.2 的方向词指方向而非旋转，写在这里是错误的参数值，会使约束失效。没有写 `direction=` 的引脚会让那条事实失效（9.2.4）。
- 它是约束：产生一个约束对象，可以命名，收 `priority=`，可以用 PRIORITY 改（14.8）；冲突时整条作为一个单位保留或丢弃（8.5）。逐个成员处理时，每个成员产生一条约束，起名字时把这组约束绑在一起（5.2.1）。已经通过 ORIENT 写了单个朝向码的成员朝向已经固定；别的成员由求解器在满足关系以及各自 ORIENT 列表的朝向里挑选（11.2）。
- 它不定实际的朝向：两个 MOS 互为镜像时，栅极朝内、朝外都满足 `"MY"`。要定下来，再写一个 ORIENT，或者端子上的 ORDER（14.3）；要缩窄范围而不定死，用带列表的 ORIENT（11.2）。

### 14.10 求解器设置（solver settings）：SOLVER-CONFIG

```rnl header
@SOLVER-CONFIG(spacing_x=2, spacing_y=1, layout="lines", lines_weights=[1, 4])    /* the default of the file */
```

```rnl
@SOLVER-CONFIG(spacing_x=1)                                                       /* this level: overrides the key spacing_x */
```

- SOLVER-CONFIG 给求解器提供设置，使文件可以用相同的设置重新求解。它不产生事实：求解器只用这些设置从满足全部保留事实的布局里挑选（14.8）。
- **写法**：RNL 字面量写成的命名参数：数、字符串、`true` 和 `false`，以及它们的数组（3.7）。没有嵌套的设置。除了本标准点名的键（见下），其余键不是标准词：各求解器自己定义自己的键。核心把参数当作 RNL 字面量读入，按下面的次序原样传给求解器，一个也不合并掉；对于取值，它只检查本标准点名的键的取值。其余的键和取值由求解器判断：不认识的键给警告并忽略。求解器也可以只在它自己的某些设置下收某个键，例如一种布局用、另一种布局不用的目标；在不用这个键的设置下，这个键同样被忽略，并给出警告。
- **本标准点名的键**：`spacing_x` 和 `spacing_y`，按网格单位计的这一层的间距，加到求解器默认间距上，与分组相同（11.5）；`junction`，求解器画分叉点圆点所用的定义，是写成字符串的 `$` 名字，如 `"$JUNCTION"`，在层记录的 SOLVER-CONFIG 里也可以是在这一层查找的 `%` 名字（6.6），使为某个子电路定义的变体留在它里面，或者写 `""` 表示不画圆点（13.2）。每个求解器都收 `junction`。本版只点名了这几个键，并非求解器只能收这几个键：求解器还有哪些别的键（如例中的 `layout` 和 `lines_weights`）以及它们是什么意思，归那个求解器，由它的文档说明。有整层间距设置的求解器按这两个名字读它。
- **写在哪里**：不带 `language` 的头段记录里，管这个文件和它引入的文件的各层，与 DEVICE 相同（2.8、6.12）；包文件的头段记录里，管用到这个包的各层（16.2）；一层的记录里，管这一层。它没有对象。写在包的内容里、内嵌包里、带 `language` 的记录里或求解器的记录里，都不起作用并给警告；因此只经由带 `language` 的头段记录用到的包不提供设置。
- **次序**：设置按键覆盖，后写的盖过先写的：求解器的默认；这一层用到的包的头段记录，按包的位置排序（同 DEVICE，6.12）；外层文件的头段记录，再到被引入文件的头段记录；这一层的记录；最后是传给工具的设置，如命令行或查看器页面里的设置。工具传设置采用括号里相同的写法，两边可以互相抄用。
- **取不上的值**，如该收数的地方给了字符串，只使那个键出错（16.4）：这个键在那个地方按没有写处理，所以此前的值继续有效，同一条语句里的其他键照常生效。取值在它适用的每一层里分别判断：头段记录里的 `junction`，在某一层里找不到定义，就只在那一层取不上，其他层仍用它。核心判断本标准点名的键的取值，取不上的就略去；求解器判断它自己的键的取值。所以求解器收到的设置是按上面次序排的一个列表，其中同一个键可以出现多次，对每个键，求解器取它能接受的最后一个值。
- **时间或工作量预算**（8.5）只由工具给出，如命令行或查看器的页面，从不由文件给出：预算取决于求解的机器。求解器里设定预算的键，如内置求解器的 `limit`、`seconds` 和 `work`，是它的工具专用键：写在 SOLVER-CONFIG 里，不论在哪种记录中，这样的键都会被忽略并给出警告，和未知键一样，生效的仍是工具给的预算或求解器的默认值。
- 对某一层生效的设置（包括包里的），是求解器散列值所覆盖的输入的一部分（第 17 章）。

### 14.11 表格：TABLE

```rnl
@TABLE layout: {
  {#M1 #M2 #M3}
  {#M4 {#M5 #M6} #M7}
}
```

- TABLE 用嵌套的 `{…}` 把对象摆成一张布局表（layout table）：上例从上到下有两行；第一行从左到右依次是 M1、M2、M3；第二行从左到右依次是 M4、由 M5 和 M6 组成的单元格，以及 M7；那个单元格里 M5 在 M6 上方。表格可以跨多行写。标准写法把关键字写在最前，读成 "@TABLE layout: {…}"（4.3）；那里的 `layout:` 一词是自由文本（3.3），而 TABLE 接收该表格的槽位名是 `rows`（附录 A）。
- **读法**：外层列表从上到下，一项是一行；嵌套在里面的每一层列表与包着它的列表垂直：在从上到下的列表里从左到右，在从左到右的列表里从上到下。`transpose=true` 使外层列表变成从左到右。传给 TABLE 的集合就是它原样的外层列表，不先拆开一层（5.2.1 第 2 条），因此 `@TABLE layout: {{#M1 #M2 #M3}}` 是一行，而 `@TABLE layout: %port_set` 让集合里的每一项各占一行。
- **项**：是对象的项是一个单元格；是集合的项（写在表里的 `{…}` 或集合引用）是往里一层的列表。这就是 TABLE 的规则：里面的集合不再代表它的每一个成员（14.1）。带符号画出的用例按自身的点作一个单元格；没有符号的用例是一个容纳其全部成员的单元格（14.1），其中每个成员都排在下一项之前；写 `%u::position` 则把它自身的点作一个单元格。
- **事实**：一条 TABLE 是一条几何事实，冲突时作为一个整体保留或丢弃（8.5）。它成立的条件是：在表格的每一层列表里，每一项的每一个点都严格排在下一项的每一个点之前（沿这个列表的方向）：至少早一个坐标单位，与 ORDER 相同（14.3）。检查器可以把它展开成这样的 ORDER；求解器把它作为一个整体连同外层列表和内层列表的方向一起收下。
- **分组**：整张表里的对象组成一个分组，就像在同一个集合上写 `@GROUP`（11.5）；它的各行、各列不各自成分组。
- TABLE 不对齐：各行不必同高，各列不必同一个 x。要对齐就写 ALIGN。单元格不能跨多行或多列。
- 表里的空列表略去，它的相邻项变为相邻（14.1）。只有一格的表格自然成立，也不成分组。同一个对象写进一张表的两个单元格，就得排在自己前面，所以这条 TABLE 失效；收到无法定位的成员（如网络或没有引脚的端子，14.1）时也失效。
- TABLE 收 `priority=`（14.8），并产生一个约束对象，可以命名。

# Vocabulary audit of RNL 0.3 revision 2

This is the exhaustive vocabulary appendix to the [supported profile](supported-profile-0.3.md), checked against the normative English [Annex A](../spec/0.3/en/annex-a.md) and [`rnl-words-0.3.json`](../spec/rnl-words-0.3.json) at `spec-0.3-r2`. It covers all 46 keywords, every parameter of each keyword, the seven record fields, 12 style properties, kinds, slot categories, sub-objects, attributes and truth values. It records implementation and test evidence, not a certification of every possible program.

**Reading the tables.** “Supported” means the named syntax and its described semantics have an implementation; qualifications are explicit. Parameter types, required flags and enumeration values below were compared with the runtime signature data and the implementing handlers. Defaults stated in the word list are reproduced below; omitted optional fields have the contextual behavior in the notes. A cited test or corpus fixture is evidence for that word; it does **not** imply that every parameter value and every invalid combination has a dedicated test. Coverage gaps are called out below. The old `tests/conformance/cases/` corpus declares 0.2 and exercises shared handlers; 0.3-specific behavior is checked in `cases-0.3/` and the focused Rust tests.

## Signature source and validation

The runtime embeds [`data/words-0.2.json`](../crates/rnl-runtime/data/words-0.2.json) through [`words.rs`](../crates/rnl-runtime/src/words.rs):`words`, rather than loading the published JSON schema at run time. After normalizing the two data formats (`term` versus `terminal`, implicit enum types, arrays versus keyed objects), all 46 keyword names, their declared named-parameter types, required flags and allowed enumeration values match 0.3. The extra 0.3 record field `numbering` comes from `words.rs:draft_header_fields`. The old identifier and draft comments are historical names, not evidence that 0.3 is disabled. The maintained [`vocabulary_parity.rs`](../crates/rnl-cli/tests/vocabulary_parity.rs) check compares the signatures actually loaded by `words()` (including the 0.3 header supplement) with the published list. It checks word inventories, parameter types/enums/required flags, positional order, at-least-one rules, slot order/names/takes/kinds/optional/enclosure, dynamic definition slots/parameters, contexts, style groups, output/selection kinds, override metadata, sections and version introductions. The F-05 follow-up corrected three descriptive discrepancies: DEFINE-STYLE's style-body kind, SELECT-USAGE's arbitrary-member scope, and TEXT's keyed override. Existing handlers already implement these rules; slot `kinds` and keyword `override` are descriptive metadata, not dispatch gates. AS/ATTACH now get their fixed optional `priority` parameter from the canonical PRIORITY signature instead of duplicating its enum in a handler.

Defaults and structured rules that live in handlers are checked by executing the published values: omitted versus explicit parameters, both recursive-inheritance outcomes, renderer style defaults, record defaults, shape dimensions/together/exclusive rules, keyed text and wire rewriting. Every JSON field is accounted for and an unknown field fails the check. Prose descriptions, example `form`/`sentence` templates with ellipses, and explanatory `items`/`key`/`meaning` strings are not compared as executable signatures; their natural-language requirements remain covered by the semantic audit and focused behavior tests. The runtime-only phase numbers have no published counterpart. This check runs in the existing Rust workspace CI, whose path filters now include the published JSON and its schema. It establishes vocabulary parity, not exhaustive coverage of every optional-value combination.

Ordinary parameters use [`eval.rs`](../crates/rnl-runtime/src/interp/eval.rs): `params / require / check_value`. Unknown names, duplicates, wrong types/enums and missing required values fail. Parameterless keywords now perform that validation too, rather than ignoring extra parameters (`kw.rs:keyword`; `profile_validation.rs:parameterless_keywords_reject_parameters_before_changing_objects`). Header/package parameters use [`unit.rs`](../crates/rnl-runtime/src/interp/unit.rs): `params_by_name`; this audit adds the missing String/Array type check. DEVICE now rejects non-string terminal array entries; terminal parameters now reject nonpositive/fractional/out-of-range indices and invalid PIN array entries instead of silently filtering or truncating them. See [`profile_validation.rs`](../crates/rnl-cli/tests/profile_validation.rs).

This is not complete semantic conformance: the VERSION, DEFINE-SYMBOL and BUNDLE rows are explicitly partial, and all rows must be read with the [main profile’s remaining gaps](supported-profile-0.3.md). `required` means there is no default. `style: line/area/wire/text/all` refers to the exhaustive property table below. `AS` and `ATTACH` also accept exactly the user-defined parameter list; those names are intentionally not a fixed standard vocabulary.

## Policy decisions and limits

- **Host support:** SPICE and Spectre adapters supply connections, model/master/type and terminals; they are netlist readers, not simulators. Vendor constructs outside their documented readers and future language 0.4 device selection are not implied by the complete keyword list. See the [SPICE](../crates/rnl-host-spice/README.md) and [Spectre](../crates/rnl-host-spectre/README.md) adapter profiles.
- **Geometry:** ordinary viewer checks use `geom.rs:TOL = 1e-6`; solver decisions use exact rationals with a configurable tolerance (default `1e-6`, `rnl-solver/src/options.rs:SolverOptions`) and configurable work/time limits. A timeout reports undecided facts, not a false proof that a conflict exists. See `rnl-solver/src/resolve.rs` and its tests.
- **Wires:** `geom.rs:route` draws auto as straight; manhattan chooses a centred dogleg along the larger separation; manhattan45 uses a centred diagonal segment. ROUTE mode is a hint (§13.7): solver v1 currently routes rectilinearly and does not rewrite authored auto WIREs. Multiple same-net ROUTEs use the first style and report different styles (`rnl-solver/src/route.rs:style_notes`).
- **Appearance:** the style defaults above, arrowhead shape, pin labels and default text placement are renderer policy. `phases.rs:text_default_place` and `drawn_default_place` choose a display position where no geometric fact supplies one. The solver does not optimize free labels or all free text; objects left free are reported. Font fallback estimates can differ from actual platform glyph advances.
- **Package lookup:** `unit.rs:resolve_package` and `rnl-cli/src/provider.rs` choose local/bundled package candidates; absent version asks for the newest, equal versions prefer earlier package directories. Bundled standard series 0.2 and 0.3 are selected by file version/pins. This is not network package installation.
- **Generated objects:** §10.5 requires a generating rule to leave out an object already written explicitly if a reread must avoid making another. Arbitrary custom generators that never exclude the written object are not made idempotent automatically; their writeback remains an open design item in the roadmap.
- **Editor and solver scope:** `rnl-edit` writes new netlists without RNL records and refuses editing existing RNL records; the solver’s generated-record writeback is a different supported path. Warm starts, drag projection, solver WebAssembly bindings and full layout quality optimization are not provided by complete language vocabulary support.
- **Regression gaps:** existing tests cover shared handlers, the published 0.3 changes and the failures repaired here. They do not exhaust the cross product of all 46 signatures, every optional parameter, aliases, all nested contexts, all enum alternatives and all erroneous values. In particular no dedicated nondefault `font`/`arrowsize` assertion or metadata-only `modified` test was located. This audit does not count source presence alone as such a test.

## Vocabulary versus normative prose

No missing keyword or parameter was found between the published JSON and English Annex A. Two useful clarifications must come from the prose: WIRE may receive one existing wire in its net slot (§13.1), although Annex A/JSON list that slot kind as net; PIN parameter type terminal permits an array but each element is a number/name and the array is nonempty (§9.2.4). The implementation handles the former explicitly and this audit fixes validation of the latter. The upper bound of terminal indices is the runtime’s `u32` representation; the standard gives no numeric implementation limit, so indices beyond it are rejected instead of silently clamped. No `spec/` file is changed.

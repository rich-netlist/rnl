# RNL core 0.6.3

The `rnl` command and the npm package `@rich-netlist/runtime` 0.6.3, built from the same core.
It reads a large design faster: a reading with records of the solver counts the objects of the
authored records with less work, and the scenes take terminals, pins, nets and instances once
where they took them again for each use. A frontend that shows one file of a document at a time
can now keep the reading of that document between its requests, ask for a smaller first answer
and the rest after, and send the Worker only the texts it does not hold. RNL Viewer 0.6.3 is
released with it and uses all of them. The language is still RNL 0.4, and every reading of a
whole document gives what 0.6.2 gives.

## Added

- **A reading cache.** An outline or file request with `"cache": true` reads through the reading
  cache the module holds. The host document that the last such request read is taken when every
  file it read reads the same, and kept for the next, so that the outline and the files of the
  document shown are read from one host document. The objects of the authored records it counted
  (5.9) are kept too, and taken by the next reading that would count them of the same. The answer
  is the same as without the cache. A request without `cache` neither takes from it nor changes
  it, and `"forget": true` drops what it holds. Nothing is written anywhere. In Rust, it is
  `rnl_view::ReadingCache`, with `outline_cached`, `build_file_cached` and
  `build_file_drawn_cached`.
- **The hints after the file.** A file request with `cache` and without `hints` keeps its
  reading. A request with `"hints_of"` set to that file then gives its geometry hints, as
  `"hints": true` would have given them, without reading it again: `{"hints": ...}`, declared as
  `FileHints`, or `hintsOf()` in `client.js`. It gives them once; when the reading is not kept,
  the answer is the error `not kept`, and the frontend asks for the file with `hints`. In Rust, it
  is `rnl_view::file_hints_cached`.
- **A smaller first answer.** A file request can leave out of its answer:
  - the texts of the files it gave, with `"texts": false`; those of the bundled packages are
    kept, even when a bundled package is the entry;
  - the spans, with `"spans": false` and `cache`.

  A request with `"rest_of"` set to that file then gives `{"rest": {"spans": ..., "hints":
  ...}}`, declared as `FileRest`, or `restOf()` in `client.js`. On a large level the spans are
  about 45% of a file's answer and the texts about 9%. In Rust, these are
  `ReadingCache::keep_spans`, `rnl_view::file_rest_cached`, and `rnl_view::leave_out_texts`, which
  gives the texts it took, by path, for a frontend that keeps them to put back.
- **The outline:**
  - `OutlineFile.records` is how many records a file holds besides its header records, each once:
    0 when its RNL is a header record alone, or when it has none. A header record is told as the
    reading tells it.
  - `Outline.missing` now lists the package files that records name by `path=`, as the reading
    looks for them: the path joined to the directory of the file whose record names it, and the
    packages that such a package names by path, joined to its own directory. Only the records of a
    file whose language version is read are looked at. A frontend that gives these files with its
    first request has a reading that does not have to start again for them.
- **The Worker keeps the texts.** Of a request with `files`, `client.js` sends the Worker only the
  texts it does not hold from the request before, with the paths of all of them, so the texts of a
  large document are not written out and sent again for each request. The request is taken as it
  is when the call is made, and the core reads the same request as before. `worker.js` takes such
  a message as `{ id, request, paths }`.
- **Rust:** `rnl_runtime::interpret_taking` and `Interpretation::authored_counts` take and give
  the count of the objects of the authored records, with `rnl_view::read_noting_taking`,
  `rnl_view::interpret_with_taking` and `RecordFinisher::finish_written` around them. A count is
  taken only when the reading would count it of the same: the same options but `generated` and
  `problems`, the same records but those of the solver, the same texts but the lines of those
  records, and the same package files, by path and text.

## Changed

- The WebAssembly core's module is built at `opt-level = 3` instead of `"s"`, so its readings
  take less time and it is larger: 5.80 MB instead of 4.58 MB, 1.86 MB instead of 1.38 MB with
  gzip. The solver's module, loaded only to solve, keeps `"s"`.
- A Worker of a build that brings packages (`build.mjs --packages`) now gives them to an outline
  request too, so that a package file a record names by path is not listed as missing. The npm
  package and the web viewer bring none.

## Faster

- **Counting the objects of the authored records.** A reading of a document with records of the
  solver that use numbers first reads it without them, to count the objects of the authored
  records (5.9). That reading now stops once nothing it gives can change, and is not made again
  where its count can be taken: a reading with the solve status or the constraints reads the host
  document once and the reading with the records takes the count of the one without; a solve's
  check that a record reads back, and each trial of its dots, finish the record on the text as
  written and take that count.
- **The scenes.** A named sub-object made by a rule is resolved again only when something it reads
  has changed, which made the fill of a level of many instances take a time that grew faster than
  the level. An owner's terminals, the nets of a bundle's terminal and the instances of a scene are
  taken once per scene, a terminal's pins are bound by its own names, and the model patterns of
  the DEVICE declarations are matched once for each model.
- **Reading the files.** A package file named by path is read once per reading. The host readers
  check a line without copying it when nothing on it can match. The type and fields of a record
  are read from its head alone. The records of the solver are looked for only when the solve
  status or the constraints ask for them.
- **In a viewer,** the reading cache, the hints after the file and the smaller first answer above
  spare a file shown its second reading, and the WebAssembly module built at `opt-level = 3`
  reads about 17% faster: in headless Chromium, the reading of the largest file of a large
  exported design takes 2.36 s instead of 2.86 s.

On the exported design of the 0.6.2 notes, of about 22,600 instances at the top with every
position written, and on a generated level of 400 instances of five pins, two of them on the
supply and ground nets (release builds, each the median of five runs, alternated):

| | 0.6.2 | 0.6.3 |
| --- | --- | --- |
| `rnl view top.scs --file F`, F the file of its largest level | 1.70 s | 0.91 s |
| The same with `--hints` | 1.94 s | 1.06 s |
| `rnl view top.scs --file top.scs` | 0.65 s | 0.43 s |
| `rnl view top.scs`, the whole design | 5.41 s | 4.18 s |
| Its largest level solved, in a file of its own: `rnl view --hints` | 1.72 s | 0.86 s |
| The same with `--constraints` | 2.40 s | 0.98 s |
| `rnl preview top.scs --level L --file F`, L its largest level | 8.64 s | 3.28 s |
| `rnl preview top.scs --level top.scs --file top.scs` | 1.29 s | 0.86 s |
| The level of 400 instances: `rnl view` | 1.45 s | 0.91 s |
| The same with 1,600 instances | 13.34 s | 3.66 s |
| The level of 400 instances, solved: `rnl view --hints --constraints` | 6.12 s | 4.10 s |
| The level of 400 instances: `rnl preview`, with a work limit of 0 | 10.60 s | 5.65 s |

The output of `rnl check`, `rnl dump` and `rnl view` on the examples of the gallery, the examples
of the skill, the cases of the solver and two large generated designs is byte-for-byte that of
0.6.2, but for the version it names, and every file of them read alone gives what the whole
reading gives for it. `rnl preview`, `rnl reroute` and `rnl solve --report` write and print
the same as 0.6.2 on them and on the exported design above, under a work limit, and so does
`rnl view` of the files they solve.

## Known limits

- A file of thousands of subcircuits reads in a time that grows faster than their count. With
  one resistor and one record of the solver in each subcircuit, `rnl view --status` takes about
  6 s for 500 and 38 s for 2,000. A design of a few hundred subcircuits is not much affected.
- A bus pin, such as a terminal of a bundle, on two different nets of one rail class, such as
  `vdda` and `vddd` both in `$SUPPLY_NET_SET`, gives errors in the fill of the standard package,
  RNL3512 first, and gets no label: take one of the nets out of the class, or wire the pin.
- The parameters of a Verilog-A module, with their defaults, are not in the outline yet.

The limit of 0.6.2 on a level of many instances whose pins the fill gives stubs is gone: the
reading of such a level now grows with the level, as the table above shows.

## For users of 0.6.2

Nothing to change in files or options. The npm package's interface is that of 0.6.2, with the
additions above: a request without the new fields is answered as before. In Rust, an
`OutlineFile` written field by field needs `records`.

## Files

The same four CLI archives as 0.6.2, each holding the `rnl` command and its licence, with
`SHA256SUMS.txt`, the checksums of every archive, the npm package's too, as a separate asset
beside them; and the npm package `@rich-netlist/runtime@0.6.3`, published with the dist-tag
`latest`.

| File | |
| --- | --- |
| `rnl-x86_64-pc-windows-msvc.zip` | Windows x64 |
| `rnl-x86_64-unknown-linux-musl.tar.gz` | Linux x86_64, statically linked |
| `rnl-aarch64-apple-darwin.tar.gz` | macOS on Apple Silicon |
| `rnl-x86_64-apple-darwin.tar.gz` | macOS on Intel |
| `SHA256SUMS.txt` | The SHA-256 sums: `sha256sum --check --ignore-missing SHA256SUMS.txt`, or `Get-FileHash` in PowerShell |

`npm i @rich-netlist/runtime` installs 0.6.3; `npm i @rich-netlist/runtime@legacy-0.3` still
installs 0.5.7. This release is the one GitHub shows as latest, so the links of the form
`releases/latest/download/…` give the files of 0.6.3.

Linux on arm64 is not built yet; build the command from the source there.

## Not signed

The executables have no code signature. Windows may show a SmartScreen warning. On macOS, a file
downloaded with a browser may need `xattr -d com.apple.quarantine rnl` after it is extracted
before it runs. Check each download against `SHA256SUMS.txt` first.

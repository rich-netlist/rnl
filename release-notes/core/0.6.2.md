# RNL core 0.6.2

The `rnl` command and the npm package `@rich-netlist/runtime` 0.6.2, built from the same core.
Its main addition is a frontend reading a design one file at a time: the outline of the whole
design first, then the files it shows, each read in the context of its entry. A level is solved
the same way, from the file it is written in, and a solve reads the files it writes fewer times,
so a level of a large design solves several times faster. RNL Viewer 0.6.2 is released with it,
and every viewer now lists, searches and solves the files it holds by the same rules, which are
kept in the core. Every reading of a whole document gives what 0.6.1 gives,
with the formats' new fields, except that the texts of constraints now use the words of RNL 0.4
and that a package directory's hidden files are not searched, as described under Changed.

## Added

- **The outline of a document.** `outline()` in `core.js` and `client.js`, and `collectOutline()`
  in `client.js`, give the outline: what reading the files gives before any RNL is interpreted.
  It has:
  - the files, their includes, and the hashes of their texts and records;
  - every level, with its kind, file, lines, parent, ports, and the subcircuits its instances
    call;
  - the roots, the global nets and the missing files.

  In WebAssembly, the request is a build request with `"outline": true`. In Rust, it is
  `rnl_view::outline`.
- **Reading one file in the context of its entry.** `buildFile()` (with `collectFile()`, which
  reads what is missing) gives the levels of one file, drawn as the whole Document draws them. It
  also gives the subcircuits they call, with the outline level of each (`host`), and the inputs
  the result depends on, by role and with their hashes, so that a frontend can keep the result.
  `symbols()` gives the block symbols of a file's subcircuits. `version.js` gives the core version
  and the format of a file's result before the module is loaded. In Rust, these are
  `rnl_view::build_file`, `rnl_view::symbols`, `rnl_view::core_version` and
  `rnl_runtime::Options::only_file`.
- **The command line:**
  - `rnl view --file F` prints the reading of one file as a viewer gets it;
  - `rnl dump --file F` prints the model of one file;
  - `rnl dump --each-file` reads every file alone, compares each with the whole reading, and
    exits 1 on any difference;
  - `rnl solve` and `rnl preview` take `--file F` with `--level`: only the file F that the level
    is written in is read, in the context of the entry, as a viewer reads the file it shows. What
    is written is the same as without it. The preview's Document is that of the file F, as
    `rnl view --file` prints it. The solver's request takes it as `file`, and every viewer of
    0.6.2 solves the level shown this way. In Rust, it is `SolveOptions::file`.
- **Verilog-A in the outline.** A module level now lists the modules its instances name, in
  `calls`, the same way a subcircuit does. Each module is found by name, with case, in any
  Verilog-A file of the document; a name that no module has is given `level: null`. A new optional
  field `OutlineCall.lines` gives the line of each instance, counted from 1. Netlist levels get it
  too. A module level still has no circuit or drawing.
- **Manifests.** A level of a manifest may name its file (`file`), when it is written in a file
  other than the entry. `loadManifest` gives the files in the order of the manifest, and a read
  stopped by the caller's signal now rejects with the signal's reason.

### One set of rules for every viewer

- **The files a frontend lists.** Each format of `formats()`, of `rnl formats` and of a Document
  gives `listed`, the suffixes of its files that a frontend lists in its file dialogs, for files
  dropped on it, in a folder it includes and in a PATH folder, and `entries`, those of them that
  are netlists opened on their own. In Rust, `rnl_view::listed_suffixes` and `rnl_view::is_listed`
  give them for all formats.
- **The built-in packages.** `bundled()` in `core.js` and `client.js`, the request
  `{"bundled": true}` in WebAssembly and `rnl_view::bundled_listed` in Rust give the bundled
  packages a frontend lists, by path with their texts: all but those of a draft series.
- **PATH folders.** A build request takes `search_paths`, the folders searched in order for a bare
  include name that is not beside the file that includes it, as `--path` is. A frontend that holds
  the files of its PATH folders gives them as both `package_dirs` and `search_paths`, and finds
  what the desktop viewer and the CLI find. In Rust, this is `MemoryProvider::search_paths`.
- **Folders included in the Library.** `folders(paths)` in `core.js` and `client.js` (the request
  `{"folders": {"paths": [...]}}` in WebAssembly) lists the files of folders as a browser gives a
  folder chosen or dropped, as every viewer lists a folder included. It answers
  `{files, truncated, limit}`:
  - `files` are the files listed, sorted;
  - `truncated` names the folders that had more files than are listed;
  - `limit` is the most files each folder brings in (2000, from up to 8 levels of folders).

  Nothing hidden is listed. In Rust, the walk is `rnl_view::folder`, and the module `rnl_cli::walk`
  lists a folder included and a PATH folder on disk with the same rules.
- **A solve reads what its build read.** The solver's request (`@rich-netlist/runtime/solver`)
  now takes the fields of a build request that say where files are: `pool`, `search_paths`,
  `auto_include`, `library_prefix` and `library_edits`, beside `files` and `package_dirs`. They
  are read as a build reads them: the pool first, then the package directories and search paths
  in order, and with Auto Include the subcircuits the pool's files define. Before, the solver
  ignored the pool and Auto Include. In Rust, a request's files are `rnl_view::RequestFiles`.
- **`rnl preview REQUEST.json --request`** reads such a solve request, JSON, instead of a netlist,
  and nothing from disk.
- **`rnl preview` prints `files`** beside `document` and `report`: the texts the solve would
  write, by path. With `--request`, they are named by the paths of the request.

## Changed

- A level whose components its facts all place and orient, and that has no ROUTE, is no longer
  searched for an arrangement (see Faster). Its `rnl solve` report says so in one line, in place
  of the search's lines. The files written are the same. Under a time limit, as the viewers solve,
  the record names the work of the steps done, so its hash differs from that of 0.6.1. Under a
  seed limit, the record is unchanged, hash included.
- Constraints write their direction as RNL 0.4 does: `ORDER left-to-right`, `DISTRIBUTE x`,
  `DISTANCE bottom-to-top`, and `exact=6` for a DISTANCE whose least and most are the same. Before,
  they wrote `x increasing` and `min=6 max=6`. This applies to:
  - the `what` of the constraints in a Document;
  - the facts, discarded facts and hints of the `rnl solve` report.

  A DISTRIBUTE constraint now gives its `sense` (`ConstraintKind`), as ORDER and DISTANCE do. The
  solver's input, its signatures and the files it writes do not change.
- Hidden files and folders of a package directory (`--package-dir`, `--path`), a name that starts
  with `.`, are no longer searched for packages.
- The web and local viewers of RNL Viewer 0.6.2 give the core their PATH folders as the desktop
  viewer searches them. A package that several folders have, and a bare include whose file is in
  a version folder, are now looked up there as the desktop viewer and the CLI look them up, which
  can change the result of a design that relies on them.

## Faster

- Reading one file reads the RNL records of only the subcircuits it depends on, instead of those
  of every file, so a file of a large design opens faster.
- A thread keeps the parse of each record text, so later readings in the same thread do not parse
  the same text again. An example is the next file a viewer's Worker reads with `buildFile`.
- **Solving a level of a large design:**
  - When a level is solved from the file it is written in (`--file`, as every viewer now
    solves), only that file is read, not the whole design.
  - A level whose components its facts all place and orient, and that has no ROUTE, takes its
    arrangement as written instead of searching for one. A level with a ROUTE is searched as
    before.
  - After a level is solved, the files written are read fewer times. The check of what is
    written, the placing of junctions and the preview share their readings instead of each
    reading the whole document again.

On an exported design of about 22,600 instances at the top, with every position written, a solve
and its preview, as a viewer runs them, take (release builds, each the median of three runs):

| Solved | 0.6.1 | 0.6.2 |
| --- | --- | --- |
| Its largest level, from the top file | 76.6 s | 8.6 s |
| The same level, its own file opened | 17.9 s | 8.5 s |
| Its top level | 53.3 s | 1.3 s |
| A level with automatic ROUTEs, its own file opened | 15.8 s | 14.6 s |

0.6.2 reads the file the level is written in, as the viewers solve. Reading the whole design, as
`rnl solve` and `rnl preview` do without `--file`, the largest level from the top file takes
31.2 s and the top level 21.8 s.

Each of these changes writes the same files as before it on the examples of the gallery, the
examples of the skill and the cases of the solver, and on the exported design above, except for
the record's hash of a level no longer searched under a time limit (see Changed).

The output of `rnl check` and `rnl dump` on the examples of the gallery, the examples of the
skill, the cases of the solver and two large generated designs is byte-for-byte that of 0.6.1.
That of `rnl view` differs only in the new `listed` and `entries` of each format of the Document.
Every file of them read alone gives what the whole reading gives for it.

## Known limits

- A level of many instances whose pins the fill gives stubs still reads in a time that grows
  faster than the level. In a level of instances of five pins, two of them on the supply and
  ground nets, so that the fill gives each instance two stubs, 400 instances take about 1.6 s and
  1600 take about 19 s.
- A bus pin, such as a terminal of a bundle, on two different nets of one rail class, such as
  `vdda` and `vddd` both in `$SUPPLY_NET_SET`, gives errors in the fill of the standard package,
  RNL3512 first, and gets no label: take one of the nets out of the class, or wire the pin.
- The parameters of a Verilog-A module, with their defaults, are not in the outline yet.

## For users of 0.6.1

Nothing to change in files or options. A program that reads the text of a constraint, or of the
`rnl solve` report, gets the new direction words above. The rest of the npm package's interface
is that of 0.6.1, with the additions above. In Rust, a `MemoryProvider` written field by field
needs `search_paths` (or `..Default::default()`), and a `FormatInfo` needs `listed` and
`entries`.

## Files

The same four CLI archives as 0.6.1, each holding the `rnl` command and its licence, with
`SHA256SUMS.txt`, the checksums of every archive, the npm package's too, as a separate asset
beside them; and the npm package `@rich-netlist/runtime@0.6.2`, published with the dist-tag
`latest`.

| File | |
| --- | --- |
| `rnl-x86_64-pc-windows-msvc.zip` | Windows x64 |
| `rnl-x86_64-unknown-linux-musl.tar.gz` | Linux x86_64, statically linked |
| `rnl-aarch64-apple-darwin.tar.gz` | macOS on Apple Silicon |
| `rnl-x86_64-apple-darwin.tar.gz` | macOS on Intel |
| `SHA256SUMS.txt` | The SHA-256 sums: `sha256sum --check --ignore-missing SHA256SUMS.txt`, or `Get-FileHash` in PowerShell |

`npm i @rich-netlist/runtime` installs 0.6.2; `npm i @rich-netlist/runtime@legacy-0.3` still
installs 0.5.7. This release is the one GitHub shows as latest, so the links of the form
`releases/latest/download/…` give the files of 0.6.2.

Linux on arm64 is not built yet; build the command from the source there.

## Not signed

The executables have no code signature. Windows may show a SmartScreen warning. On macOS, a file
downloaded with a browser may need `xattr -d com.apple.quarantine rnl` after it is extracted
before it runs. Check each download against `SHA256SUMS.txt` first.
